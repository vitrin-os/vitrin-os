# Decision log

Registry of decisions (Part A) and open questions (Part B) for Vitrin OS. Entries are ADR-shaped and cited by short ID (`D-005`, `Q11`) from every other plan document. Once a decision is **accepted**, its entry is append-only: changes are recorded as a new superseding entry, never edits.

Convention: this stays a single file until it exceeds ~25 accepted entries or external contributors begin proposing decisions, at which point it splits into `docs/plan/adr/` (see D-013).

---

## Part A — Decided

Entries D-001 through D-011 are seeded from decisions the [PRD](../PRD.md) already made; the PRD section cited is the full rationale. D-012 onward originate in this plan tree.

### D-001 — Rust + Smithay for the trusted core
**Status:** accepted (PRD Doc 2 §9, §17)
**Decision:** the trusted core (`vitrind`: compositor, capability kernel, grant store, input router, journal, motion synthesis) is Rust on Smithay.
**Context/consequences:** the core is the entire TCB; memory safety eliminates vulnerability classes in the most privileged component. Smithay is production-proven (niri, COSMIC) at frame deadlines. Go rejected (GC pauses vs. frame deadlines); C/C++ rejected for the core (TCB memory-safety argument).

### D-002 — C + wlroots shims, outside the TCB
**Status:** accepted (PRD Doc 2 §4.2, §17)
**Decision:** the Wayland shim is C on wlroots; the later X11 shim is C/C++ (Xwayland-derived) with an embedded minimal WM. Shims are unprivileged and disposable.
**Context/consequences:** the legacy semantics we want live in wlroots, mature; reusing them *outside* the TCB is the point. See Phase-1 risk R2 for the held-in-reserve Rust-shim pivot option.

### D-003 — Wayland-style Unix-socket wire protocol with SCM_RIGHTS; Cap'n Proto rejected for the local hot path
**Status:** accepted (PRD Doc 2 §3.2)
**Decision:** local principals speak a Wayland-style binary protocol over Unix domain sockets with fd passing; handles are per-connection, sender-constrained. Cap'n Proto RPC's conceptual model (handles-as-capabilities, attenuation, pipelining) is adopted; its transport is not (no shared-memory transport in practice; buffers move as dmabuf fds outside the payload). Protobuf/gRPC and FlatBuffers rejected for the local path.

### D-004 — QUIC (quinn) for network sessions
**Status:** accepted (PRD Doc 2 §10)
**Decision:** remote sessions run over QUIC: multiplexed streams, TLS 1.3, connection migration; workload identity bound to the channel. Cap'n Proto remains optional for the network control plane (final call at E3.1 — see Q6 for the codec question).

### D-005 — Split licensing
**Status:** accepted (PRD §11)
**Decision:** protocol spec + wire definitions under Apache-2.0 (explicit patent grant), spec prose CC-BY-4.0; reference implementation under weak copyleft (MPL-2.0 preferred, LGPL-3.0 the fallback); client SDKs Apache-2.0.
**Consequences:** setup work (LICENSE files, SPDX headers) executes at first public push — see [12-workstream-community.md](12-workstream-community.md) §2.

### D-006 — Naming: Vitrin OS
**Status:** accepted (PRD Naming section)
**Decision:** project **Vitrin OS**, daemon `vitrind`, org `vitrin-os`, npm scope `@vitrin-os`, crates `vitrin-os`/`vitrind` (namespaces claimed 12 July 2026). Kavşak dropped (pronounceability), Torii recorded but not adopted.

### D-007 — Scope tiering: invariants / v1 / horizon / renounced
**Status:** accepted (PRD §5)
**Decision:** scope statements are kept in four distinct classes: permanent invariants (§5.1), v1 sequencing (§5.2), claimed-but-deferred horizon (§5.3), renounced non-goals (§5.4). Every plan document inherits this discipline; horizon items never silently migrate into a phase without an M4 gate review ([04-phase-4-horizon.md](04-phase-4-horizon.md)).

### D-008 — Pluggable identity verifier; no hard commitment to in-flight standards
**Status:** accepted (PRD Doc 2 §5.1, Caveats)
**Decision:** identity verification (SPIFFE SVID, OIDC, SSH certificates, MVP static identity) sits behind a pluggable `Verifier` abstraction. IETF AIMS, MCP authorization revisions, and OID4VC profiles are tracked, pinned, and re-checked — never hard-wired (see the liaison table in [10-workstream-spec.md](10-workstream-spec.md)).

### D-009 — Transparency log for provenance; deliberately not a blockchain
**Status:** accepted (PRD P14, Doc 2 §13)
**Decision:** app provenance uses Sigstore-style identity-bound short-lived signing certificates plus a Merkle transparency log (checkpoint + inclusion proof verified locally). No consensus, no tokens, no ledger on the grant-time hot path. DIDs acceptable as an identity *format* only.

### D-010 — Per-realm isolation dial
**Status:** accepted (PRD Doc 2 §4.5)
**Decision:** isolation strength is per-realm policy over one identical GUI protocol: default (namespaces + seccomp + Landlock), hardened (gVisor-class), paranoid (microVM). Every realm gets its own network/PID/IPC namespaces and UID regardless of tier. Security claims are stated per tier (only the microVM tier escapes shared-kernel escape classes).

### D-011 — v1 deployments: headless fleet + local nested; one Wayland shim first
**Status:** accepted (PRD §5.2, §8)
**Decision:** v1 targets the two deployments with no open incumbent (headless agent fleets; nested-in-a-desktop). The X11 shim, network sessions, and fleet mode follow in Phase 3. Session mode on bare DRM/KMS is horizon-tier.

### D-012 — DCO, not CLA
**Status:** accepted, executed
**Decision:** contributions are accepted under the Developer Certificate of Origin (sign-off), not a Contributor License Agreement.
**Execution:** [`CONTRIBUTING.md`](../../CONTRIBUTING.md) states the policy and `.github/workflows/dco.yml` enforces it per commit on every pull request, so the decision is machine-enforced rather than aspirational. This status line read `proposed` until 2026-08-16, months after both landed — see [12-workstream-community.md](12-workstream-community.md) §2, which said the same thing on its own checklist. That is the drift [#172](https://github.com/vitrin-os/vitrin-os/issues/172) exists for, and `cargo xtask limits-check`'s `dco-is-executed` claim now holds the checkbox, this file and the published pages to the existence of that workflow.
**Rationale:** a CLA is a contributor deterrent, and a single-maintainer project needs contributors more than it needs relicensing optionality; the licensing split (D-005) already secures the protocol/implementation boundary. Revisit only if a fiscal host requires otherwise.

### D-015 — No patent filings; defensive publication instead
**Status:** accepted (2026-07-26)
**Decision:** Vitrin OS files no patents. Protection rests on three things instead: **defensive publication** (the PRD and the IDL published with a timestamp are themselves the prior art), the **patent grants already carried by the licenses** (Apache-2.0 §3 on the protocol and SDKs, MPL-2.0 §2.1(b) on the reference implementation — see D-016), and **Open Invention Network membership**, to be joined (free below $10M revenue; OIN 2.0 launched January 2026; 4,000+ members cross-licensing 3M+ patents royalty-free within the Linux System definition, which covers the graphics stack).
**Rationale:** the economics do not work and the posture is wrong. A patent family costs roughly EUR 10–30k per jurisdiction and takes 2–5 years to grant, and Europe's absolute-novelty rule would force filing *before* publication — delaying the one act that actually protects the project. Publishing the design is the protection: it blocks anyone else from patenting these claims, immediately and for free. It is also the only posture consistent with the project's own argument: a capability-security system asking to be trusted is stronger defensive-permissive than behind a patent wall, and D-005's whole point is that the protocol is a commons.
**Consequences:** a public-source patent-landscape scan was performed on **2026-07-26** and is recorded here so a later reader can tell what was and was not checked.

- *Nearest neighbour.* Anthropic's portfolio, acquired via Adept AI Labs. **US20250299023A1** (filed 2024-03-20, pending): claim 1 covers generating **training data** through an intermediary that intercepts user actions and translates them into actuation commands — no mention of permission, authorization, consent, capability, revocation, or a display server/compositor. The sibling **US 12,430,150** covers a client-side interface-automation language at runtime. Neither reads on a capability-scoped display protocol; the overlap is the *setting* (an intermediary between an agent and a GUI), not the claimed mechanism.
- *Prior-art anchors that protect Vitrin's own mechanisms.* Trusted path and the attention key: **US 4,918,653**, "Trusted path mechanism for an operating system" (expired), and the TCSEC / Secure Attention Key lineage behind it. The unforgeable trust band: **Qubes OS**'s dom0-drawn coloured window borders (2010, published). The nested per-app compositor and per-app security context: **Sommelier** and Wayland **`security-context-v1`**, both published. Capability security itself: **Dennis & Van Horn (1966)**, KeyKOS, EROS, seL4, Capsicum.
- *Limits, stated plainly.* This was a **public-source landscape scan, not a freedom-to-operate opinion**. No FTO has been obtained and none is budgeted. Pending claims get amended and continuations get filed, so the Anthropic applications above are an explicit **re-check item before 1.0**, not a settled result.
- *Residual risk.* The realistic exposure is a non-practising entity in the RPA space (UiPath's portfolio; Microsoft via the Softomotive acquisition), and that risk materialises with **revenue**, not with publication — which is another reason publishing early costs nothing here.

### D-016 — D-005's weak-copyleft half executed as MPL-2.0
**Status:** accepted (2026-07-26) — executes D-005, closes the open question in issue #133
**Decision:** the reference implementation ships under **MPL-2.0**, not the LGPL-3.0 fallback D-005 recorded. The boundary between the copyleft and permissive halves is drawn by **derivation, not by directory**: content transliterated from the Apache-2.0 protocol artifacts stays Apache-2.0, original implementation expression goes MPL-2.0. Concretely — the trusted core and the IPC layer (`crates/vitrin-core`, `crates/vitrin-ipc`) and the shim's own C sources, hand-written headers and fixtures go MPL-2.0; `crates/vitrin-protocol` **including its checked-in generated code**, the generated C header under `shim/include/`, the IDL scanner and its `xtask` driver, the conformance instruments (`crates/vitrin-golden`, `crates/vitrin-mock-shim`, `fuzz/`), the SDKs, `tests/integration/` and `examples/` all stay Apache-2.0. `shim/wlcs/` remains the GPL-3.0-only carve-out it already was. Mechanism: per-file `SPDX-License-Identifier` headers plus a per-crate `license` field, with the root [`NOTICE`](../../NOTICE) as the normative path→license map — **not** per-directory LICENSE files.
**Rationale:** MPL-2.0 over LGPL-3.0 on four grounds, one of which is the real one.

- **Security is the core argument.** Vitrin's central claim is a *small, auditable* trusted core. Copyleft on the TCB makes that a property of the license rather than a promise in a README: a modified capability kernel, grant store or consent path cannot be shipped as a black box, and security-relevant fixes come back.
- **File-level scope is the right shape here.** MPL's copyleft attaches to files, not to the process image, so an app running inside a shim is never derivative and the Larger Work allowance (§3.3) makes linking MIT wlroots and MIT Smithay clean rather than an argument.
- **No patent regression.** MPL-2.0 §2.1(b) carries an explicit patent grant and §5.2 a termination-on-litigation clause, so moving a file from Apache-2.0 to the copyleft half does not lose the patent protection D-005 chose Apache-2.0 for (and D-015 leans on).
- **GPL compatibility is load-bearing, not theoretical.** MPL names GPL-3.0 a Secondary License (§1.12) and permits distributing the Larger Work under GPL terms (§3.3) — which is what keeps the advisory `shim/wlcs/` module lawful now that it compiles MPL-2.0 shim sources. **Hard constraint: Exhibit B ("Incompatible With Secondary Licenses") must never be added to any file in this repo.**
- **LGPL-3.0 rejected on deployment reality.** Its anti-tivoization / Installation Information terms (GPLv3 §6) are a known deterrent to embedded and kiosk vendors — and kiosk/embedded panels are a genuine deployment target for a display server, not a hypothetical one.

**Consequences:**

- **Adoption is unaffected by design:** nobody has to touch an MPL-2.0 file to write a client, build an alternate compositor, or ship an integration, because the protocol, the generated bindings, the codegen and the SDKs are Apache-2.0. Copyleft binds the people who modify the trusted core, and only them.
- The workspace-wide `license` default is **removed** rather than changed, so a crate added later cannot silently inherit the wrong half; every crate states its own.
- Root license texts + `NOTICE` + per-file headers, because per-directory LICENSE files would be *false*: `shim/` carries three licenses and `shim/include/` two.
- The repo has shipped a GPL-3.0-only file since P1.9.4 with no GPLv3 text anywhere in the tree, which GPL-3.0 §4 requires. Pre-existing gap; closed by this pass.
- `LICENSE-CC-BY-4.0` had been a 28-line human-readable *summary* that said of itself it was "not a substitute for the license" — so one of the four licenses the map names had no legal text in the tree. Replaced with the verbatim CC BY 4.0 legal code, matching what this pass did for MPL-2.0 and GPL-3.0-only. Another pre-existing gap, closed here rather than noted and left.
- **Inline SPDX headers cover sources only** — every first-party `.rs`, `.c`, `.h`, `.py`, `.sh` and `.js` file. Build manifests, the IDL and its schema, Markdown and fixture data deliberately carry none: `Cargo.toml` states the license in its own field, and the rest is covered by `NOTICE`'s path map, which now includes a catch-all clause so no tracked path is left unassigned. A file without an inline header is not an unlicensed file, and `NOTICE` says so explicitly rather than leaving a reader to infer it.
- The `license: 'MIT'` assertion in the shim's build file — and the MIT prose claims that grew around it — are retired. No MIT license text has ever existed in this repository, so that assertion was never backed by anything. `shim/wlcs/integration.c`'s `SPDX-License-Identifier: GPL-3.0-only` tag is preserved exactly; only the surrounding prose about "the rest of the repository" changes.
- Generated files take their SPDX line from the scanner's templates, never by hand, or `cargo xtask codegen --check` goes red in CI.
- **Known cost, accepted knowingly:** GitHub's license detector reads the root `LICENSE` and will keep labelling the repository "Apache-2.0", which now understates the copyleft half. The clean fix is the REUSE Specification layout plus a `reuse lint` CI check — which would also stop header coverage rotting — and is deliberately deferred to a follow-up rather than folded in here.
- Third-party carve-outs are untouched: the OFL-1.1 font vendored under `crates/vitrin-core/assets/` and the wlroots/wayland trees under `shim/subprojects/` keep their own licenses.
- Two placements are the arguable ones and are recorded as such so a future reversal is cheap: `crates/vitrin-ipc` (MPL-2.0, though its `client` feature is SDK-facing) and `crates/xtask` (Apache-2.0, though it also drives core dev tasks). Each is a one-field change that disturbs nothing else in the map.

### D-017 — Per-principal cursors: the model is decided and on the wire; delivery is deferred to M2
**Status:** accepted (2026-07-26) — closes Q15 / PRD §20.15, issue #147
**Decision:** five answers, one wire change.

1. **Cursor identity needs no new object.** Each principal has exactly one virtual pointer per realm it holds pointer authority over, and `vitrin_actuator_pointer` **is** that pointer's name on the wire. `move` already meant "this principal's virtual pointer"; the model was implicit and is now normative. No new interface, no cursor object, no cursor id.
2. **Cursorless is by construction, not by declaration.** A principal that never petitions for `actuate_pointer` has no cursor. The headless-fleet case therefore costs zero wire vocabulary. There is deliberately **no request** to declare, disown, or hide a cursor — and the missing *hide* is itself the decision: a visually distinct agent cursor is a human override (PRD P10), so visibility is never the actuating principal's own choice.
3. **Visibility is a relation, it is settled on the observation side, and it is asymmetric.** A captured frame contains no cursor except the human principal's, and that one only for a grant holding `observe_cursor` (4) — otherwise the same rule the consent overlay already obeys. The asymmetry is the decision, not an oversight: **agent→agent is closed outright** and purchasable at no verb set, ever (a side channel revealing what another principal is doing), while **agent→human is closed by default** and opens only through a verb. What is refused throughout is a *per-pair toggle matrix*: the only "toggle" that exists is the one grant verb, visible on a consent prompt and revocable with the grant. Human→agent visibility, including the per-agent toggles a human supervising thirty agents needs, is a shell and core concern: the human has no wire presence in v0.
4. **Agent→human cursor visibility is a grant verb**, not a display preference: new bit `observe_cursor` (0x8) on `vitrin_grant.verb`. It attaches to the grant, not to the view facet, because it is authority over what a capture *contains*, and it has no facet interface of its own — it widens `frame_ready`, it does not add a request. It is **meaningful only alongside `observe`**: a petition naming it without `observe` names no capture to widen and resolves `unsupported`, rather than granting a bit that changes nothing (the same rule that forbids granting a verb the deployment does not enforce). Seeing *another agent's* cursor is not purchasable by this or any verb.
5. **Cursors are core-composited.** A realm may never supply the pointer bitmap; `vitrin_shim_surface` has no cursor-surface role and will not gain one. A realm drawing its own could paint a **decoy cursor** and mislead the human about where input is going — the spoofing class the consent surface exists to exclude (issue #85). An app-painted pointer image is ordinary realm content, never the composited pointer.

**Why this simplifies the core rather than growing it:** `ConsentGrab` carries a defensive rule — never let emulated motion relocate the position the human's hit test reads — that exists *only* because one cursor is shared between origins. With structurally distinct pointers the human's hit test follows the human's pointer and the special case is deleted. It also clarifies preemption: with one pointer, "physical input preempts agent input" is a contention rule; with N+1 pointers there is nothing to contend for on the pointer axis, and preemption is purely about focus and actuation ordering.

**DEFERRED, explicitly:** **per-principal cursor *delivery*** — to **M2** (spec 1.0-candidate). Version 1 delivers **one shared pointer position** per realm view to the shim and composites **no cursor at all** (in nested operation the host desktop draws the human's cursor, outside the realm view entirely). Serving `observe_cursor` is likewise deferred: v1 refuses it `unsupported`. The correction is purely additive because the agent-facing half is already principal-relative — only `vitrin_shim_seat` delivery is shared, and it grows `since`-gated sibling events that name the principal, each still ending with `origin` so the schema's B2 rule holds.

**Costs, stated:**
- One verb bit (0x8) is burned on authority nothing implements. Enum values are immutable and `deprecated-since` marks but never removes, so if the model changes the bit is dead weight forever.
- A verb defined but unserved is a claim the core must keep honest at exactly one place; the guard is `grants::UNSERVED_VERB_BITS` (derived from `Verb::VALID_MASK`, so a newly appended verb is unserved by default — forgetting to classify one fails closed at *runtime*) plus the admission refusal and its unit test. Because that constant is derived, "served ∪ unserved = the wire bitfield" is an identity and cannot fail; the *tripwires* that actually go red when a verb is appended to the IDL are **two literal pins and one derived one**, and the count was wrong here until #189's review measured it: `vitrin-protocol/tests/decode_errors.rs` on `Verb::VALID_MASK == 639` (63 until `realm_launch` = 512 landed at wire version 2, then 575 until `designate_file` = 64 landed at P2.6.5; the pin is re-stated at its literal value on every verb addition, which is what makes it a tripwire — and it fired on both), `crates/vitrin-core/src/attention.rs` on the same literal for D-023's reason, and `consent/render.rs`'s catalogue test on the unserved set's exact bits, which holds no literal and forces a human to classify the new verb as served (with prompt copy) or unserved. `cargo xtask limits-check`'s `verb-valid-mask` MIRROR row now renders the generated constant into both literal pins, into the three documents that state it ([02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5, [04-vitrin_grant.md](../protocol/04-vitrin_grant.md), this entry) and into `protocol/vitrin-v0.xml` itself, so a stale copy is a red build. The IDL was added last and after it had already gone wrong: its normative `<description>` said *"any combination of the seven defined verb bits (value 575) but a bit reserved for a future verb (for example value 64) is fatal"* through a fully green build in which the same branch had defined 64 as `designate_file` and moved the mask to 639 — the file CLAUDE.md makes normative over every prose page restating it, wrong in three clauses at once, held by nothing. Two of its renderings are therefore not the decimal but functions of it (the count of defined bits, and the lowest bit the mask leaves out), because those are the registers the paragraph writes in; [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5 carries the site list and its own scan. Stated because the first draft of that doc comment claimed a tripwire the derivation had removed.
- **The Python SDK's hand-transcribed `Verb` mirror is out of sync as of this landing.** `sdk/python/src/vitrin_os/protocol.py` still carries only `observe`/`actuate.pointer`/`actuate.text` (mask 7 against the IDL's 63), and nothing fails: `IntFlag` accepts the undefined bits and no golden vector covers a verb bit. That file's own docstring says the IDL wins and this file must be fixed, so the divergence is a debt, not a design. It is `track:sdk`-owned and out of `track:protocol`'s file set; it is recorded here so it cannot be lost, and the dotted names to add are `observe.cursor`, `layout.arrange`, `layout.focus` (the existing convention maps `actuate_pointer` → `actuate.pointer`). Whoever closes it should add a parity check against `protocol/vitrin-v0.xml` rather than a second hand-transcription. **Closed by WS-E.1.5/#211** on those terms: `sdk/python/tests/test_verb_parity.py` re-derives the members, the dotted names, `VERB_MASK` *and the served/unserved split* from the IDL and asserts the SDK agrees — and, because that last one is a string match against the IDL's own "refused unsupported in version 1" phrasing, it also pins that the phrase is still load-bearing, so a rephrase cannot silently turn the derivation into a tautology that a matching hand-edit of `VERBS_SERVED_IN_VERSION_1` would keep green.
- The shared-cursor defect and its `ConsentGrab` workaround **survive through M1**. The security argument for per-principal cursors is therefore recorded, not yet realised, and the prose says so rather than implying otherwise.
- The human→agent toggle surface is unanswered here because the human is not on the wire; it lands with the mission-control shell (E3) and D-018's arrangement model.

### D-018 — Layout is a capability: grant-governed arrangement, core-enforced ordering
**Status:** accepted (2026-07-26) — closes Q16 / PRD §20.16, issue #149
**Decision:** five answers, two wire bits.

1. **Layout is grant-governed; the shell holds no ambient layout authority.** Layout verbs are attenuable, revocable, journaled verbs on a grant, exactly like `observe`/`actuate_pointer`/`actuate_text`. *"The shell is trusted"* was not available: PRD §5.1 makes it an invariant that window-management policy lives outside the core, so trusting the shell would move exactly the code that invariant exiles back into the TCB, defeating the Nitpicker/Scenic argument the design rests on.
2. **Core-enforced, unpurchasable ordering invariants** (no grant buys these at any verb set, ever): (a) the consent surface and the trust indicator composite above every principal's content; (b) the core's own hit test — never a client's claimed stacking — decides which surface an input event reaches; (c) no arrangement may occlude, fullscreen over, or resize away the consent surface; (d) no **agent** principal's cursor is composited into another principal's captured frame — the one cursor a capture may ever contain is the human's, and only for a grant holding `observe_cursor` (shared with D-017(3)/(4), and the single carve-out). The shell gets *arrangement*; the core keeps *ordering*.
3. **`focus` is a separate verb from placement.** New bits: `layout_arrange` (0x10) covering place/resize/raise/fullscreen, and `layout_focus` (0x20). Focus theft is at once the sharpest attack and the most legitimate need, so it must be attenuable alone. `raise`/`move`/`resize`/`fullscreen` are deliberately **not** split further: with ordering held by the core (2), each stops being an attack primitive, and splitting them would be attenuation theatre — more bits, no more safety.
4. **One layout-holder per output; no arbitration in the core.** Arbitration between two principals holding layout grants is window-management *policy*, which §5.1 forbids inside the TCB. At most one live grant carries `layout_arrange` per output. The refusal code a second holder receives is settled with the shell's design (E3); the additive mechanism is an appended `outcome` entry, since outcome is a plain enum and entries append. Version 1 refuses **every** layout petition `unsupported`, so the contention cannot arise yet.
5. **Epoch interaction (E2.3) is a binding constraint, not a sequencing note.** A layout change invalidates an agent's cached coordinates exactly as a repaint does, so **E2.3's epoch MUST be defined over (frame content + view geometry + stacking), not content alone**, and a layout mutation MUST bump it. Third-party arrangement is also the reason the epoch must be a compare-and-swap *on actuation*, not merely a token returned by observation: between an agent's capture and its click, a shell holding `layout_arrange` may have moved the target. The two are designed together, per Q16's own instruction.

**DEFERRED, explicitly:** **layout enforcement in its entirety** — to **E3** (mission-control shell), gated on M2's epoch work per (5). Version 1 has no window manager; both verbs resolve `unsupported` at petition admission. The layout **facet** (a `since`-gated `get_layout` structural mint on `vitrin_grant`, since `request_grant`'s five `new_id` arguments are frozen) is not added now — an unserved verb needs no facet.

**Costs, stated:**
- Two more immutable bits burned on unimplemented authority, with the same dead-weight risk as D-017's.
- The single-holder-per-output escape is a real restriction, not a neutral simplification: two shells, or a shell plus a tiling agent, cannot both arrange the same output. That is the price of keeping arbitration policy out of the core, and it is revisitable only by an additive design that puts arbitration *outside* the TCB.
- Choosing the refusal code for a second layout holder is left open. Naming one now would either widen an existing `outcome` entry's meaning (a wire-semantics change the growth rules forbid) or append an entry for a mechanism that does not exist.
- The consent surface is unspoofable today partly because nothing outside the core does layout at all. This decision does not make it *more* spoofable — v1 still serves no layout — but it does commit the project to invariants (2) as *invariants*, and their current standing is uneven: (a) holds because the core composites the consent prompt above the realm view; (b) and (d) hold vacuously, since no client can state a stacking order and no cursor is composited at all; (c) has nothing to be true of, because there is no arrangement mechanism. None of the four is tested *as an invariant* against a client trying to violate it, and none can be until something outside the core can arrange realms. That test is E3's, and D-018 is the reason it must exist.

### D-019 — The agent cursor is drawn: display-only, human-visible output only; D-017's delivery deferral stands
**Status:** accepted (2026-07-26) — amends D-017's cursor-*drawing* half only; residual on Q15 unchanged
**Decision:** the core composites a cursor sprite at each actuating agent's own pointer position, into human-visible output and nowhere else. Four parts.

1. **The position is agent-owned, not the shared one.** `input/mod.rs`'s `RealmSeat::agent_pointer` is a second field beside `RealmSeat::pointer`, written **only** when `origin == Emulated` and dropped with the rest of that realm's seat state when its shim generation ends (both were fields of `InputRouter` itself until WS-E.1.6 made the seat state per realm). The shared field is written by both origins — that is exactly the delivery D-017 deferred — so a sprite drawn on it would follow the human's physical mouse and tell the human an agent is pointing wherever the human is. This is the mirror image of `consent/grab.rs`'s `ConsentGrab::pointer`, which is deliberately *physical*-only so an agent cannot slide a hit target under the human's finger: same idiom, one origin over.
2. **Drawing is not delivery, and only drawing changed.** Seat delivery to the shim remains **one shared pointer position per realm view**, `vitrin_shim_seat` events carrying `origin` and not principal identity. `agent_pointer` feeds no hit test, no routing decision, and no wire event; it reaches the compositor through one presentation seam (`session::Presenter::set_agent_cursor`, driven once per dispatch round from `post_dispatch`) and nothing else.
3. **Human-visible output only, at the existing fork.** The sprite is composited at the output stage — downstream of the `Scene::compose` every capture is taken from — exactly like the consent overlay (P1.7.1) and the dead-man hold indicator (P1.7.3). The exclusion from captures is therefore structural, not a checked flag. Both human-visible paths draw it, from one geometry function (`cursor::agent_cursor_rects`): the CPU composite and the nested zero-copy dmabuf draw list. Painting only the first is issue #85's exact bug one property milder, so the sprite rides *inside* `dmabuf::human_visible_frame`'s fixed-length draw list rather than being applied by whoever calls the presenter. The geometry clips every rectangle to `y >= TRUST_BAND_HEIGHT`, because an agent chooses its own position and an unclipped sprite at row 0 would be a new forgery surface against the trusted band, not a cosmetic overlap.
4. **Nested always; headless on `--agent-cursor`.** Nested mode is where the human is, and drawing nothing there is the defect this closes. Headless is off by default because its human-visible framebuffer is *measured* byte-for-byte against the realm view by `backend/band_witness.rs` (issue #139) and by `tests/integration/test_real_trust_band.py`, whose `tracks_view == 1` assertion is taken after a real `grant.pointer.click()` — a sprite on by default there would turn a mock-free gate red for a cosmetic reason. The flag exists rather than the feature being simply absent because headless is the only backend CI can run, so it is the only place the capture-exclusion property can be proved on real composited pixels. `--agent-cursor` with `--nested` is refused at parse time rather than accepted as a no-op.

**What this supersedes, sentence by sentence.** Only the "composites no cursor" claims: `protocol/vitrin-v0.xml`'s §SCENE AUTHORITY "Version 1 serves neither layout verb and composites no cursor of its own", `vitrin_view`'s "version 1 also composites no cursor at all … so the rule is currently satisfied by construction", and `vitrin_actuator_pointer`'s "and composites no cursor of its own"; plus their prose restatements and the "invariant 4 holds vacuously" readings in `docs/protocol/00-conventions.md` §1.4, `docs/protocol/04-vitrin_grant.md`, and PRD §20.15/§20.16.

**What still stands, unchanged.** D-017 (1)–(5) in full, including that cursors are core-composited and that a realm may never supply the bitmap. `observe_cursor` is still refused `unsupported`, so **no capture contains any cursor today**. Agent→agent cursor visibility is still unpurchasable at any verb set, ever. The `ConsentGrab` defensive rule still exists and is still needed, because the *delivered* position is still shared.

**DEFERRED, explicitly:** **per-principal cursor *delivery*** — still **M2**, exactly as D-017 left it, arriving as `since`-gated sibling `vitrin_shim_seat` events that name the principal. Serving `observe_cursor` is likewise still deferred. Per-agent *drawing* over a shared *delivered* position is what v1 now ships; the two are independent, so this closes none of that deferral. Also deferred: a per-agent visual identity (colour or label per principal) — v1 draws one crosshair in one colour, so two agents pointing at once are indistinguishable on screen. That is a real limitation and it lands with the human→agent toggle surface (E3), which needs the human on the wire.

**Costs, stated:**
- **One more thing the compositor draws in the TCB.** `crates/vitrin-core/src/cursor.rs` is integer math over a borrowed buffer with const colours and no allocation — the `deadman::composite_hold_indicator` posture — but it is still new code in the trusted core for a display feature, and it is reachable from a position an agent controls. The band clip and the degenerate-geometry guards are the answer, and both are tested; there is no path here that trusts an agent's coordinate.
- **The two presentation paths can still drift, and only a test stops them.** Nothing structural forces the CPU composite and the dmabuf draw list to agree; what forces it is one shared geometry function plus `no_presentation_path_can_drop_the_agent_cursor`. That is exactly the arrangement the trusted band has, and the band's first cut shipped drift anyway.
- **Nested's sprite is not proved by a mock-free gate.** The capture-exclusion property is proved on headless (`the_agent_cursor_reaches_human_visible_output_but_never_a_capture`, a component test on real composited pixels) and the nested halves are pinned display-free (`window_pixels`, the texture key, the draw list). GL presentation itself needs a display, so "a human really sees the crosshair move in the host window" remains unproven by CI and rests on the operator recipe in `docs/demo/RECORDING.md`. Stated because the whole reason this change exists is a runbook that told an operator to watch something that was not there.
- **Two agents are visually identical**, per the deferral above.
- **Headless's default makes the two backends differ in what a human would see**, which the backend module docs otherwise argue against. The difference is a flag, not a code path — one `if` over the same shared function — and the reason is a named gate rather than convenience, but it is a real asymmetry and this is where it is recorded.
- **A hovering agent now costs composites it did not before.** An emulated motion that changes the integer hotspot dirties the frame and requests a present, where before only a client commit or a consent transition did. It is bounded at one composite per dispatch round by the existing `dirty` gate, and quantizing to whole view pixels drops sub-pixel churn, but an agent sweeping the pointer does make the nested backend draw.

**Amended by WS-E.1.3 (issue #209), 2026-08-07 — the sprite is drawn only for the realm on the output; sharpened by WS-E.1.6 (issue #212).** This decision was taken while a session held one realm, so "human-visible output" and "the realm the agent is acting in" were the same thing and part (3)'s output-stage fork said everything. With the output bound to one of up to `MAX_REALMS` realms, they are not: the sprite is painted in the *output's* coordinates over the *output's* realm, so `post_dispatch` looks the position up **by the realm the output shows** (`InputRouter::agent_pointer(realm)`) and an agent actuating inside a hidden realm draws **nothing**. Under #209 this was a *filter* on one session-wide position, which meant a hidden realm's agent motion could overwrite the position the visible realm would have drawn; the router now keeps one agent pointer per realm, so it cannot. The drawn-versus-delivered gap D-017 defers therefore exists N times over rather than once — per-principal *delivery* is still M2, and there are now N shared delivered positions to be wrong about instead of one. Parts (1)–(4) are otherwise unchanged — one seam, one geometry function, the same band clip and the same capture exclusion. The cost is that the human loses the only visual signal that an agent is acting, for everything off-screen, which is precisely the defect this decision exists to close, reintroduced for hidden realms. It is published in `docs/book/src/limits.md` and in `docs/plan/14-workstream-session-mode.md`; the fix is a per-realm indicator in the trusted band and nobody has scheduled it. Recorded here rather than left in the code because a reader of D-019 would otherwise conclude the sprite always draws.

### D-020 — The realm boundary is a namespace boundary: intra-user by default, in-namespace uid/gid, and a residue that lives outside every realm
**Status:** accepted (2026-08-06) — closes Q11 / PRD §20.11, issue #160; refines [D-010](#d-010--per-realm-isolation-dial)
**Decision:** six answers, one refusal floor.

1. **A realm is intra-user by default.** One host uid for the whole session — the uid `vitrind` already runs as — with the per-realm uid/gid PRD Doc 2 §4.5 promises delivered *inside* an unprivileged user namespace: `CLONE_NEWUSER` with a single-id `uid_map`/`gid_map` written by the parent while the child blocks on a sync pipe, and `setgroups` set to `deny` before `gid_map` (the kernel requires that order for an unprivileged writer). Alongside it, per-realm `CLONE_NEWNS | NEWPID | NEWIPC | NEWUTS | NEWNET`. The alternative — a distinct host uid per realm — was not available as a *default*, because it cannot be reached without privilege: it needs a provisioned subordinate-id range plus a setuid `newuidmap`-class helper, and requiring either would mean `vitrind` cannot start a realm on a machine nobody provisioned. A display server that refuses to run on an unprovisioned host is not a display server.
2. **PRD Doc 2 §4.5's "own UID" is delivered in-namespace, and the property it was bought for survives anyway.** §4.5 asks for own-UID for a stated reason — "so `/proc` snooping, SysV IPC, and same-UID `ptrace` do not cross realms." Each of the three is still closed, by a different mechanism than the one the sentence implies: `/proc` snooping by the PID namespace plus a private `/proc` mount, SysV IPC by the IPC namespace, and cross-realm `ptrace` by the user namespace — `ptrace_may_access` grants a same-uid tracer only when the tracer's user namespace is the target's *ancestor*, and two sibling realms' namespaces are ancestors of neither. So the guarantee holds while the mechanism differs, which is exactly the kind of gap that becomes a false claim if it is left implicit. **This refines D-010's "and UID regardless of tier":** read as a *host* uid, that sentence is false for the default tier as shipped, and the honest reading is per-realm uid/gid *within the realm's own user namespace*.
3. **The per-UID tier is a provisioned upgrade, never a silent default.** Where `/etc/subuid` carries a range for the invoking user and a `newuidmap`-class helper exists, a realm may be mapped to a distinct host uid; the preflight reports whether that tier is reachable, and it is selected explicitly, never inferred. **No packaging for this exists in this repo or anywhere else**, which is why it is stated as an exported limitation on C4 rather than as an available tier: E3.3 must own that packaging or the fleet ships on the weaker intra-user tier.
4. **The realm's private accessibility bus socket is a first-class member of the realm's private resource set** — at the same rank as the realm runtime dir and the realm's private storage, not a later addition. The realm mount table therefore reserves a **fixed in-realm path** for it now, in P2.6.2, before P2.1.3 exists to need it. This is decided here rather than in E2.1 because the ordering is forced: P2.6.2 owns the mount table, so a bus built first would have to be bind-mounted in afterwards and the confinement claim re-made (R2.6). A realm's private resource set is thus: its runtime dir, its private storage, its accessibility bus socket, and nothing else it did not receive by designation.
5. **Host-level sidecars are outside every realm, and therefore outside every realm's confinement.** The VLM parser (P2.4.3) and the egress proxy (P2.7.3) are ordinary host processes with principal identities. They are deliberately not realm members — the parser's memory-unsafety must be irrelevant to the TCB (PRD §17), and the proxy must be able to hold a listener inside a realm's netns without being confined by it. **The consequence is named rather than left to be discovered: the VLM sidecar has unmediated host network access.** E2.7's headline claim is therefore *"a realm with no egress grant emits zero outbound packets"* — a statement about the realm — and is **not** a statement that realm content cannot leave the machine. It can, through a sidecar the realm's netns says nothing about. That sentence belongs in `docs/book/src/limits.md` verbatim, and P2.9.4's sweep is its enumerator. Constraining the sidecars themselves is a decide-by-M3 item; it is not solved by attribution metadata and must not be described as if it were.
6. **The core measures its isolation tier at startup and refuses to start below a floor.** `--isolation=default` requires the full namespace set plus a Landlock ruleset plus seccomp; where the kernel cannot supply them, `vitrind` refuses rather than degrading silently, and `--isolation=none` is the explicit, named opt-out that exists so the confinement gates can run their positive controls. The tier is reported by `vitrind --print-isolation` and journaled per realm at spawn, so the flight recorder answers "what confined this realm" per run rather than per build.

**Why the question could not be deferred.** Q11 is the earliest hard gate in this log because it is not a policy preference — it is the shape of a syscall sequence three epics are written against. P2.6.2's clone flags, P2.6.3's Landlock ruleset, P2.6.6's picker resolution, P2.7.1's netns and P2.1.3's bus socket all encode the answer. Deciding it after any of them means rebuilding that one.

**DEFERRED, explicitly:** the **hardened (gVisor-class)** and **paranoid (microVM)** tiers of D-010's dial — neither ships in Phase 2, and the dial's *existence* must not be read as their availability. Also deferred: **per-UID provisioning packaging** — to E3.3; and **any confinement of the host-level sidecars** — decide-by M3, per (5).

**Costs, stated:**
- **D-010's plainest sentence is now qualified.** "Every realm gets its own network/PID/IPC namespaces and UID regardless of tier" reads, to anyone who has not found this entry, as a distinct host uid. It is not, at the default tier. The PRD sentence stays and this entry qualifies it, per the append-only rule — but a qualification a reader has to go looking for is a weaker instrument than a sentence that was right the first time.
- **A shared host uid means the host-side blast radius of a kernel userns escape is the whole session.** An escape from any realm lands as the user, with the user's files. Only the microVM tier escapes that class (D-010), and it is deferred. This is the cost of being startable on an unprovisioned machine and it is not mitigated, only stated.
- **R2.9 is not retired by this decision, only measured by it.** Distros that restrict unprivileged user namespaces turn the default tier into a refusal to start. The preflight makes that a clear message instead of a mysterious spawn failure; it does not make those machines work.
- **The sidecar residue is real, unmitigated, and ours.** (5) states it; nothing in Phase 2 closes it. Every honest statement of E2.7's guarantee has to carry it, which means four surfaces (`limits.md`, the epic, the gate's docstring, the entry here) must agree, and they will drift unless P2.9.4 checks them.
- **One more startup path that can refuse.** A floor that refuses is the right posture and it is also a new way for `vitrind` to fail on a machine where it previously started. `--isolation=none` keeps that escapable, and that flag is itself a way to run with no confinement while believing otherwise — which is why the tier is journaled per realm rather than only printed at startup.

### D-021 — Session mode is scheduled as a maintainer-dogfooding workstream (WS-E), and that is not the horizon item
**Status:** accepted (2026-08-06) — opens [14-workstream-session-mode.md](14-workstream-session-mode.md); supersedes the "keep at Phase 4" verdict recorded on issue #184
**Decision:** four answers, one boundary that must not blur.

1. **Session mode on bare DRM/KMS becomes scheduled work, as workstream WS-E.** [D-007](#d-007--scope-tiering-invariants--v1--horizon--renounced) says horizon items never migrate class without a decision-log entry, and [04-phase-4-horizon.md](04-phase-4-horizon.md) names session mode the **last** horizon item behind the M4 gate. This entry is that instrument. The maintainer has asked three times for vitrin to replace his existing compositor; the goal is now recorded rather than re-litigated, and WS-E is where its cost lands visibly instead of leaking into Phase 2 as unplanned drift.
2. **WS-E is not Phase 4's session mode, and the M4 gate is untouched.** This is the boundary the entry exists to hold. The horizon item is *a display server other people can run*: a hardware matrix, HDR, color management, fractional scaling, human accessibility, and IME for every user — the support treadmill [PRD](../PRD.md) §5.3 calls "90% of the effort for 0% of the differentiator". WS-E is *one maintainer's one laptop*: a single Intel-driven eDP output at scale 1, Wayland-only, spartan, with the maintainer fixing it when it breaks. Those targets differ by an order of magnitude, and conflating them would let a dogfooding success be read as clearing a gate it never approached. **No WS-E deliverable may be cited as evidence toward M4.**
3. **It is sequenced nested-first, bare-metal-last.** Stages 1–2 (multi-realm, layout verbs, a shell client, cross-realm clipboard — decided by [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing), which is the entry a reader looking for the clipboard's trust argument wants — a core-drawn lock screen) are backend-independent and build inside a window on the existing desktop; only Stage 3 takes DRM master. This ordering is chosen because it front-loads every deliverable that is *also* roadmap work — [D-018](#d-018--layout-is-a-capability-grant-governed-arrangement-core-enforced-ordering)'s layout verbs are allocated and unserved, and raising `MAX_REALMS` is Phase-3 fleet work — and because a backend that takes the seat cannot be iterated on safely from inside the session it would kill.
4. **The shell stays a client.** [PRD](../PRD.md) §5.1 makes "window-management policy lives outside the core" a *permanent invariant*, so WS-E's switcher and launcher are an SDK client holding `layout_focus`/`layout_arrange`, never core code. The cheap path — a switcher inside the compositor — was available, costs about the same, and was refused: an invariant that bends the first time it is inconvenient was never an invariant.

**Why this is defensible rather than merely wanted.** Dogfooding has already paid for itself once, measurably. Within an hour of `vitrind` being runnable by hand, a real terminal aborted the shim on a wlroots assertion (#203): `on_new_deco` answered an xdg-decoration request before the surface's initial commit, killing **every** decoration-aware client. The entire milestone suite could not have found it, because Firefox — the acceptance app — never binds `zxdg_decoration_manager_v1` at all. A project whose acceptance set is two clients has a blind spot exactly the width of what those two clients do not do, and a maintainer living in the thing is the only instrument that finds the rest.

**DEFERRED, explicitly:** everything in (2). No hardware matrix, no HDR, no color management, no fractional scaling (the target panel runs at scale 1, which is why this is affordable), **no accessibility of any kind**, and no IME beyond E2.8's single reference combination. XWayland stays E3.2's, not WS-E's.

**Costs, stated:**
- **Roughly a Phase-2's worth of maintainer time.** WS-E is estimated at 4–6 focused months against a Phase 2 whose remaining budget is about the same. Stage 1 is genuinely dual-use and Stages 3–4 are not; the schedule risk is that the differentiator stalls while the treadmill starts, which is the precise failure PRD §5.3 warns consumed prior alternative display servers. Nothing in this entry mitigates that. It is a priority choice and it is the maintainer's to make.
- **The DRM backend arrives with structurally weaker evidence than anything else in the tree.** GitHub runners have no DRM device and no seat, so the repo's mock-free definition-of-done cannot reach it. That is a real asymmetry against D12 and it must be published in `docs/book/src/limits.md` up front rather than discovered.
- **A shell-as-client means a shell crash loses window management.** The invariant in (4) is right and it has a price: with no core-side fallback, a dead shell leaves a running compositor the human cannot drive. WS-E must state what happens then.
- **`known-limit` grows before it shrinks.** No X11, no bars or launchers (no `zwlr_layer_shell_v1`, measured: waybar connects, binds six globals and never maps), no touch or gestures or lid switch, no accessibility. Each is a published gap this workstream *creates* by making a desktop people might otherwise assume is complete. **Annotated 2026-08-10, not rewritten:** the gesture half of that list closed in WS-E.4.2 under [D-032](#d-032--relative-motion-and-pointer-gestures-grow-the-seat-vocabulary-pointer-constraints-grow-the-shim-session-instead-and-touch-and-tablet-are-deferred-against-named-evidence) — pinch and multi-finger swipe are on the wire, unproven on hardware. Touch, the lid switch and the rest stand. The original sentence is left as written because it records what was foreseen at the time.
- **One machine, one GPU, one output.** Every WS-E number is measured on hardware chosen for being easy: Intel drives the panel, the discrete GPU is not in the display path, and the panel needs no scaling. None of it generalizes, and stating a WS-E result as a portability claim would be false.

### D-022 — Layout enforcement lands early for the nested single-output case; D-018's deferral is discharged, and its unpurchasable set gains a fifth member
**Status:** accepted (2026-08-07) — supersedes [D-018](#d-018--layout-is-a-capability-grant-governed-arrangement-core-enforced-ordering)'s "DEFERRED, explicitly" clause and closes the open name in D-018(4); issue #210, workstream [WS-E](14-workstream-session-mode.md)
**Decision:** six answers, no new verb bits.

1. **`layout_arrange` and `layout_focus` are served now, not at E3.** D-018 deferred *layout enforcement in its entirety* to E3, gated on M2's epoch work. That deferral is discharged **for the nested, single-output case only**: WS-E's shell (#211) is the first client that needs them, and it cannot be written against an unserved verb. What is *not* discharged is D-018(5) — E2.3's epoch does not exist, so an agent's cached coordinates can be invalidated by a shell with no compare-and-swap available to notice. That is a correctness gap for agents, created here and closed later, and it is stated in the costs below rather than implied.
2. **Two facet interfaces, not one, and the dialect forces it.** `vitrin_layout_focus` (`verb="layout_focus"`, request `focus`) and `vitrin_layout_arrange` (`verb="layout_arrange"`, request `set_fullscreen`), each minted by its own `since="2"` structural mint on `vitrin_grant`. `interface/@verb` is one value per interface — it is the codegen chokepoint that generates the single-site authority check — so a combined `get_layout` facet could declare only one of the two verbs and the other's requests would reach the chokepoint with no verb to check them against. D-018(3) requires the two independently attenuable; two interfaces is how the dialect makes that structural rather than conventional. `docs/protocol/00-conventions.md`'s Appendix A row said "layout facet", singular, and **understated the seam**; it is corrected in place, with the correction stated, because that row was the record.
3. **`layout_focus` is one act: bind the output and move the human's physical input with it.** Splitting "which realm is shown" from "which realm receives the human's keys", in a scene that shows one realm at a time, would let a holder make a human type into a realm they cannot see — the sharpest possible form of the focus theft D-018(3) names as "at once the sharpest attack and the most legitimate need". So **D-018(2)'s unpurchasable set gains a fifth member**: *the human's own physical input reaches only the realm the output is bound to.* An agent's injected input is not governed by it — that is addressed to the realm its own grant names and carries the `emulated` origin tag. Mechanically, `session::seat_target` now consults the output binding first and falls back to its old rule only when nothing is bound. **WS-E.1.6 (issue #212) made that its whole job**: it answers for the human's input alone, an agent's actuation is addressed by its own grant's realm through `InputRouter::route_emulated`, and the chokepoint's cross-realm refusal — which had made "an agent's injected input is not governed by it" true only by refusing the input outright — is deleted.
4. **`layout_arrange` serves exactly `set_fullscreen`, and every other arrangement request is ABSENT rather than refusing.** No `place`, no `resize`, no `raise`, no stacking — not a request that refuses, but no request at all. The scene fixed by #209 (one bound realm, no stacking, no overlap, no resize; `scene/layout.rs` says it "must never grow") cannot honour them, and a granted verb whose requests the server cannot carry out is the IDL's own "a deployment MUST NOT grant a verb it does not enforce" turned inside out. The two modes are the only arrangement this scene can express and neither invents a size: **fullscreen** means the realm's view size tracks the output's (`configure` re-sent with the output size, on entry and on every later output resize), **windowed** means the core imposes no size at all and the compositor letterboxes whatever the app keeps committing. A core that chose a third size would be choosing where a window goes, which is the window-management policy PRD §5.1 exiles.
5. **The single-holder answer is `layout_held`, an appended `outcome` entry checked at admission.** D-018(4) fixed the mechanism — "an appended `outcome` entry, since outcome is a plain enum and entries append" — and left the name open; this closes it at value 6. Admission-time rather than use-time, because contention is about who *holds* the authority rather than about one use of it, and because the refusal then never reaches a prompt and costs the human nothing. `busy` could not be reused: its meaning is the consent-fatigue valve, and widening it is a wire-semantics change the growth rules forbid. The check is against **any** holder, not against another *principal*'s — scoping it per principal would let one agent fragment itself into N arrangement grants and leave the core arbitrating between the fragments, which is exactly the arbitration D-018(4) refuses to do. **Holder counts a pending petition as well as a live grant**, and that is a decision rather than an implementation detail: were only live grants counted, two petitions could both be admitted while both waited, a human could approve both, and the session would end up with the two arrangers this rule exists to make unreachable — with no answer left to give the second, because it has already been granted. The slot is therefore taken from admission and released when the pending petition resolves non-`granted`. The cost, stated: a principal whose petition is in front of a human locks out a second principal for as long as that human takes to answer.
6. **Both layout requests are attention-shaped, so they meet `consent_held` and `preempted`.** The chokepoint's step 5b/5c were "actuation only"; they are now "actuation and layout". A principal that could fullscreen a realm over its own pending prompt's card, or move the output away from it, would be arranging the very decision it is waiting on; and moving the output out from under a hand already on the keyboard is the same hazard a synthetic click poses. Both verbs also meet `no_surface`, and the asymmetry with `realm_launch` is deliberate: a vacant realm is the state *launch* exists to leave, while focusing or arranging one would be a successful-looking answer to a request that did nothing.

**Why the four invariants could finally be tested.** D-018's cost note said of its own set that "none of the four is tested *as an invariant* against a client trying to violate it, and none can be until something outside the core can arrange realms". This is that moment, and the tests are the reason this entry exists rather than a note in a PR. Each drives a real client over a real socket, holding **every verb the reference core serves**, through the whole production path, and sweeps the *entire* arrangement space the two verbs can express — finite and small precisely because (4) defines one request. A property proved at the maximum verb set is a property of *no grant*, which is what "unpurchasable" has to mean.

**Costs, stated:**
- **D-018(2) gains a fifth invariant D-018 did not state.** Extending an accepted decision's enumerated set from a later issue is the drift the append-only log exists to prevent, which is why this is an appended entry rather than an edit to D-018 — and an appended entry a reader has to go looking for is still a weaker artifact than having got it right once.
- **The consent surface's unspoofability rested partly on nothing outside the core doing layout at all.** D-018's cost note says so in as many words, and this entry removes that circumstance. What replaces it is five invariants and five tests, and tests are a weaker instrument than "there is no mechanism".
- **The partial-verb hazard is avoided by omission, which is fragile.** Nothing structurally stops a later issue adding a `place` request to `vitrin_layout_arrange` while the scene still cannot honour it. What guards it is prose plus one test that pins the IDL's message count with a comment naming the stake — a tripwire, not a barrier.
- ~~**A `layout_focus` holder can deny service to every other agent.** `enforcement.rs` step 5d refuses an actuation whose grant's realm is not the seat's target; that target now follows the binding, so a holder chooses which *other* principals' actuations are refused. The refusal is recoverable, journaled, spends no token and burns no `once` rung, and it closes when #212 routes per realm — but until then it is a real cross-principal denial-of-service surface created by serving this verb. Published in `docs/book/src/limits.md`.~~ **Closed by WS-E.1.6 (issue #212), 2026-08-07.** Step 5d is deleted rather than relaxed: the grant's realm travels with the event (`UseEnv::grant_realm` → `session::route_seat`), an actuation over a realm the output is not showing is *delivered* to that realm, and there is no comparison left for a holder to influence. The `limits.md` paragraph that published it is gone with it.
- **`set_fullscreen` is a no-op whenever the output and the realm are the same size**, which is the ordinary case for a realm spawned into an output that has not resized. Honest, documented in the IDL, and surprising.
- **Serving layout early breaks D-018's stated sequencing**, per (1). E2.3's epoch is a *binding constraint* on layout in D-018(5), and it does not exist.
- **Two more facet interfaces and two more served verbs inside the TCB's enforcement path.** `single_enforcement_path` keeps the chokepoint singular, but the number of arms it dispatches grows and each is a place a future edit can route around.
- **`Verb::VALID_MASK` is unchanged, so the tripwires here were softer than WS-E.1.1's.** No new bit means `crates/vitrin-protocol/tests/decode_errors.rs` did not fire. **Six** did, and the count is stated exactly because this bullet is the artifact recording the guard's record: the consent catalogue's unserved-set pin (`consent/render.rs`), the grant table's served/unserved pins (`grants.rs`, both halves), `vitrin_grant`'s defined-opcode test, the roundtrip table's message-count exhaustiveness gate (`crates/vitrin-protocol/tests/roundtrip.rs`), the C header's parallel gate (`shim/tests/test_header_compiles.c`, 32 → 36), and `protocol/test-mutations.sh`'s `verb-without-facet` case — which fired by going *stale*: its mutation (`realm_launch` → `layout_arrange`) became a legal document once `layout_arrange` gained a facet, so it reported the schema as broken when the schema was right, and was re-pinned on `observe_cursor`, which is facetless by construction. Each was re-pinned with a stated reason rather than a mechanical bump. Had any been weakened, a verb could have become served with no prompt copy, which is the exact failure D-017's guard was built against. A seventh, in the Python SDK (`test_typed_exception_mappings_are_exhaustive`), did **not** fire when it should have: it counts `Outcome` members against the mapping table, and appending `layout_held` to the IDL alone left both untouched — the SDK's copy of the enum is a hand transcription, so the gate could only fire once a human edited it. That gap is what let `layout_held` decode to `ServerContractViolation` and close the connection until it was found in review.
- **The nested half is not proved by a mock-free gate.** That a human sees the focused realm change in the host window is a manual runbook step: runners have no display and headless is the only backend CI runs (D-019(4)).

### D-023 — The core owns a second physical chord: a tapped, consumed attention key that lifts `preempted` for the two layout verbs only, and delegates nothing
**Status:** accepted (2026-08-08) — falsifies `crates/vitrin-core/src/deadman.rs`'s "the core owns exactly one physical chord" and makes [D-022](#d-022--layout-enforcement-lands-early-for-the-nested-single-output-case-d-018s-deferral-is-discharged-and-its-unpurchasable-set-gains-a-fifth-member)(6)'s `preempted` conditional; issue #232, workstream [WS-E](14-workstream-session-mode.md)
**Decision:** three answers, no new verb bit.

1. **The attention key is a statement about the human's own input state, not a delegation — and the whole design rests on that reading.** A human at an in-realm shell cannot ask it to change the layout: they type `focus editor`, press Enter, and that Enter marks `PhysicalPresence` in the realm they are in, so D-022(6)'s step 5c refuses the request `preempted`. **The input that tells the client to act is the input that forbids it**, and pressing Enter again re-arms the window, so it is a deterministic loop rather than a race; `fullscreen on<Enter>` hits the identical loop. The mechanism is the smallest thing that expresses the missing distinction: a second core-owned chord — **Super, tapped, consumed** — opening a one-second, single-use, session-wide window in which a `layout_focus`/`layout_arrange` use by a principal the signal reached is not refused `preempted`, plus one argument-free `vitrin_principal.attention` event to every principal holding layout authority. What makes a bare bit defensible is that **step 5c is not a focus-theft defence**: it is a 500 ms courtesy, and a `layout_focus` holder can already take the output at any moment the human pauses for half a second, which is most moments. The grant, its revocability and the dead-man switch are what bound focus theft. So the press *withdraws a courtesy the core extends to the human's typing*; every authority exercised afterwards came from a grant approved on a consent card naming the principal and the realm, and a client that provokes the press gains **timing, never authority**. Consequences that follow from that reading and were taken rather than argued around: **no verb bit is allocated** (a grantable "receive the human's attention key" verb would put the delegation framing on the wire — `Verb::VALID_MASK` stays 575 and [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5's registry is untouched); the event carries **no arguments, forever** (a `window_ms` would make the core's own security parameter a client's timer); the chord is **consumed**, so no confined app learns the human pressed it and the authority-gated wire event is the only observation path, closing a free keystroke-timing oracle; and the chord still **marks physical presence**, because the core must not manufacture a false fact about where the human is.
2. **This should not have been a consent prompt, and the reason is that the consent surface's value is its scarcity.** The honest alternative was *no chord at all*: when 5c would refuse a layout use, raise a prompt naming the principal and the realm. That is strictly stronger on every property this decision is weakest at — it cannot be hoarded, it names its subject in core-drawn pixels, and confused-deputy provocation dies against it. It loses on one thing and it is decisive: in an in-realm shell 5c fires on *every* switch, so the prompt would appear on the session's single most-used action, answered by a mouse click through `GUARD_INTERVAL` several times a minute. That trains reflexive clicking on the one surface in this system whose entire worth is that a human reads it, and it degrades every *other* prompt in the session — Q9 already tracks consent fatigue as a live problem and this would be its largest single contributor. A modal card is the right instrument for a first-contact delegation of authority and the wrong one for a courtesy the human is withdrawing from themselves. What replaces the card is: the exemption is **single-use** and claimed only at step-6 admission and only when 5c actually suppressed a refusal (`Exemption` is `#[must_use]`, not `Copy`, and consumed by value, so a second claim from one press is a compile error); delivery is **filtered** to live layout holders and the claim is restricted to that same set resolved at press time; every press and every claim is **journaled**; and the human sees a **marker beside the trusted band** while the window is open — beside, never inside, because the band's whole value is having exactly one correct appearance (#215's rule for the clock and battery, applied here for the same reason).
3. **A second core-owned chord must justify itself and must not borrow the dead-man's warrant.** `deadman.rs`'s module docs were emphatic that the core owns exactly one physical chord *because the human's off-switch must not depend on a client*. That sentence is now false and is rewritten rather than quietly left — but the warrant stays **narrow**: it was never "the core may own chords in general", and a third chord makes its own case from scratch. The general rule this fixes for any future one: **a hold is for the irreversible and severe; a tap is for the cheap and reversible.** An accidental attention press costs at most one focus change, undone by pressing again; an off-switch may not fire by accident at all. The two are kept structurally apart at every level: disjoint vocabularies (`Chord::VOCABULARY` excludes every modifier for its own reason, the attention vocabulary is nothing *but* the two Supers, so they cannot collide even before the startup equality check that is kept anyway); the dead-man detects in `observe` — unconditional, unstoppable, owning all its own state — while attention only ever gates, suppressible by a consent prompt, by the dead-man, and by anything above it; `DeadManHook` is stacked **outside** `AttentionHook` so a chord press wins; `apply` clears any open window belt-and-braces beside `seal_dead_man`; and the hold indicator stays the last thing composited so the marker can never hide it. Attention's failure mode is a focus change that does not happen; the dead-man's is a revocation that does not happen. They are not in the same class and nothing may make them look like it.

**Costs, stated:**
- **The core now eats Super, everywhere, unconditionally.** A confined app that legitimately wants it — a nested compositor, a VM viewer, a remote-desktop client in a realm — loses the key with no pass-through and no way to ask for one. That is the cost `deadman.rs` refused to pay for Escape, paid here for a different key on the argument that every desktop already reserves it for the compositor. If that argument is wrong for someone's workload the only remedy is `--attention-chord rsuper`, which is not a remedy. Published in `docs/book/src/limits.md`.
- **The session-wide window is a real hole and the delivered-to set only narrows it.** Any principal the event reached may claim it; the core cannot tell which of two layout holders the human meant, and it cannot be fixed here — choosing a recipient means choosing a shell, which is the window-management policy PRD §5.1 exiles, and the mapping that would make it structural ("the principal that draws in the bound realm") does not exist because a realm and a principal connection have no binding. A second holder can consume a press the human aimed at the shell; the human's own switch then silently fails and the thief's lands. Journaled, revocable, and still a hole.
- **Confused-deputy provocation is not closed and cannot be.** A shell printing "press Super to apply" is doing the right thing; a malicious one printing the same string and banking the timing is indistinguishable. What bounds it is that the press confers no authority the client did not already hold — an argument only as good as the reader's willingness to follow it, and a human who learns "press Super when the screen tells me to" has learned a habit an attacker can invoke.
- **`preempted` on the layout verbs becomes conditional on invisible core state.** An agent reading its own journal can no longer reconstruct why one `focus()` landed and an identical one did not without correlating attention entries it cannot see. The refusal used to mean one thing. This is the protocol's **first conditional refusal code**, and the precedent is the cost as much as the confusion is.
- **Other principals lose a guarantee nobody tells them they lost.** "A human typing means nobody moves the output" was true for 500 ms at a time and is now suspendable by a gesture no wire event announces to anyone but layout holders — the same shape as the narrowing WS-E.1.6 published, and it needed the same `limits.md` paragraph.
- **`vitrin_principal` grows past "the root of the connection's authority chain".** It becomes the place session-level facts about the human arrive. That is defensible once; it is also the seam through which a future issue puts a second, less defensible fact there because there is now a precedent. Recorded on `docs/protocol/02-vitrin_principal.md` so the precedent is at least visible to whoever cites it.
- **The dead-man's docs were written as if it would stay alone, and rewriting them risks weakening the argument by generalising it.** The sweep kept the warrant narrow — admitting a neighbour rather than opening a category — and that is a harder edit than it looks. What guards it is prose plus `an_attention_press_in_the_same_round_changes_nothing_here`, which compares every observable of a full hold with and without the neighbour stacked.
- **A new way for a session not to start.** Startup now refuses on chord collision. Correct, fail-closed, unreachable today (the vocabularies are disjoint), and one more configuration an operator can get wrong at the moment they least want to.
- **Two indicators now compete for the top strip and a third is scheduled** (#215's clock/battery/focused realm). Nobody has designed that strip as a whole, and each issue that adds to it is deciding the layout of a surface whose whole purpose is being unambiguous.
- **The nested half is not proved by a mock-free gate, and cannot be.** `SeatInput::physical` is private by design, headless has no input device, and headless is the only backend CI runs (D-019(4)). `tests/integration/test_attention.py` proves the *consequence* half through the `physical-input-injector` channel — the same split #212 wrote out and the same one `deadman.rs` accepts for its detection half. That a real Super press on real hardware reaches the gate is a nested manual runbook step (`shim/docs/nested-multi-realm.md`), not a criterion.
- **What this does not fix, and must not be read as fixing:** the in-realm shell's confinement problem (#211 decision 2 — the shell still has to reach the core socket from inside a realm); the absence of a read of which realm is focused (page 17 refuses it on purpose); D-018(5)'s missing epoch, so an agent's cached coordinates are still invalidated by a layout change with no compare-and-swap to notice; a shell crash losing window management; or anything about `actuate_pointer`/`actuate_text`, which stay preempted by a human's hand exactly as they are today.

### D-024 — The cross-realm clipboard is a core-held single slot, PULLED by the core on two human gestures that delegate nothing
**Status:** accepted (2026-08-08) — implements [PRD](../PRD.md) §11's clipboard broker for the nested single-output case, narrows PRD §15's first threat row, and falsifies `shim/src/globals.c`'s *"cross-realm clipboard remains exactly where it belongs, unbuilt"*; issue #213, workstream [WS-E](14-workstream-session-mode.md) §4.1
**Decision:** five answers, one refusal, and **no verb bit**.

1. **The bytes live in one core-held slot, and the maintainer chose that knowing what it costs.** This is the only answer in this log recorded as an owner's call rather than as an argument's conclusion, and it is recorded that way on purpose. Taha was asked, in plain terms, on **2026-08-08**, and given four options: (a) a core-held single slot, (b) no buffer and a direct A→B pipe brokered at paste time, (c) a per-realm broker, and (d) do not build it. He was told the cost of (a) in exactly these words — *for the first time the trusted core retains bytes an application authored, so a compromised core exposes whatever was last copied* — and chose (a). (b) was rejected for its **timing leak**: it needs both realms alive at paste time, and it tells A exactly when B pasted, which is a covert channel running from the sink back to the source, the one direction a mediator exists to close. (c) multiplies state by `MAX_REALMS` and changes no trust question. (d) was offered and declined. Nothing in this decision is a default somebody picked.
2. **The core PULLS, and the wire shape makes that structural rather than conventional.** `vitrin_shim_session` gains three `since="2"` messages: `request_selection` (event, core → shim), `selection` (request, shim → core), `offer_selection` (event, core → shim). There is deliberately **no `selection_changed` event**: a shim that forwarded every app-side copy upstream would make every ordinary Ctrl-C a cross-realm event, which is an ambient channel wearing a broker's clothes and would make the Qubes phrase this design quotes — *"fully controlled by the user, it cannot be triggered/forced by any"* realm — false in the first sentence. The hybrid (push a MIME-and-length notification, pull the bytes) was rejected too: a per-copy cross-realm signal is a free keystroke-timing oracle over the human's own editing, and it buys nothing. What makes "the core pulls" more than a rule the code follows: `ClipboardSlot::fill` takes a `PendingPromotion` **by value**, that type has no public constructor, is neither `Copy` nor `Clone`, and is minted only when a human's promote gesture actually fires — so an unsolicited `selection` from a compromised shim has no ticket to consume and fills nothing. A shim that pushes is a type error, in the mould of D-023's `Exemption` and #207's `SpawnRecord`.
3. **The human path is not grant-governed, and that is a considered answer.** Grants key on a `PrincipalIdentity` bound at `hello`; **the human at the keyboard is not a wire principal in v0**, so a `clipboard` verb bit would name a principal that is not the actor, burn an immutable bitfield entry on authority nobody can hold, and touch `identity.rs`, `principals.toml`, the grant table and the consent surface in one change. The dead-man switch sets the precedent this follows: the human's gesture is **a fact the core acts on, journaled** — never authority the core issued. A consent prompt per transfer was the honest alternative and is refused for [D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing)(2)'s reason, which binds harder here: copy-paste is a several-times-a-minute act, and a modal card on it would train reflexive clicking on the one surface in this system whose entire worth is that a human reads it. `Verb::VALID_MASK` therefore stays **575** and [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5's allocation registry is untouched.
4. **The gesture is Ctrl-Shift-Insert (promote) / Shift-Insert (offer), and it could not have been Ctrl-Shift-C.** `invariant_keysym` is a fixed scancode table with **no letters and no digits** — asserted, not assumed (`crate::input::invariant_keysym`'s own test asserts `KEY_A -> None`). Letters reach the core today only in nested mode, because winit resolved `logical_key` and the *host* compositor did the interpreting (#118); on bare DRM in WS-E Stage 3 there is no host, so the Qubes chord would work on the maintainer's laptop and stop working the day the workstream arrived at its point. Growing an xkbcommon keymap in the core is refused here rather than merely deferred: `crate::input`'s module docs, the **Keys pair the same way, per key** paragraph records that a real keymap moves key pairing from the keysym to the scancode — a **router invariant**, on the path the dead-man switch depends on — and it is Stage 3's decision, which a clipboard issue must not pre-empt. `KEY_INSERT` is in the table and already in the dead-man vocabulary, and Shift-Insert is the historical X11 clipboard chord, so the pair is familiar rather than invented. A chord this build cannot deliver is refused at **startup**, through the same `input::keysym_is_intakeable` check `deadman::Chord::parse` uses, for the same fail-closed reason.
5. **`text/plain;charset=utf-8` only, 61 440 bytes, cleared on timeout, on source-realm death, and on a dead-man trigger.** Every other MIME type is a decoder question and *"no image codec in the core, in any dependency class"* is a rule `crates/vitrin-core/Cargo.toml` states twice; `text/uri-list` is refused separately, because a path is a **designation** and designation belongs to the powerbox (E2.6) — a clipboard that moves paths is a file-transfer channel wearing a clipboard's clothes. The cap is **measured, not asserted** (WS-E §4.1 carries the table). Two bounds meet and only one is a choice: the wire's `u16` frame size caps a whole frame at 65 535 bytes, so the largest string a `selection` can carry is **65 476** and the issue's proposed 1 MiB is *inexpressible* without an fd — which would put a shim-controlled mapping inside the TCB, re-opening the size-lie and SIGBUS class the buffer path already spends `invalid_buffer` on, to carry a clipboard. Within that ceiling, over this repository's text files a 60 KiB cap copies **92.26%** of them whole against the frame maximum's **92.90%** — so the last 4 036 bytes buy **0.64 points** and spend every byte of framing headroom. (Those figures are the corrected ones. The first measurement globbed the working tree, which then held ~40 scratch worktrees, a vendored wlroots checkout and build output, so ~96% of the 6 550 files counted were not this repository and none of its five statistics reproduced; re-measured over `git ls-files`, 310 tracked text files, median **11 410 B**, p95 **106 707 B**, p99 **240 239 B**. WS-E §4.1 was corrected when the error was found and **this entry was not**, which is the drift a decision log exists to prevent — recorded rather than silently patched.) 61 440 leaves 4 039 bytes spare, which is room for `selection` to gain an argument later without the cap moving; the cap lives in the IDL's immutable `(max N bytes)` token and therefore *cannot* move. "Cleared on paste" was rejected because humans paste twice.

**This discharges NONE of E3.5's exit criteria, and the reason is not modesty.** [03-phase-3-network-x11-fleet.md](03-phase-3-network-x11-fleet.md) §E3.5 owns the *hardened* broker, drag-and-drop as designation, window activation and the portal-compat layer, and its criteria are `copy in realm A → paste in realm B requires two explicit user actions and is journaled`, `the portal-compat matrix is published with pass/fail per app`, and `no shared clipboard exists anywhere (verified, not asserted)`. The first *looks* discharged and is not: E3.5's is a **fleet-scale** claim over network sessions and the headless deployment PRD §81 promises *"no shared seat, no shared clipboard"* for, and this is one nested single-output session on one laptop with no network path, no agent-facing verb, no drag-and-drop and no portal. The third is a verification obligation over every deployment, and this issue **adds a clipboard** to one of them. What #213 delivers is the *subset* E3.5 hardens; citing it against any E3.5 criterion would be the exact class of honesty gap the milestone rule in `CLAUDE.md` exists to forbid.

**Also decided here, because two later issues consume it:** the modifier-aware chord matcher (`crates/vitrin-core/src/chord.rs`) is **general**, not clipboard-private. `deadman::Chord` deliberately excludes every modifier (a human holds Shift for seconds at a time, so a modifier off-switch fires during ordinary use) and `attention::AttentionChord` is nothing *but* the two Supers; neither can express `ctrl+shift+insert`. WS-E.2.2's lock chord (#214) and WS-E.2.4's screenshot key (#216) both want one, and whichever lands second must consume this rather than adding a parallel matcher in the same hook stack — which `deadman.rs`'s module docs spend hundreds of lines explaining the hazard of.

**Costs, stated:**
- **The TCB stores application-authored bytes.** (1)'s accepted cost, restated here because it is the entry's whole weight: a password copied from a manager transits `vitrin-core` and rests in a slot with a lifetime. The cap, the allow-list, digest-only journaling and three clearing rules bound it; **none removes it**, and no future entry should describe them as if one did.
- **A published claim becomes narrower, in the PRD itself.** PRD §15 row 1 said a malicious app cannot *"reach the session's real seat/clipboard/a11y bus"*. It can now reach a clipboard — through a human gesture, one direction at a time, one MIME type, 60 KiB at a time. The row is **edited**, not left standing, and `docs/book/src/limits.md` carries the channel. PRD §81's headless-fleet promise is untouched and must stay untouched: nothing here is reachable without a physical keyboard.
- **It is a covert channel with a stated bandwidth, not an absent one.** Two colluding realms move ~60 KiB per human gesture pair. Qubes accepts the same bound. The honest statement is always the bound.
- **New wire surface freezes into v0.** Three `since="2"` messages and one enum, immutable thereafter. A shape chosen against one maintainer's laptop is a shape E3.5 inherits, and the one place that is load-bearing is the byte cap: it is a `(max N bytes)` token, so raising it later is a *new message*, not an edit.
- **The core owns two more physical chords, in the hook stack the dead-man switch lives in.** D-023 said a second chord *"must justify itself and must not borrow the dead-man's warrant"*, and that warrant does not stretch to a third and fourth. What justifies these: they are **taps, for the cheap and reversible** (D-023(3)'s general rule — an accidental promote costs one slot overwrite, an accidental offer costs one seat selection), they live in `gate` only and never in `observe`, they are stacked **inside** both the consent grab and the dead-man hook so neither can be delayed by them, and their vocabulary is disjoint from both existing chords by a startup check rather than by assertion. What it costs anyway: `deadman.rs`'s sentence about how many chords the core owns is now wrong for the second time in two issues, and a stack of four chord matchers is four places to get the gate wrong.
- **Shift-Insert is taken from every app in every realm.** The historical X11 primary-paste chord, consumed with no pass-through and no way to ask for one — the cost `deadman.rs` refused to pay for Escape and D-023 paid for Super, paid a third time. The argument that makes it affordable is narrower than D-023's: not *"every desktop reserves it"* (they do not), but *"the gesture the human loses inside a realm is the gesture they gain across realms"*.
- **The detection half cannot be proved in CI, and that is structural.** GitHub runners have no physical input device; `SeatInput::physical` is private by design and headless is the only backend CI runs (D-019(4)). The gesture's *effect* is proved through the `physical-input-injector` channel, reaching the same entry point a real chord reaches; that a human really holding Ctrl-Shift-Insert produces the gesture is a manual runbook step in `shim/docs/`, and the acceptance criterion is written as a runbook rather than a green check on purpose.
- **The slot has no wire event when it is cleared.** A human who copies, waits out the timeout and then presses Shift-Insert gets nothing and no message. The core has no surface on which to say so — the trusted band is a colour and the consent stack is for authority decisions — and inventing one for this was refused as scope. It is a real usability hole.
- **Dependency budget.** Issue #201 records that there is still no `deny.toml` and no `cargo-deny` job, so plan risk R7's stated mitigation is unbuilt while this adds wire code, C code and core state. Unchanged by this entry; restated because it is still true.

### D-025 — A locked screen does not suspend agent observation; the gap is published, not papered over

**Status:** accepted (2026-08-08) — implements WS-E.2.2's lock screen (issue #214) under [PRD](../PRD.md) §5.1's trusted-path reading of the window-management invariant; workstream [WS-E](14-workstream-session-mode.md) §6

**Decision:** **the maintainer's call, asked and answered in plain terms on 2026-08-08, and recorded as his rather than as an argument's conclusion.** Taha was told, in exactly these words, that a lock screen on this stack takes the *human's* input away and leaves an agent's authority untouched — so a principal holding `observe` keeps capturing the realm across a lock, frame for frame, and one holding `actuate_pointer`/`actuate_text` keeps acting. He was offered the alternatives below and chose to **leave observation concurrent and publish the gap loudly**. Nothing in this entry is a default somebody picked, and it is not to be re-litigated by a later issue that finds it surprising: being surprising is the reason it is published.

**Rejected *with* him, each for a reason that is not "it was hard":**

1. **A new refusal code** (`locked`, or `preempted` widened to cover a lock). This is a **v0 wire-semantic change**: `protocol/vitrin-v0.xml`'s `vitrin_view` states that observation is concurrent by design, so `preempted` and `consent_held` deliberately never refuse a capture. Redefining that is the protocol track's and E3's, not a `track:rust-core` issue's, and `Verb::VALID_MASK` stays **575** with [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5's allocation registry untouched.
2. **Blanking the realm view for agents while locked.** An agent silently receives black frames and is never told why — a lie by omission, and the exact class of dishonesty `refusal.no_surface` exists to avoid. It would also make "the capture is byte-for-byte `Scene::compose`" false, which is the sentence three modules' structural arguments rest on.
3. **Routing the lock through the enforcement chokepoint as a synthetic human principal.** This invents a wire principal the identity layer does not have. The dead-man switch already sets the precedent for the honest shape: the human's gesture is **a fact the core acts on, journaled** — never authority the core issued.

**What makes it defensible rather than merely decided:** the human's instrument for "stop everything" is unchanged and, by design, **still works while locked**. Holding the dead-man chord revokes every grant, denies every pending petition, seals the table and clears the clipboard slot. Issue #214 called that stacking requirement "not optional — a lock that disables the human's off-switch inverts the safety argument", and it is enforced structurally rather than by review: the lock's policy implements `crate::input::ConsumingGate`, a trait with **no observation method**, and the `PreemptionHook` impl that forwards the observe tap lives in `crate::input`, which has no `use crate::lock` at all. An edit inside `crate::lock` cannot make the off-switch's detection conditional, because the code that observes is not reachable from there. That is the [#210](https://github.com/vitrin-os/vitrin-os/issues/210)/[#232](https://github.com/vitrin-os/vitrin-os/issues/232) shape — make the mistake unconstructible — applied one level up, and `the_dead_man_chord_arms_and_fires_through_a_locked_gate` holds the consequence against the **real** `InputRouter<LockGate<ConsentGate<DeadManHook<ClipboardHook<AttentionHook<NoopHook>>>>>>` rather than a stub.

**Also decided here, because they are the same judgement applied to smaller questions:**

- **The lock screen is core code, and PRD §5.1 does not say otherwise.** The invariant exiles window-management *policy* — decorations, layout, arrangement. It does not exile the trusted path: the consent surface, the trust band, the attention marker and the dead-man indicator are all core-drawn under it. The discriminator is whether the pixels make an authority claim a human must be able to believe, and a lock screen makes the sharpest one in the system. [D-021](#d-021--session-mode-is-scheduled-as-a-maintainer-dogfooding-workstream-ws-e-and-that-is-not-the-horizon-item)(4) closes the alternative: the WS-E shell is deliberately a client and D-021 already prices "a shell crash loses window management" — as a lock screen that would read "a shell crash leaves the session unlocked".
- **The card says the surprising part, not only this log.** `crate::lock::render`'s honesty block tells the human, on the trusted surface itself, that agents keep working and that the dead-man chord is what stops them. A warning a human cannot act on is one `crate::consent::render` already refuses to print; this one names the instrument in the same sentence.
- **A passphrase is nested-only, and refusing it elsewhere is fail-closed.** `crate::input::invariant_keysym` has no letters and no digits — asserted, not assumed. Letters reach the core in nested mode only because winit resolved `logical_key` and the *host* compositor did the interpreting (issue #118). `--lock-passphrase-file` is therefore **refused at startup** with `--headless`, naming the keymap as the reason and exiting non-zero, exactly as `--headless --consent=interactive` is. Growing an xkbcommon keymap is refused here rather than deferred quietly, on [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing)(4)'s grounds: `crate::input`'s module docs, the **Keys pair the same way, per key** paragraph records that a real keymap moves key pairing from the keysym to the scancode — a **router** invariant, on the path the dead-man switch depends on — and that is Stage 3's decision to take explicitly.
- **The shared rasterizer moved out of `consent`.** `crate::paint` (canvas, embedded-font text engine, one `centered`) is now its own module, because `deadman`, `cursor` and `attention` were already importing `consent::canvas` — a path that said the off-switch draws with the consent surface's private tools. Moved, never copied: two rasterizers in one TCB is two places for a golden to drift.

**Costs, stated:**

- **A locked screen an agent can still watch.** The whole weight of this entry, restated because it is the thing a reader will most want to believe was fixed. It was not fixed; it was decided, and it is published on the card, in `docs/book/src/limits.md` and in [WS-E](14-workstream-session-mode.md) §6.
- **In nested mode this is a demo, not a lock.** `vitrind` is a client of the host compositor, which owns the real session; anyone can alt-tab away. Stages 1–2 ship a lock screen that locks a *window*.
- **On bare DRM, VT switching is an escape** unless the core inhibits it — and inhibiting it means a session a human cannot leave when the compositor wedges. Not decided here, and this entry must not be read as deciding it.
- **A KDF entered the TCB, and it processes operator-supplied input.** Four crates (`argon2`, `base64ct`, `blake2`, `subtle`), measured against `Cargo.lock` rather than estimated. Unlike fontdue — justified on "the only bytes it parses are a compile-time constant" — this one really does parse bytes an operator wrote, though never bytes that arrived over the wire. Issue #201 records that `deny.toml` and the `cargo-deny` job still do not exist; `crates/vitrin-core/Cargo.toml` is the only place the budget is checked.
- **A fourth gate in the input stack, and a fourth chord taken from every app.** D-023 said a second chord *"must justify itself and must not borrow the dead-man's warrant"*, and D-024 already spent that argument twice. What justifies this one: it is the one gesture in the set that **cannot** be a client's, for exactly the reason the dead-man switch cannot; and it is cheap and reversible in D-023(3)'s sense only when no passphrase is configured, which is why the card names which of the two it is. What it costs anyway: `Ctrl-Alt-Delete` is consumed in every realm, and `--dead-man-chord delete` is now refused on an otherwise default command line — because the switch detects in the unconditional observe tap, so a lock chord sharing its key would arm the off-switch every time a human locked their screen.
- **CI cannot prove the security property, and the criterion is written to say so.** "A human at a real keyboard cannot get past it" needs a real keyboard and, on bare metal, a real seat; no GitHub runner has either. What CI proves is the composite, the golden, the gate's pairing behaviour, the recorder entries and the off-switch's survival through the real stack. The end-to-end claim is a dated manual runbook (`shim/docs/nested-lock-screen.md`), which is the same split [D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing) and [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) already accept for their detection halves.
- **New always-resident core state on the frame path.** A second `ConsentSurface`-shaped cost per backend, and a raised lock forces the CPU compositing path for as long as it is up — so the zero-copy dmabuf branch is off while the screen is locked. That last part is not a cost so much as a requirement: without it the branch would present the client's own texture, full-window, with the lock nowhere on it.

### D-026 — The top strip is designed as one surface: the band alone, then the status strip beside it, and the app's rows are still overdrawn

**Status:** accepted (2026-08-08) — implements WS-E.2.3's status strip (issue [#215](https://github.com/vitrin-os/vitrin-os/issues/215)); workstream [WS-E](14-workstream-session-mode.md) §6

**Why an entry at all:** three issues drew into the rows around the trusted band and each was designed without the others — the dead-man hold bar ([D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing)'s neighbour), WS-E.1.7's attention marker (#232), and this strip. WS-E §6 recorded that as an unowned collision and named the third to land as its owner. This is that decision, made once and written where the next person will find it.

**Decision, in draw order:**

```text
realm view -> consent overlay -> lock cover -> STATUS STRIP -> trusted band
           -> attention marker  ...  -> dead-man hold indicator (last of all)
```

1. **Nothing is ever composited into the band.** Rows `[0, TRUST_BAND_HEIGHT)` stay exactly one colour. This is not a review rule: the strip's raster is the *strip's* own height and is blitted at `y = TRUST_BAND_HEIGHT`, so no coordinate expressible in `status::render` lands in the band. It is also measured — `band_witness`'s `band_changes` stays `0` over composites its new sibling `strip_changes` proves were really repainting.
2. **The strip is composited over the lock cover, not under it.** #215 left this open for whoever landed second; #214 landed first, so #215 decided it. A clock is the one thing a human wants on a lock screen, and "the strip is always there" must have no exception — a rule with an exception is a rule a human cannot apply. It leaks nothing the lock exists to hide: the lock's job is that *client* content stops being legible, and every field on the strip is core-owned, including a `realm.toml` id the lock card itself already prints.
3. **The attention marker keeps a lane rather than relying on z-order.** The strip's content starts past `attention::MARKER_W`, read from that constant and never restated, under a `const` assertion that turns an overgrown marker into a compile error. Ordering alone would keep the marker *visible*; it would still leave a glyph half-covered whenever the window is open.
4. **The dead-man hold indicator stays composited last of all.** Unchanged, and restated because every addition to this surface is a chance for it to stop being true.
5. **The strip is opt-in (`--status`, off by default).** The `--agent-cursor` precedent, for the same measured reason: the headless human-visible framebuffer is compared byte-for-byte against the realm view by `band_witness` and by `tests/integration/test_real_trust_band.py`, and a clock on by default would make a mock-free gate a function of the time of day.
6. **The clock is a fixed offset, not a timezone.** The core takes no tzdata parser and no recurring `/usr/share/zoneinfo` read into the TCB for a cosmetic field. `--status-utc-offset` states an offset; the strip always labels the zone it draws, so a wrong hour is a wrong flag rather than a wrong clock. No DST.

**Costs, stated:**

- **The realm view is NOT inset, and #215 asked for it.** The strip overdraws 20 rows of client content the way the band already overdraws 8; the app is not configured smaller and does not lay out for it. A correct inset needs one usable-view value reaching `scene::layout::place` from three paths that share no carrier for a second number (`Scene::compose`, the router's `surface_local`, `dmabuf::human_visible_frame`) plus the `configure` size the shim is told — a `ViewGeometry` refactor of its own — and a half-done version, one path reserving rows the others do not, is strictly worse than none. Deferred deliberately, published in `docs/book/src/limits.md`, and the reason `--status` is opt-in.
- **The indicator story is three rules where it was one.** "Everything above the coloured line is trusted, the line itself is the proof, and the strip below it is trusted-but-not-self-proving." An app can paint a convincing fake strip one row lower; the band is the only anchor. `limits.md` already concedes the indicator is "unforgeable, not necessarily noticed", and this widens what a human has to notice.
- **A recurring filesystem read inside the TCB.** The first one: `/sys/class/power_supply`, every 30 s, bounded to one fixed root, 16 entries and 16–32 bytes per attribute through `Read::take`, every failure an empty slot rather than a guess. When E2.6/E2.7 confine the core with Landlock this becomes a rule the core must grant itself — a real widening of that future sandbox, recorded here and in WS-E §6 rather than left to be rediscovered.
- **The zero-copy draw list gained its first stateful member.** `dmabuf::human_visible_frame` was a pure function returning solid-colour draws, which is what made "no arm omits the band" structurally true. `Draw::StatusStrip` carries a rectangle only — the texture is the executor's — so the function stays pure, but the frame now depends on an upload that can fail. A failed upload drops the strip for that frame and logs; it never drops the band and never refuses to present, because the strip asserts nothing about authenticity and the band asserts everything.
- **It is not a panel.** Three facts, no tray, no notifications, no workspace switcher, no click targets, and no interaction at all — a principal cannot receive physical input and the core is not taking a fifth gesture for a status bar.

### D-027 — The human's screenshot key reads the REALM VIEW, and it is a chord rather than a bare Print

**Status:** accepted (2026-08-08) — implements issue #216, extends [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) to a fifth core-owned chord, and answers a question #216's text raises and does not close; workstream [WS-E](14-workstream-session-mode.md) §6

**Decision:** four answers.

1. **The file contains the realm view, never human-visible output, and that is a security decision rather than a shortcut.** `crates/vitrin-core/src/consent/indicator.rs` is explicit that the session's trusted-indicator secret *"is never written to any descriptor or file"*, because the confined realm runs as the core's own uid: anything the core writes, the app can read. Human-visible output carries that secret twice — the always-present band and the ring around a genuine consent card — so a screenshot of it would destroy the trusted indicator on the first press of the key, permanently, for the rest of the session. Reading the realm view keeps "the indicator never reaches a file" **structural**: it is the same fork `capture.rs` already sits on, and there is no check anyone can forget.

   **Two softer designs were examined and both are worse, which is why this is a decision and not a preference.** *Cropping the band's rows out* does not close it: the ring is painted around a card in the middle of the output, so a crop protects the secret only while no prompt is up — precisely when a screenshot is least wanted. *Redacting by colour* — replacing every pixel equal to the secret — is actively dangerous and it is worth writing down because it looks thorough: it hands the app an **oracle**. An app paints its own surface with a field of candidate colours, the human takes a screenshot, and the app reads back which of *its own* pixels were recoloured; each screenshot tests as many candidates as the output has pixels, so the ~22-bit secret (`TrustedIndicator::generate` scales each channel into `[64, 255]`) falls in a handful of screenshots at 1080p. A structural exclusion has no oracle because there is nothing to compare against.

   The cost is real and is published rather than softened: **a vitrin screenshot cannot show a suspicious dialog.** "Send me a picture of that weird prompt" is the single most useful thing a screenshot does, and this one cannot do it; the answer is a phone camera, which is worse than every other desktop offers.

2. **It touches no grant, and that is a type rather than a rule.** There is no human principal in the identity model and inventing one to satisfy a picture would grow the identity layer for the wrong reason, so the chord's effect is not a *use* at all — no facet, no verb, no bucket, no refusal event, and `Verb::VALID_MASK` stays 575. What holds that up is not review: `capture::render_screenshot` takes a `HumanGesture` whose field is private to `crate::screenshot`, which is `!Copy`/`!Clone` and is minted only from a gesture the physical-origin chord matcher produced — so a principal holding every verb this core serves cannot construct the argument, and "an agent took a screenshot" is a compile error. `enforcement.rs`'s source scan counts the identifiers in **both** directions (zero occurrences of the encoder in the chokepoint; zero occurrences of the chokepoint's entry point in the screenshot module), and `render_frame`'s own single-caller clause stays literally true because the screenshot entry is a *sibling* of it rather than a caller. Same shape as #207's `SpawnRecord` and #213's `PendingPromotion`.

3. **A chord, not the bare `Print` issue #216 proposed — and this is the first core-owned gesture that pays a cost back.** [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) makes `crate::chord` the one matcher later chords consume, and `ModChord` refuses a modifier-less chord by construction, because a bare-key gesture belongs to `deadman::Chord` or `attention::AttentionChord` and a third spelling of one is how two mechanisms end up disagreeing about which keys the core owns. So the choice was a modifier or a parallel matcher in the stack the human's off-switch lives in, and the parallel matcher is what D-024 exists to forbid. The default is `ctrl+print`, and the side effect is the payback: **bare PrintScreen is still delivered**, so an app that binds it keeps it — the first time this workstream has taken a gesture without taking the key. `KEY_SYSRQ` (99 → `XK_Print`) joined `input::invariant_keysym` first, on that table's own terms; the startup collision check is now over five chords.

   **Stack position, deliberately:** inside `LockGate` — so a person standing at a locked machine cannot write the session behind it to a file, which is the single most important line of this decision; inside `ConsentGate` and `DeadManHook` — a convenience whose worst failure is a picture that did not happen must be suppressible by a security question and by the off-switch; inside `ClipboardHook`, its peer, because the clipboard moves an app's bytes across a realm boundary and this only reads; and **outside** `AttentionHook`, which consumes both Supers and would leave a modifier matcher's `super` bit permanently wrong.

4. **PNG, through code already in this tree, and the crate boundary is the point.** *"No image codec in the core, in any dependency class"* is stated twice in `crates/vitrin-core/Cargo.toml`. A raw dump is dependency-free and user-hostile on a daily driver; an external `png`/`image` crate brings a **decoder** into the TCB. So `vitrin-golden`'s hand-rolled artifact encoder was **promoted** to `crates/vitrin-png` — zero dependencies, ~130 lines of arithmetic, consumed by both the harness and the core, so there is one reviewed copy rather than two. The mitigating fact is that it only ever *encodes*: it consumes a buffer the core composited and returns bytes the core writes, so it never parses attacker input — the same argument `Cargo.toml` already makes for fontdue's unreachable `unsafe`. What it costs is that code written for test artifacts is now TCB code and must be reviewed as such, and that argument holds only for as long as nothing else feeds it bytes it did not itself produce.

**Costs, stated:**

- **The first file the core writes whose contents are a picture of the screen.** The recorder's log and `--capture-dump` came first, so this is not the first descriptor; it is the first one worth stealing. Every screenshot is readable by every app in every realm because everything runs as one uid ([D-010](#d-010--per-realm-isolation-dial)'s dial is still at its lowest setting, and E2.6/E2.7 own the fix). Mode `600` is about *other users* and does nothing about the confined app.
- **A wrong `--screenshot-dir` puts pictures of the screen somewhere unintended, and nothing below the core enforces the choice.** The directory is audited at startup (absolute, existing, a directory, not a symlink, not group- or world-writable) and then **held open** for the process's life, so the path is resolved exactly once — before any client exists — and no later rename or planted symlink can redirect a write. Until the core is confined, that audit is the whole of the enforcement.
- **The enforcement module's one-path claim has one more clause to keep true.** Its value comes from being short and grep-checkable, and every carve-out, even a correctly-argued one, makes it slightly less so. The compensating move is that the new clause is *itself* a grep, in both directions, rather than a sentence.
- **A fifth key is taken from every app,** and the collision check five chords must pass is one more thing an operator can trip over on an otherwise reasonable command line.
- **Issue #216's own "CI cannot press a key" criterion is now stale**, and this decision records that rather than repeating it: WS-E.1.6's `physical-input-injector` channel presses this run's configured chord on its own scancodes through the production intake, so `tests/integration/test_screenshot.py` covers detection as well as effect. What remains manual is a real finger on real hardware — `shim/docs/nested-multi-realm.md` step 11.

### D-028 — A bare-metal session interprets the keyboard inside the core, from a pre-compiled keymap file; and key pairing moves to the scancode

**Status:** accepted (2026-08-08) — corrects a claim [`protocol/vitrin-v0.xml`](../../protocol/vitrin-v0.xml) and [page 11](../protocol/11-vitrin_shim_seat.md) stated as fact, discharges the warning `crates/vitrin-core/src/input/mod.rs` has carried since P1.3.7, and gates **WS-E.3.2** (#218); issue #217, workstream [WS-E](14-workstream-session-mode.md) §4 Stage 3

**The problem, in one line.** Under `--nested` the core never interprets a keyboard: winit hands it a resolved `logical_key`, `input::host_keysym` turns that into an X keysym, and `resolve_key_seat` prefers it over everything else (issue #118). libinput hands a DRM backend evdev scancodes and nothing else, and `input::invariant_keysym` maps no letter, no digit and no punctuation — its own test asserts `invariant_keysym(30) == None` for `KEY_A`. **A session-mode core cannot type.** The four sub-questions below are the whole of the answer; a decision that answered only the first would be re-litigated by whoever hit the other three.

**Decision: four answers.**

1. **Interpretation happens in the core, the wire is untouched, and the keysym is normalised to one convention on the way out.** The core owns an `xkb_state`, feeds it `(keycode, direction)` from libinput, and emits `xkb_state_key_get_one_sym` on the existing `keysym` argument of `vitrin_shim_seat.key`. This satisfies the IDL's *normative* modifier-suppression rule exactly as written — keysyms arrive already modifier-resolved, and the shim binds each non-modifier keysym at a plain level — so **the C shim needs no edit at all** and `shim/src/seat.c`'s generated single-key-type keymap keeps working unchanged. No new message, no new interface version, no `since` bump.

   **The part nobody had named, and it is not an implementation detail.** libxkbcommon returns what the keymap says, and a Turkish keymap says `gbreve` — `0x000002bb`, a Latin-3 *legacy* keysym — for `ğ`. That number is not its codepoint (U+011F). The core reads keysyms as codepoints in exactly one place a human touches: `lock::gate::printable`, which types the lock-screen passphrase, and whose rule is the `keysymdef.h` convention (below `0x100` a keysym is its own codepoint, otherwise it must be `0x0100_0000 | codepoint`). Fed raw, `ö` `ç` `ü` type — they are Latin-1, so their keysym *is* their codepoint — and **`ğ` `ş` `ı` `İ` are silently dropped**, which is a maintainer locked out of his own session in a way that looks like a typo. It also forks the two backends: nested already emits Unicode keysyms above Latin-1, so without normalisation the same letter would be a different number depending on which backend produced it. So `input::keymap::unicode_keysym` re-encodes through `xkb_keysym_to_utf32` into that one convention, leaving keysyms that type no character (`Return`, whose UTF-32 is `0x0d`) exactly as the keymap gave them.

   *Rejected: a keymap relay plus a `keycode` event.* The IDL already names this as the growth path and it is architecturally purer — the TCB stays keymap-free. It is a new interface version, a new message carrying an fd, and, decisively, it moves modifier resolution to the shim, inverting the normative rule the shim's replay machinery is built around and making agent `text` actuation and human keys travel through two different mechanisms. Deferring it costs nothing: the wire is untouched, so the relay stays purely additive and this decision closes none of it.

   *Rejected: extending `invariant_keysym` with a hardcoded US-QWERTY table.* It is a lie for every other layout, and unlike today's table it fails by **mistyping** rather than by dropping — worse than the bug it fixes.

2. **The keymap is a pre-compiled keymap FILE the operator names, compiled with `Keymap::new_from_string`; layout-name resolution is never called. Refuse to start if it does not compile.** This is the owner's call, taken 2026-08-08 against three costed options, and the rejected one is the one every other compositor uses — so the reason has to survive here rather than in a PR.

   *Rejected: RMLVO name resolution (`new_from_names`, `XKB_DEFAULT_LAYOUT=tr`).* It is what every other compositor reads and it would need no config schema. It also searches **`~/.config/xkb` before `/usr/share/X11/xkb`** and honours the `XKB_*` environment. Realms run as the core's own uid and confinement is Phase 2 ([D-010](#d-010--per-realm-isolation-dial)'s dial is at its lowest setting), so **an app inside a realm can plant a keymap the trusted core then parses** — and this is not hypothetical: `~/.config/xkb/symbols/vncsuper`, mode 0644, already exists on the machine this workstream is dogfooded on. The same objection applies to the environment: a variable is not a capability, and reading five of them turns "which keymap does the TCB parse" into a question about process environment rather than about operator intent.

   *Rejected: a hand-built in-core scancode→keysym table (~400 rows plus level arithmetic).* Zero dependency delta — the only option that meets this repo's house standard outright, and it types the maintainer's name. It permanently forecloses dead keys, Compose (5 145 sequences in `en_US.UTF-8/Compose`; the file is 5 192 lines, and the difference is comments — the line count is what an earlier draft of this entry quoted) and `xkb_options`, and that same `vncsuper` file is proof the maintainer uses custom options. A table also has to be *right*, and the failure mode of a wrong row is the mistyping (1) rejects.

   **What makes the accepted option more than a preference is that it is structural.** `input::keymap::CoreKeymap` builds its context `NO_DEFAULT_INCLUDES | NO_ENVIRONMENT_NAMES`, so libxkbcommon holds no include path and reads no `XKB_*` variable; the core reads the operator's file *itself* and hands the bytes to `new_from_string`; and a unit test that runs in the **default** build — the configuration where this module is not even compiled — greps the crate for a call to the name constructor and for the environment prefix. A keymap text that tries to `include` anything fails to compile rather than reaching a directory, which is asserted rather than assumed. Fail-closed on a compile failure follows `deadman::Chord::parse`'s precedent and this repo's rule that a session must never come up with a silently-broken human input path; there is deliberately no fallback layout to fall back *to*.

3. **Key pairing moves from the keysym to the scancode, and the release carries the keysym its own press delivered.** `input/mod.rs` has said since P1.3.7 that keysym pairing is sound *only* because `invariant_keysym` is a fixed table with no modifier resolution — the same key yields the same sym on press and on release, by construction. With a keymap it does not: press `a` with Shift held, release it after Shift is up, and the release carries `a` where the press carried `A`. `pressed_keys` would find no pair, drop the release, and leave the app believing a key is held; a latched `Ctrl`/`Alt`/`Super` *"silently rewrites the meaning of every keystroke the app receives afterwards"*. So a key event carries a `KeySource` — the evdev scancode where a device is behind it, the keysym where none is — and the router pairs on that.

   **The second half is the one it is easy to stop one step short of, and it is a wire-visible change in what the app receives.** Pairing correctly inside the core is worth nothing if the wire then carries `a` for a release whose press carried `A`: the shim binds a dynamic keycode *per keysym*, so the app would be told to release a keycode it never held while the one it is holding stays down — the same latched key, one layer out, where the core can no longer see it. The pairing entry therefore remembers the delivered keysym and both the ordinary release path and the two drains send that one back. The drains already did; the ordinary path had no reason to until now. This is a **router invariant** on the path the dead-man switch depends on, and it has been got wrong twice in this codebase already (P1.7.2, and again for the lock gate), which is why it has its own tests rather than a comment.

4. **Resolve the sym *before* `update_key`.** libxkbcommon documents the order — *"you should prefer to get the keysyms before updating the key, such that the keysyms reported for the key event are not affected by the event itself"*. Backwards, a modifier applies to its own event and a released key resolves at the level its own release just left. It is a two-line ordering bug with a silent symptom, so `CoreKeymap::resolve` is the only place either call appears and the ordering has a test that fails under the reverse order.

5. **Key repeat: the core synthesizes it, for `Origin::Physical` presses only, and WS-E.3.2 implements it.** `shim/src/seat.c` disables client-side repeat with the reason that *"the core forwards each host key event individually (the host's own auto-repeat included)"*. Off a host there is no such thing: libinput synthesizes no repeats, so held keys would not repeat at all — no held backspace, no held arrow. The alternative was for the shim to re-enable `wlr_keyboard_set_repeat_info`, which is the architecturally correct Wayland answer and is refused because it is **seat-wide**: an agent's held key would repeat too, inventing keystrokes nobody sent, which is exactly what that comment forbids and what the `origin` tag exists to keep distinguishable. The core can filter on the tag because it has it; the shim's repeat machinery cannot, because `wl_keyboard`'s repeat is a property of the keyboard and not of an event. **The cost is a timer in the TCB**, and a weakening of the "no duplicates" property `seat.c` is defending — the core will now emit key events no device produced. The mitigations are that a repeat can only ever duplicate a press already in `pressed_keys` (so it cannot invent a key the app is not holding), that it is cancelled by the same release, drain, focus change and gate-consume that clears the pairing entry, and that the delay/rate pair comes from the same operator config the keymap path does. Nothing of it is built here.

**What this decision costs, stated in the units that matter rather than in crates.**

- **"Zero new crates" is true of `Cargo.lock` and misleading about the TCB, and the issue's own text said the misleading half.** `xkbcommon 0.8.0` is already in the lock file via smithay → winit → smithay-client-toolkit, so enabling it resolves no new package. But **the shipped binary does not link libxkbcommon today**, measured on this tree: `readelf -d target/release/vitrind` has no `NEEDED` entry matching `xkb` and `nm -D --undefined-only` finds **zero** `xkb_*` symbols — it is in the crate graph and dropped by `--as-needed`, because nothing calls it. Adopting it adds **`libxkbcommon.so.0`, 383 144 bytes** of C (1.13.2) to the runtime image of the entire TCB, reached through **87** `extern "C"` declarations and **91** lines mentioning `unsafe` in the binding crate, plus a **parser** running inside `vitrind` over a ~73 KB keymap file (`xkbcli compile-keymap --layout tr` emits 73 028 bytes). That is strictly larger than the constant table it replaces, and one class weaker than the argument `Cargo.toml` makes for fontdue: fontdue's bytes are a compile-time constant vendored in this repo, and these are a file an operator names. **At the commit that lands this decision that cost is not yet paid, and saying so is part of the measurement**: nothing calls `CoreKeymap` outside tests, so even `--features session-keymap` still links nothing. Wiring a throwaway caller into `main` (built, measured, reverted) is what produced the numbers: `NEEDED libxkbcommon.so.0`, six undefined `xkb_*` symbols, and 9 245 480 → 9 267 160 bytes of binary. #218 is what makes it real.
- **So it is feature-gated, and the gate is checkable rather than claimed.** `session-keymap` is off by default; nested gets its keysyms from winit and headless has no keyboard, so neither may pay. A default build must still show zero `xkb` in `readelf` and zero `xkb_*` in `nm`, and CI's existing `rust` job is what holds that. Unlike `gpu-tests`, `dead-man-injector`, `consent-injector` and `physical-input-injector`, this is **not** a test instrument: it is a deployment feature a shipped bare-metal `vitrind` will have ON, and the only reason it is off today is that no backend needs it yet.
- **A stated invariant becomes conditional.** "No keymap lives in the core" appeared in the IDL, in page 11, and in three module doc comments. It is now a `--nested`/headless property rather than a core property, and the IDL's `<description>` — which by this repo's own rule *wins* over prose — was the worst place for it to be stale. Corrected in the same commit.
- **The two backends resolve keys by different mechanisms**, so a nested integration test that types successfully proves less about DRM than it used to. There are now three paths (the synthetic table, winit's `logical_key`, the core's xkb) and the suite covers two of them end-to-end.
- **Key tests grow a layout dependency.** Anything asserting a keysym must pin its keymap, so three compiled keymaps are checked in under `crates/vitrin-core/tests/fixtures/` rather than resolved at run time — which is also the only shape that tests the production constructor, since the context cannot reach an XKB search path.
- **`Verb::VALID_MASK` stays 575.** This decision allocates nothing and touches no authority: which keysym a scancode produces is not a capability question.
- **Not claimable from CI, and this is not a formality.** That a real keyboard, on the maintainer's real layout, types correctly through a real shim into a real app cannot be shown by any test in this repository: runners have no seat and no input device, and headless is the only backend CI runs ([D-019](#d-019--the-agent-cursor-is-drawn-display-only-human-visible-output-only-d-017s-delivery-deferral-stands)(4)). The unit tests prove the resolution and the pairing; they prove nothing about hardware. That check is a numbered step in **WS-E.3.4**'s manual runbook, and #217 must not be closed citing a unit test as evidence for it.

### D-029 — The bare-metal backend drives exactly one output and refuses to start otherwise; and on bare metal the core composites the human's cursor, which the IDL said it never does

**Status:** accepted (2026-08-09) — corrects a second claim [`protocol/vitrin-v0.xml`](../../protocol/vitrin-v0.xml) and [page 6](../protocol/06-vitrin_view.md) stated as fact, and supersedes the *stated reasoning* (not the conclusion) of issue #218's decision 5; issue #218, workstream [WS-E](14-workstream-session-mode.md) §4 Stage 3

**Decision 1: zero or more than one connected connector is a startup refusal, and the reason is the `Presenter` contract rather than the amount of content.**

Issue #218 justified this refusal with "`Scene` holds at most one client surface and `MAX_REALMS = 1`, so a second output has nothing to display". **Both halves are now false.** `MAX_REALMS` is 16 (raised by WS-E.1.2), and every realm has held its own `Scene` since WS-E.1.3 (#209) — a session really can carry sixteen live realms with fifteen unbound, each with content that could in principle drive a second panel. A refusal resting on a stale premise is one the next reader deletes, so it is re-derived here.

The singularity is in the **contract**, in six named places, each of which has exactly one answer and would need two: `Presenter::view_size` is one size for the whole session and `start_realm_in` reads it **once** before the first realm forks, configuring every shim with it; `RealmScenes::bound` is a single `Option<RealmId>`; `physical_seat_target` follows that one binding, which is [D-018](#d-018--layout-is-a-capability-grant-governed-arrangement-core-enforced-ordering)(2)'s fifth ordering rule; `post_dispatch` draws the agent cursor in *output* coordinates resolved from `view.focused()`; `apply_output_resize` bumps every realm's `layout_generation` from one size; `refresh_status` captions the strip with one focused realm.

And the fail-open consequence is **worse** now than the stale argument claimed, not milder. With sixteen realms an operator has plausibly configured content for both panels, so coming up anyway would light whichever connector enumerated first, bind the output to one realm, and leave a physically connected, powered display dark — with no message, and no verb in the protocol that could ever move the output to it. The core would be telling a lie about itself. The zero-connector half is independent of all of that and needs no re-derivation: a session with no display can raise a consent card nobody can read and a lock nobody can answer, which is `HEADLESS_INTERACTIVE_REFUSAL`'s argument one step further out.

**The gap this leaves, stated rather than discovered.** It is a **startup** refusal. The backend enumerates once and installs no udev monitor, so a connector hot-plugged mid-session is neither lit nor complained about, and unplugging the only panel leaves the session compositing where nobody can see it. That is deliberate and named — answering it means answering what a session *does* when its display disappears, which belongs with **WS-E.3.3**'s session-pause question — and it is a numbered item in WS-E.3.4's runbook rather than an omission to be found later.

**Decision 2: on bare metal the core composites the human's cursor, and the IDL sentence saying it never does becomes nested-conditional.**

`vitrin-v0.xml` stated flatly: *"No human cursor is composited at all: in nested operation the host desktop draws it outside the realm view entirely."* True of the two backends that existed, false of the third: there is no host desktop on bare metal, so either the core draws the human's pointer or the human has none. Both halves of the sentence are now stated, conditioned on who owns the display, in the IDL and in its prose twin — the paired edit this repo's protocol rule requires.

**Nothing above it changes, and that is the point.** The sprite is applied at the same output stage as the agent cursor, the consent card and the trusted band ([`backend::human_visible_from_view`] and `dmabuf::human_visible_frame`'s draw list), so it is excluded from `vitrin_view.frame_ready` *structurally* rather than by a check, exactly as [D-019](#d-019--the-agent-cursor-is-drawn-display-only-human-visible-output-only-d-017s-delivery-deferral-stands) established for the agent's. The `observe_cursor` verb still resolves `unsupported`, so no capture contains any cursor today whichever backend is running, and [D-017](#d-017--per-principal-cursors-the-model-is-decided-and-on-the-wire-delivery-is-deferred-to-m2)'s delivery deferral is untouched: this is drawing, not delivery.

Three sub-decisions inside it, each with a cost:

1. **One geometry function, two sprites.** The human's crosshair is the agent's with a shorter arm and a white core, from the same `crate::cursor` function — so it inherits the clip that keeps a sprite out of the trusted band's rows. The cost is real: the human's pointer is invisible in the top `TRUST_BAND_HEIGHT` rows. Giving the human sprite its own clip policy was rejected because the band's whole value is having exactly one correct appearance, and a human's mouse is not worth a second exception to it.
2. **The human's slots come after the agent's in the GPU draw list**, so an overlapping human pointer is drawn over an agent's crosshair rather than under it. D-019's signal is "a crosshair is somewhere on this screen", which survives partial occlusion; a human's own pointer disappearing does not.
3. **No hardware cursor plane.** A KMS cursor plane is composited by the display controller, outside any draw list this core owns — a presentation path with no trusted band in it and no way to put one there, which is precisely what `backend/mod.rs`'s draw-list rule exists to prevent. The cost is a full composite per pointer move instead of a plane update, measured at bring-up.

**Decision 3: `--drm` requires `--consent=interactive` and refuses `auto-approve`.** The inverse of `--headless`'s refusal and the sharper of the two: this backend *is* the human's display and there is a human at a real keyboard, so every petition can be shown and answered. Auto-approving on the machine that is somebody's actual desktop is the fail-open posture refused everywhere else that configuration is read.

**Decision 4: a composite is not a presentation.** `Presenter::redraw` answers `Presentation::Scheduled` and queues a page flip; `session::emit_presented` is called from the vblank handler and from nowhere else, so a realm's `frame_done` follows the frame reaching the panel. Answering `Completed` at queue time is silently wrong rather than loudly wrong — a `frame_done`-paced shim gets a permit per dispatch round with no presentation between them and stops throttling. Correspondingly, **nothing in the presentation path is fatal**: a flip that returns `EBUSY`, a modeset race, or a frame composed while the VT is switched away leaves the frame owed and retries at the next vblank, because the runtime stops the loop for exactly one condition and a display hiccup must not be an outage.

**What this decision costs.**

- **The largest single TCB dependency increase in the project's history**: 14 crates and four system libraries (`libgbm`, `libinput`, `libseat`, `libudev` — *not* libdrm, which nothing in the graph links), five of them `-sys` crates doing unsafe FFI. Measured and itemised in `crates/vitrin-core/Cargo.toml`'s `drm-backend` block and budgeted in `deny.toml` (#201, a hard prerequisite for exactly this reason).
- **The core's build starts invoking a C toolchain, and the probe fails soft.** `smithay/build.rs` compiles two gbm feature-probe files and downgrades to an older buffer-allocation path on failure with a `cargo:warning` and a green build. CI asserts the two cfgs are set rather than that the build passed.
- **A same-uid app can now plausibly read the real keyboard.** On a real seat logind ACLs `/dev/input/event*` to the logged-in user, and the realm's app runs as the core's uid with no namespace, no seccomp filter and no Landlock ruleset — so it can open the devices directly and bypass this core entirely, consent grab included. This backend does not *create* that hole; nesting hid it, because the host compositor was the only reader. It is logged at startup and belongs in `docs/book/src/limits.md` (WS-E.3.4).
- **The capture-path compose gets expensive, and the published figure was per-realm.** `post_dispatch` refreshes every live realm's view cache on every dirty round; at 2560x1600 that is 16 MB per realm, up to ~262 MB per dirty round at `MAX_REALMS`. Measure at bring-up. If it hurts, the fix is a recorded decision — *not* gating the refresh on grant state, which was already considered and rejected because it would make a capture's freshness depend on whether a grant happened to exist.
- **Evidence gets structurally weaker, and the PR must say so.** No green check in this repository will ever show that this backend sets a mode, presents a frame or delivers a key: runners have no DRM device and no seat. What CI holds is a compile check and five device-free unit tests (the one-output refusal, the pointer accumulator, the flip-coalescing gate, and two source assertions holding `redraw` to `Scheduled` and the capture path off the scanout buffer). The mock-free evidence is **WS-E.3.4**'s runbook, executed on the target machine and recorded — and `vitrin-mock-shim` has nothing to say about a display controller.
- **This must not merge while WS-E.3.3 is open.** `SessionEvent::PauseSession` is handled here only to the extent that its absence would be a defect (the dead-man hold is forgotten and every held key is released, or a VT switch latches keys in the confined app and leaves a hold armed with no gesture behind it). Whether a switch away should also raise the lock screen is not decided here. **Discharged by [D-030](#d-030--the-trusted-band-asserts-only-about-the-screen-this-core-is-driving-and-the-session-colour-is-never-re-minted-a-paused-seat-raises-no-prompt-it-could-record-as-shown)** (2026-08-09), which answers that question explicitly — it does not — and adds the three gates the minimal handler left out.

### D-030 — The trusted band asserts only about the screen this core is driving, and the session colour is never re-minted; a paused seat raises no prompt it could record as shown

**Status:** accepted (2026-08-09) — closes the deferral [`docs/book/src/limits.md`](../book/src/limits.md) published as *"that trade is not decided, and it will be decided by whoever lands the DRM backend rather than pre-empted here"*, discharges the `warn!` `crates/vitrin-core/src/backend/drm.rs` has carried since #218 and the last cost bullet of [D-029](#d-029--the-bare-metal-backend-drives-exactly-one-output-and-refuses-to-start-otherwise-and-on-bare-metal-the-core-composites-the-humans-cursor-which-the-idl-said-it-never-does); amends [D-025](#d-025--a-locked-screen-does-not-suspend-agent-observation-the-gap-is-published-not-papered-over) for the seat-pause case, and **corrects three of the seven decisions issue #219 drafted**; issue #219, workstream [WS-E](14-workstream-session-mode.md) §4 Stage 3

**Issue #219 drafted seven decisions. Two are adopted as drafted (its 3 and 7), four are adopted with a correction that is stated as one (its 1, 2, 4 and 6), and one is refused outright (its 5) — plus two this entry adds: the lock question [D-029](#d-029--the-bare-metal-backend-drives-exactly-one-output-and-refuses-to-start-otherwise-and-on-bare-metal-the-core-composites-the-humans-cursor-which-the-idl-said-it-never-does) deferred here by name and never asked, and the held-button drain neither issue noticed.** A decision log that silently agrees with its issue is worth nothing, so each divergence is stated as one, with the reason, rather than smoothed over. Numbering below is this entry's own; the mapping to #219's is named in each heading.

**Decision 1: the core does not prevent VT switching, and the band is scoped to *this screen and this process* rather than to "DRM master".**

> **Superseded in its operative half by [D-031](#d-031--the-core-implements-ctrl-alt-fn-itself-because-refusing-to-is-what-trapped-the-human-d-030s-reasoning-stands-and-its-effect-was-its-own-opposite) (2026-08-09), after first light on real hardware. The paragraph below is left exactly as written, because the reasoning it gives is sound and the code it describes did the opposite of what it intended; rewriting it would hide the inversion this project needs on the record.** The band's scoping sentence — the rest of this decision — is untouched and still stands.

It cannot prevent it — the kernel owns `VT_SETMODE` — and it will not try: a display server that traps the human on its own VT is one they cannot leave when it wedges, which contradicts the posture the dead-man switch is built on (the human always has an off-switch). `LibSeatSession::change_vt` is held by `DrmState` for the seat's *lifetime* and is never called; the field's `#[allow(dead_code)]` reason says so, where it previously named this issue as the owner of a verb that turns out not to exist.

**The scoping sentence is not #219's.** The issue drafted *"these pixels were drawn by the `vitrind` that holds DRM master on this device right now"*. That names a fact **no human can observe** — there is no indicator for DRM master, and a runbook step cannot ask an operator to verify one — so as a published claim it is prose, not a check. What is checkable at the panel is the colour's continuity, so the two are published as one sentence: **everything above the line on *this* screen was drawn by the `vitrind` you started; the same colour means the same core, and a different colour means the core you left is not the core you came back to.** "This screen" rather than "this device", inheriting D-029's one-connected-display refusal. The runbook step is *photograph the band before switching, compare side by side on return* — not *remember the colour* — because `limits.md` already publishes that nobody has evidence a human notices a wrong band, and a memory test of an arbitrary RGB is exactly the check that page refuses to claim.

**Decision 2: a VT switch does not raise the lock screen, and `LockCause` gains no third variant. #219 never asked this; D-029 deferred it here by name.**

> **Superseded in its operative half by [D-034](#d-034--losing-the-seat-is-a-configurable-lock-policy-with-d-0302s-answer-as-the-default-and-lockcause-gains-the-third-variant-that-entry-declined) (2026-08-11, issue #246). The paragraphs below are left exactly as written, because unlike D-030(1) the reasoning here is not only sound but is still the reasoning behind the shipped *default* — `--lock-on-seat-change never`, which is this decision verbatim and is what a session that never names the flag gets.** Two sentences of it are nonetheless now false and are flagged rather than edited: **`LockCause` *does* gain a third variant** (`SeatChange`), argued in D-034(2) rather than skipped, exactly as the paragraph below asked; and the closing *"what is deliberately not built here is the policy that would make this a choice rather than a default"* is built — the three answers that paragraph names are the three the flag takes. The owner's answer did not move; it stopped being the only one available.

The tempting answer is to raise the lock on `PauseSession` and reuse everything WS-E.2.2 built. It is refused on four grounds. It would **claim a protection this core does not have**: the lock covers `vitrind`'s own output, the other VT is untouched, and [D-025](#d-025--a-locked-screen-does-not-suspend-agent-observation-the-gap-is-published-not-papered-over) keeps every grant live regardless — the half-believed claim `limits.md` exists to refuse. It would **charge the human a passphrase for using the escape hatch decision 1 deliberately leaves open**, and an escape hatch that is expensive to come back from erodes the reason it is open. `LockCause`'s own docs say both its causes are *human-attributable* — "a gesture the human made, or a gesture they conspicuously did not make" — and a seat event is neither. **And the idle clock does not run while the seat is gone — an owner decision by Taha on 2026-08-09, taken against the behaviour this code had inherited.** An earlier draft of this entry argued the inherited behaviour was already correct: `LockScreen::tick` advances `last_activity` only on physical input, physical input is suspended for the whole pause, so with `--lock-idle` a long enough absence locks the session whether the human walked away or switched VT. That reasoning is wrong in a way worth recording, because it is the shape this log exists to catch — it describes an accident and calls it a policy. Nobody chose it. Its actual behaviour is that a session locks **during** an absence, at an instant no human can observe, so the human returns to a passphrase prompt they never asked for; and a session *without* `--lock-idle` gets no lock from a switch ever. Two unchosen behaviours, selected by a flag that is about something else.

Asked directly, the owner chose: **switching away does not lock the session.** `LockScreen::set_seat_absent` freezes the idle clock for the duration and restarts the countdown on return, because returning to your own screen is the one thing an idle timer is asking about. The accepted cost is stated rather than hidden: **a session switched away from for eight hours is unlocked when it is switched back to**, and it is asserted in `a_seat_taken_away_stops_the_idle_clock_and_returning_restarts_it` so it cannot drift silently. The suppression is of the *raise* only — a lock already up survives a switch untouched, held by its own test, because a VT switch must never be a way past a lock screen.

**What is deliberately not built here is the policy that would make this a choice rather than a default.** Lock-on-switch, lock-on-idle-only, and never-lock are three reasonable answers for three reasonable operators, and this entry hard-codes the third. A configurable policy is filed as its own issue rather than guessed at inside a decision about what the trusted band asserts.

**Decision 3: the session colour is minted once per process and never rotated — #219's decisions 2 *and* 3, adopted as one, with the corollary corrected.**

(They are one decision: "do not re-mint on resume" and "a resumed session is the same trust session, a new process is a new colour" are the same fact stated forward and backward, and splitting them would let a later reader adopt half.)

"Refresh the secret when the session is interrupted" sounds like hygiene and is the exact opposite: the indicator defends against a replica by being *stable*, and a colour that changed after every switch would leave the human unable to tell a legitimate change from a forgery. The threat models for rotating were examined and none survives — another VT's compositor cannot read this core's GBM buffers, the confined app's channel to the colour is the output-stage fork it structurally cannot observe, and the one real exposure (a camera on the panel, newly plausible when the panel is in the room) is neither caused by the switch nor cured by rotating afterwards, because the photographer photographs the new colour too.

**The corollary as #219 wrote it — "the mitigation is ending the session" — is misleading and is not published in that form.** There is no core-owned gesture that ends a `vitrind` session on any backend: `apply_dead_man` revokes every grant, denies every petition, clears the clipboard and seals the table, and **returns**. So the one instrument this project teaches a human to reach for does nothing at all for a compromised trust colour, because the process and its colour keep running. On bare metal, ending the session means leaving `vitrind`'s VT and signalling the process — i.e. the remedy is reachable only through the escape hatch decision 1 declines to close, from a screen the band asserts nothing about. That is what `limits.md` says, in those words.

**Decision 4: no consent prompt is raised while the screen is not ours — keyed on the seat pause, which is producible, and NOT on a dark output, which is not. This is the sharpest correction to #219.**

The judgement #219 reached is right: `ConsentGrab::raise` writes `Event::ConsentTransition { state: Shown }`, which is the flight recorder's record that *a human was asked*, plus `mark_prompt_shown`, which makes the enforcement chokepoint refuse that principal `consent_held`. Raising against a screen nobody can see puts a falsehood in the one artifact that has to reconstruct the session afterwards.

**The condition #219 named cannot occur.** `dpms`, `power_save` and display blanking appear nowhere in `crates/vitrin-core` — every DPMS hit in the repository is a vendored shim subproject, unreachable from `vitrind`. smithay 0.7 exposes exactly one DPMS-touching API (`DrmSurface::clear`) and this core never calls it. **The core can neither enter nor observe a dark output.**

> **SUPERSEDED 2026-08-10 by [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only), which is the change this paragraph named in advance.** The sentence above was true when written and is now false in both halves: the core calls `DrmSurface::clear` on an idle timer, so it both **enters** and **observes** a dark output. The paragraph is left standing rather than rewritten because the reasoning it gives is the reason D-033 owed the gate at all — *"if DPMS is ever implemented, extending this gate is that change's job and its acceptance criterion"* — and D-033 discharges it with a third `PromptVisibility` variant for the dark case, answered from the same field the composite and the flip gating read, so this core keeps one notion of *"can the human see this"* rather than two that can disagree. **The wider hazard the next paragraph names — a panel darkened by `/sys/class/backlight` or by a monitor's own power button — is untouched and stays open**; D-033 closes only the darkness this core causes itself.

Note the limit of that claim, because an earlier draft of this entry overstated it. It says only that *this core* neither blanks nor senses a blank. It does **not** say the panel cannot go dark: `/sys/class/backlight` is a separate interface that DRM master does not gate, a monitor's own power button is outside the machine entirely, and either can leave the human staring at nothing while `vitrind` believes it is presenting. **That hazard is real, is exactly what #219's decision 4 was reaching for, and is not closed here.** What is closed is the far more common case of the seat being taken away. The residual gap is published rather than left as an unwritten assumption. A guard written for that condition would be unreachable code that reads as a live protection, which this project has already shipped once: the `preempted` hook that no backend stacked from P1.4.4 until issue #212's review, while the book described it as live. So **the dark-output gate is deliberately not written, and its absence is named here rather than implied.** If DPMS is ever implemented, extending this gate is that change's job and its acceptance criterion — and doing it the other way round, adding a feature so that a guard becomes reachable, is the tail wagging the dog.

**What *is* written, because the falsehood was live on this branch.** `post_dispatch` calls `service_consent` unconditionally and the calloop loop keeps dispatching through a pause, so an agent petitioning while the human was on another VT got `consent_transition{shown}`, `prompt_shown`, and a `vitrin_consent.state(shown)` on the wire — for a card `should_queue_flip` would never flip. Authority failed closed the whole time (the sweep times the petition out); the **record** was the lie. `service_consent_round` therefore takes a `PromptVisibility`, and **only step 4 is gated**: `retire_stale` and the decision drain must keep running through a pause, or a dead petition's card stays composited and the queue never advances. The bare-metal backend answers it off `DrmOutput::active` — the *same* field `should_queue_flip` reads, so this core has one notion of "is this screen ours" rather than two that can disagree. It is a parameter rather than a field on `ConsentGrab` for the reason `set_view`'s docs give: a fact fed in from somewhere else with no co-feed is drift-prone shadow state. **Nested passes `Reachable` unconditionally and that is scoped, not skipped**: the nearest analogue is winit's `Occluded`, which is not the same fact, is not delivered on every platform, and would make a host compositor's bookkeeping decide whether this core journals a prompt as shown.

**Decision 5: on resume the consent guard restarts and the armed press is dropped; the petition's deadline is never refreshed. #219's decision 5 is refused on both halves.**

#219 said *"input that arrived while dark does not decide anything — discard the decision and re-raise with a fresh deadline"*. **The condition has no producer:** `handle_session_event` calls `libinput.suspend()` in the same handler that clears `active`, on a single-threaded loop with nothing dispatching in between, and `libinput_resume` replays nothing — so no physical event is ever judged by the grab during a pause. **And the remedy contradicts a contract this codebase reasoned out three weeks ago:** `restart_guard`'s docs say *"only the guard restarts: the petition's own `deadline` is deliberately untouched, since that bounds how long the human has to decide"*. Refreshing it would silently override `PetitionConfig::consent_timeout`, change what the petitioner was told, let a principal extend its own petition by inducing VT churn, and break the invariant `a_grab_never_outlives_its_petitions_deadline` pins.

**The reachable hazard is a different one, and it is a live clickjack this branch shipped.** `GUARD_INTERVAL` runs from `ArmedPrompt::raised_at`, and until now `restart_guard` had exactly **one** production caller — `service_lock_round`'s `Unlocked` arm. A prompt raised before a switch away therefore spends its guard on somebody else's VT, and the first click on return commits it. Worse, `ConsentGrab::armed` survives the pause and `commit` re-checks only the last *physical* pointer position, which a pause does not reset — so a press armed on Allow, held across the switch, released after resume with the pointer unmoved, **commits**. `restart_guard` closes both in one call (it clears `armed` by design) and leaves the deadline alone. That is the second call site, on `ActivateSession`.

**Decision 6: captures keep being *served* across a pause, but the frame clock stops — so the sentence published is not the one #219 drafted, and #219's own decision 7 is what falsifies it.**

The premise is true: `DrmView::view_rgba` CPU-composes the retained scene and never reads `output.active`, `realm_is_live` asks the scene and the shim session, and the serve path reads `Runtime::view_cache` directly. So an agent's capture **requests keep succeeding**. The conclusion #219 drew — "keeps receiving frames while the human is on another VT" — is false. `emit_presented` has three production callers — `backend/winit.rs`, `session.rs`'s `post_dispatch` (gated on `Presentation::Completed`) and `backend/drm.rs`'s `on_vblank` — and since `DrmView::redraw` returns `Scheduled` unconditionally, the `post_dispatch` site never fires on bare metal and `on_vblank` is the only bare-metal caller; while paused no flip is queued and the flip in flight at pause time died with DRM master, so **no vblank occurs for the whole pause**, no realm's owed `frame_done` is discharged, and every `frame_done`-paced client stops painting. The agent is served the pre-pause frame, indefinitely, with no staleness signal and no refusal — which `emit_presented`'s own doc comment already calls *"worse than a stall"* and which `vitrin_grant.refusal.no_surface` forbids in as many words ("never a stale frame").

**Why [D-025](#d-025--a-locked-screen-does-not-suspend-agent-observation-the-gap-is-published-not-papered-over)'s sentence does not transplant.** "An agent keeps capturing the realm across a lock, frame for frame" is true *because a lock does not stop the frame clock*: the cover composites, the flip lands, the vblank fires, apps keep painting. A pause stops the clock. Copying D-025's sentence into the one state that falsifies it would have been a false published limit — the exact failure this workstream is documenting against. **And the part #219 did not state at all is the worst of it:** agent *actuation* is not gated on session activity, so across a VT switch an agent can still act and cannot see the consequences. That was adopted by accident rather than chosen; it is chosen now, published as what it is, and the honest fix (a software frame cadence for paused realms) is named and not scheduled.

**Decision 7: while paused, `redraw` answers `Scheduled` and never flips — #219's decision 7, adopted, and already true as #218 built it.** The owed callbacks stay owed and discharge on the first page flip after resume; `should_queue_flip`'s docs are explicit that it answers "not now", never "not ever". Nothing here needed changing, and it is recorded in the same entry as decision 6 rather than on a separate page because the two cannot both be read in isolation: the honest reading of 7 is *every realm's frame clock stops for the duration of the pause*, and that sentence is why 6-as-drafted could not be published.

**Decision 8: the pause drains held pointer BUTTONS as well as keys — which neither #219 nor #218's minimal handler did.** `InputRouter::release_physical_buttons` was added by issue #212 for exactly the mid-drag case — a held button *"wedges the app's implicit pointer grab"* — and had one production caller. The nested precedent deliberately drains keys only, because winit keeps sending pointer events and a synthetic release would end a drag the human is still making; on a seat pause the devices are closed, no motion or release can arrive for the duration, and the human's next press is a new gesture. So the asymmetry is principled rather than inherited, and it is stated because a reader of `handle_focus` would otherwise conclude the two paths should match.

**What this supersedes, sentence by sentence.** `docs/book/src/limits.md`'s *"That trade is not decided, and it will be decided by whoever lands the DRM backend"* — decided here. `crates/vitrin-core/src/backend/drm.rs`'s `warn!` that *"whether a VT switch should also raise the lock screen is WS-E.3.3's decision"* — answered by decision 2 and deleted. The `seat` field's dead-code reason naming *"the VT-switch verb this handle exists for"* — there is no such verb; the handle is held for the seat's lifetime. `crate::consent::indicator`'s two-backend reading of *"the display vitrind owns"* — now three cases, the third of which can be taken away. `crate::consent::grab`'s *"the nested backend carries it in its router"* and its one-directional statement of the headless refusal — two backends carry the gate, and the two configuration refusals are a pair pointing opposite ways. `backend/mod.rs`'s lock-cover comment, which argued the input half correctly and was silent on the record half.

**What still stands, unchanged.** [D-025](#d-025--a-locked-screen-does-not-suspend-agent-observation-the-gap-is-published-not-papered-over) in full for a *lock*: a locked session still owns its panel, so a card raised behind the cover really is on the human's screen the moment they unlock, its guard is restarted for them, and they can answer it. That is why a locked session is still allowed to raise a prompt and a paused one is not, and the difference is one sentence rather than an inconsistency. The clipboard slot's two-minute expiry runs on the loop's sweep timer, which a pause does not stop, so a VT switch neither preserves the slot past its deadline nor clears it early — confirmed benign, and stated so nobody "fixes" it later.

**DEFERRED, explicitly:** **a software frame cadence for paused realms** — unscheduled. It is what would make decision 6's observation half true rather than merely served, and it is a real design question (what clock, at what rate, and whether an app should burn a GPU for nobody). *(Still deferred as of 2026-08-10, and [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only) makes it hurt more: an idle blank stops the frame clock the same way a pause does, so this now fires on a timer rather than only when a human leaves.)* **A dark-output gate** — to whichever change implements DPMS, as that change's own acceptance criterion; there is nothing to gate today. *(**DISCHARGED 2026-08-10 by D-033**, which implements DPMS and takes the gate as its own criterion, exactly as this line required.)* **Whether nested should gate on host-window visibility** — to whoever can name a host fact that means "the human cannot see this", which `Occluded` is not. **And what a session does when its only display is *unplugged*** — [D-029](#d-029--the-bare-metal-backend-drives-exactly-one-output-and-refuses-to-start-otherwise-and-on-bare-metal-the-core-composites-the-humans-cursor-which-the-idl-said-it-never-does)'s hot-plug gap pointed here, and it is **not** absorbed: a paused session still has its panel and is told when it gets it back, while an unplugged one has no event promising a return, so "hold everything and resume" is not an available answer. It stays unowned rather than being quietly folded into this entry, and `pick_sole_connected`'s docs now say so.

**What this decision costs.**

- **The published claim about the trusted band gets weaker, and it should.** This is the first place the project writes down that the trusted path has an edge the core does not own. "The band is unforgeable" was only ever true inside one VT, and now says so — a second qualifier on the same claim `limits.md` already qualifies with "not necessarily noticed".
- **The secret has no rotation path, and that is now load-bearing rather than incidental.** A colour observed once is observed for the session, the mitigation is killing the process, and the dead-man chord — the instrument a human is taught to reach for — does not help. Naming the alternative does not remove the weakness.
- **A human who switches away long enough gets `timed_out` refusals instead of a prompt on return.** An operator will experience decision 4 as obstruction. It is the fail-closed answer and the flight recorder makes the reason legible (`petition_resolved{timed_out}` with no preceding `consent_transition{shown}`), but it is a real behaviour change and it is bought with a real annoyance.
- **A pause silently *widens* agent authority.** `preempted` is judged against recent physical input; with libinput suspended, presence decays, so the instant the human switches away is the instant agent actuation stops being refused `preempted`. Correct — the human really is absent — and it means agent authority is at its widest exactly when human observation is at its narrowest. Published rather than left to be found.
- **The human's one core-owned emergency stop follows the seat.** The dead-man chord is a physical gesture and libinput is suspended, so from another VT the only stop is a shell and a signal. `limits.md`'s "still works while locked" stays literally true (locked is not paused) and is now scoped.
- **Two acceptance criteria of #219 were rewritten rather than met, and one test was deliberately not written.** Criterion (c), *"`TrustedIndicator` compares equal across pause→resume"*, is **vacuous**: the value is `Copy`, nothing on either arm touches it, so the assertion passes against an empty handler and would go on passing against a handler that did the wrong thing everywhere else. It is replaced by the structural fact that actually holds the property — `TrustedIndicator::generate()` has exactly one call site in the crate and it is in `run_session` — which goes red if a re-mint is added to the activate arm, and which nothing else in the workspace would catch. Criterion (e), *"a decision timestamped inside a dark window is discarded"*, tests a state nothing can produce and is **not written**; what replaced it is decision 5's reachable hazard, driven through `resume_physical_seat`.
- **Three of the new gates are held by source assertions rather than by execution.** `DrmState` cannot be constructed without a real `DrmDevice`, `LibSeatSession`, `GbmDevice` and `GlesRenderer`, so `handle_session_event` is unreachable from any test in this workspace. The *behaviour* was therefore extracted into `session::suspend_physical_seat` / `session::resume_physical_seat`, which have real behavioural tests that run in the default build with no feature flag; what is left in `backend/drm.rs` is which arm calls which, pinned by a source-inspecting test. Every mutation of it compiles, which is the only reason such a test is worth anything. The real check remains **WS-E.3.4**'s runbook: switch to VT2, run something, switch back, photograph-and-compare the band, and observe that a petition raised while away is still pending or cleanly timed out. That observation, dated, is the evidence — not these unit tests.

**Status:** accepted (2026-08-09) — amends the escape-route requirement in issue **#220** (WS-E.3.4) and the standing safety rule in workstream [WS-E](14-workstream-session-mode.md) §7; implemented by [`docs/drm-bringup.md`](../drm-bringup.md)

**What was required.** Issue #220's decision 3 requires that the DRM bring-up runbook's step 0 be *"an isolated VT **and** an SSH session from a second machine"*, and calls it **non-negotiable**, on the grounds that a DRM backend started from inside the live session takes DRM master away from the running compositor and the worse failures leave the panel in an unrecoverable mode with no console to fix it from. [WS-E §7](14-workstream-session-mode.md) states the same requirement as the workstream's standing rule.

**What was decided instead.** The maintainer declined the SSH half, on 2026-08-09, in these words: *"Nah we have arch installer disk, we can do chroot if something goes really wrong. I dont want to run ssh server, no need to open another security layer."* The trade being made is explicit and is his to make: a permanently listening remote-access service on the machine that is about to become his daily driver, against a slower recovery path in a failure mode that may never occur.

**The escape route this machine actually has**, verified read-only on 2026-08-09 and written into the runbook in this order:

1. **VT switching, first line.** `Ctrl+Alt+F1` returns to Hyprland, which holds `seat0` on `tty1`. `logind` is active and grants the display to whichever VT is active, so this is ordinary and reversible rather than a rescue. It survives on purpose: this configuration's keybind wrapper skips `F1`–`F12` precisely so `Ctrl+Alt+F<n>` stays reachable. `tty2`–`tty6` are free and `NAutoVTs` is at its default of 6, so a login prompt is one chord away.
2. **The maintainer's remote control is NOT an escape route, and the runbook says so rather than omitting it.** `wayvnc` runs as a client of Hyprland over `wlr-screencopy`, bound to `127.0.0.1:5900` and reached over Tailscale — it runs *through the desktop*, so it dies with the display and can neither show `vitrind`'s output nor give a shell. Naming it as a fallback would be worse than leaving it out, because it would be reached for in exactly the situation where it is guaranteed to be gone.
3. **Arch installer USB and `arch-chroot`, last line.** Real, and slower by orders of magnitude: physical presence, a power cycle, mount, chroot, edit, reboot. Minutes to tens of minutes, against seconds for a console command.

**The cost, stated rather than argued.** **A wedged DRM master with no live console is now a reboot, where #220's design assumed it was a command.** SSH's specific value was a *second, independent* path to a shell that does not depend on the display, the seat, or the local keyboard — and none of the three above has that property. VT switching depends on the local keyboard not being wedged; the USB path depends on a power cycle having already happened. There is no substitute for the property that was given up, only a slower path around it.

Two secondary findings, both recorded because they change what recovery is available:

- **`Alt+SysRq` is not a safety net here as configured.** `/proc/sys/kernel/sysrq` is `16` — sync only. `REISUB` does not work from the keyboard, and neither does `r` (unraw), the one that recovers a keyboard a wedged compositor left grabbed. The runbook offers `sysctl kernel.sysrq=1` as an explicit, temporary, security-traded pre-step (anyone at the physical keyboard can then reboot the machine unauthenticated) rather than assuming it.

  > **AMENDED 2026-08-10 by [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only), in both halves.** The last sentence is **no longer true**: the owner settled the mask that day and **it is not touched**, so `docs/drm-bringup.md` §0.4 no longer offers `sysctl kernel.sysrq=1` and the recommendation is deleted rather than left standing. What replaces it is a **`sudo`-only** path through `/proc/sysrq-trigger`, which the kernel allows regardless of the bitmask, in [`docs/book/src/recovery.md`](../book/src/recovery.md#route-3--sysrq-through-procsysrq-trigger-sudo-only). And *"with no `sysctl.d` override"* was wrong when written: `16` is set explicitly by `/usr/lib/sysctl.d/50-default.conf:19` [verified 2026-08-10], not inherited from a kernel default — which matters, because it means a distribution package upgrade can move it and nothing here would notice.
- **`seatd` is installed but not running and the operator is not in a `seat` group**, so `libseat` must use its logind backend — which grants devices only to a session logind considers *active on its own VT*. That makes "log in on the VT" load-bearing rather than optional, and makes `LIBSEAT_BACKEND=seatd` a configuration mistake rather than a bring-up finding.

**What this does not change.** The hazard itself, and the rule that follows from it: **never take the human's live display out from under them.** No Stage-3 task runs from inside the live session, with or without SSH. WS-E §7 is amended to describe the substitute route rather than to soften the rule.

**Why an entry at all.** #220 called its requirement non-negotiable, and it was negotiated. Silently writing the runbook as though SSH existed, or writing it against SSH that is not there, would each have produced a document that fails at the moment it is needed. The decision is recorded so that the next person reading #220 finds the amendment beside the requirement instead of concluding the runbook missed it.

### D-031 — The core implements `Ctrl-Alt-F<n>` itself, because refusing to is what trapped the human; D-030's reasoning stands and its effect was its own opposite

> **NUMBERING: this is the SECOND of two entries numbered D-031**, and it is the one every `D-031` cross-reference in this repository resolves to — in other plan documents and in `crates/vitrin-core/src/vt.rs`, `recorder.rs` and `backend/drm.rs`. The first is directly above. Neither is renumbered, because this id is cited from landed code; a renumbering would go to **D-033**.

**Status:** accepted (2026-08-09) — **supersedes the operative half of [D-030(1)](#d-030--the-trusted-band-asserts-only-about-the-screen-this-core-is-driving-and-the-session-colour-is-never-re-minted-a-paused-seat-raises-no-prompt-it-could-record-as-shown)**, taken earlier the same day and superseded by the evening's first run of that backend on real hardware; workstream [WS-E](14-workstream-session-mode.md) §4 Stage 3

**This entry exists because of an observation, not an argument.** On 2026-08-09 the bare-metal backend (#218, merged as `cf653eb`) ran on hardware for the first time — the repo owner's laptop, tty3, a 2560x1600 panel on `/dev/dri/card1`. Much of it worked: the panel lit, the mode was set, the trusted band drew, 88 physical input events routed through libinput, a compiled Turkish keymap let him type, `Ctrl-Alt-Delete` raised the lock screen, the passphrase unlocked it, and `SIGTERM` shut the session down cleanly. Three defects came out of the same run and this entry is about the one that mattered.

**Decision 1: on bare metal this core binds `Ctrl-Alt-F1`…`F12`, consumes them, and calls `Session::change_vt`. D-030(1) refused exactly this, for a reason that was correct, and the refusal produced the outcome the reason forbids.**

D-030(1) is quoted in full above and is worth reading again before this one. Its premise — *"a display server that traps the human on its own VT is one they cannot leave when it wedges"* — is not repudiated here. It is adopted, and it is the reason for the reversal. What the entry got wrong is a fact about the kernel, and the whole decision turned on it: **once a process holds DRM master and the VT is in graphics mode, the kernel stops handling `Ctrl-Alt-F<n>`.** The chord is not a thing a compositor declines to interfere with; it is a thing a compositor either implements or abolishes. D-030(1) reasoned as though not calling `change_vt` left the escape hatch alone. Not calling it *is* what welds the hatch shut.

That was not deduced afterwards. `Ctrl-Alt-F1` and `Ctrl-Alt-F2` did nothing. The owner could not leave his own session and was freed only by killing it from another machine-local shell. The preserved flight recorder for the run contains 96 entries — `session_locked`, `unlock_attempted`, `session_unlocked` — and **not one entry of any kind about the chords he pressed**, because nothing in this core could consume an F-key: those presses were either delivered to the confined `solid-client` (which was told the human was trying to leave) or swallowed by the lock cover, and in neither case did anything act on them or write them down. The one artifact built to reconstruct a session afterwards was silent on the single most consequential thing that happened in it.

So the sentence this project publishes inverts:

**A display server that does not implement the VT chord is a display server that traps the human on its own VT. Implementing it is how the off-switch stays open, not how it closes.**

**What is *not* reversed, and must not be read as reversed.** The core still does not *inhibit* a switch — it has no `VT_SETMODE` inhibition, no `VT_PROCESS` refusal — and it never initiates one on its own account or switches *back*. `change_vt` has exactly one caller (`DrmState::drain_vt_requests`), reached only through a `crate::vt::VtRequest` whose constructor is private and whose only producer is a **physical-origin** chord match — the `screenshot::HumanGesture` shape, so *"no principal can move the human between VTs"* is a compile error rather than the current absence of such a call. D-030(1)'s posture in one line: **the core moves the human's VT only when the human's own hands ask it to, and never otherwise.**

**The band's scoping sentence is untouched and remains D-030(1)'s.** "This screen and this process", the colour-continuity check, and the runbook's photograph-and-compare step are all orthogonal to who implements the chord, and all still hold. If anything they now matter more: before this decision the human could not leave, so there was nothing to come back from.

**Decision 2: `Ctrl-Alt-F<n>` works while the screen is locked, and while a consent prompt is up.** Decided rather than inherited, because both answers are defensible and the mechanism forced a choice: `LockGate::judge` consumes *every* physical press while the lock is up, so the hook is either outside it and works, or inside it and is dead exactly when a trapped human most needs it.

It loses nothing worth keeping. A VT switch from the lock screen **does not lower the lock** — D-030(2) already holds that, by its own test, because a VT switch must never be a way past a lock screen — so what a stranger at a locked panel reaches by chording is a login prompt on another VT, which they could equally have reached by pressing `Ctrl-Alt-F2` before `vitrind` started, or by power-cycling the machine. The marginal authority is a denial of service against a machine they are already standing in front of. And this core has already, deliberately, decided that a physically present adversary can wreck a locked session: the **dead-man chord fires through the lock by construction**, which is the entire reason `LockPolicy` implements `ConsumingGate` rather than `PreemptionHook`. Withholding the benign gesture from the same stranger who is already granted the destructive one is not a coherent threat model.

The positive case is stronger than the negative one is weak. Locked is the state where being trapped is worst, and this project's own risk register says so: the lock's passphrase path is Argon2id over a keysym stream that has already had one Turkish-layout defect class (`gbreve` at `0x02bb`), and `shim/docs/nested-lock-screen.md` has still never been executed on hardware. A human whose passphrase will not go in, on a lock they cannot dismiss, on a VT they cannot leave, is this entry's defect one state deeper with no exit at all.

**Verdict, in one sentence: the VT chord works in every state this core can be in — locked, prompting, mid-dead-man-hold, with no realm bound at all — and the only state in which it does not fire is the one in which it cannot, while the seat is already paused and no physical input exists.**

**Decision 3: a `change_vt` that fails, or that is accepted and never happens, is put on the panel — not only in the log.** `libseat_switch_session` is asynchronous, so `Ok(())` means *accepted*, not *switched*, and an accepted request that produces no `PauseSession` is exactly the shape of the defect above: a chord that appears to work and does not. Three journal entries (`vt_switch_requested`, written **before** the call so a request that never returns is still on record; `vt_switch_refused`, with a fixed reason label and an integer errno, never an OS string; `vt_switch_stalled`) plus a two-second watchdog, plus a new bounded human-visible surface, `crate::notice::CoreNotice`.

The surface is the part that must not be argued away. The human is looking at the panel; if they could read `stderr` they would not be trapped. A failure that lives only in the log reproduces this entry's defect exactly — a key that does nothing and says nothing. The notice carries a closed vocabulary of compile-time strings plus core-chosen integers, is drawn at the same output-stage fork that already excludes the band and the cards from `vitrin_view.frame_ready` (so an agent cannot observe that a human's session is trapped), and **cannot reach the band's rows**: it blits at `y = max(TRUST_BAND_HEIGHT, height - band_height)`, which is `status`'s discipline.

The watchdog is armed only when the session's own VT is known (`XDG_VTNR`, else `/sys/class/tty/tty0/active`, neither needing a new privilege). With no VT resolved, **the chord still works and the watchdog is off**, with the startup banner saying so: a silent watchdog beats a lying one — a false stall alarm on a working session teaches the human to ignore the one indicator that matters — and the escape must never be gated on a diagnostic.

**Decision 4: a seat pause makes every chord matcher forget its physical state, on every backend that has a seat.** This is a live defect this entry found rather than caused, and the VT escape makes it fire on the first use. `suspend_physical_seat` pays the confined app its held presses by handing `SeatDelivery`s straight to the delivery funnel; they are not `SeatInput`s and never re-enter the hook stack, so every `ChordMatcher` keeps whatever it believed at the instant the devices went away — and at the instant of a VT switch the human is holding **Ctrl and Alt by construction, because that is how they left**. On return their next bare `F5` switches VT, their next bare `Insert` fires a clipboard gesture, and their next bare `Delete` raises the lock screen; and a stale `consumed` entry makes the next release get eaten while its press was delivered, which is the latched key the pairing contract exists to prevent. `ChordMatcher::forget_physical_state` is called for all four matchers on the pause arm. **The nested backend needs none of it and does not get it** — winit keeps delivering, the real release arrives, `observe` clears the bit — which is the same principled asymmetry as D-030(8)'s button drain.

**What this changes in the source.** Three artifacts said the refusal out loud and all three moved together, or the code and the log would disagree in the file a reader checks first:

- `DrmState::seat`'s `#[allow(dead_code, reason = "… D-030(1) refuses `change_vt` outright")]` — **deleted**; the field is used. The compiler does not flag a stale `allow`, which is exactly why it had to go by hand.
- that field's doc comment — *"D-030(1) is the decision that this core never calls it"* — rewritten to the italicised line above.
- `the_seat_handler_drains_on_pause_restores_the_guard_on_resume_and_rotates_nothing`'s third forbidden token, `change_vt` — **the assertion survives and its message is rewritten.** It is scoped to the body of `handle_session_event` and it was always right about *that* method: a `change_vt` on the pause or activate arm would be a core that moves the human in response to a **seat event** rather than a human gesture — a core that switches back, or one that fights another compositor for the terminal. That is the trap D-030(1) correctly named and this entry does not license. What was wrong was never the test's scope; it was the decision behind it.

**What this costs.**

- **Twelve keys taken from every confined app on bare metal.** `Ctrl-Alt-F1`…`F12` are consumed in every realm and never delivered. It is what every other Linux compositor does, and it is stated because this project states what it takes.
- **`f1`…`f12` leave the configurable vocabulary of every other core chord on this backend** — `deadman::Chord`'s usable set drops from 19 keys to 7 — because the dead-man watcher detects in the router's unconditional observe tap, so a chord sharing a key with the escape would arm the human's off-switch *every time they left the VT*, and no hook ordering can prevent it. Refused at startup, scoped to `--drm` on the `--headless` precedent, with `the_vt_reservation_does_not_reach_the_other_backends` as the control. Nothing collides on a default command line: the first-light run used `esc`, `super`, `insert`, `ctrl+print` and `ctrl+alt+delete`, with no F-key among them.
- **One more hook outside `LockGate`**, the first ever, so *"the lock gate is the outermost hook"* becomes *"outermost among the hooks it may blind"*. Sound because a `ChordMatcher` never consumes a modifier — `LockGate::judge` still sees every Ctrl/Alt/Shift/Super transition it saw before — and because the collision refusal reserves the twelve triggers. Held by a type-level test that stops the crate compiling if the order changes, not by prose.
- **A stranger at a locked panel can switch VT** (decision 2). Strictly less than the dead-man chord, which already fires through the lock on purpose, and it never lowers the lock.
- **One more always-resident surface on the frame path**, and a raised notice forces the CPU composite for its ten seconds exactly as the lock cover and the consent card do. The same cost class WS-E has already accepted twice.
- **None of the above is evidence that the human can now leave.** No test in this workspace can take DRM master or a seat: `DrmState` cannot be constructed without a real `DrmDevice`, `LibSeatSession`, `GbmDevice` and `GlesRenderer`. What the tests hold is that the chord is recognised, consumed, unreachable by any agent (both origin guards pinned adversarially), alive under a lock and under a consent grab, wired to one call site, and that a pause leaves no stale state behind. **Whether `Ctrl-Alt-F2` actually puts a tty on the panel is knowable only from WS-E.3.4's runbook, executed by the owner and dated.** Until that line exists, the honest status of this defect is "closed in the tree, unverified on hardware".

**Decision 5: the scanout transform was wrong, and the fix is a stated relationship rather than a second guessed literal.** The same first-light run showed the trusted band — drawn in rows `[0, 8)` by construction — along the **bottom** edge of the panel: a pure vertical mirror. `backend::drm`'s `SCANOUT_TRANSFORM` was `Transform::Flipped180`, taken from the nested backend's window surface on the reasoning that both need the same flip. They are opposite kinds of target. smithay's `GlesRenderer::render` already post-multiplies GL's own y-flip, so `Normal` puts the logical top row at framebuffer row 0 and `Flipped180` cancels it; and "row 0" then means the *bottom* of an EGL window surface but the *first row of storage* of a GBM buffer, which a CRTC scans out as the top scanline. The constant is now `Normal`, the two kinds are named once in `dmabuf::MEMORY_TARGET_TRANSFORM`, and `the_scanout_and_the_window_are_opposite_kinds_of_target` asserts the relationship. **It cannot be confirmed here either** — nothing in this workspace can put a frame on a panel — and the same runbook owns the check.

**DEFERRED, explicitly:** **a configurable or disableable VT escape** (a kiosk deployment has a real case for `--no-vt-escape`) — filed separately rather than shipped in the same change, because the whole defect is an escape hatch that was not there and shipping the off-switch for it alongside is how it ends up off or misspelled. **The 99%-CPU half of first light** — the same run pinned a core, and only the smallest defensible part of that is addressed here (`shim::copy_in`'s per-pixel append, `Scene::compose`'s whole-view matte fill, and a startup line naming the build profile, without which no performance measurement from that binary is interpretable). Gating the capture-cache refresh on grant state is **refused**, on `backend::winit`'s existing reasoning: it would make the cache's freshness depend on whether a grant happens to exist. The shipped shim also never sends a dmabuf at all (`upstream.c`'s only `.kind =` is a literal `SHM`), so `zero_copy_source` is unreachable against real apps — a `track:c-shim` question, named here and not scheduled.

### D-032 — Relative motion and pointer gestures grow the seat vocabulary; pointer constraints grow the shim session instead; and touch and tablet are deferred against named evidence

**Status:** accepted (2026-08-10) — issue #222, workstream [WS-E](14-workstream-session-mode.md) §4.3 Stage 4. **Amended the same day, before landing**, by the owner: Decision 2 was written as a *shape* finding with every line of its implementation downstream of it, and the owner directed that the pointer-constraint half be built in this branch rather than handed on. Decision 2 is therefore a shape finding **and** a build, and it carries a new **Decision 2b** — the core hides its own cursor sprite while a constraint is active — which the first draft of this entry explicitly declined to take.

**What is built is stated per decision in [its own section below](#what-is-built-what-is-not-and-what-cannot-be-known-here), not in this line.** That is deliberate. **Five** sentences across this workstream and this entry said the work "is not built" while sitting in the change that built it — the review that caught it found three, and a sweep for the same phrasing found two more (WS-E's Stage-4 table row and its games paragraph in §4.2). One of the five was in a published-limits section, where an error in the optimistic direction is the one that misleads a user. A build status compressed into a status line is exactly the sentence nobody re-reads.

> **This log carries two entries numbered D-031** — the DRM bring-up escape route and the `Ctrl-Alt-F<n>` implementation, both above, both accepted 2026-08-09. The collision is reported rather than fixed here, because a landed decision id is cited from other documents and from `crates/vitrin-core/src/vt.rs`, `recorder.rs` and `backend/drm.rs` — all of which mean the **second**. This entry therefore takes **D-032**, the next free number by count, and a renumbering of either D-031 must go to **D-033** rather than to D-032. A forward pointer now sits at each D-031 heading, because a reader meets the collision there and not here.

> **Citations in this entry name symbols, not line numbers.** Every `file:line` in this entry's first-draft argument resolved to unrelated code by the time it was reviewed. **The cause is worth stating exactly, because the obvious guess is wrong**: checked against the parent commit on 2026-08-10, five of the six were *correct when written* — `hook.observe`, both drain call sites in `bind_to`, the drain in `suspend_physical_seat`, the one in `NestedState::handle_focus`, and the shim's touch-capability comment all pointed where they claimed. **This change moved every one of them**, by inserting well over a thousand lines into the files it cites. (The sixth, the `intake_physical` drop comment, was already two lines off and its text was then deleted outright.) So the failure was not carelessness in the first draft; it is that a line number in a permanent record is invalidated by the very commit the record describes. A symbol name is not. Where prose has no symbol to name — a module-doc section, a log line — it is cited by heading or by content and dated.

**The problem, in one line.** `crates/vitrin-core::input::intake_physical`'s doc comment, **as it stood before this change**, dropped five input classes at intake — *"touch, gestures, tablet, switches, relative motion"* — because *"v0's seat vocabulary is pointer + keyboard … and inventing a lossy translation at intake would bypass the protocol's own growth path"*. That was the right call and it is not a decision; it is a decision **postponed**, and all five had been postponed long enough that a laptop could not pinch-zoom, could not lock a pointer, and could not tell the compositor its lid closed. This entry decides each class. The measurement, the per-class reasoning and the wire shape are in [WS-E §4.3](14-workstream-session-mode.md#43-the-five-input-classes-the-seat-vocabulary-drops-a-verdict-each); what follows is what was decided and what it costs.

That quoted sentence **no longer exists**, and the citation is written in the past tense for that reason rather than repaired: this change rewrote `intake_physical`'s doc comment, which now names only touch and tablet as still dropped and states each as a *not yet*. The original text is recoverable from `git show` against the parent of the commit carrying this entry. The five-class list is quoted here because it is what the decision was taken *against*, not because it describes the tree.

**Decision 1: relative motion and gestures (pinch, multi-finger swipe) are served, as five `since="2"` sibling events on `vitrin_shim_seat` at event opcodes 5–9, each ending with `origin`.** `relative_motion(dx, dy, dx_unaccel, dy_unaccel, origin)`; `gesture_begin(kind, fingers, origin)`; `gesture_swipe_update(dx, dy, origin)`; `gesture_pinch_update(dx, dy, scale, rotation, origin)`; `gesture_end(kind, state, origin)`; plus `gesture_kind {swipe, pinch}` and `gesture_state {completed, cancelled}` on the same interface.

Swipe and pinch **share** their begin and end, because in Wayland's own gesture protocol those two signatures are identical and a signature is immutable forever ([00-conventions.md](../protocol/00-conventions.md) §7.4). Four events with no dead argument is the shape; six with duplicated ones pay an opcode for nothing, and two phase-tagged events would freeze a `cancelled` flag and a delta pair into a signature where each is meaningless in two phases out of three.

*Rejected: a timestamp argument.* No existing seat event has one, and `shim/src/seat.c` stamps every replay with its own `now_msec()`. Putting a device clock on the wire beside it is the second unsynchronised clock `wp_presentation` was refused for (`shim/docs/firefox.md`). The cost is real and is paid rather than argued away: a consumer integrating deltas over `dt` gets the shim's arrival time, not the device's event time.

*Accepted, with its cost named: `zwp_pointer_gestures_v1` is advertised at wlroots' own version, which is 3.* **The first draft of this decision recorded the opposite** — that version 3 was *rejected* and the global advertised at version 2 — and the shipped `shim/src/globals.c` gave the other answer, so an accepted decision and the code it governed contradicted each other inside one uncommitted change. The code is right and the decision text was wrong, for a reason checked against the header on this machine rather than reasoned about:

- `wlr_pointer_gestures_v1_create(struct wl_display *display)` takes a display and **no version**, so capping the advertisement at 2 is not expressible through wlroots' helper at all; capping it would mean not using wlroots' gesture implementation and hand-rolling the global. Verified in `/usr/include/wlroots-0.19/wlr/types/wlr_pointer_gestures_v1.h` (package `wlroots0.19 0.19.3-1`) on 2026-08-10.
- That same header declares `wlr_pointer_gestures_v1_send_hold_begin`/`_hold_end` and a `holds` resource list, and `get_hold_gesture` is `since="3"` in `/usr/share/wayland-protocols/unstable/pointer-gestures/pointer-gestures-unstable-v1.xml` (interface `version="3"`). A wlroots that implements hold advertises 3.

Version 3 adds `hold`, which the core never sends. **That is not the half-serving `shim/src/globals.c` refuses elsewhere**, and the distinction is the whole of the answer to Decision 3's rule: the three gesture families live behind **one** global, so declining hold would decline swipe and pinch with it, and a client learns which gestures exist from the **events it receives** rather than from the global — unlike a `wl_seat` capability, which is a positive claim a toolkit changes its fallbacks on. The application evidence points the same way: the run in `shim/docs/globals-touched-firefox-140.12.0esr.log` shows Firefox binding this interface twice, once at version 1 and once at version 3 (`version_requested=1`, `version_requested=3`; summarised as `binds=2 version_min=1 version_max=3 status=bound`). Hold reopens on an application that binds version 3 **and** does something with a hold.

**Decision 2: pointer constraints are served, and the verdict is NOT a seat event — it is a paired request and event on `vitrin_shim_session`.** This is the finding that changed the shape of the work, and it comes from backward requirement B2 rather than from taste. The RNG's `seat-event` define makes `origin` the mandatory trailing argument of every event on `vitrin_shim_seat`, supplied by the `origin-arg` define, and `origin` has exactly two values: a human's device, or a principal's actuator. **A constraint activation is caused by the confined app, which is neither**, so any tag it carried would be false — on the one interface whose entire design idea is that the tag never drifts. Worse, the schema forecloses the alternative outright: the RNG's `seat-interface` define admits only `seat-event` and `enum` children, so a *request* on that interface is not merely unwise, it is inexpressible.

So the **ask** is a shim→core request and the **verdict** a core→shim event, both on `vitrin_shim_session` — the only interface carrying shim→core requests — and what the seat gains for this class is `relative_motion` alone, the input a lock actually delivers. It is the cross-realm clipboard's shape ([D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing)) reused: the core decides, the shim asks, and the state lives where nothing outside the core can strand it. The concrete signatures — `pointer_constraint(serial, surface, kind, lifetime, x, y, width, height)` and `pointer_constraint_state(serial, state)`, plus `pointer_constraint_kind`, `pointer_constraint_lifetime` and `pointer_constraint_status` — are in the IDL and in [page 09](../protocol/09-vitrin_shim_session.md), which are normative; they are not restated here.

**Why #222 did not see this coming, which is worth recording because the issue's frame was reasonable.** #222 asked one question five times: *the seat vocabulary drops five classes, decide each*. Four of the five genuinely are seat-vocabulary questions — touch, tablet, switches and relative motion are all input events with a physical origin. A pointer constraint is not an input event at all. It is an application's **ask** and the core's **verdict**, and the interface it was being sized for demands an `origin` tag that neither of those has. The frame made the mismatch invisible; the schema made it undeniable the moment anyone tried to write the event down. The lesson is narrow and worth keeping: *"which interface does this class grow?"* is a question the schema can answer mechanically, and asking it early is cheaper than discovering it in an IDL draft.

**Decision 2a, taken by the owner on 2026-08-10: the constraint half is built in this branch, not handed on.** The first draft of this entry left every line of it downstream. That would have shipped a wire vocabulary — `relative_motion` — whose only serious consumer is a locked pointer, with no way to lock a pointer: an app that binds `zwp_relative_pointer_manager_v1` and gets deltas it cannot correlate with a lock is worse served than one that gets nothing, because it will believe the feature works. Building both halves together also keeps `zwp_pointer_constraints_v1` from having to be advertised inert, which is the half-serving `shim/src/globals.c` refuses on principle.

**The recorded objection is answered rather than overruled, by one rule: a constraint binds physical motion only.** `shim/docs/firefox.md`'s `zwp_pointer_constraints_v1` row did not serve it because *"a client that can warp or confine the pointer can invalidate what the agent observed between observation and actuation"*. An agent's actuation is minted absolute by the chokepoint and routed by `InputRouter::route_emulated` to the realm its grant names; it is never re-expressed as a delta and never clipped to a confinement region. `route_physical` and `route_emulated` are two separately named entry points precisely so a call site has to say which rule it is following, and the constraint check is written on the physical arm only, gated on `Origin::Physical`. So observation and actuation stay in one coordinate space whatever the app has locked — and, the sharper half, **an app that locks the pointer does not thereby confine an agent**, which would otherwise hand a confined app a way to trap a principal's actuation.

#### Decision 2b: while a constraint is active, the core hides its own cursor sprite — and the un-hide obligation is the safety property of this entire change

The first draft declined this, calling it *"a core decision this entry does not take"*. **The owner took it on 2026-08-10**, with the cost stated rather than discovered:

**Why the core must be the one to hide it.** The core owns the pointer sprite — which is why `wp_cursor_shape_manager_v1` is not served: *"the shim has no cursor at all"*. So "lock and hide" is one verb an app can ask for and one it cannot perform, and a locked pointer whose sprite the core keeps drawing is a frozen arrow sitting over a game the human is trying to aim in. Serving the lock and refusing the hide would serve half of what a lock is for.

**What it costs, plainly, because this is the part that can hurt a person.** Every path on which a constraint ends must restore the sprite. **A single missed path leaves the human with no visible cursor on a display server they cannot exit** — on the maintainer's only machine, in the one mode where there is no host desktop to fall back to. That is a worse outcome than any other defect this change could cause, and it is the reason the design below is not a matter of style.

**So the sprite is a derived predicate, never a stored flag.** Visibility is recomputed once per frame from live state at the single line in `backend::drm`'s `compose_and_queue` that decides it — the one that feeds both the zero-copy and the CPU presentation paths — and nothing else in the crate is permitted to write sprite visibility. The argument is arithmetic rather than aesthetic: **a flag toggled at N sites strands the human's cursor by omission on the N+1st path**, and this workstream has already learned that lesson twice under a gentler penalty (`forget_presence_of` was a caller's obligation for exactly one review cycle before the realm-death funnel, which did not know it existed, became its third caller). A predicate evaluated per frame cannot be stranded by omission at all. It can only be stranded by a stuck *record* — and a stuck record still cannot hide the sprite unless the realm is also focused, no overlay is up, and the output is active.

**That shape also buys the reactivation half for free**, which a flag design would have had to remember: Wayland's `persistent` lifetime requires a lock to become active again when its surface regains focus, so a flag would need an un-hide on switch-away *and* a re-hide on switch-back — two sites, one of which gets forgotten. The predicate gives both, and the reconciler reports the transition.

**The deactivation paths are enumerated exhaustively in [WS-E §4.3](14-workstream-session-mode.md#43-the-five-input-classes-the-seat-vocabulary-drops-a-verdict-each)** and split into two classes there: *record removal* (the app withdraws; the realm or its shim dies; the seat is paused; the dead-man switch fires; the session tears down) and *transient* (the realm is not focused; a consent card, the lock screen, the dead-man hold or the core notice is up; the surface is uncommitted; the output is inactive; the pointer is outside the region). The transient class needs **no un-hide code at all**, which is the point of deriving rather than storing.

**Ranked, because the two effects are not equally dangerous.** A constraint also **freezes** the absolute position the core's own hit tests use. The freeze is ranked strictly *below* the sprite: a frozen visible cursor looks like a hung compositor but leaves the human every escape they had, whereas a hidden one does not. If an implementation has to retreat from either, it retreats from the freeze.

**And the honest note about evidence, which belongs here rather than in a test plan.** The sprite exists only on bare metal — `backend::winit`'s `window_pixels` is handed `None` for the human cursor on nested and headless, because the host desktop draws it there. So **every mode CI can run is structurally immune to the failure this decision creates**, and the one mode that is not is the maintainer's own machine. Immune where it is cheap to test, dangerous where it is not: that is the shape that lets a defect ship green, and it is why the mitigation must be a named, skipped-with-a-reason integration rung on the target machine rather than a unit test.

**That a locked, hidden pointer cannot beat the core is argued, not assumed** — and every citation below was re-derived by opening the file on 2026-08-10, because in the first draft of this paragraph all four missed.

1. **The dead-man chord is untouched by construction.** The tap is `hook.observe(&input)` inside `InputRouter::route_into`, called unconditionally one statement *before* `hook.gate` and therefore above every gate. `DeadManHook::observe` reaches `DeadManSwitch::observe_event`, whose second statement destructures `SeatInputKind::Key` and returns on anything else — it is a **keyboard** chord and no pointer state is on its path. The unconditionality is structural, not conventional: `GateOnlyHook::observe` forwards to its inner hook with no gate consulted, and the `ConsumingGate` trait it wraps declares **no observation method at all**, so an edit inside `crate::lock` cannot make observation conditional because the trait it calls through cannot express one. A pointer constraint sits below both and reaches neither.
2. **The consent grab runs before the constraint is ever consulted.** The hook point is *after* origin binding and *before* coordinate mapping and hit-testing — the argument is in `crates/vitrin-core/src/input`'s module docs under *"The preemption hook"*, and it is the one citation from this entry's first draft that still resolved when checked. A constraint is a delivery decision inside `route_into`'s per-kind match, reached only after `hook.gate` has declined to consume and after the realm has resolved. The module docs already make this argument for the letterbox matte — *"a gate that ran after the app hit-test could be dodged by parking the pointer off the surface"* — and a pointer lock is that dodge with a protocol behind it, landing on the wrong side of the hook point to attempt it.
3. **The core owns the constraint state and ends it alone.** Record removal lives at the funnels the router already has: `InputRouter::bind_to` for a realm switch, `session::suspend_physical_seat` for a seat pause, `InputRouter::reset_for` for realm and shim death, and `Runtime::apply_dead_man` for the chord. `reset_for` is the placement that matters and it is not a preference — `lifecycle::die`, the single death funnel, reaches teardown by two arms (the shim connection closing, and a hand-rolled reset when the realm died before its shim came up), and clearing inside `reset_for` covers both with one edit. Everything else is transient and needs no site at all.
4. **The app cannot hide the cursor, because it never had it.** Decision 2b above, and this is the reason it had to be taken rather than left open: the capability the app is asking for is one only the core can perform.

There is a fifth reason the first draft did not name, and it is the maintainer's actual last resort on this machine: **the VT escape is the outermost member of the hook stack** and `Ctrl-Alt-F<n>` is a keyboard chord ([D-031](#d-031--the-core-implements-ctrl-alt-fn-itself-because-refusing-to-is-what-trapped-the-human-d-030s-reasoning-stands-and-its-effect-was-its-own-opposite)). A locked, frozen, sprite-less pointer is not on its path at any layer.

**And the sixth, which is the invariant the other five hang off** ([00-conventions.md](../protocol/00-conventions.md) §1.4, invariant 2): *the core's own hit test — never a client's claimed stacking — decides which surface an input event reaches*. A constraint changes only what the **app** is told. It never changes what the core believes: the core's accumulated position, the consent card's recorded pointer and the lock screen's passphrase path are all upstream of it, and the freeze is applied where the app-facing position is *minted* rather than by rewriting any of them. Nothing in this change writes a second hit test — the region check reuses the router's existing `pointer_over_surface`, because a second hit test would be a second answer to a question invariant 2 says has one.

**Decision 3: touch is DEFERRED, and every surface in this repository states it as *not yet served*.** No device on the target machine can produce a touch event: not one node carries `INPUT_PROP_DIRECT`, decoded from `/proc/bus/input/devices` on 2026-08-10 rather than assumed. That is a measurement of **one laptop**, not a property of the class, and a permanent wire protocol may not foreclose a device class on that ground. `shim/src/globals.c`'s choice to advertise `WL_SEAT_CAPABILITY_POINTER | KEYBOARD` and no more **stays** — it is the precedent against half-serving — but its *wording* did not: this change rewrote that comment, which now reads *"a `wl_touch` bound here would have nothing behind it, and advertising a capability the shim cannot honour is worse than not advertising it: a toolkit that sees TOUCH stops installing its pointer fallbacks"*, under the heading `TOUCH IS NOT YET SERVED`. Cite it by that heading rather than by line, since it has already moved once inside this branch. **What reopens it:** a touchscreen in the measured device set **and** an application in the session matrix that needs it. Both, because a device with no app that wants it buys a permanent wire surface for nobody, and an app that wants it on a machine that cannot produce it cannot be tested. Touch is also the one class here for which no `globals-demand` line is possible in either direction: it is a `wl_seat` capability rather than a global, so the shim's ledger cannot record a demand for it even in principle.

**Decision 4: tablet is DEFERRED, on the device alone, because the application half of its evidence is already banked.** No node on this machine carries `BTN_TOOL_PEN`, `BTN_STYLUS` or any other pen tool — and the evidence log nonetheless carries a real `globals-demand` line for `zwp_tablet_manager_v2` (`seq=39`, `version_requested=1`), because GTK binds the tablet manager whether or not a tablet is plugged in. **What reopens it:** a tablet or stylus device in the measured set. Nothing else. It is the class most likely to reopen first, because a graphics tablet is something a person buys rather than something a laptop has.

**Decision 5: the lid switch is not a seat-vocabulary gap, and goes to WS-E.4.3 (#223) unchanged.** Wayland clients do not receive switch events at all; the compositor consumes them, and on this machine logind does. A switch event on this wire would put a message under something no application can use. #222 reasoned this correctly and it is restated rather than re-decided.

**Decision 6: no version bump, and no scheduling question — because version 2 has never left this repository.** #222 treats the version as a hard constraint, citing [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md):303's *"Nothing may bump to version 3: P2.1.2 owns the single bump for the whole phase"*, and concluding that new seat events must ride P2.1.2 or wait past the P2.9.2 spec freeze. **There is nothing left to ride.** The 1→2 bump landed 2026-08-06 in WS-E.1.1 (`6abe8dd`), and version 2 has been appended to three times since (`4fdcab6`, `53cee3a`, `2f7c7cf` — eleven `since="2"` messages in all); the same Phase-2 document already anticipated this at `:383-390` — *"the 1→2 version bump is owned by whoever lands first, not by P2.1.2 by name … the invariant that actually matters is unchanged — one bump, and every later addition at `since=\"2\"`"*. This work adds `since="2"` siblings and bumps nothing.

That is legitimate only because of the check that would otherwise have stopped it: **version 2 has never been released, frozen or negotiated by any implementation outside this repository.** The one tagged release, `v0.1.0` (2026-07-26), ships `<protocol name="vitrin" version="1">` — verified with `git show v0.1.0:protocol/vitrin-v0.xml`. There is no second release; the shim's version is *pinned at spawn* because core and shims are release-paired ([00-conventions.md](../protocol/00-conventions.md) §7.2); and the only other speaker is this repo's own Python SDK. Had version 2 been released, appending to it would be a silent redefinition of what a released integer means — a client built against the older version 2 meeting an unknown opcode — and the honest answer would have been version 3, which the Phase-2 plan forbids. It has not been, so §7.4's first growth rule applies unchanged: *"New messages are appended with `since` attributes. Opcodes are implicit document order."*

**Decision 7: no verb bit, positively.** `Verb::VALID_MASK` stays **575**. Nothing agent-facing is added: these are core→shim delivery events on the physical path, `vitrin_shim_seat` carries no `@verb` attribute and no requests, and an `actuate_gesture` verb would name authority nobody has asked for. The registry in [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5 is untouched (64 `designate_file`, 128 `egress`, 256 `publish_tree`, 512 `realm_launch`), and this decision allocates nothing there.

**Decision 8: the gesture pairing discipline is the one `pressed`/`pressed_keys` already enforce, plus a drain.** A `gesture_begin` with no `gesture_end` is the latched-modifier bug in a new shape. So: at most one in-flight gesture per `RealmSeat`, with a second `begin` dropped and traced rather than trusted away; an `update` or `end` delivered **iff its own `begin` was delivered**, exactly as *"a release is delivered iff its own press was"*; a gate-consumed `begin` starting nothing, so its updates and end are dropped; a consumed `end` whose `begin` **was** delivered reconciled the way a consumed release is, with the app-side debt belonging to the gate implementor and one new sentence owed to `PreemptionHook`'s pairing contract; and a drain, `InputRouter::end_physical_gesture`, sibling to `release_physical_keys`/`release_physical_buttons`, emitting `gesture_end(kind, cancelled)` — cancelled, because the human did not finish it.

**The drain runs on exactly two paths, and the first draft of this decision claimed five.** This is corrected here rather than smoothed over, because the same over-claim reached the IDL, where a `<description>` is normative and outranks every prose page. The two are `InputRouter::bind_to` (a realm switch) and `session::suspend_physical_seat` (a seat pause). On both, the human's fingers are still down and no end can ever arrive, so one is minted rather than waited for. The three that were claimed and are not true:

- **a consent prompt** and **a raised screen lock** do *not* mint one. Both gates answer `Gate::Deliver` for `GestureEnd` — checked in `ConsentGrab`'s and `LockGate`'s judge arms — so they withhold the gesture's *updates* and then deliver the device's own end when the human lifts. No latch forms, which is why this is a gap rather than a defect; but an app that was previewing a zoom is told the human **completed** what they in fact abandoned behind a card they could not see past. Closing it needs `scenes` at the consent-round service point and is a separate change, named here so it has a shape rather than a sentence.
- **the dead-man switch** never took physical input away in the first place: it revokes grants, so its clause was vacuous.

`NestedState::handle_focus` is a fourth non-caller and a *deliberate* one, documented where it sits: a gesture is pointer-side, so it follows the buttons' exclusion rather than the keys' inclusion — and smithay's winit backend surfaces no gesture events at all, so a nested session can never have one in flight.

`relative_motion` needs no pairing of its own; its latch shape lives in the constraint, which is why the constraint's state is core-owned, why its removal sits inside `InputRouter::reset_for` rather than at each caller, and why an **emulated** motion must not move the frozen physical position while a constraint is active.

**What this costs.**

- **The permanent wire surface grows by half again, designed against one laptop.** Five events on an interface that had five, plus two enums, plus two messages and three more enums on `vitrin_shim_session`. A message signature is immutable forever (§7.4), so every future implementation carries these — and the device set that justified two of them is one machine measured on one day. #222 names this risk first and nothing above reduces it; it is accepted, with the mitigation that no argument in any of the five seat events is device-specific (deltas, finger counts, scale and rotation are what every gesture protocol carries). **Two hostages to fortune on the constraint pair specifically**, named here rather than discovered later: `lifetime` is carried because Wayland has it, not because anything in this repository has yet needed `oneshot`; and the region is **one rectangle** where Wayland allows an arbitrary `wl_region`, so an app whose confinement is genuinely non-rectangular is given a bounding box.
- **Trusted-code growth in the most safety-critical path in the core, and Decision 2a enlarges it.** The input router is what the dead-man switch and the consent grab hang off, and this adds five `SeatInputKind` variants, a per-realm gesture state, a third drain, a constraint state machine, a shared per-realm table, a freeze on the intake arm and a per-frame reconciler to it. Each is new TCB code that must honour pairing, and this codebase has got a pairing invariant wrong twice already ([D-028](#d-028--a-bare-metal-session-interprets-the-keyboard-inside-the-core-from-a-pre-compiled-keymap-file-and-key-pairing-moves-to-the-scancode)(3)) — three times counting the review of this change's own first half, which found a `_Static_assert` whose comment claimed a bound it did not enforce and which permitted a real out-of-bounds write. The constraint's pairing obligation (every `active` owes an eventual `inactive` or `withdrawn`) is the same latch shape as `gesture_begin`/`gesture_end`, and it is the shape this repository keeps getting wrong.

All three carry the `globals-demand` evidence that file's own rule demands, in `shim/docs/globals-touched-firefox-140.12.0esr.log` (`seq=80` for constraints, `seq=81` for relative pointer, `seq=36`/`seq=82` for gestures, each summarised `status=bound` in the same file), so no addition here is argued from a wish — but the contract is longer, and each new global is protocol semantics the shim must now be correct about. **Review note:** a review of the first half correctly recorded this as *two*, because the constraints global was deliberately not created then. For the cursor sprite this is sharper than usual: nested and headless pass `None` for the human cursor, so **no test in this workspace can strand a cursor even if the logic is wrong**. A unit test may not stand in for that rung.
- **A word is now overloaded and must stay qualified.** `constraint` already means a *petition* constraint in this protocol — `request_grant`'s `flags`, and Appendix A's `set_constraint` builder row. The pointer variety is `pointer_constraint` everywhere, in the IDL, in prose, in Rust and in C, or two unrelated capabilities share a noun in a document that cannot rename either.

WS-E.2.1 had landed three `since="2"` messages on `vitrin_shim_session` without extending the table; this change adds its own seven and the three missing ones together, along with the three new enums — [00-conventions.md](../protocol/00-conventions.md) §7.3's enum paragraph takes the largest single addition it has ever had, which makes it the likeliest thing in the paired edit to be forgotten.

**DEFERRED, explicitly, and each with what would settle it:** **touch** (Decision 3) and **tablet** (Decision 4), on the evidence named there. **The hold gesture**, on an application that binds `zwp_pointer_gestures_v1` version 3 and does something with a hold. **Cancelling an in-flight gesture when a consent card or the lock screen raises** (Decision 8), on the change that puts `scenes` in reach of the consent-round service point. **An agent-facing gesture or relative-motion verb**: none is allocated, none is designed, and nothing above forecloses one — `origin` is on all five events from the first landing precisely so an emulated source stays purely additive.

### D-033 — Idle blanks the screen and does not lock it; suspend is detected after the fact or not at all; and the recovery path is sudo-only

**Status:** accepted (2026-08-10) — issue #223, workstream [WS-E](14-workstream-session-mode.md) §4.4 Stage 4. **Discharges [D-030](#d-030--the-trusted-band-asserts-only-about-the-screen-this-core-is-driving-and-the-session-colour-is-never-re-minted-a-paused-seat-raises-no-prompt-it-could-record-as-shown)'s explicit deferral of "a dark-output gate — to whichever change implements DPMS, as that change's own acceptance criterion"**, and falsifies D-030(4)'s *"the core can neither enter nor observe a dark output"*; amends the escape-route half of [D-031 (the first)](#d-031--the-drm-bring-up-escape-route-is-a-hyprland-side-shell-and-an-installer-usb-not-ssh-and-not-vt-switching) by adding a `sudo`-only SysRq path and deleting a standing recommendation. Decisions 1 and 4 are **the owner's**, taken 2026-08-10 and recorded rather than derived.

> **NUMBERING: this entry takes D-033, and that closes the escape hatch the D-031 collision was relying on.** Two entries above are numbered D-031, and both of their notices — and D-032's — say *"a renumbering would go to **D-033**, since D-032 is taken."* D-033 is now taken by this entry, so **that remedy no longer exists**: any future renumbering of either D-031 must go to the next free number at the time, and the collision is now permanent unless someone renumbers deliberately against landed code in `crates/vitrin-core/src/vt.rs`, `recorder.rs` and `backend/drm.rs`. This is said here because three separate notices promise a fix that this entry consumes, and a promise that quietly stops being available is worse than one that was never made.

> **Citations in this entry name symbols, not line numbers**, for [D-032](#d-032--relative-motion-and-pointer-gestures-grow-the-seat-vocabulary-pointer-constraints-grow-the-shim-session-instead-and-touch-and-tablet-are-deferred-against-named-evidence)'s reason: a line number in a record describing a change is invalidated by the change it describes. Machine facts are dated and marked, on [`docs/drm-bringup.md`](../drm-bringup.md)'s verified/inferred convention.

**Issue #223 was filed 2026-08-06T08:35Z and five of its factual claims about the tree were false by 2026-08-10.** The full table is in [WS-E §4.4](14-workstream-session-mode.md#44-session-lifecycle-build-what-the-hardware-forces-delegate-the-rest); the two that would have caused real damage are that it plans to *publish "there is no lock screen" as a limit* (one landed in WS-E.2.2 and was exercised end to end on bare metal) and that its first task, activation transitions, was **already built and hardware-confirmed** by D-030 and D-031. A decision entry that acted on the issue as written would have re-derived working code and published a false limit in the pessimistic direction. This is recorded because the staleness was structural rather than careless: the issue was filed before three stages landed.

**Decision 1, the owner's: on idle the screen blanks; the session does not lock. The two are not coupled.**

The panel goes dark after a period with no physical input and the session stays **unlocked**; any physical input restores it. Locking remains the human's manual chord, which already exists. **The cost is real and is published unsoftened**: an unlocked session behind a dark screen, so anyone who walks up and touches a key gets the session rather than a passphrase prompt — worse than what the maintainer's machine does under Hyprland today. It is his trade and it is recorded as one rather than argued down.

**What the non-coupling forbids concretely.** The idle *lock* clock must keep running while the screen is dark. If the blank suppressed it, a session configured with a blank timeout shorter than its lock timeout would silently never lock — a comfort feature disabling a security control, which is exactly the class of unchosen behaviour [D-030(2)](#d-030--the-trusted-band-asserts-only-about-the-screen-this-core-is-driving-and-the-session-colour-is-never-re-minted-a-paused-seat-raises-no-prompt-it-could-record-as-shown) was written to catch and which needs a named test rather than a comment. Blanking while unlocked and then locking behind the dark screen is the **correct** sequence: the human touches a key, the wake is consumed, and the screen returns showing the lock card.

**Decision 2: the activity clock is one clock with one writer, shared by the lock and the blank, and an agent's actuation neither postpones nor wakes.**

The postpone half was already decided by landed code and is inherited structurally rather than restated: `LockScreen::judge` returns early for non-physical origin *above* the activity stamp, commented *"an agent's actuations must not hold the idle lock open for a human who left"*, pinned by `an_agents_actuation_never_holds_the_idle_lock_open`. Sharing the clock rather than adding a second one is the point — two timestamps meaning *"when did the human last touch this session"* would drift, and the drift would be invisible.

**The wake half needs its own argument, and it is the stronger one: there is no verb in the IDL for "power the human's display".** An agent that could wake the screen would be making an unrequested change to the human's physical environment, remotely triggerable, under no grant — the shape [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) refuses for the clipboard, and the inverse of what [D-019](#d-019--the-agent-cursor-is-drawn-display-only-human-visible-output-only-d-017s-delivery-deferral-stands) buys: an agent's action must be *visible when a human is there*, not *summoning*. **The counter-argument is stated and rejected:** *"an agent doing visible work should keep the screen on so the human can watch"* — a human who wants to watch is present and touching things, and D-030(6) already publishes that agents keep working while the human's screen is not showing them.

**The core's own drawing wakes nothing, and the list is exhaustive rather than illustrative**, because *"the core drew something"* is how a wake rule leaks. A **consent card raising must not wake**, and this is the sharpest of them: a core that woke the screen because an agent petitioned would hand every principal a remote wake primitive, and petitioning needs no grant at all. The **status strip's minute rollover** must not wake, or a session would wake itself once a minute and never blank. A **realm's commit, a realm launch and a client's layout verb** must not wake — an app painting is not the human. The **dead-man chord** and the **VT chord** need no rule: both are held physical keys, so the first press wakes by the ordinary predicate.

**Decision 3: the wake event is consumed, for the whole dark-to-first-frame window rather than for one event, and the consume is bounded.**

Consumed so that a press aimed at a dark screen neither commits a consent card nor acts inside a confined app. For the whole window, because unblanking is a modeset and a modeset is long enough for a human to type several characters into an app they cannot see. **Bounded**, because a dark screen that also swallows input is indistinguishable from a wedged session, and manufacturing those is precisely what decision 6's runbook exists to avoid. The rule in one line: **fail open on input, fail closed on authority.** The consent guard restart is what holds the security property, so the consume is defence in depth and may be lost to the bound without opening a clickjack.

**Decision 4: no D-Bus client in the core, and — because libseat delivers nothing on suspend either — a resume is detected after the fact from a clock pair the core already samples, or not at all.**

The no-D-Bus half is unchanged and not re-argued: logind's `PrepareForSleep` would mean a message bus and its dependency tree inside the TCB, while [D-020](#d-020--the-realm-boundary-is-a-namespace-boundary-intra-user-by-default-in-namespace-uidgid-and-a-residue-that-lives-outside-every-realm) and #160 exist to *remove* ambient bus access from realms.

**What #223 got wrong is the fallback.** Its task 2 says to *"route post-suspend recovery through the same reactivation path as VT switch, so there is one code path and not two"*, on the assumption that libseat's device pause/resume covers the device half. It does not: libseat's logind backend fires `disable_seat` on the session's `Active` property going false or on a `PauseDevice` signal, and **logind emits neither for a system suspend** — so a suspend/resume delivers no session event at all and there is nothing to route. The sentence was vacuous as written, and adopting it would have produced a handler for an event that never arrives, which is the unreachable-guard-that-reads-as-live failure D-030(4) already refused once.

**What the core can actually observe is one fact it already takes every round**: `Instant::now()` and `SystemTime::now()` in the same call. `Instant` is `CLOCK_MONOTONIC` and does not advance across a suspend; `SystemTime` does. A round in which wall time advanced by seconds while monotonic time did not **is** a suspend that just ended — detectable with no D-Bus client, no new syscall and no new clock, which is exactly what the no-bus decision leaves available. Routing that into the same reactivation path the blank's wake uses is what makes #223's *"one code path and not two"* true rather than vacuous.

**The residual is the one #223's own key-decisions block already states, and it is not reduced here:** this detects a resume **after** the fact and never before, so a frame may be submitted into a suspending device and the first post-resume frame may be late.

**Decision 5: suspend, lid and power-key policy stays logind's, and the switch device class stays dropped at intake.**

`HandleLidSwitch`, `HandlePowerKey` and `HandleSuspendKey` exist and are configured per machine; reimplementing them would be session policy in the TCB. This restates rather than re-decides [D-032(5)](#d-032--relative-motion-and-pointer-gestures-grow-the-seat-vocabulary-pointer-constraints-grow-the-shim-session-instead-and-touch-and-tablet-are-deferred-against-named-evidence), which handed the lid here. Confirmed on the machine 2026-08-10: the lid is `SW_LID` on `event0`, `vitrind` sees it through libinput and drops it, and `crate::input::intake_physical`'s doc comment already says *"Switch events (a lid closing) and hold gestures have no wire event either."*

**The accepted cost is that behaviour now depends on files this repository does not own**, so *"suspend works"* is not reproducible from a checkout. The mitigation is publication rather than ownership: the effective values are read from the running logind and printed with the runbook, together with the finding that `/etc/systemd/logind.conf` is **empty** on this machine, so every value is a systemd default that can move without any change here. [verified 2026-08-10]

**Decision 6: the recovery runbook is a new book page; its SysRq path is `sudo`-only through `/proc/sysrq-trigger`; and `kernel.sysrq` is not touched.**

**The owner settled the mask on 2026-08-10, having been asked about it repeatedly**, and it is recorded so nobody asks again: raising it would hand `REISUB` to anyone at the physical keyboard of a machine whose entire premise is confining what runs on it. `/proc/sys/kernel/sysrq` is `16` here — sync only — so the physical `Alt+SysRq` sequence is inert by configuration. **`docs/drm-bringup.md` §0.4 carried a standing recommendation to raise it; that section is deleted and replaced, and its R2 rungs 2–3 rewritten**, because a landed recommendation is not answered by declining to repeat it elsewhere.

**The trigger file is allowed regardless of the mask, verified against the kernel rather than asserted.** From `Documentation/admin-guide/sysrq.rst`, read 2026-08-10: *"Note that the value of `/proc/sys/kernel/sysrq` influences only the invocation via a keyboard. Invocation of any operation via `/proc/sysrq-trigger` is always allowed (by a user with admin privileges)."* The mechanism behind that sentence is `write_sysrq_trigger` calling `__handle_sysrq(c, false)` — the second argument is `check_mask`. The node is `--w------- root root` here, so the capability is root's alone, which is the property being bought.

**And the correct sequence is not REISUB, which is the substantive finding of this task.** Three checks, all against the kernel's own source and documentation on 2026-08-10:

1. `echo reisub > /proc/sysrq-trigger` performs `r` and **silently nothing else** — only the first character is processed unless the string is prefixed with `_`.
2. The kernel's own bulk-mode example, `echo _reisub > /proc/sysrq-trigger`, **is a hard reboot with two no-ops in front of it.** `sysrq_handle_sync` calls `emergency_sync()` and `sysrq_handle_mountro` calls `emergency_remount()`; **both are `schedule_work(...)` and return immediately** (`fs/sync.c`, `fs/super.c`), while `sysrq_handle_reboot` calls `emergency_restart()`, which does not return at all. Bulk mode runs the whole string inside **one** `write()` with no pause between letters — that is what the leading `_` buys. So the sync and the remount are queued and the machine reboots before either can run. The kernel documentation states the same fact about the sync in its own words (*"the sync hasn't taken place until you see the "OK" and "Done" appear on the screen"*), and bulk mode is exactly the form that denies you the chance to see them.
3. `e` and `i` are wrong for **this** machine independently of the above. The trigger path needs a reachable shell by construction, and on this machine the escape route *is* a shell in the running Hyprland session — so `e`'s SIGTERM-to-everything destroys the thing being recovered with, along with the maintainer's open work. Route 2's signal to **one resolved PID** is the aimed version of what `e` does bluntly. (Written as `pkill` here originally; corrected 2026-08-11 per #260 — `pkill -f` on this pattern is not aimed, it signals the rescuer.)

The runbook therefore prescribes **three separate writes with a wait between them** — `s`, wait; `u`, wait; `b` — each destructive step marked as destructive, and drops `e`, `i` and the bulk form entirely. **The caveat is stated plainly:** the trigger file needs a **reachable shell**. It covers *"vitrind wedged the display"* once a VT or the tty1 shell is reachable; it does **not** cover *"input is completely dead"*, which is the only case the physical combo would have covered and which the owner has declined knowingly. No new mitigation is invented — the page documents the routes that exist (D-031's Hyprland-side shell, the core's own `Ctrl-Alt-F<n>`, the installer USB and a chroot).

**Two machine facts that change how the page reads and were nearly missed.** `kernel.dmesg_restrict` is `1` and the console log level is `1` here [verified 2026-08-10], so the kernel's completion messages reach neither an unprivileged `dmesg` nor the console — the documentation's *"wait until you see them on the screen"* does not work on this machine, and `sudo dmesg -w` in a second shell is the observable. And the unprivileged redirect fails: `echo s > /proc/sysrq-trigger` returns permission denied and writes nothing, as does `sudo echo … >`, because the redirect happens in the calling shell. [verified 2026-08-10, tested non-destructively] **The `sudo` write path itself was not executed** — `sudo -n true` fails here and the session that wrote the page could not supply a password — so it is marked documented-and-unexecuted, and the owner is asked to run the harmless `s` rung himself as the page's own smoke test.

**What this decision costs.**

- **An unlocked session behind a dark screen** (decision 1). Real, the owner's, and published without softening.
- **A dark screen stops being evidence that nothing is being watched.** An `observe` holder keeps capturing while the panel is off. That is not a new policy — it is [D-025](#d-025--a-locked-screen-does-not-suspend-agent-observation-the-gap-is-published-not-papered-over)'s, decided for a lock on 2026-08-08 on the ground that the grant is the authority and not the human's gaze — and it is published **citing** D-025 rather than beside it, so two surfaces cannot read the pair as unrelated oversights.
- **And the sharper half, which #223 did not see: a blank halts every agent in the session.** CRTC disabled → no vblank → `on_vblank` never runs → `session::emit_presented` is never called → no `frame_done` is discharged → every paced client stops painting, and the agent is served the pre-blank frame indefinitely with no staleness signal and no refusal. `emit_presented` has exactly one bare-metal call site, inside `on_vblank`, pinned by a source-inspecting test, because `redraw` answers `Scheduled` unconditionally. **D-030(6) already published this for a VT switch and called it *"worse than a stall"*; blanking makes it routine and timer-driven** on an agent-first display server rather than something a human causes by leaving. This may change the owner's mind about a default timeout, and it is put in front of him rather than in a module comment.
- **Unblank is a full modeset**, so the return is not free and a modeset that fails leaves a dark panel with the session running — the wedge the runbook exists for, now reachable from an idle timer rather than only from a VT switch. Two mitigations are structural rather than documentary: the opaque cover is composited *before* DPMS is asked for, so a failed blank degrades to a black screen rather than to the human's last screenful; and the input consume is bounded (decision 3).
- **The backlight alternative was examined and refused, and the trade is recorded so it is not rediscovered.** Writing `/sys/class/backlight` keeps the CRTC active, so vblanks continue, the frame clock never stops and unblank is one sysfs write with no modeset risk. It is refused because it puts a **second** display-power interface inside the TCB, does nothing for external displays, saves almost no power, and is an interface D-030 already names as one DRM master does not gate.
- **TCB growth for zero differentiator**, exactly as #223 predicted: an idle state machine, a cover surface, an extra flip-gating term, a third `PromptVisibility` variant, an activity clock lifted out of the lock, and a wider invariant keysym table — all inside the trusted core. ### D-034 — Losing the seat is a configurable lock policy, with D-030(2)'s answer as the default; and `LockCause` gains the third variant that entry declined

**Status:** accepted (2026-08-11) — issue #246, workstream [WS-E](14-workstream-session-mode.md). **Discharges the lock-on-*switch* half of [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only)'s standing deferral** and the configuration surface [D-030(2)](#d-030--the-trusted-band-asserts-only-about-the-screen-this-core-is-driving-and-the-session-colour-is-never-re-minted-a-paused-seat-raises-no-prompt-it-could-record-as-shown) filed as its own issue; **revisits and reverses D-030(2)'s refusal of a third `LockCause`**, which that entry asked to have argued rather than skipped. The lock-on-*blank* half stands deferred, untouched: D-033(1) is the owner's non-coupling decision and nothing here couples them. **No decision in this entry is the owner's** — his decision is the default, and the default is what this entry is built to preserve.

**Decision 1: `--lock-on-seat-change immediate|idle|never`, `--drm` only, defaulting to `never`.**

D-030(2) is an owner decision and it stays the shipped behaviour of every session that does not name the flag: the idle clock freezes for the absence and the countdown restarts on return. What changes is that it is now *chosen* rather than *the only thing available* — which was the whole complaint in #246, filed against the entry's own closing sentence. The default is asserted from both sides, because a configuration surface can weaken a default two ways: `a_seat_taken_away_stops_the_idle_clock_and_returning_restarts_it` never names a policy and pins the unnamed path, and `naming_the_default_seat_policy_changes_nothing_about_the_session` pins that the named one is the same session.

**It is refused on `--nested` and `--headless`**, `--blank-idle`'s posture: neither backend ever receives a seat event, so the policy could only be stored and never read, and an operator who believed their nested session locked itself on alt-tab would have been told that by their own command line. Nested grows no seat handling to make the flag meaningful — a host compositor's focus loss is not a seat loss, the human can still see the window, and #246 says so in as many words.

**Decision 2: `LockCause` gains `SeatChange`, and D-030(2)'s reason for refusing it no longer holds.**

That entry refused a third cause because both existing ones are human-attributable — *"a gesture the human made, or a gesture they conspicuously did not make"* — and *"a seat event is neither"*. Two things have changed and only one of them is this issue. The first is **[D-031](#d-031--the-core-implements-ctrl-alt-fn-itself-because-refusing-to-is-what-trapped-the-human-d-030s-reasoning-stands-and-its-effect-was-its-own-opposite)**: on bare metal this core now implements `Ctrl-Alt-F<n>` itself, consumes it, and calls `change_vt` from a physical-origin chord match whose producer is private — so on the path that actually produces this cause, the pause *is* the acknowledgement of a gesture this core watched the human make. That is the first shape, not a third one. The second is that the policy is the operator's own: under `immediate` they have said in advance that leaving this screen is to be read as leaving.

**What is not claimed, and the card does not say:** that every pause is a chord. logind can deactivate a session for reasons this core never sees. So the card names the event and the policy — *"the seat went to another VT, and this session is set to lock when it does"* — rather than a gesture it cannot know happened, and the journal label is `seat`.

**Decision 3: under `idle` the absence is charged to the countdown as an offset on the one clock, and the raise lands on the human's return.**

#246 describes `idle` as *"what the code did before D-030, by accident rather than by choice"*. It is implemented as the same **outcome** and deliberately not the same **mechanism**, for two reasons that pull the same way.

The first is D-030(2)'s own objection to the inherited behaviour: it locked the session *during* the absence, at an instant no human could observe. Under this policy `LockScreen::tick` still returns early while the seat is gone; the absence is added to `seat_absence_carry` on the way back in, read before the shared record restamps the clock, and the ordinary idle raise fires on the first dispatch round after the human returns. The human comes back to a locked screen, which is what the policy promises, and nothing locks itself on a VT nobody is looking at.

**This whole mechanism rests on issue #257, and that dependency is stated because for one draft of this branch it was not met.** The charge is `now - last_activity`, so it is only ever non-zero if `now` is sampled *at the human's return*. The activate arm used to pass `DrmState::now`, the cell `route_physical_inputs` writes once per **input turn** — and a paused session sees no input turn, because the chord that switches back is delivered to whichever session is currently active. That cell was therefore, by construction, the same instant as `last_activity`: the charge was exactly **zero** on the only backend that can produce a seat event, so `idle` was `never` in production while `lock::gate`'s tests stayed green, because they drive the call with a fresh instant the backend never supplied. `session::note_seat_presence` (#257) samples the instant itself and takes **no `now` parameter at all**, so the stale stamp is no longer expressible; `self.now.get()` and a bare `set_seat_absent(` are both forbidden tokens in `handle_session_event`'s body. Same defect, same fix, one direction worse for the default: with the stale stamp `never`'s restart-on-return was assigning `t` over `t`, so an eight-hour absence with `--lock-idle` returned to a **locked** screen — the exact opposite of what this log and `limits.md` publish.

The second is [D-033(2)](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only): the activity clock is **one** clock with one writer, shared with the blank, and the blank needs the restamp-on-return this policy must not inherit. A second clock is exactly what WS-E.4.3 merged to prevent, so the policy is an offset on the one clock rather than a fork of it. The offset accumulates across repeated absences and is cleared by any physical event, at the same site that restamps the clock — a carry that survived a keystroke would lock the screen of a human demonstrably sitting at it.

**Decision 4: no policy lowers a lock that is already up, and that is not one of the three options.**

A VT switch must never be a way past a lock screen. `losing_the_seat_never_lowers_a_lock_that_is_already_up` now runs over all three policies, and also asserts that a seat event does not *rewrite* an existing lock's cause — a journal reader has to be able to tell an idle lock from a seat lock. `immediate` also raises at most once across any number of switches, so three departures are not three `session_locked` entries.

**What cannot be known here, and is therefore not claimed.** CI has no DRM device and no seat, `DrmState` needs a real `DrmDevice`, `LibSeatSession`, `GbmDevice` and `GlesRenderer`, and `handle_session_event` is unreachable from every test in this workspace — D-030's bound, unchanged. **So no test anywhere proves that a real VT switch reaches this policy.** What is proven is each half: the policy's behaviour against driven seat events in `lock::gate`'s own tests, the CLI's resolution in the parse tests, and the wiring between them by source shape in `the_bare_metal_backend_hands_the_lock_its_configured_seat_policy` — the same instrument, for the same reason, this file already uses for the pause arm. The honest status is **landed in the tree, unproven on hardware**. The bring-up rung this owes is now **written** — [`docs/drm-bringup.md`](../drm-bringup.md) step 12a, `immediate` and `idle` across a real VT switch, with the record block left empty — and **written is not run**: nobody has executed it, its rows are inferred, and this entry's status does not improve until the owner pastes dates into that block.

### D-036 — The screenshot encode moves to a worker thread that owns the directory descriptor; the encoder itself is left alone

**Status:** accepted (2026-08-11) — issue [#240](https://github.com/vitrin-os/vitrin-os/issues/240), workstream [WS-E](14-workstream-session-mode.md). Found in review of WS-E.2.4 (#216), measured on hardware, decided here.
>
> **Renumbered from D-034 to D-036 on 2026-08-13.** It was filed as a second
> D-034, colliding with the lock-policy entry above it. Nothing cited this one —
> every `D-034` reference in the tree (`backend/drm.rs`, the WS-E workstream doc,
> two anchors in this file) resolves to the lock policy — so the collision is
> resolved by moving this entry rather than by touching any reference.

**The problem, measured rather than estimated.** `ScreenshotDir::write` and the PNG encode both ran synchronously inside `route_physical_turn`'s gesture drain, so one press blocked compositing for the whole encode: **71.7 ms** in a release build for one 2560x1600 frame into a 12.3 MB PNG — about seventeen dropped frames at 240 Hz, on every press. It was never a correctness problem. It was plainly visible to the human who pressed the key.

**Decision: option 1 of the issue — move the encode off the compositor thread — and *not* option 2.** `crates/vitrin-png` keeps its stored-block DEFLATE, its bitwise CRC-32 and its per-byte Adler-32. Those are the reason the encode is slow and they are also the reason a ~130-line encoder in the TCB is auditable; a 256-entry CRC table and a chunked Adler are cheap, but they are an optimisation of code that no longer runs anywhere a human can feel it. **No image codec enters any dependency class**, which the issue names as a criterion and `crates/vitrin-core/Cargo.toml` states twice.

**Why a thread in the TCB is acceptable here, stated as the issue demanded rather than assumed.** The frame that crosses the boundary is the human's screen, and the safety argument for it was "one place writes it, and that place holds no path". The change makes that *narrower*, not wider:

- **The audited descriptor moves to the worker and the compositor thread stops holding one.** `Kernel::screenshot_writer` can submit a frame and read back what happened to it; it no longer owns a `ScreenshotDir`. What that buys is TOCTOU and symlink resistance: every file is created relative to a descriptor opened `O_DIRECTORY|O_NOFOLLOW` and held for the session, `O_CREAT|O_EXCL|O_NOFOLLOW`, mode 600, so a same-uid app cannot redirect the write by planting an entry at a predictable name. **The first draft of this bullet claimed more than that and was wrong** ([#261](https://github.com/vitrin-os/vitrin-os/issues/261)): it said no thread in the process holds both a realm's pixels and a way to create a file in the operator's directory. `vitrind` is unsandboxed and single-uid — D9 of `limits.md`: no namespaces, no seccomp, no Landlock — so every thread can already name any path and create a file under it. A thread boundary does not remove ambient filesystem authority; only a sandbox would, and there is none. Caught before this entry was ever published, which is the only reason it is corrected in place rather than superseded.
- **Nothing new can reach the encoder.** The worker's only input is a private `EncodeJob` whose only producer is `ScreenshotWriter::submit`, which still takes a `ScreenshotGesture` that only the physical-origin chord matcher mints; `HumanGesture` is still minted inside `capture_to_file`, one thread over. `the_encoder_has_one_call_site_and_it_is_inside_the_worker` scans the crate's sources for it, so a second call — "it is only one frame, encode it here" — fails to build a green suite rather than silently reintroducing the stall.
- **The bytes are a copy of something the process already keeps.** The same realm view sits in `Runtime::view_cache` and is sealed into a memfd for any `observe` holder. A `Vec<u8>` down a channel carries no descriptor, no `Rc` and no handle.
- **The journal stays single-threaded.** The worker reports an outcome; `session::journal_screenshot_outcomes` writes the entry on the compositor thread. Giving a second thread the flight recorder would have been a far larger change to the TCB than moving an encode, for nothing.

**What a pending encode does at the two moments the issue asked about.** The **session ending** waits for it: `Runtime::into_recorder` — the one funnel every backend leaves through — calls `ScreenshotWriter::finish`, which stops accepting work, waits up to five seconds for what it already accepted, and journals each result, so a screenshot taken a moment before `SIGTERM` lands on disk *and* in the log of its own run. Past that deadline the process exits and the file may be truncated, journalled `writer_timeout`: a bounded wait, because a filesystem that has stopped answering must not turn "the session ended" into "the session hangs". The **dead-man switch does not cancel it**, deliberately and consistently with #216: the off-switch destroys authority, and a human photographing their own screen is not authority — which is also why a hold does not suppress the chord in the first place.

**The bound covers the thread, not only its outcomes — and the first draft of this change did not.** Review of the branch caught it by experiment rather than by argument: a worker patched to take 20 s made `finish` return after 20.008 s, having journalled `writer_timeout` at the 5 s mark and then blocked for another fifteen inside a plain `worker.join()`. Every sentence above was true of the timed drain and false of the call as a whole, so on a genuinely hung mount `vitrind` would not have exited on `SIGTERM` at all — the exact outcome this paragraph promises it prevents, in the TCB's shutdown funnel. `screenshot::join_before` now polls `JoinHandle::is_finished` against the same deadline and **detaches** rather than joining when it expires; `a_wedged_worker_does_not_hold_the_session_open` holds the property against a real wedged thread with the deadline shortened, and goes red against a plain join. `writer_timeout` accordingly means *"no outcome before the deadline"*, not *"no file"*: a detached worker may yet finish its write, and the exiting process has no way to learn that it did.

**What it costs, with the new number measured in the same way as the old one.**

- **A press still costs the compositor 4.2 ms** at 2560x1600 — the copy of the frame out of the capture cache — against 73.9 ms to encode the same frame in the same release build. One frame at 240 Hz instead of seventeen. **Both are CPU measurements on the development machine, not a measurement of a session driving a panel**; what a screenshot does to a bare-metal session's frame timing is a `docs/drm-bringup.md` rung and CI cannot stand in for it.
- **A bounded queue means a press can be refused.** Two frames may wait behind the one being encoded; a press past that is journalled `encoder_busy` and writes nothing. Each job is a whole frame — 16 MB on the measured panel — so an unbounded queue is the compositor's memory spent on pictures nobody is waiting for.
- **`screenshot_written` lands a few milliseconds after the press** rather than inside the input round. Still exactly one entry per accepted gesture, still with the digest of the bytes on disk.
- **A second thread exists in the TCB**, but only when the operator passed `--screenshot-dir`. A default `vitrind` spawns none and is as single-threaded as it was.

**DEFERRED, explicitly:** **making the encoder itself faster** (a CRC table, a chunked Adler, fixed-Huffman DEFLATE). It is now off the frame path, so it buys disk space and worker CPU rather than frames; fixed-Huffman in particular is materially more code in the TCB and would want its own justification. **Reopens on:** a session where the worker's own cost matters — a screenshot burst, or a panel large enough that 12 MB per press is the constraint. **Recycling the frame buffer** between presses would cut the remaining 4.2 ms to the memcpy alone, at the cost of retaining a frame of the human's screen in a pool between presses; not taken here because the retention wants its own argument and one frame at 240 Hz does not force it.

### D-035 — The capture cache skips a realm whose scene has not changed; gating it on consumers stays refused

**Status:** accepted (2026-08-11) — issue [#252](https://github.com/vitrin-os/vitrin-os/issues/252), workstream [WS-E](14-workstream-session-mode.md). The third of the three findings the second `docs/drm-bringup.md` run left open.

**The problem.** `session::refresh_view_cache` composed **every live realm's** full view on **every dirty round**, where "live" is `realm.server.is_some()` and nothing else. It was not keyed on whether anything would read the result, and `dirty` is one session-wide flag — so a session with no agent connected, no `--capture-dump` and no `--screenshot-dir` allocated, filled and freed a 16.4 MB buffer per live realm per dirty round that nothing ever read, and one realm's commit paid for its siblings' composites too. That is waste, not incorrectness: the bytes composed are exactly the bytes a reader would be served.

**Decision: option 2 of the issue — skip a realm whose `(Scene::generation, view size)` is the one its cached entry already carries. Option 1 is NOT taken and is not routed around.** `backend/winit.rs`'s `view_rgba` refuses gating the refresh on a live `observe` grant in the source, and [D-031](#d-031--the-core-implements-ctrl-alt-fn-itself-because-refusing-to-is-what-trapped-the-human-d-030s-reasoning-stands-and-its-effect-was-its-own-opposite) records the refusal as a decision. That argument is about correctness and it outranks the CPU: a consumer-gated cache that refreshes one round late serves a frame composed before the grant existed, and `no_surface` is documented as *"never a stale frame"*. **This entry does not reverse it.** The cache is still refreshed for every live realm on every dirty round, with no knowledge of grants, `--capture-dump` or `--screenshot-dir` anywhere in it.

**Why the skip is sound, in two sentences that were already written.** `Scene::compose` is documented pure — *"same scene + same size = same bytes"* — and `Scene::generation` is documented to change *"exactly when composed output may have changed (for a fixed view size)"*. `ViewKey` is that parenthesis made into a value, so a skipped entry is byte-for-byte what a recompose would have produced and **no reader can tell**. That is the whole difference from the refused option: freshness is untouched, only the arithmetic is skipped.

**The enumeration was diffed rather than assumed**, because this repo's recurring defect is an enumeration missing one member — the overlay reconciliation that forgot the consent card, and the texture cache key that forgot the lock (#243). `ViewKey` deliberately contains none of `compose_human_visible`'s other parameters (the consent surface, the lock cover, the blank cover, the status strip, the attention flag), and that is not an omission of the same kind: `Presenter::view_rgba` serves the **realm view**, which is upstream of the output-stage fork where every one of those joins. If any of them ever reached this cache the bug would be that it reached it. The one backend not answering from `Scene::compose` is headless, which reads back its retained **view** framebuffer for the bound realm — pinned by its own tests as a byte-for-byte identity of `Scene::compose`, and written on the same redraw the key is taken after.

**The key is stored in the same value as the bytes** (`CachedView`), not in a second map. #252 names the risk exactly: a per-realm freshness fact beside the session-wide `dirty` flag is a second definition of "has this realm changed", and two that can disagree is the shape of #243. One insert writes both, one removal drops both, and there is no second map to forget.

**What it costs, and what it does not buy.**

- **It buys nothing for a single-realm session whose app is painting** — the runbook's own configuration. The generation moves every commit, so the composite happens exactly as often as before. What it removes is every composite of a realm that is *not* moving: idle siblings, a session at rest, and the N-1 realms a sibling's commit used to charge.
- **`--capture-dump` follows the compose, not the round.** A skipped realm's dump file already holds those exact bytes, so the M1.3 fidelity gate's ground truth is unchanged; an unmoving realm simply stops rewriting a 16 MB file every dirty round.
- **A `kind=dmabuf` commit bumps no generation** (`crate::shim` returns before `commit_with_damage`), so such a realm is skipped — and served the same bytes it was already being served, because `apply_dmabuf` never touches the CPU scene. This neither creates nor worsens [#253](https://github.com/vitrin-os/vitrin-os/issues/253); the shipped shim never sends one.
- **A resize invalidates every entry**, because `apply_output_resize` deliberately bumps `layout_generation` and *not* `Scene::generation`. A key of generation alone would have served every later capture at the old geometry — the exact missing-member failure the paragraph above is about, one member closer to home.

**What is NOT claimed, and cannot be from here.** #252 asks for a CPU measurement before and after, in a release build on the 2560x1600@240 panel, beside the existing 32.9% figure in `docs/drm-bringup.md`. **That criterion is not met by this entry and CI cannot meet it**: runners have no DRM device, no seat and no GPU. What is held here is the count — `a_realm_whose_scene_did_not_change_is_not_recomposed` pins `Presenter::view_rgba` calls per `post_dispatch` round for a stated realm count and pairs every skip with the bytes a recompose would have produced — which is exactly the criterion the issue marks as provable in CI. The measurement is a third execution of the runbook, by the owner, and **#252 stays open until he pastes the number in**.

**Options 3 and 4, which the issue lists as composable.** Option 3's cheaper composite is **partly already landed** — [D-031](#d-031--the-core-implements-ctrl-alt-fn-itself-because-refusing-to-is-what-trapped-the-human-d-030s-reasoning-stands-and-its-effect-was-its-own-opposite) took `Scene::compose`'s whole-view matte fill — and its remaining half (composing into the existing cache entry rather than allocating a fresh `Vec` each round) changes `Presenter::view_rgba`'s signature across four implementations and is **deferred**, not refused. **Reopens on:** the runbook measurement showing the allocation rather than the composite is what costs. Option 4 is taken *as well*: `docs/book/src/limits.md` published only the hidden-realm half of this cost and is rewritten in the same change to say what does and does not happen with no agent connected.

### D-037 — The realm's namespaces are built by a helper that execs first and unshares second; the core proves the confinement from outside before it commits; and the measured ceiling and the selected policy are two vocabularies whose bottoms may never share a word

**Status:** accepted (2026-08-13) — executes [D-020](#d-020--the-realm-boundary-is-a-namespace-boundary-intra-user-by-default-in-namespace-uidgid-and-a-residue-that-lives-outside-every-realm)(1)(4)(6) in P2.6.2, issue [#186](https://github.com/vitrin-os/vitrin-os/issues/186). Corrects the P2.6.2 plan row's implied ordering. Supersedes `spawn.rs`'s D9 section for the `--isolation=default` path only.

**1. The helper `execve`s first and unshares itself; the core does not clone into namespaces.** The plan row's phrasing — "clone the realm child with `CLONE_NEWUSER|…` and exec a new core-owned `vitrin-realm-init`" — is not implementable while the core keeps `std::process::Command`, and the reason is a **deadlock**, not a preference: D-020(1) requires the parent to write the maps while the child blocks on a sync pipe, but std's fork path has the parent already blocked reading its exec-report pipe until EOF-on-`execve`. Parent waits for exec; child waits for maps.

The inversion is the **stronger** posture, which is why it is recorded rather than treated as an implementation detail. `execve` recomputes capabilities, and the root special case fires only when the process's uid is 0 *in its own user namespace*. Unsharing before the exec would therefore force the map to be `0 <euid> 1` — handing the confined app `CAP_SYS_ADMIN` in its own namespace, from which it could bind-mount over its own confinement. Unsharing after means an **identity map and zero capabilities**. It also deletes a window in which a not-yet-`exec`'d child holds a copy-on-write image of the core's address space — grant table, principal keys — readable through `/proc/<pid>/mem` by any same-uid process.

**2. A supervisor process is forced, and it closes a published residual.** `unshare(CLONE_NEWPID)` never moves the caller; it sets `pid_ns_for_children`, so the next `fork` produces PID 1. **Measured on the target machine 2026-08-13:** after the unshare the child's own `ns/pid` is byte-identical to the core's. So `vitrin-realm-init` forks — the supervisor stays in the host PID namespace and is the process the core's `Child` names, and the PID-1 child builds the mount table and `execve`s the shim. With `PR_SET_PDEATHSIG` (measured to survive that `execve`) this closes `lifecycle.rs`'s residual, where rung 3 killed the shim and left its app reparented to init.

**3. Every confinement claim the journal makes is a fact the *parent* read from the kernel.** This is what licenses clause 1: the core does not trust a helper that confines itself. **Measured 2026-08-13:** the core can read `/proc/<pid>/ns/*` and `stat` `/proc/<pid>/root` for both the supervisor and the PID-1 child across the realm's user namespace. The spawn is **refused** when those cannot be read. The invariant, verbatim: *`applied` is computed from what the kernel says about the child, never from the flag that was requested.* Anything not sourceable that way is labelled `child-asserted`.

**4. `--isolation=default | off`; `none` is retired before it ships.** Of the two colliding tokens, the selector's is the one no earlier decision fixed — `Tier`'s renderings carry a stability contract, because changing a string there changes every committed matrix cell. The rule is **not** "no shared token": when D-020(3)'s per-uid upgrade becomes selectable, `--isolation=per-uid` may share that word, because there the relation is required equality. The rule is that **the tier's bottom may never be a selector value**, because `Tier::None` is also what an *unmeasured* probe yields — so `none` would conflate "the operator chose no confinement" with "nothing was measurable", which is exactly the silent degradation D-020(6) forbids.

**5. `setgroups(0, NULL)` is impossible here, and the consequence is published rather than mitigated.** D-020(1) is silent on supplementary groups; the design that preceded this entry assumed they could be dropped in the window after `unshare`. They cannot. `userns_may_setgroups` requires a non-empty `gid_map`, and `new_idmap_permitted` will not admit an unprivileged single-id map until `setgroups=deny` has cleared the flag it reads. **The windows are disjoint; measured `EPERM` in both orderings.** So a realm retains the invoking user's supplementary groups — `video`, `render`, `input`, `docker` — as kgids, because `setgroups=deny` blocks the *call* and drops nothing. The count is journaled per spawn as `supplementary_groups_retained`, and the mount table is consequently the **only** barrier between a realm and any device those groups would open. Published on `limits.md` and `SECURITY.md`, not left to be discovered.

**6. The preflight probes the mount, not just the namespace — because measuring only the `unshare` let it certify a machine that could not confine.** P2.6.1's probes each measured `unshare(CLONE_NEWUSER | <flag>)` and stopped there, which honored the letter of the module's rule 1 (*attempt, never infer*) and missed its point: `vitrin-realm-init`'s request is `unshare` **and then** `mount(NULL, "/", NULL, MS_REC|MS_PRIVATE, NULL)`, and probing only the first half infers the second. **Measured on a GitHub `ubuntu-latest` runner 2026-08-13:** the unshare returns 0, the preflight reports the machine fit, `vitrind` boots — and every realm spawn is then refused because that first mount returns `EPERM`. The refusal was correct and came from clause 3's post-spawn verification; the point is that **the gate written to catch exactly that machine passed it**, so what actually held the confinement claim was the verification, not the preflight. A `mount.in_userns` row now measures the second half in the same forked child (already inside its own mount namespace, so the mount is unobservable outside it and dies with the `_exit`), `Mechanism::Namespaces` is both halves and reports whichever said no, and the matrix schema is **2** — a version-1 matrix is not merely missing a row, its `tier` cell was computed without it and can read a rung too high, so it must be recollected rather than patched.

**What this costs, stated unmitigated.** A second trusted binary in the TCB, and two spawn paths inside one file — which is exactly how a confinement claim rots, held apart only by clause 3's verification. The GPU render node is bound read-write, carrying an ioctl surface and cross-realm GPU-memory side channels that nothing here addresses; read-only was rejected because it disables the node rather than restricting it. And **R2.9 is not retired by this entry**: the refusal path will not fire on the maintainer's machine, which measures `apparmor_restrict_unprivileged_userns=unset`, so the maintainer's box alone could never say whether "refuse to start" is the edge case or the common case — tracked as issue [#281](https://github.com/vitrin-os/vitrin-os/issues/281). **One data point has since arrived, and it is not the reassuring one:** on a stock GitHub `ubuntu-latest` image (kernel `6.17.0-1020-azure`) no realm can start at all — see clause 6. That is one mainstream CI image, not a distribution survey, but **the cause is now measured rather than inferred.** The runner reports `apparmor_restrict_unprivileged_userns=1` with the module enabled, and the matrix it produces is `ns.all=available`, `mount.in_userns=restricted-by-policy(errno=13)`, `tier=none` — the AppArmor restriction permits the unshare and denies the capabilities inside it, exactly the signature clause 6 predicted. The same code before clause 6 rendered `tier=per-uid` on that machine. CI records the knobs, the LSM context and `--print-isolation` on every integration run *before* it changes anything, so #281's matrix collects evidence instead of inference; the integration job then takes the printed remedy (`sysctl kernel.apparmor_restrict_unprivileged_userns=0`) in order to exercise the confinement path at all, which means **nothing after that step describes a default Ubuntu install**. What can be said today is that refuse-to-start is **not** an edge case: it is what a stock Ubuntu 24.04 machine does.

### D-038 — The desktop shell becomes a realm that draws: one realm holding both a shim surface and a principal connection, with the status rows moving below the trust line and the socket question routed to the confinement work rather than guessed

**Status:** accepted (2026-08-17) — issue [#304](https://github.com/vitrin-os/vitrin-os/issues/304), workstream [WS-E](14-workstream-session-mode.md). **Adopts the shape #211's decision 2 named and nothing built**, which `docs/book/src/limits.md`'s `principal-cannot-draw` bullet publishes verbatim as *"the shell running **as a realm**, drawing through its own shim like any other app while holding the layout verbs through the ordinary grant path — which needs no new protocol, but does need that realm to reach the core socket, and that is a confinement question nobody has answered"*. **Supersedes [D-026](#d-026--the-top-strip-is-designed-as-one-surface-the-band-alone-then-the-status-strip-beside-it-and-the-apps-rows-are-still-overdrawn) as the session's status surface** for any session that runs a shell realm, and leaves D-026(1) — nothing is ever composited into the band — untouched and load-bearing. Holds [D-021](#d-021--session-mode-is-scheduled-as-a-maintainer-dogfooding-workstream-ws-e-and-that-is-not-the-horizon-item)(4)'s *"the shell stays a client"* exactly as written. **Decisions 1 and 2 are the owner's**, taken 2026-08-17 and recorded rather than derived; everything after them is derivation and is marked where it is not.

> **NUMBERING, AND A SPLIT THIS FILE STILL OWES.** D-038 through D-041 are the next four free numbers: the accepted set is D-001…D-037 with no gaps. **This entry does not touch the live D-031 collision** — two entries above are both numbered D-031, [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only) consumed the D-033 renumbering remedy all three notices promised, and the ids are cited from landed code — so nothing here should be read as fixing it. Separately: this file's own preamble says it *"stays a single file until it exceeds ~25 accepted entries … at which point it splits into `docs/plan/adr/` (see D-013)"*. That threshold was passed long ago and these four take the count to 41. The split is **not** done here, because doing it inside a shell decision would rewrite every anchor in the tree in a commit about window management; it is flagged so the next reader knows it is owed rather than forgotten.

**Decision 1, the owner's: one realm holds both halves — a shim surface, so it draws like any other app, and a principal connection, so it holds `layout_focus`, `layout_arrange` and `realm_launch` through the ordinary grant path.**

The shipped switcher is a line-oriented host-side program for a reason this repo already publishes: `vitrin_view` is capture-only, there is no principal-facing surface interface in the IDL, and so **no client can put a pixel on the output**. The answer taken here is *not* to give principals a surface. That would be a new interface on the authority side of the wire, and it would make every connected client a potential painter of the human's screen — a far larger change to the TCB's surface than a shell needs. Instead the shell is an *app* and a *principal* at once, over two connections, and the core is not asked to know they are the same program.

**That last clause is the security content of the decision and it is stated before any of its benefits.** The core cannot verify the pairing. *"The thing drawing the bar is the thing holding arrange"* is a deployment fact, not an invariant, and no test in this workspace will ever assert it: grants key on a `PrincipalIdentity` bound at `hello`, a shim surface carries no principal identity at all, and inventing a binding between them would be inventing exactly the realm↔principal mapping [D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing)'s cost note records as *"does not exist because a realm and a principal connection have no binding"*. The alternative — minting that binding so the core can require it — was available and is **not taken here**, because *"the principal that draws in the bound realm"* is a rule about which client owns the session's chrome, and choosing that rule is window-management policy the core deliberately does not have (PRD §5.1). What the human gets instead is the ordinary consent card, naming a principal and a realm, for a shell like for anything else.

**Decision 2, the owner's: the core composites that realm into the rows `--status` occupies below the trusted band, and stops drawing the status strip itself.** The status rows go from core-drawn to client-drawn — below the trust line — and the owner accepted that consequence when the decision was put to him in those words.

**The premise underneath decision 2 is wrong in the tree, and correcting it is the first thing this entry owes.** The decision was stated as compositing the shell into *"the rows `vitrind --status` already reserves"*. **No rows are reserved.** `crates/vitrin-core/src/status/mod.rs` carries a section headed *"# The realm view is NOT inset, and that is an unmet part of issue #215"*, and it says in as many words that the app *"is not configured smaller"* and the strip therefore **overdraws** `DEFAULT_HEIGHT` = 20 rows of client content at `STRIP_TOP = TRUST_BAND_HEIGHT`, *"the way the band already overdraws 8"*. D-026's first cost bullet publishes the same fact, and so does `limits.md`: *"Every app loses rows while the strip is on."*

So there are no rows to hand a shell realm. There are rows the core takes from the app by painting over them, and the distinction is not pedantry — **it converts a deferred nicety into a prerequisite of this decision.** A core-drawn strip could get away with no inset because the only geometry in play was the strip's own height and the thing it overdrew was pixels the app had already committed. A *client* drawn there has a `configure` size of its own, and the app realm below it must be told a smaller one, or two clients will lay out for the same rows and the shim will size a view that does not exist. That is the `ViewGeometry` thread #215 asked for and **closed without** — one usable-view value reaching `crate::scene::layout::place`, which is asked by `Scene::compose`, by the router's `surface_local` and by `crate::dmabuf::human_visible_frame`, *"three paths that receive the view size from three different places and share no carrier for a second number"* — plus the `configure` size the shim is told. **This entry does not build it, and the judgement `crates/vitrin-core/src/status/mod.rs:120-121` states as *"a half-done inset — one path reserving rows the others do not — is strictly worse than none"*, and D-026's cost bullet at `20-decision-log.md:348` as *"a half-done version, one path reserving rows the others do not, is strictly worse than none"*, now guards a shell rather than a clock.** It is the single largest piece of unbuilt work this decision implies and it was not in the owner's statement of it.

**What moves below the trust line, and the published sentence it falsifies.** `limits.md` today says of the strip: *"The strip is unspoofable in pixels but is not self-authenticating … an app **can** paint a convincing fake strip one row lower."* After this decision the strip below the line **is** a client's pixels, so the forgery stops being a forgery: the real strip and the fake are the same category of thing, and the only distinction left is which client the core placed there. The rule *"trusted content is everything above the coloured line"* survives intact and gets **simpler** to state, which is the honest upside — D-026's complaint that the indicator story became *"three rules where it was one"* is partly paid back. What it costs is that the clock, the battery and the focused realm's name become facts a client asserts and a human has no way to check. The band still proves itself and still cannot be drawn into (D-026(1)); the consent card, the lock cover, the attention marker and the dead-man indicator are unaffected, because they composite above everything a realm can reach.

**Drawing the numbers is not the same as reading them, and the reading does not move.** The battery comes from `/sys/class/power_supply` on a 30 s cadence, bounded to one fixed root, 16 entries and 16–32 bytes per attribute (`crates/vitrin-core/src/status/battery.rs`). A confined realm cannot read it: [D-020](#d-020--the-realm-boundary-is-a-namespace-boundary-intra-user-by-default-in-namespace-uidgid-and-a-residue-that-lives-outside-every-realm)'s realm boundary and [D-037](#d-037--the-realms-namespaces-are-built-by-a-helper-that-execs-first-and-unshares-second-the-core-proves-the-confinement-from-outside-before-it-commits-and-the-measured-ceiling-and-the-selected-policy-are-two-vocabularies-whose-bottoms-may-never-share-a-word)(5)'s mount table are exactly what stands between a realm and the host's device tree, and a shell realm is a realm. So the numbers arrive one of two ways: the core keeps the sampler and ships them over the wire — a paired IDL and prose edit on `track:protocol`, for a clock — or the shell realm's mount table gets a hole into `/sys`, which is a confinement widening decided for cosmetics. **Neither is chosen here**, and the choice is named because the owner's decision moved the *drawing* and said nothing about the *reading*. D-026's *"recurring filesystem read inside the TCB"* cost is therefore reopened as an open question rather than closed by this entry.

**The unanswered question is routed, not guessed: may a realm reach the core's principal socket, and under what authority?** The owner's call is that it goes through E2.6's confinement work — [#185](https://github.com/vitrin-os/vitrin-os/issues/185) (P2.6.1, decide Q11 and land the isolation preflight) and [#187](https://github.com/vitrin-os/vitrin-os/issues/187) (P2.6.3, the Landlock ruleset and the ABI ladder) — and is not answered ahead of it. **Q11 is not reopened, and this entry must not be cited as reopening it:** Part B records Q11 **CLOSED by D-020** on 2026-08-06, and the question here is not *where the principal boundary sits* but whether the realm boundary D-020 drew has a hole in it shaped like this socket, and whether that hole is a grant, a mount or a bind. Guessing it inside a shell issue is how a confinement claim rots — D-037's closing sentence names *"two spawn paths inside one file"* as exactly that shape, and a socket reachable from inside a realm because a shell needed it would be a third.

**Sequencing, the owner's, and deliberately not a clause of this decision:** #185 and #187 land before the shell-as-realm work starts. It is recorded here so a reader does not schedule it from this entry — [`docs/plan/`](00-roadmap.md) is this repo's sequencing authority and the tracker is not.

**`zwlr_layer_shell_v1` is NOT taken, and the waybar class stays unable to map.** waybar was measured rather than assumed — it connects, binds six globals and never maps a surface. rofi is the same class by linkage; **wofi is not installed on the target machine and its cell was never filled** (`docs/plan/14-workstream-session-mode.md`:514-516), so this entry does not count it as measured, and neither should any surface that cites this one. The shell realm draws because the **core places it**, not because a client asked for a layer, which is precisely why this decision needs no new protocol. Why layer-shell is deferred rather than refused, and what it shares with tiling, is [D-040](#d-040--layer-shell-and-tiling-are-one-deferral-rather-than-two-because-both-need-a-scene-that-holds-more-than-one-client-surface-x11-stays-e32s-and-multi-output-stays-behind-the-m4-gate).

**What this decision costs.**

- **The session's most-read chrome becomes untrusted pixels.** Stated above and repeated here because it is the entry's weight: a human who reads a client-drawn clock and treats it as the system's clock has been trained by the old strip to do so. A published limit that changes meaning is worse than a new one, and `limits.md`'s strip bullets have to be rewritten rather than amended.
- **A shell crash now loses the status surface as well as window management.** D-021's *"a shell crash loses window management"* cost, and `limits.md`'s `shell-crash-loses-re-aim` bullet, both get wider: after this the human also loses the clock, the battery and the name of the realm they are looking at, at the exact moment they are trying to work out what happened. There is still no core-side fallback and this entry does not add one.
- **The pairing is unverifiable, forever.** See decision 1. A malicious or merely broken client holding `layout_arrange` while a different client draws the bar is a configuration the core cannot detect and will not refuse.
- **The unmet inset becomes blocking work this entry does not do, and nothing tracks it.** #215 shipped the strip and **closed**; the view inset it also asked for is unimplemented, and there is **no open issue** carrying it — so it is a `ViewGeometry` refactor across three paths plus the shim's `configure` size, which D-026 already declined to bolt onto a status strip, which is no more welcome bolted onto a shell, and which no tracker row will remind anyone about. That is worse than a dependency, and it is stated as such rather than dressed up as one.
- **It widens what a realm is for.** Every realm was an application to confine; one realm is now session furniture the core composites in a privileged position. Nothing in D-020 or D-037 distinguishes the two, so the confinement applied to a shell realm is the confinement applied to a browser, which is either an accident waiting to be discovered or a property to assert deliberately — and this entry does not assert it.
- **The status read may end up on the wire for a cosmetic.** See above; a `track:protocol` edit whose justification is a battery percentage is a bad trade that has to be made explicitly if it is made.
- **[D-025](#d-025--a-locked-screen-does-not-suspend-agent-observation-the-gap-is-published-not-papered-over) is untouched and must stay untouched.** The lock cover composites above everything a realm draws, so a shell realm does not paint over a lock, and nothing here changes that. D-026(2) put the strip *over* the lock cover; the composite reconciliation in `crates/vitrin-core/src/backend/mod.rs:221-236` reversed it and accepted the cost in as many words — *"an opaque lock cover now hides the clock, so 'the strip is always there' gains the exception 'except behind a lock'"*. So the core's strip does **not** survive a lock today, a shell realm's pixels must not either, and the ordering that guarantees it is precisely the thing this decision changes. Whoever builds this must re-assert that ordering as a test rather than inherit it.

**What cannot be known here, and is therefore not claimed.** **Nothing in this entry is built.** There is no code, no closed issue, no measurement and no hardware run behind any sentence above; it is a decision about work not yet done, and the numbers it will owe do not exist yet. When it is built, the halves CI can hold are the least interesting ones: that a shell realm's surface composites where the strip used to is a golden-image comparison, and headless is the only backend CI runs (D-019(4)); that the drawing client and the arranging principal are the same program is **not expressible as a test at all**; and that a human correctly stops trusting a clock that moved one row's worth of meaning is not a property of software. The honest status of this entry is **decided, unbuilt, and gated on a confinement question nobody has answered.**

### D-039 — Global hotkeys are served as named actions the core resolves, never as keystrokes it forwards; the attention key's one bit becomes an operator-configured chord table, and no verb for observing the human's input is designed

**Status:** accepted (2026-08-17) — issue [#305](https://github.com/vitrin-os/vitrin-os/issues/305), workstream [WS-E](14-workstream-session-mode.md). **Extends [D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing)'s attention key from one bit to a table**, which is the growth D-023's own cost note predicted in writing. **Falsifies `docs/book/src/limits.md`'s published sentence** that *"'Super+Tab switches windows' is not a missing feature"* — in its first half only, and the second half is accepted rather than argued away. Does **not** touch `vitrin_principal.attention`, whose *"NO ARGUMENTS, AND THAT IS PERMANENT"* holds. **Decisions 1 and 2 are the owner's**, taken 2026-08-17; the rest is derivation and is marked as such.

**Decision 1, the owner's: a global hotkey is served as a NAMED ACTION, never as a keystroke.** The core matches the chord, resolves it against an operator-configured table, and delivers an **action identifier** to the client that can act on it. It never forwards the human's keys to a principal.

**The shape refused here is the one every other system uses, and it already has a name in this tree.** `limits.md` says *"There is no `observe_input` verb and none is designed"*, and after this decision that sentence is still true — deliberately, not by omission. A client receiving the human's keystrokes would be reading the human's typing, which is the surveillance shape this project exists to make grantable-and-visible rather than ambient; it would need a verb bit, a consent card, and a prompt copy that honestly said *"this principal will see what you type"*, for a window switcher. It would also route the core's **own** chords through a client's field of view, or else make them invisible to it, and the dead-man switch is in that set. **Named actions cost the client expressiveness and buy the human the property that a hotkey grant reveals nothing about what they type.** That trade is the decision.

**Decision 2, the owner's: the core resolves the chord itself, using the xkbcommon it already has behind the off-by-default `session-keymap` feature.** No new dependency, no new parser, no second keymap: [D-028](#d-028--a-bare-metal-session-interprets-the-keyboard-inside-the-core-from-a-pre-compiled-keymap-file-and-key-pairing-moves-to-the-scancode) already put `xkb_state` in the core, fed from a pre-compiled keymap **file** the operator names, with `NO_DEFAULT_INCLUDES | NO_ENVIRONMENT_NAMES` so it reaches no search path.

**What follows from that, and it bounds where hotkeys exist at all.** `input::invariant_keysym` maps no letter and no digit — its own test asserts `KEY_A -> None` — so a chord naming a letter is resolvable **only** where a keymap is. That is a bare-metal `--features session-keymap` session; nested resolves letters from winit's already-interpreted `logical_key` by a different mechanism, and headless has no keyboard at all. D-028's cost note already records this as *"three paths"* and *"the two backends resolve keys by different mechanisms"*. **Derived here, not the owner's:** a table naming a chord this build or backend cannot resolve must be **refused at startup**, through the same `input::keysym_is_intakeable` check `deadman::Chord::parse` uses and for the identical fail-closed reason — the alternative is a hotkey configured, accepted, and silently never firing, which is the unreachable-guard-that-reads-as-live failure [D-030](#d-030--the-trusted-band-asserts-only-about-the-screen-this-core-is-driving-and-the-session-colour-is-never-re-minted-a-paused-seat-raises-no-prompt-it-could-record-as-shown)(4) refused once and [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only)(4) refused again.

**Decision 3: this is D-023's one bit becoming a table, and D-023 predicted this entry by name.** That entry's cost list says of `vitrin_principal`: *"It becomes the place session-level facts about the human arrive. That is defensible once; it is also the seam through which a future issue puts a second, less defensible fact there because there is now a precedent."* **This is that future issue.** Being named in advance is not a justification, so the case is made from scratch below rather than inherited.

**`attention` does not grow an argument, and structurally cannot.** The IDL is explicit — *"NO ARGUMENTS, AND THAT IS PERMANENT. A window length was considered and refused: signatures are immutable"* — so the action **cannot** ride on it, and nothing here proposes widening its meaning. The action arrives as a **new `since`-gated sibling message**, which is how every interface in this protocol grows and is the rule `vitrin_layout_arrange` states about itself: *"Growth arrives as since-gated sibling requests when the scene can honour them, exactly as every other interface grows, and never by changing set_fullscreen's meaning."* Per CLAUDE.md's protocol authoring rule that is a **paired** edit — `protocol/vitrin-v0.xml` plus the matching `docs/protocol/NN-*.md` page, validated with `xmllint --relaxng` — and because the gating deliverable is the wire edit, the issue is **`track:protocol`** even though the resolver is core code.

**What changes in character, stated because it is this entry's weakest point.** `attention` *"confers NOTHING"*; the IDL's own words are *"the human made a statement about their own input state"*, which *"withdraws a transient courtesy the server extends to a human's typing"*. A named action does not merely withdraw a courtesy — **it instructs**. It still confers no authority: the recipient must already hold `layout_focus` or `layout_arrange`, every use still meets the enforcement chokepoint, and every grant behind it was approved on a consent card naming a principal and a realm. But the IDL's sentence *"a client that provokes the press gains TIMING, never authority"* was written for a signal carrying no instruction and **must not be copy-pasted onto one that does**. Provocation is now worth more: a hostile realm printing *"press Super+h"* gets a **specific action fired at a specific moment** rather than a bare window it must race to fill. D-023 already conceded that provocation *"is not closed and cannot be"*; this widens the payoff without widening the defence, and that is the cost being accepted.

**The recipient can be structural here where `attention`'s could not — a real narrowing, and it does not close the hole. Derived, not the owner's.** The IDL says of `attention`: *"a server cannot know which of two layout holders the human meant, and choosing would be window-management policy."* That is true of `layout_focus`, which several principals may hold at once. It is **not** true of `layout_arrange`: [D-018](#d-018--layout-is-a-capability-grant-governed-arrangement-core-enforced-ordering)(4) and [D-022](#d-022--layout-enforcement-lands-early-for-the-nested-single-output-case-d-018s-deferral-is-discharged-and-its-unpurchasable-set-gains-a-fifth-member)(5) make it **at most one holder per output**, resolved `layout_held` at admission, precisely so the core never arbitrates. So an action delivered to the bound output's arrange holder has exactly one recipient by construction, with no choosing and no policy — the answer D-023 could not reach and the reason a table is more defensible than the bare bit it grows from. What it does **not** fix: an operator whose table names focus-shaped actions is back in the many-holder case, and the core must not silently pick one. Whichever way that is resolved is a decision this entry does not make.

**The core must not interpret the identifier. Derived, not the owner's, and it is the line that keeps PRD §5.1 intact.** If the core knows that some action means *the next window*, it has acquired a window-management vocabulary — the exiled policy arriving as an enum through the back door, one variant at a time. The core's entire share is *which chord carries which name*, which is keyboard configuration; what the name means is the holder's, exactly as `crates/vitrin-core/src/chord.rs` already puts it for the matcher it owns: *"This module knows about keysyms, modifier state and bindings; what a match **means** is the caller's."*

**Explicitly NOT taken, both of them the owner's refusals.**

- **An `observe_input` verb for principals.** It does not exist, is not designed, and this decision does not design it. Decision 1 is the whole argument.
- **Borrowing the dead-man switch's warrant.** D-023(3) fixed the general rule — *"a hold is for the irreversible and severe; a tap is for the cheap and reversible"* — and fixed its scope: *"it was never 'the core may own chords in general', and a third chord makes its own case from scratch."* An operator table is **not a third chord; it is an unbounded family of them**, so the warrant question is asked once about the family and answered narrowly: these are taps, for cheap and reversible acts, they live in `gate` and never in `observe`, they are stacked **inside** both the consent grab and the dead-man hook so neither can be delayed by them, and their vocabulary is checked disjoint from the existing chords at startup rather than by assertion — D-024's posture for the clipboard chords, applied to a set whose size the operator chooses.

**The published sentence this falsifies, and the half of it that survives.** `limits.md` says: *"'Super+Tab switches windows' is not a missing feature: it would mean the core reserving a chord on behalf of whichever client asked first, which is window-management policy the core deliberately does not have."* **The first half is answered and the second is not.** Nothing here lets a *client* reserve a chord: the table is the operator's, in the operator's configuration, a client cannot ask for a binding, cannot learn one exists, and cannot discover that another principal consumed one. Nothing is reserved *on behalf of whichever client asked first*. But naming actions is closer to window-management policy than this core has been, and the second clause stands as a cost rather than a refutation. The sentence must be rewritten on `docs/book/src/limits.md` and on `docs/plan/14-workstream-session-mode.md`'s `principal-has-no-hotkey` block — both, per CLAUDE.md's `known-limit` rule to enumerate every surface — and rewritten to say what actually became true, not to disappear.

**What this decision costs.**

- **The core takes an operator-unbounded set of keys away from every confined app, with no pass-through.** D-023 paid this for Super and D-024 for Shift-Insert, each with an argument specific to that key (*"every desktop reserves it"*; *"the gesture the human loses inside a realm is the gesture they gain across realms"*). **A table has no such argument available**: the operator may bind anything, an app inside a realm has no way to ask for it back, and an operator who binds a chord an application needs has broken that application with no diagnostic anywhere. The startup check catches unresolvable chords; it cannot catch *inadvisable* ones.
- **`deadman.rs`'s sentence about how many chords the core owns is wrong for the third time in this workstream**, and `limits.md`'s enumeration of core-owned gestures stops being an enumeration at all — it becomes a fixed set plus whatever the operator added, which is a materially harder thing to publish honestly.
- **`crates/vitrin-core/src/chord.rs` must be consumed, not paralleled.** D-024's *"Also decided here"* clause makes that matcher general and binding on later consumers, *"which `deadman.rs`'s module docs spend hundreds of lines explaining the hazard of"*. A hotkey table that grew its own matcher would be a second place to get the gate wrong, in the stack the human's off-switch lives in.
- **Hotkeys exist only where a keymap does**, so the daily-driver experience diverges by backend: the maintainer's bare-metal session gets them and a nested demo does not. That is a real asymmetry between what this project shows people and what it runs.
- **A conditional refusal precedent gets wider.** D-023 recorded `preempted` becoming *"the protocol's **first** conditional refusal code"* and named the precedent itself as a cost. A table of operator-defined actions is that precedent being drawn on.
- **Every press and every delivery must be journaled**, or the session acquires a class of authority-adjacent event with no flight-recorder entry — the property D-023 held for the attention key and which is easier to lose across a table than across one bit.

**What cannot be known here, and is therefore not claimed.** **Nothing in this entry is built.** No wire message exists, no resolver exists, no table format exists, and no issue is closed by it. When it is built, CI still cannot press a key: `SeatInput::physical` is private by design, runners have no input device, and headless is the only backend CI runs (D-019(4)). The `physical-input-injector` channel can prove the **consequence** half — that a resolved action reaches the right holder and no other — exactly as D-023 and D-024 already accept for their chords, and it proves nothing about a human's finger on a real keyboard through a real keymap. That half is a manual runbook step, and it must be **written before it can be run**, which is D-033's own lesson from rungs that did not exist until someone wrote them. The honest status is **decided and unbuilt**; when it lands it will be **landed in the tree, unproven on hardware** until a rung says otherwise.

### D-040 — Layer-shell and tiling are one deferral rather than two, because both need a scene that holds more than one client surface; X11 stays E3.2's and multi-output stays behind the M4 gate

**Status:** accepted (2026-08-17) — issue [#307](https://github.com/vitrin-os/vitrin-os/issues/307), workstream [WS-E](14-workstream-session-mode.md). Records what four separately-tracked deferrals actually depend on, taken alongside [D-038](#d-038--the-desktop-shell-becomes-a-realm-that-draws-one-realm-holding-both-a-shim-surface-and-a-principal-connection-with-the-status-rows-moving-below-the-trust-line-and-the-socket-question-routed-to-the-confinement-work-rather-than-guessed). Does not reverse [D-021](#d-021--session-mode-is-scheduled-as-a-maintainer-dogfooding-workstream-ws-e-and-that-is-not-the-horizon-item)(2)'s boundary or [D-029](#d-029--the-bare-metal-backend-drives-exactly-one-output-and-refuses-to-start-otherwise-and-on-bare-metal-the-core-composites-the-humans-cursor-which-the-idl-said-it-never-does)'s single-output refusal, and deliberately does not restate the six X11 requirements #221 handed to E3.2. Follows the owner's correction on #222 that [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only) adopted: **an unbuilt capability is deferred, not refused**, and *"never"* and *"will not"* are the wrong register for one.

**The finding, and it is the reason this is an entry rather than a bullet on D-038.** Layer-shell and tiling read like two futures — one about bars and launchers, one about window arrangement — and get deferred separately, in different sentences, with different reopening evidence. **They are one.** Both require `Scene` to hold **more than one client surface**, and today it holds at most one. The evidence is in the tree and it is unambiguous:

- `crates/vitrin-core/src/scene/mod.rs:249-250` — `surface: Option<SurfaceContent>`. A single `Option`, not a collection. `commit` writes `Some` (`:301`), `clear_surface` writes `None` (`:315`), and there is no other writer.
- `crates/vitrin-core/src/scene/mod.rs:239–248` — *"**One realm's** scene: at most one client surface in the MVP (single maximized, plan P1.3.3) … "At most one client surface" is a statement about **this realm**, not about the session: it is the MVP's single-maximized model per app, and it is what `scene::layout` says must never grow."*
- `crates/vitrin-core/src/scene/layout.rs:1–30` — *"Single-maximized placement — the **entire** layout policy of the MVP core, quarantined in this module … This module exists only because the scene holds exactly one surface, so the 'policy' degenerates to **center the surface, unscaled** … **It must never grow: tiling, stacking order, focus policy, decorations, or any second placement rule are a design smell here and belong outside the core.**"*
- `crates/vitrin-core/src/scene/layout.rs:16–25` — multi-realm was the pressure that would most obviously have grown it and did not: *"two realms are not two placements, they are one placement asked twice"*, and stacking, overlap and per-realm resize *"were all declined explicitly (issue #209 decision 3)"*.
- `protocol/vitrin-v0.xml`, `vitrin_layout_arrange`'s `<description>` — *"**ONE REQUEST, AND THE ABSENCES ARE THE DESIGN. There is no place, no resize, no raise, no lower, no close and no stacking request on this interface - not a request that refuses, but no request at all.**"*

A layer-shell surface is a **second surface composited beside the app's**. A tiled workspace is **N surfaces placed against each other**. Neither is expressible against one `Option`, and — this is the part that makes them the same deferral rather than two with a coincidence — **neither is a protocol gap**. [D-022](#d-022--layout-enforcement-lands-early-for-the-nested-single-output-case-d-018s-deferral-is-discharged-and-its-unpurchasable-set-gains-a-fifth-member)(4) already records that the arrangement requests are absent *because the scene cannot honour them*, and the IDL's own rule is that *"a deployment MUST NOT grant a verb it does not enforce"*. Adding a `place` request before the scene can carry it out is the partial-verb hazard D-022 lists among its costs, guarded today by *"prose plus one test that pins the IDL's message count"* — *"a tripwire, not a barrier"*.

So the deferral is not *"we have not written a bar protocol"* and not *"we have not written a tiler"*. **It is one scene-model change, and whichever motive arrives first pays for it in full.**

**Reopening trigger, singular. Reopens on:** the scene model growing to N surfaces, whichever motive gets it there first — a bar, a launcher, an OSD, a tiled workspace, or something not yet named. Nothing else reopens either half; in particular, a client asking for `zwlr_layer_shell_v1` does not, because the shim advertising a global the core's scene cannot honour is the same partial-verb failure one layer out.

**Note carefully what this does NOT say, because the published sentences are wrong in three different ways and — this is the part a sweep gets wrong — they are not in the same bullet or even the same file.** The correction is not one find-and-replace, and treating it as one is how a doc sweep marks itself done having fixed the sentence it happened to open first.

- **The register defect is the workstream doc's, and `limits.md` does not share it.** `docs/plan/14-workstream-session-mode.md`'s limit register (`:1989-1992`) reads *"**No bars, launchers, notifications or OSD** — there is no `zwlr_layer_shell_v1` and there will not be one at the app level; the replacements are core-owned surfaces."* *"There will not be one"* is the wrong wording for an unbuilt capability, under the owner's correction on #222 that D-033 followed and [D-032](#d-032--relative-motion-and-pointer-gestures-grow-the-seat-vocabulary-pointer-constraints-grow-the-shim-session-instead-and-touch-and-tablet-are-deferred-against-named-evidence) applied to touch and tablet. **`docs/book/src/limits.md`'s `no-layer-shell` bullet (`:1310-1312`) must not be "corrected" as though it said the same thing**, because it does not: it says *"`zwlr_layer_shell_v1` is not in the shim's global contract, and that was measured rather than assumed"*, which is a statement about what is served today, already in the right register, and true. What that bullet owes is the prerequisite and the trigger below it — not a change of mood it never needed.
- **The substance defect is in a different bullet again, and it is D-038's doing rather than this entry's.** `limits.md`'s `principal-cannot-draw` bullet (`:1305-1308`) ends *"anything you would call a desktop shell — a bar, a launcher, an OSD, a window-switcher overlay — cannot exist on this display server, and the replacements are core-owned surfaces (the trusted band, the consent card, the attention marker, the lock screen and the status strip) that no client can add to."* D-038 makes the replacement a **client**, so *"the replacements are core-owned surfaces"* is falsified there and in the workstream register's copy of the same clause, independently of anything about layers — and *"cannot exist on this display server"* is the register defect a second time, in the file that did not have it in its layer-shell bullet.
- **A third form, stronger than either, sits where nobody sweeping limits pages would look, and its citation does not check out.** `docs/plan/14-workstream-session-mode.md:508-509` reads *"PRD §5.1 keeps window-management policy out of the core, and §6 says there will be no `zwlr_layer_shell_v1` at the app level either."* `layer_shell` appears **nowhere in `docs/PRD.md`**, so that sentence attributes to the PRD a refusal the PRD does not make. It needs its citation checked, not merely its register softened, and it is named here so the sweep does not stop at the two obvious bullets.

**What genuinely stays refused rather than deferred is narrower, and deserves its own words so the two are not blurred.** PRD §5.1 keeps window-management policy out of the trusted core as a *permanent invariant*, so **a tiler inside `vitrind` is refused, permanently, on principle** — that is the sentence `scene/layout.rs` has carried since P1.3.3 and it is not softened here. What this entry defers is a tiler **outside** the core: a shell realm holding arrangement verbs that a grown scene can honour, arriving as `since`-gated sibling requests when it can, exactly as the IDL prescribes. Confusing the two would let a future reader conclude either that tiling is forbidden (it is not) or that the core may grow one (it may not).

**Also deferred, separately, and NOT against the scene model.**

- **X11.** Already scoped rather than built: WS-E.4.1/#221 handed **six requirements** to E3.2 and measured the X11-only software on the target machine, and `docs/plan/14-workstream-session-mode.md` §4.2 carries that list. **It is deliberately not restated here.** A decision log that copies a scoped list acquires a second copy that can drift from the first, which is the failure this file exists to prevent and which D-024 already had to confess to once when a measurement was corrected in the workstream doc and not in its own entry. **Reopens on:** E3.2 being scheduled, on its own criteria, in its own plan document. Nothing in WS-E reopens it, and #221's own finding stands: the waybar/rofi class *"is not an X11 gap and must never be counted as one"*.
- **Multi-output.** The owner confirmed on 2026-08-17 that he daily-drives the single eDP panel, which is the fact the deferral rests on. [D-029](#d-029--the-bare-metal-backend-drives-exactly-one-output-and-refuses-to-start-otherwise-and-on-bare-metal-the-core-composites-the-humans-cursor-which-the-idl-said-it-never-does) makes the bare-metal backend drive exactly one output and **refuse to start otherwise**, so this is not a gap left open by accident. Reopening it is not a scene change at all: it is an **M4 hardware-matrix commitment**, which is exactly what D-021(2) was written to keep out of this workstream — *"WS-E is one maintainer's one laptop … No WS-E deliverable may be cited as evidence toward M4."* D-018's residual already names *"multi-output arrangement"* as E3's, and this entry keeps it there. **Reopens on:** a second output on the maintainer's own desk **together with** a decision to spend WS-E budget on it, or the M4 gate being approached deliberately — never on a nice-to-have and never as a side effect of a shell issue.

**What this decision costs.**

- **One deferral with one trigger is easier to lose than two with two.** Collapsing them is correct and it removes two reminders from the tree. What replaces them is this entry plus the surfaces that cite it, and a reader looking for *"why can I not run waybar"* now has to follow one more hop to find that the answer is about `Option<SurfaceContent>`.
- **Naming the prerequisite makes it look tractable, and it is not.** *"Let `Scene` hold N surfaces"* is one sentence and a large change: `scene::layout::place` returns a bare centred `Placement` and would have to become a policy; the *"must never grow"* comment would have to be rewritten by whoever grows it, and **that comment is load-bearing** — it is the artifact that has kept window-management policy out of the core through two pressures already. It also collides with #215's unmet inset, which D-038 turns into blocking work.
- **The published surfaces are wrong in three places for two different reasons, and the correction is not free.** The workstream register needs *"there will not be one"* replaced with a deferral and its trigger; `limits.md`'s `principal-cannot-draw` bullet needs *"the replacements are core-owned surfaces"* and *"cannot exist on this display server"* corrected for D-038 and for register; `limits.md`'s `no-layer-shell` bullet needs the prerequisite added and its own wording left alone; and `14-workstream-session-mode.md:508-509` needs a PRD citation it cannot support. Every surface must be enumerated per CLAUDE.md's `known-limit` rule rather than fixed on whichever page someone opened first — which is exactly the trap here, because the two bullets that look like copies of each other are not.
- **A single-output deferral is a decision made from a sample of one machine.** D-021's last cost bullet already states it: *"One machine, one GPU, one output … None of it generalizes."* This entry inherits that and does not improve it.

**What cannot be known here, and is therefore not claimed.** **Nothing in this entry is built, and it deliberately builds nothing** — it is a finding about what four deferrals depend on, not a change to any of them. Specifically, **nobody has costed the N-surface scene change**: there is no estimate, no design sketch, no issue and no measurement behind the claim that it is one change rather than two, only the reading of `scene/mod.rs`, `scene/layout.rs` and the IDL recorded above. If that reading is wrong — if a bar could be composited without a second `SurfaceContent`, say by the core placing a realm the way [D-038](#d-038--the-desktop-shell-becomes-a-realm-that-draws-one-realm-holding-both-a-shim-surface-and-a-principal-connection-with-the-status-rows-moving-below-the-trust-line-and-the-socket-question-routed-to-the-confinement-work-rather-than-guessed) does for the shell — then the layer-shell half separates from tiling again and this entry is the thing to supersede. That possibility is stated rather than hidden, because it is the one way the entry's spine could fail.

### D-041 — The core writes `/sys/class/backlight` so the brightness keys actuate; D-033 refused that interface as a BLANKING mechanism and half of its reasoning still bites here

**Status:** accepted (2026-08-17) — issue [#303](https://github.com/vitrin-os/vitrin-os/issues/303), workstream [WS-E](14-workstream-session-mode.md). **Discharges the deferral [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only) filed verbatim as** *"**Backlight actuation for the brightness keys.** **Reopens on:** a shell client holding a named verb (Stage 2's design), or an explicit owner decision to let the core write `/sys/class/backlight`"* — **this is that owner decision, taken 2026-08-17**, and `docs/plan/14-workstream-session-mode.md` names the same trigger in its *"Deferred, each with the evidence that would reopen it"* section under *"Reopened by:"*. It does **not** reverse D-033's refusal of the backlight as a blanking mechanism, which stands untouched, and it does **not** close the volume half of the same published limit. Independent of Q11 and of [D-039](#d-039--global-hotkeys-are-served-as-named-actions-the-core-resolves-never-as-keystrokes-it-forwards-the-attention-keys-one-bit-becomes-an-operator-configured-chord-table-and-no-verb-for-observing-the-humans-input-is-designed) and [D-040](#d-040--layer-shell-and-tiling-are-one-deferral-rather-than-two-because-both-need-a-scene-that-holds-more-than-one-client-surface-x11-stays-e32s-and-multi-output-stays-behind-the-m4-gate), and can land before any of them. **Decision 1 and the bounding constraint are the owner's**; every clause marked *derived* is not.

**The distinction this entry exists to make, stated before anything else, because a reader who skips it will conclude the log contradicts itself.**

D-033 already examined writing `/sys/class/backlight` and refused it. The bullet, verbatim:

> - **The backlight alternative was examined and refused, and the trade is recorded so it is not rediscovered.** Writing `/sys/class/backlight` keeps the CRTC active, so vblanks continue, the frame clock never stops and unblank is one sysfs write with no modeset risk. It is refused because it puts a **second** display-power interface inside the TCB, does nothing for external displays, saves almost no power, and is an interface D-030 already names as one DRM master does not gate.

**That refusal was of the backlight as the DPMS/blank mechanism** — the thing an idle timer would reach for instead of `DrmSurface::clear()`. It stands, unaltered: nothing here blanks through the backlight, `DrmSurface::clear()` remains the one DPMS call in the design, and the idle path is untouched.

**Decision 1, the owner's: the core writes `/sys/class/backlight` so `XF86MonBrightnessUp`/`Down` actuate; the backlight is still never the blanking mechanism.**

**What is decided here is key actuation.** Those two keysyms cause a brightness change instead of being delivered to an application that cannot act on them. Different trigger — a human's finger, not a timer. Different purpose — the human asked for a brightness, not for a dark screen. Different failure mode — nothing happens, rather than a modeset that leaves a dark panel with the session running. **Anyone reading only the heading of D-033's bullet would conclude this contradicts it, and it does not.** But two of that bullet's four reasons transfer, and one of them transfers harder than it did there, so the entry is written around them rather than around the feature.

**Which of D-033's four reasons still bite.**

1. **"It puts a *second* display-power interface inside the TCB" — still true, and knowingly accepted rather than answered.** After this change the core has two ways to change what the human sees: the DRM path it holds as master, and a sysfs file it holds by ordinary filesystem permission. Two interfaces is two places a bug leaves a human staring at nothing, and the blank state machine knows about exactly one of them. The owner accepted this with the objection stated to him in these terms; it is recorded as **accepted, not mitigated**, and it is why this entry is longer than the change it authorises.
2. **"Does nothing for external displays" — still true, and it gets *worse* here than it was under the refusal.** Under the published half-fix the key did nothing, uniformly, everywhere; a human learns that in one press. After this it works on the internal panel and silently does nothing on an external one, so the behaviour varies by which display is being looked at — harder to publish, harder to learn, and a worse shape than a uniform absence. It is bounded *today* only by [D-029](#d-029--the-bare-metal-backend-drives-exactly-one-output-and-refuses-to-start-otherwise-and-on-bare-metal-the-core-composites-the-humans-cursor-which-the-idl-said-it-never-does): the bare-metal backend drives exactly one output and refuses to start otherwise. It is not bounded in principle, and multi-output stays deferred in [D-040](#d-040--layer-shell-and-tiling-are-one-deferral-rather-than-two-because-both-need-a-scene-that-holds-more-than-one-client-surface-x11-stays-e32s-and-multi-output-stays-behind-the-m4-gate).
3. **"Saves almost no power" — does not transfer.** That leg argued against the backlight as a *power* mechanism. This decision is not about power; it is about a labelled key doing what its label says. Stated explicitly so the bullet is not quoted as if all four reasons were being overridden together.
4. **"An interface D-030 already names as one DRM master does not gate" — still true, and it is the sharpest of the four, because here it cuts the other way.** [D-030](#d-030--the-trusted-band-asserts-only-about-the-screen-this-core-is-driving-and-the-session-colour-is-never-re-minted-a-paused-seat-raises-no-prompt-it-could-record-as-shown) says, verbatim: *"`/sys/class/backlight` is a separate interface that DRM master does not gate, a monitor's own power button is outside the machine entirely, and either can leave the human staring at nothing while `vitrind` believes it is presenting. **That hazard is real, is exactly what #219's decision 4 was reaching for, and is not closed here.**"* Under D-033 that was a reason **not** to touch the interface: it is authority the core does not already hold. Under this decision the core reaches for it anyway, so the honest reading is that **the core is taking a new authority rather than exercising one it had** — a file it can write only because it runs as a uid that can write it, which is the ambient-authority shape `limits.md`'s D9 already concedes for the whole process and which [D-037](#d-037--the-realms-namespaces-are-built-by-a-helper-that-execs-first-and-unshares-second-the-core-proves-the-confinement-from-outside-before-it-commits-and-the-measured-ceiling-and-the-selected-policy-are-two-vocabularies-whose-bottoms-may-never-share-a-word)'s worker-thread correction had to publish once already.

**The hazard the core now becomes a source of, and the constraint that follows. Derived here, not the owner's.** D-030's paragraph names a panel darkened by `/sys/class/backlight` as a hazard *outside* the core's knowledge — a consent card can be raised, and recorded as shown, while the human sees nothing. A core that can write that file can now **create** that state itself: brightness zero is a dark panel that the blank state machine does not know is dark, produced by the core's own hand, on a path with no `PromptVisibility` term in it. **So the core must never write a value it cannot expect to be legible** — a floor above zero, or the blank state's own knowledge extended to cover the backlight — because the alternative is a trusted core manufacturing precisely the hazard D-030 published as open and untouched. This is a constraint on the implementation rather than an option within it, it was not part of the owner's statement of the decision, and it is written here so that whoever builds this does not discover it from a black screen.

**The key is consumed, and that reverses part of what WS-E.4.3 shipped. Derived, not the owner's.** #223's XF86 rows landed so those keys stop being dropped at intake and reach the focused realm's shim seat. If the core actuates **and** delivers, two things go wrong at once: a confined application gets a free timing oracle over the human's brightness presses — D-023's exact stated reason for consuming Super — and two actors share one interface with no arbitration. So the key is consumed, which means the rows WS-E.4.3 added stop reaching the app on the brightness path. That is the cost `deadman.rs` refused to pay for Escape, [D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing) paid for Super and [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) paid for Shift-Insert, paid once more: a nested compositor, a VM viewer or a remote-desktop client inside a realm loses the key with no pass-through and no way to ask for one.

**No verb, no wire surface, and no agent may do it — and that is D-033(2)'s argument about waking a screen, applied unchanged.** That entry's strongest half is *"there is no verb in the IDL for 'power the human's display'"*, and the reason is that an agent able to change the human's physical environment, remotely, under no grant, is the inverse of what this system is for. Setting the human's brightness is the same act one notch quieter. So: **physical origin only**, `Verb::VALID_MASK` unchanged, **no IDL edit at all**, and the human's press is a fact the core acts on and journals — never authority the core issued, which is D-024(3)'s rule and the dead-man switch's precedent. An agent that wants a brighter screen has no request to make and no refusal to receive, because there is no message.

**The sysfs access is bounded exactly the way the battery read already is. This is the owner's accepted implementation constraint, not a suggestion, and the pattern is a file rather than a description.** `crates/vitrin-core/src/status/battery.rs` is that file, and it is the pattern precisely because it was got wrong once:

- **One fixed root, never composed from anything a client or agent can influence.** `SYSFS_ROOT` at `battery.rs:56`; the sampler holds it as a `&'static Path` (`sample.rs:187`), which `battery.rs:16-17` states as *"so there is no field a later edit could make client-settable"*, and the `root` parameter exists only so unit tests can point at a fixture tree. The backlight root must be a constant of the same kind, with the same reason written next to it.
- **A bounded number of directory entries — and the sort happens BEFORE the cap.** `MAX_ENTRIES = 16` at `battery.rs:61`; the ordering rule is at `battery.rs:104–125` and it is the paid-for one. Capping before sorting was a **shipped defect**: on a machine whose battery is not among the first sixteen `readdir` entries the strip reported *"no battery"* on hardware that has one, non-deterministically, because `readdir` order is not stable across kernels. A backlight scan is the same walk over the same kind of class directory and will reproduce that defect exactly if it is written from memory instead of from this file.
- **A hard cap on every read, enforced by `std::io::Read::take` rather than by a length check afterwards.** `read_capped` at `battery.rs:158`, on the ground `battery.rs:20-21` states as *"The cap is a property of the reader, so \"read the whole file\" is not expressible here"* — the difference between a bound and an intention.
- **No panic and no error path.** Every battery failure collapses to `BatteryReading::Absent`, drawn as an empty slot, *never a guess*. The equivalent here is that **every failure collapses to the key doing nothing** — which is exactly today's published behaviour. A bounded, failing backlight write therefore degrades to the status quo rather than to a new failure mode, and that is the strongest property this change has. It should be written as an acceptance criterion rather than left as a hope.

**A write is not a read, and the difference lands on the future sandbox.** `battery.rs:32–39` already records that the *read* becomes *"a rule the core has to grant **itself**"* once E2.6/E2.7 put Landlock over `vitrind`'s own process, and records it in three places rather than leaving it *"to be rediscovered by whoever writes the ruleset"*. **A write to `/sys/class/backlight/*/brightness` is a strictly larger widening of that same sandbox** — the first rule in it with a write bit — and owes the same three-surface record: the module doc beside the code, `docs/book/src/limits.md`, and `docs/plan/14-workstream-session-mode.md`. It lands directly in [#187](https://github.com/vitrin-os/vitrin-os/issues/187) (P2.6.3, the Landlock ruleset and the ABI ladder), which is where the ruleset is actually written. It also depends on a permission this repository does not own: on a stock install the write is reachable through a `video`-group membership or a logind/udev tag, so **"the brightness key works" is a property of the machine's udev rules rather than of a checkout** — the same non-reproducibility D-033(5) accepted for logind's lid and power policy, and it is published rather than owned for the same reason.

**Volume actuation is NOT discharged and stays deferred.** `docs/book/src/limits.md` publishes *"Backlight and volume actuation are **deferred, with named reopening evidence**"*, and `README.md` publishes the same fact in its own words — *"Backlight and volume actuation are deferred behind either a shell verb or an owner decision to let the core write `/sys/class/backlight`; **no issue tracks it.**"* Only the backlight half moves here, and the two surfaces have to be edited separately because they are not the same sentence. The two are not the same shape and that is why one moves and one does not: there is no one-file sysfs equivalent for volume, and every route to a mixer runs through a sound server — a bus or socket client inside the TCB, which is the dependency D-033(4) refused for logind and refuses here for the identical reason. **Reopens on:** a shell client holding a named verb for it — which [D-039](#d-039--global-hotkeys-are-served-as-named-actions-the-core-resolves-never-as-keystrokes-it-forwards-the-attention-keys-one-bit-becomes-an-operator-configured-chord-table-and-no-verb-for-observing-the-humans-input-is-designed) makes newly plausible, since a named action delivered to a shell realm is exactly the shape that puts a mixer outside the TCB — or an explicit owner decision of the kind this entry records for the backlight. **Whoever closes the backlight half must not rewrite that bullet as though both halves closed.**

**Surfaces this change must touch when it lands, enumerated because the `known-limit` rule requires it and because the deferral is recorded in four places.** `docs/book/src/limits.md` — the `media-keys-reach-an-app-that-cannot-act` block, including the sentence *"the human presses brightness and nothing happens, exactly as before"* and the standing claim *"**No issue tracks it**"*, which this entry's issue falsifies. `README.md` — the one-bullet form. `docs/plan/14-workstream-session-mode.md` — **both** the *"Deferred, each with the evidence that would reopen it"* bullet, which uses **"Reopened by:"** where this file uses **"Reopens on:"**, and the published-limit block carrying the same text. And this file. `site/index.html` deliberately omits this limit under the stated-subset decision — *"at one line it reads as a fix"* — and that omission should be revisited only once the key actually works. `NOTICE` is unaffected.

**What this decision costs.** The four objections above are where most of these are argued; this list exists so no reader has to reconstruct a cost sheet out of an objection walk, and because two of them — the consumed key and the write-side widening of the future sandbox — are argued in their own paragraphs and appear nowhere in that walk.

- **A second display-power interface inside the TCB, accepted rather than mitigated.** Two mechanisms can now change what the human sees, and the blank state machine knows about one of them. Blanked-but-bright and unblanked-at-an-illegible-brightness are both reachable states and nothing here makes the two paths agree.
- **The behaviour stops being uniform.** It works on the internal panel and silently does nothing on an external one — bounded today only by D-029's single-output refusal, not in principle, and a worse thing to publish than the uniform nothing it replaces.
- **The brightness keys stop reaching apps, reversing part of what WS-E.4.3 shipped.** A nested compositor, a VM viewer or a remote-desktop client inside a realm loses both keys with no pass-through and no way to ask for one — the cost D-023 paid for Super and D-024 for Shift-Insert, paid once more and for two keys rather than one.
- **The core's future self-sandbox goes from read-only to read-write.** `battery.rs`'s recorded read-side debt becomes a write rule on a sysfs tree, and #187 inherits it rather than discovering it.
- **"The brightness key works" becomes a property of the machine, not of the checkout.** The write is reachable through a `video`-group membership or a logind/udev tag this repository does not own, so the feature is non-reproducible in exactly the way D-033(5) accepted for logind's lid and power policy.
- **Half the published bullet stays true and the edit is easy to overclaim.** Volume does nothing and external displays do nothing; a rewrite that reads *"the media keys work now"* would make the docs worse than the half-fix they replace.

**What cannot be known here, and is therefore not claimed.** **Nothing in this entry is built.** No code writes any backlight file, no issue is closed, no brightness has been changed by this core on any machine, and no measurement exists behind any sentence above. When it is built, CI cannot help: runners have no DRM device, no seat, no ACPI and **no backlight**, D-030's and D-033's bound unchanged. `battery.rs` can point its reader at a fixture tree because a read is satisfiable by a directory; **a write has no fixture equivalent** — writing into a temp directory proves the bounds and the failure collapse, and proves exactly nothing about a panel. So *"the key changes the brightness"* is a hardware rung on [`docs/drm-bringup.md`](../drm-bringup.md) or [`docs/book/src/recovery.md`](../book/src/recovery.md), on the one machine that has the hardware, and it must be **written before it can be executed** — D-033's own lesson, learned when its suspend, lid and blank rungs turned out not to exist yet. The honest status of this entry today is **decided and unbuilt**; the best it can reach on the day it merges is **landed in the tree, unproven on hardware**, and it does not improve until the owner pastes a dated result into that rung's record block.

### D-042 — An idle inhibit is a property of the realm the human is looking at, not an authority a grant confers; it suppresses the blank and never the lock

**Status:** accepted (2026-08-17) — issue [#306](https://github.com/vitrin-os/vitrin-os/issues/306), workstream [WS-E](14-workstream-session-mode.md). **Discharges the deferral** `docs/plan/14-workstream-session-mode.md` files verbatim as *"**Idle inhibition** (`zwp_idle_inhibit_manager_v1`). Needs a new shim global **and** a shim→core wire verb, i.e. paired IDL + prose work on `track:protocol`. **Reopened by:** that paired edit"* — this is that paired edit. It settles the question #306 asks in as many words: **is holding an idle inhibit an authority that needs a grant, or a property of a focused realm's surface?** Independent of [D-039](#d-039--global-hotkeys-are-served-as-named-actions-the-core-resolves-never-as-keystrokes-it-forwards-the-attention-keys-one-bit-becomes-an-operator-configured-chord-table-and-no-verb-for-observing-the-humans-input-is-designed), [D-040](#d-040--layer-shell-and-tiling-are-one-deferral-rather-than-two-because-both-need-a-scene-that-holds-more-than-one-client-surface-x11-stays-e32s-and-multi-output-stays-behind-the-m4-gate) and [D-041](#d-041--the-core-writes-sysclassbacklight-so-the-brightness-keys-actuate-d-033-refused-that-interface-as-a-blanking-mechanism-and-half-of-its-reasoning-still-bites-here); it neither reverses nor weakens any clause of [D-033](#d-033--idle-blanks-the-screen-and-does-not-lock-it-suspend-is-detected-after-the-fact-or-not-at-all-and-the-recovery-path-is-sudo-only).

**EVERY CLAUSE BELOW IS DERIVED. NONE OF IT IS THE OWNER'S**, and that is stated first because D-041's own header marks which of its clauses were his and a reader will look for the same mark here. #306 asked for the question to be decided "in whichever direction it goes" and no owner statement exists on this date. The clause an owner is most likely to reverse is named at the end, with what reversing it would cost.

**Decision 1: no grant, no verb bit, no facet, and no IDL surface a principal can reach.** An idle inhibit is asked for by the **confined app** over its shim connection. The four reasons, in ascending order of how hard they are to argue around:

1. **There is no petitioner.** A grant is one row of principal × resource × verbs × constraints, and the asking party here is not a principal at any version — the human has no wire presence in version 0 and a confined app has less. A grant table with no principal to key on is not an attenuated authority, it is a table with a hole in it.
2. **A verb bit is allocated once, repo-wide, and is immutable** ([conventions §7.4](../protocol/00-conventions.md)). Spending one on an app-asked capability would put a bit in an agent-facing bitfield that no agent can ever hold and no `request_grant` can ever ask for. `Verb::VALID_MASK` is unchanged at 575.
3. **The precedent is already in the tree and was already argued.** `pointer_constraint` is the identical shape — app-asked, derived from no grant — and `crates/vitrin-core/src/input/constraint.rs` writes the "no" down with a named test (`revoking_every_grant_leaves_an_apps_pointer_constraint_alone`) precisely so the absence stays deliberate. This entry follows it rather than re-deciding it, and owes the same kind of named test, which is `an_inhibit_in_a_realm_nobody_is_looking_at_holds_nothing` plus the round-level `an_idle_inhibit_reaches_the_blank_round_and_dies_with_its_realm`.
4. **What a grant would be trying to express is already expressed by the human's attention.** The core honours an inhibit only while its own output is bound to the realm holding it. Switching realms ends it, a VT handover ends it, the app dying ends it. That is attenuation by the human's own eyes, applied continuously, with no petition to answer and no revocation to race.

**The objection this decision has to answer, because `crates/vitrin-core/src/backend/blank.rs` already refused an agent the smaller version of the same thing.** That module's docs state, of waking a dark panel: *"there is no verb in the IDL for 'power the human's display': an agent that could wake a panel would be making an unrequested change to the human's physical environment, remotely triggerable, under no grant."* An inhibit changes the human's physical environment too — the panel stays lit — so why may a confined app do what an agent may not?

Three differences, and the third is the load-bearing one:

- **It cannot wake.** An inhibit declines a blank that has not happened. There is still no message, for an app or for an agent, that turns a dark panel back on; `an_inhibit_arriving_after_the_screen_went_dark_does_not_wake_it` pins that the guard is a suppression term and not a wake.
- **It is not remotely triggerable.** An agent's actuation arrives over a network-reachable principal connection. An inhibit arrives from a process the human started, in a realm the human put on their own screen, and it stops counting the moment they look away.
- **It is gated on the same physical/emulated line D-033(2) already draws — and that line stops an *actuation*, not every verb.** The clock has one writer and an agent's actuation neither postpones nor wakes; the inhibit writes no clock at all, and the realm it is judged against is the realm *physical* input is bound to. So **an emulated actuation never moves the binding**: a principal cannot activate a background realm's inhibit by pointing or typing into it, however much it actuates. **What `layout_focus` can do is move the binding, and that is a grant-governed verb use rather than an actuation.** `UseKind::LayoutFocus` maps to `LayoutAct::Focus` (`crates/vitrin-core/src/enforcement.rs:1088`), `apply_layout` calls `router.bind_to(&realm)` (`crates/vitrin-core/src/session.rs:3231`), and `service_blank_round` reads exactly that binding (`crates/vitrin-core/src/session.rs:2386`). So that verb *does* reach this record, and an earlier draft of this bullet claimed it could not. **What bounds it is that the same act moves the OUTPUT with it** (`view.bind_output(&realm)`, `session.rs:3246`): the realm whose inhibit starts counting is the realm the human is then being shown, so this is the attention gate doing what it was written to do rather than being stepped around — a principal cannot hold the panel lit on behalf of a realm the human is not looking at, because making its inhibit count *is* putting it in front of them. The residual is real and is listed in the cost sheet below rather than argued away here.

**Decision 2: it suppresses the idle blank and never the idle lock, and the non-coupling is structural rather than remembered.** D-033(1) is that idle **blanks** and does not lock, and D-033(2) is that one activity clock has one writer shared by both mechanisms. The obvious implementation of "hold the blank off" — pushing that clock forward while an inhibit is held — would postpone the lock too, because `LockScreen::tick` reads exactly that field. So the inhibit is a **fourth guard inside `SessionActivity::tick`** and touches nothing else: `--blank-idle 300 --lock-idle 600` still locks at 600 with an app holding an inhibit. `an_idle_inhibit_holds_the_blank_and_not_the_lock` is the assertion, deliberately sited beside `a_blank_does_not_disable_the_idle_lock` so the two read as one property. **A comfort request from a confined app must not be able to disable a security control**, and that sentence is the whole of why this feature is a guard in one function rather than a clock write.

**The consequence for the human, published rather than softened:** with both flags set, a film longer than the idle-lock timeout gets a lock screen drawn over it. That is not a regression — it happens today, with no inhibit — but a reader who hears "idle inhibition works now" will expect otherwise. The common case is unaffected because `--lock-idle` is off by default.

**Decision 3: two removal paths, and three deliberate absences.** A record leaves when the shim says `released`, or with the realm, through `RealmTeardown` — the funnel every death path reaches, which is where the clipboard slot is already cleared for the same reason. The three things that do **not** remove one:

- **A grant revocation does not**, per decision 1, and the dead-man switch's session-wide grant sweep therefore cannot reach it.
- **A seat handover does not**, and here this design departs from `PointerConstraintTable`, which withdraws on a pause. The difference is **recoverability**: a withdrawn constraint is *announced* on the wire and the app can ask again, while `idle_inhibit` carries no verdict event, so a core-side drop would be silent **and permanent** — the app's inhibitor object is still alive, its count never changes again, and no `held` would ever follow. Nothing is lost by keeping it: `seat_absent` already suppresses the countdown for the whole pause and forces the screen lit.
- **The dead-man chord does not**, for that reason plus one: the chord destroys *authority*, and by decision 1 an inhibit is not authority. The precedent is `--screenshot-dir`, which `deadman::apply` deliberately leaves alone on exactly that ground. And the chord is physical input, so pressing it stamps the activity clock and forces the screen lit regardless of this table — a human taking their session back never has to get past an inhibit to see their screen.

**Decision 4, derived and worth recording because #306's own body assumed the opposite: the message lands at `since="2"`, and the protocol version integer stays 2.** The issue's task says to add the request "as a `since`-gated sibling and bump the interface version". `since="3"` is not available: `crates/vitrin-scanner/src/parse.rs`'s `validate_since` rejects any `since` above `protocol/@version`, so it would force the document to version 3 — which would make `vitrind` refuse every client offering 2 with fatal `version_unsupported` (`principal.rs`), and would require a hand edit to `sdk/python/src/vitrin_os/protocol.py`, which is deliberately not generated (D8). **The repo's own practice is the answer**: every `since="2"` message on `vitrin_shim_session` — the clipboard's three, the pointer constraint's two — was appended to version 2 *after* version 2 already existed, and §7.3's normative table was extended in the same edit. This follows that precedent exactly, and the interface's own `version` attribute stays 2 for the same reason it did then: that counter names the protocol version at which the interface last grew. **A version matrix is still P2.1.2's**, unmoved by this.

**The cost of appending at an already-published version, recorded because the precedent above does not make it disappear.** [§7.4](../protocol/00-conventions.md#74-growth-rules-wayland-style)'s letter is satisfied — a new message appended with a `since` attribute, no signature changed, §7.3's normative table extended in the same edit — but **§7.3's *semantics* are strained, and this is an exception taken knowingly rather than a rule complied with.** That section reads the negotiated version as naming a fixed message set ("the connection speaks exactly that version for its whole life", and "a server whose maximum version is N implements every version from 1 to N ... rejecting later-`since` opcodes"). Appending to a version that already exists means the integer `2` no longer names one set: it names whatever set the build in question shipped with. **The concrete failure is a third-party shim's, not an agent's.** A shim built against this IDL, pointed at an older `vitrind` that also says version 2, sends `idle_inhibit` and is answered by the catch-all in `crates/vitrin-core/src/shim.rs` — `ShimViolation::UnknownOpcode`, which on a shim connection is log-and-close, so that shim loses its realm with nothing on the wire naming a version mismatch as the cause. Nothing in the handshake could have told it, because the two cores agree on the integer. **Accepted, on three grounds and no more:** no shim outside this repo exists, version 2 has never been frozen or released, and the alternative — bumping to 3 — costs a fatal `version_unsupported` for every current client plus a hand edit to the ungenerated Python protocol module (above). **What makes it stop being acceptable** is the first out-of-tree shim, or version 2 being published as frozen; at that point appending to a live version needs a real answer, and the place for it is P2.1.2's version matrix, which is where this cost is owed rather than here.

**Decision 5, derived: there is no verdict event, and the absence is a design rather than an omission.** `zwp_idle_inhibitor_v1` defines **no events at all**, so a core→shim verdict would have exactly one possible consumer — the shim's own log — and no path to the app. A refusal is therefore unobservable *and* harmless: a deployment with no `--blank-idle` blanks nothing and has satisfied the ask vacuously. This is the one place the pair differs from `pointer_constraint`, whose app *is* waiting for an activation and would latch forever without one. The cost is named in Decision 3 (a silent core-side drop is unrecoverable, which is why there are no core-side drops beyond realm death) and the reopening condition is named in the prose page's Growth section: if a later Wayland protocol grows an event, the verdict is an appended `since`-gated message, never a change to this request.

**The residual this decision accepts, stated as a residual and not as a mitigation.** While the human is looking at a realm whose app holds an inhibit, `--blank-idle` does not fire — for as long as that stays true. There is **no time ceiling**, deliberately: a ceiling would blank a ten-hour stream at hour six, which is inventing a policy nobody asked for, and Wayland's own compositors rely on the visibility gate rather than a clock. So an app with a leaked-but-live inhibitor object *and* the human's attention does pin the panel. The remedies are the human's and are all ordinary: look at another realm, kill the app, or press the dead-man chord (which lights the screen through the clock, though it does not clear the record). What is *not* left to the human is the leak that matters more — an app that exits without destroying its inhibitor — and that is closed twice over: wlroots destroys an inhibitor resource with its client, so the shim releases; and the core drops the record with the realm, so a dead shim needs nobody to send anything.

**What this decision costs.**

- **A confined app can hold a human's panel lit indefinitely while that human is looking at it.** No ceiling, by choice; the gate is attention, and attention is the only thing bounding it.
- **With `layout_focus`, a principal can cause the human's screen to stay awake.** Decision 1's third bullet says an emulated actuation cannot reach this record, and that is true; a `layout_focus` use is not an actuation and *does* reach it. Focusing a realm whose app holds an inhibit moves the router binding, and the blank round reads that binding — so a grant-governed verb composes with an app-asked comfort feature to produce an effect on the human's physical environment that neither half was designed to give a principal. **What it is bounded by, and what it is not.** Bounded: the same verb moves the output, so the realm holding the panel lit is the realm the human is being shown; `layout_focus` is itself grant-governed, attenuable and revocable ([D-018](#d-018--layout-is-a-capability-grant-governed-arrangement-core-enforced-ordering), [D-022](#d-022--layout-enforcement-lands-early-for-the-nested-single-output-case-d-018s-deferral-is-discharged-and-its-unpurchasable-set-gains-a-fifth-member)); and a `layout_focus` use is journalled where the suppressed blank is not. Not bounded: by revocation, which is the bound this bullet claimed in its first draft and does not have. `GrantTable::revoke` and `revoke_principal` flip `entry.liveness` and nothing more (`grants.rs:1184`, `:1200`); no path in the tree un-binds the router or moves the output on revocation — the only non-test callers of `bind_to`/`bind_output` are `apply_layout` (`session.rs:3231`, `:3246`), `rebind_output_after_death` (`:1844-1864`) and admission (`:1606-1620`), and none is reachable from a revoke. So revocation stops the principal making a **further** focus move and does not undo the one it already made: the binding stays, the output stays, and the panel keeps being held lit with no live grant behind it until the human looks elsewhere, the app releases its inhibitor, or the realm dies. Also not bounded: by any timer, and not by a test — no assertion in this workspace exercises the `layout_focus` → `bind_to` → `service_blank_round` path end to end, so this cost is derived from the three call sites and not measured.
- **The feature is invisible in the flight recorder.** The core logs the held/released *edges* with `tracing` at INFO, and `journal_screen_transition` records blanks and wakes — but a blank that *did not happen* produces no recorder entry, so "why did my screen not blank at 21:00" is answerable from the log and not from the journal. Adding a recorder event was not done here and is not tracked; it is named so it is owed rather than forgotten.
- **`surface` is carried and not used for gating.** The IDL says so, and the honest reading is that the argument exists because signatures are immutable forever and nothing in this protocol hard-codes one surface per shim. Today it is recorded and logged, nothing more.
- **`shim/docs/firefox.md`'s refusal register loses a row, and the objection recorded there is *not* being called wrong.** That row's reasoning — *"a realm has no screen and no idle timer; the host's screen is the core's, and inhibiting it from inside a confined app is a decision for the core"* — is upheld by this entry, clause for clause. What changed is that the ask now reaches the core. The row is removed rather than left standing, because a refusal register that lists a served interface is worse than one entry shorter.
- **A fifth catalogue row stops being armed.** `EXPECT_ARMED` in `firefox_bringup.sh` drops 17 → 16, measured rather than derived (`probes_armed=16 catalogue=21`). The row stays in `shim/meson.build`, so the evidence that admitted the global is not deleted along with the probe.

**Amended 2026-08-19 by P2.6.5 (issue [#189](https://github.com/vitrin-os/vitrin-os/issues/189)) — the remedy this entry applied to `vitrin_shim_session`'s description was reversed, and reversing a logged remedy belongs in the log rather than only in the file it changed.** This entry replaced that interface's closed count (*"the only two"*) with a **rule** — *every exchange whose asking party is inverted* — on the ground that a closed count in a normative description is exactly the tripwire [§7.4](../protocol/00-conventions.md#74-growth-rules-wayland-style) warns about. P2.6.5's `designation` falsified the **rule**: it is a one-way core→shim *delivery*, not an exchange, and its asking party is a third one the shim connection cannot name. The IDL now carries a count again (*"VERSION 2 ADDS FOUR CONVERSATIONS TO THIS OBJECT"*) **alongside** the list it counts, with the wider rule stated after it. The argument for going back, recorded so a future author does not re-apply this entry's remedy by reflex: a rule that widens to admit whatever arrives next is not a stronger invariant than a number, it is an unfalsifiable one, and it fails silently where a wrong number fails to a reader who can check it against the messages below it. **What is not claimed:** the restored count is checked by a reader, not by a build — nothing in CI compares "four" to the IDL — so it carries the same staleness risk this entry named, taken deliberately with the list beside it as the cross-check. The paired prose is `docs/protocol/09-vitrin_shim_session.md`, which records both moves in order.

**What cannot be known here, and is therefore not claimed.** **Nothing in this entry has been observed to keep a screen lit.** The core-side guard, the shim relay and the realm-death cleanup are built, and every one of them is covered by tests in this workspace — but blanking needs a display controller, CI has none, and `crates/vitrin-core/src/backend/drm.rs` is the only production caller of `service_blank_round`. `shim/tests/acceptance/idle_inhibit.sh` is a **component** test against `shim/tests/mock_core.c`, and by CLAUDE.md's rule it can never be cited as milestone acceptance; what it settles is what the *shim sends*, including that a client killed holding an inhibitor still releases. The claim *"full-screen video no longer blanks the screen"* is a **hardware rung** on the one machine that has the panel, and it is not merely unproven — the honest form of it is that **a human has to watch a video**, because the failure this closes is one a human noticed rather than one a test found. Until that is run and pasted, the status of this entry is **decided and landed, unproven on hardware**, and `docs/book/src/limits.md` says so in those words rather than announcing a fix.

### D-043 — P2.6.5 landed two deviations from issue #189's own text, and both are recorded here rather than left as a silent disagreement between a tracker and a tree
**Status:** accepted (recorded 2026-08-23, during the pre-merge review of P2.6.5 / issue [#189](https://github.com/vitrin-os/vitrin-os/issues/189), four days after the landing commits it describes)
**Decision:** two of #189's written asks were not executed as written. Both departures are upheld; what is logged is that they happened, why, and what the tree carries instead. An issue body is a plan, and a plan that a landing quietly contradicts is the same class of defect as a stale published count: nobody is lied to on purpose, and everybody who reads the issue afterwards is told something false.

**1. Acceptance criterion 5's `fd_count` case is in `crates/vitrin-protocol/tests/decode_errors.rs`, not in `protocol/test-mutations.sh`.**

The criterion asked for *"an `fd_count` mismatch case that must die fatal `fd_violation`"* in the mutation corpus. It is not there. `protocol/test-mutations.sh` applies one illegal edit to a copy of `protocol/vitrin-v0.xml` and asserts `xmllint --relaxng` rejects it — every case it can hold is a statement about the **dialect**. `fd_count` is not in the dialect: it is a byte of the 8-byte frame header ([`00-conventions.md`](../protocol/00-conventions.md) §2.4), the IDL has no syntax that could express a mismatch, and there is therefore no mutation whose rejection would prove anything about it. A case invented to satisfy the sentence would have exercised the schema and been *named* for the framing rule, which is worse than not writing it.

What carries the criterion instead, on P2.6.5's own messages and asserting the exact wire code the criterion names:

- `designated_fd_count_mismatch_is_rejected_in_both_directions` — `vitrin_powerbox.designated` decoded with an honest one-fd header and no fd supplied, and with a lying zero-fd header while the fd really is supplied. Both return `DecodeError::FdCountMismatch`, and both are asserted to map to `vitrin_handshake.error.fd_violation`.
- `request_dir_rejects_an_unsolicited_fd` — the other arm: an fd arriving on a message that declares none.

The nine mutation cases P2.6.5 *did* add exercise the dialect against the newest surface, which is the corpus's actual job. **What is not claimed:** these are unit tests against the generated codec, not an end-to-end demonstration that a peer sending such a frame is killed — the connection-level kill lives in `vitrin-ipc`, whose `tests/transport.rs` covers `UnsolicitedFd`, `MissingFd` and `FdCountExceeded` against a real socketpair, and no test in this tree drives a hostile peer through a live `vitrind` with a lying `fd_count` on a powerbox message.

**2. Task 5 asked the IDL to say the `file:`/`dir:` prefixes are "now **served**". The IDL says they are defined and resolve `unsupported` in every deployment, because that is what is true.**

`request_grant`'s description states that the two prefixes *"resolve 'unsupported' in every deployment today, since no deployment serves `designate_file` yet"*. That is measured, not hedged: `crates/vitrin-core/src/grants.rs`'s `SERVED_VERB_BITS` is `1|2|4|16|32|512`, bit 64 is absent, and `UNSERVED_VERB_BITS` picks it up by derivation, so this core resolves every petition naming it `unsupported` whole. The picker that would serve it is P2.6.6 and has not landed. Writing "served" would have been false of `main` on the day it landed and would have stayed false until an unrelated task made it true — the precise shape of published claim this repo's gates exist to catch.

The prefixes are nevertheless **defined**, and defining an unserved selector costs nothing on the wire: an unserved prefix already resolves `unsupported` recoverably, so no client at any version changes behaviour. That is exactly the posture the verb bit itself takes — bit 64 is allocated by the registry in [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5, defined in the IDL, and served by nothing — and stating prefix and bit in one register is what keeps a reader from concluding that a defined prefix implies a served one.

**Costs, stated:**
- Issue #189's body is now wrong in two places and will stay wrong: a closed issue is not edited to match what shipped. This entry is the record; whoever reads #189 later has to reach it, and nothing forces them to.
- Deviation 1 leaves `protocol/test-mutations.sh` with no case named for the framing invariant, so a reader auditing the corpus against the criterion list finds a gap and has to come here to learn it was moved rather than dropped. The alternative — a comment in the script — was also taken (the `powerbox-mode-as-array` case says the one-fd rule is a framing invariant the schema does not model), but a script comment is not a record of a plan being changed.
- Neither deviation is held by any gate. A future edit could put "served" back into the IDL description while `SERVED_VERB_BITS` still omits bit 64, and nothing in CI would go red — `cargo xtask limits-check` holds the *verb mask* and the *interface count*, not this sentence. Naming that here is the whole of the mitigation.
