# Phase 1 — MVP slice (deep plan)

**Scope anchor:** [PRD](../PRD.md) §8 Phase 1 and §19 — trusted core in Rust+Smithay (nested + headless) · one Wayland shim (C+wlroots, one instance per app) · Firefox in a realm · agent client with a static identity · one grant (`observe + actuate.pointer + actuate.text`) · core-rendered consent · pixel capture + scoped input injection.

**Explicitly out of Phase 1:** semantic trees, epochs/CAS, network sessions, X11, multi-realm fleet, filesystem powerbox, credential wallet, provenance, signed-journal replay tooling, IME, motion synthesis beyond trivial interpolation.

**MVP object-model subset** (of PRD Doc 2 §3.1): `principal`, `realm` (exactly one, `realm-0`), `surface`, `view` (implicit: one view = the realm's composited framebuffer), `actuator`, `grant`. Not in MVP: `scene`, `epoch`, and the signed `journal` of P6 — a plain structured event log ("flight recorder") is kept as a debugging aid and future journal seed (see the backward requirements below).

**Phase exit = milestone M1** in [00-roadmap.md](00-roadmap.md).

---

## 1. Exported-artifact contract (what later phases may depend on)

Phases 2–3 cite these as their Phase-1 dependencies; anything not listed here is an internal detail free to change.

- **A1 — Principal-facing protocol core:** connect/handshake, grant request/consent, surface observe, actuator inject. Consumed by every Phase-2 epic and by spec extraction (WS-A).
- **A2 — Realm spawn model:** shim fork, realm identity assigned at fork, spawn/sandbox skeleton. Consumed by E2.6/E2.7 (which extend the namespace setup) and E3.2/E3.3.
- **A3 — Grant table + consent surface.** Consumed by E2.6, E2.7, E3.7.
- **A4 — Flight-recorder log** (journal seed). Consumed by E3.4 — see backward requirement B1.
- **A5 — Wayland shim** with buffer/input/damage paths. Consumed by E2.1 (the bridge lives inside it), E2.8, and as the template for E3.2.
- **A6 — Nested + headless output modes.** Consumed by E3.3 (fleet generalizes headless).

### Backward requirements (placed on Phase 1 by Phase-2/3 planning)

- **B1 — Replay-ready log entries.** Flight-recorder entries carry observation digests (hash of each captured frame) and epoch-ready reference fields from day one, even though epochs don't exist yet. E3.4 (journal replay) is unbuildable retroactively if the MVP's records don't identify *what was observed*. Fields may be null-versioned; the schema slot must exist.
- **B2 — Physical-vs-emulated input distinction end-to-end.** The Phase-1 input pipeline tags every event's origin (physical device vs. agent actuator) and preserves the tag through core → shim → app delivery (the libei/EIS model, PRD Doc 2 §4.4). E3.7's physically-originated consent depends on this being structural, not bolted on.

## 2. Planned repository layout (documented now, created when Phase 1 begins)

```
vitrin-os/
├── Cargo.toml                      # [workspace] members = crates/*
├── rust-toolchain.toml             # pinned stable toolchain
├── docs/
│   ├── PRD.md
│   ├── plan/                       # this tree
│   └── protocol/                   # prose spec, one page per interface (spec-first; PRD §9 bus-factor mitigation)
├── protocol/
│   └── vitrin-v0.xml               # single IDL source of truth (Wayland-XML dialect — D1)
├── crates/
│   ├── vitrin-scanner/             # codegen: vitrin-v0.xml → Rust (core/SDK) + C header (shim)
│   ├── vitrin-protocol/            # generated message types + codec; no I/O
│   ├── vitrin-ipc/                 # Unix-socket transport: framing, SCM_RIGHTS, SO_PEERCRED, calloop glue
│   ├── vitrin-core/                # the TCB. binary: `vitrind`
│   │   └── src/{main.rs, comp/, capkernel/, grants/, identity/, input/, consent/, spawn/, capture/, log/}
│   ├── vitrin-sdk/                 # Rust client library (reference client; keeps the protocol honest)
│   └── xtask/                      # `cargo xtask codegen|bless|demo`
├── shim/                           # NOT in the Cargo workspace. C + wlroots, Meson build
│   ├── meson.build
│   ├── include/vitrin-protocol.h   # generated by vitrin-scanner (checked in, regenerated by xtask)
│   └── src/{main.c, compositor.c, upstream.c, seat.c, buffer.c}
├── sdk/
│   └── python/                     # `vitrin_os` package — pure-Python wire client (D8)
├── examples/
│   └── agent-demo/run_demo.py      # the Phase-1 demo agent
├── tests/
│   ├── integration/                # spawn vitrind headless, run scripted clients
│   ├── clients/input-echo/         # tiny Wayland test app logging every event it receives
│   └── golden/                     # reference frames for pixel assertions
└── .github/workflows/ci.yml
```

Layout rationale: the shim is deliberately outside the Cargo workspace (C+wlroots per PRD §17, Meson-built, glued via `xtask`/CI); `vitrin-protocol`/`vitrin-ipc` are separate crates so the codec is testable with zero I/O and the SDK doesn't link Smithay; one IDL file serves both the principal-facing and shim-facing protocols as distinct interfaces (same wire format, different authentication: handshake credential vs. inherited socketpair).

**Two parallel tracks after the IDL freezes** — Track A (Rust: ipc → core → capkernel → consent) and Track B (C: shim skeleton → upstream → seat → Firefox). The IDL freeze (P1.1.1/P1.1.2) is the only hard serialization point. The plan is also valid fully serialized (M1.1 → M1.5) for a single maintainer (R8).

**Walking skeleton (first end-to-end target):** core (headless, pixman) renders a test pattern → Python agent connects with a static identity → grant auto-approved via `--consent=auto-approve` → agent captures the frame to PNG. No shim, no Firefox, no consent UI, no dmabuf. This exercises every seam that is *new invention* (IDL, codegen, framing, fd delivery, handshake/identity, grant table, enforcement, capture, SDK) while deferring everything that is *known-hard integration* (wlroots, Firefox, GPU).

### D12 — Definition of done: a milestone closes only on a named mock-free integration gate

**Adopted following the #111 re-audit.** Through most of Phase 1, every
component was verified against a **mock on the far side of its seam** —
`vitrind` against `vitrin-mock-shim` (a synthetic Rust peer that animates a
hand-drawn buffer and forks no app), and the real C shim against
`shim/tests/mock_core.c` (a hand-written core stand-in). Both mocks are
useful and stay, but neither half had, at the time, ever met the *other real
half*, and the closure record for E1–E8 read "done" without either half
having run once end to end. That gap is now closed by rule:

> **A milestone M1.2–M1.5 is done only when its named integration-gate issue
> passes green, and that gate must have no mock on any seam the milestone
> claims.** `vitrin-mock-shim` and `shim/tests/mock_core.c` are
> **component/unit-test scaffolds only** — they may never be the source of a
> milestone's definition-of-done evidence. Existing green tests that use them
> stay (they still catch real regressions in the half they exercise) but are
> labelled **component tests**, never milestone acceptance, in
> [tests/integration/README.md](../../tests/integration/README.md).

The named gates (table above): **M1.2 = #105**, **M1.3 = #107**,
**M1.4 = #108 + #109**, **M1.5 = #110**. M1.1 predates this rule (walking
skeleton, no real second app existed yet to be mock-free about) and is not
retroactively gated.

The milestone-closing checklist (used when marking M1.2–M1.5 done in an issue
or PR) requires: (1) the named gate issue is closed; (2) its test file boots
its `Core`/shim with an explicit real binary path, never the mock defaults
(check (2) above); (3) no prose anywhere claims the milestone is met on a
component-test result; and (4) — added by the P1.9.8 gate-integrity pass —
**the gate has been watched failing.** Mock-freeness proves what a test is
*wired to*, never what it *discriminates*: both a gate that waited only for
the view to stop being the empty test pattern and one that asked for 24
changed pixels were mock-free and could not fail on the property they named.
Before citing a gate, break the behaviour it claims to prove and confirm it
goes red.

## 7. Phase-1 risks

- **R1 — Smithay nested-mode maturity.** The winit backend is primarily a dev harness (niri/COSMIC run on DRM). Risks: input-model gaps, HiDPI oddities, host-compositor quirks. *Mitigation:* keep nested rendering trivial (one window, one texture blit + overlay); test on GNOME and Hyprland from M1.1; headless is the fallback demo venue and CI never depends on nested.
- **R2 — wlroots as a library.** API churns per release, docs thin, and "tiny compositor serving exactly one app, forwarding upstream" is an unusual shape (closest prior art: gamescope, cage). *Mitigation:* pin + vendor (D11); crib structure from cage; keep the global list a contract, not a floor. *Reserve option:* a Smithay-based Rust shim is viable but weakens the PRD §17 reuse rationale — a deliberate documented pivot, not drift.
- **R3 — dmabuf across the shim boundary.** Format/modifier mismatches, multi-GPU, implicit-sync stalls. *Mitigation:* D3 (shm first; dmabuf is an M1.5 optimization with automatic fallback); linear-only allowlist; per-GPU compatibility notes. MVP success does not depend on zero-copy (PRD caveat: performance numbers are design targets).
- **R4 — Firefox quirks.** Binds many globals, behaves differently without them, Wayland path evolves per release. *Mitigation:* bring-up ladder weston-terminal → GTK app → Firefox (M1.2 gates on the terminal); pin an ESR; drive the stub list from the shim's "globals touched" log; software WebRender fallback.
- **R5 — Text/keymap fidelity.** Synthesized keymaps are known-fiddly (keymap size, xkb state, apps that read the keymap once). *Mitigation:* `input-echo` fidelity tests before Firefox; restrict demo text to what the technique handles; the clean fix is E2.8.
- **R6 — Consent-in-headless contradiction.** A careless `auto-approve` default would quietly rot the security story. *Mitigation:* auto-approve only behind an explicit flag that prints a persistent warning and refuses to run if the identity registry contains more than the demo principal.
- **R7 — TCB dependency creep.** Consent text rendering, capture encoding, config parsing all tempt heavyweight deps into `vitrin-core`. *Mitigation:* a checked-in cargo-deny budget for `vitrin-core`, reviewed each milestone; PNG encoding lives in the SDK, never the core.
- **R8 — Single-maintainer schedule.** The two-track plan assumes parallelism that may not exist. *Mitigation:* milestone order valid fully serialized; IDL + docs-first posture keeps the project enterable by a second contributor at any point (Q8).
