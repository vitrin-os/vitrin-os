# Decision log

Registry of decisions (Part A) and open questions (Part B) for Vitrin OS. Entries are ADR-shaped and cited by short ID (`D-005`, `Q11`) from every other plan document. Once a decision is **accepted**, its entry is append-only: changes are recorded as a new superseding entry, never edits.

Convention: this stays a single file until it exceeds ~25 accepted entries or external contributors begin proposing decisions, at which point it splits into `docs/plan/adr/` (see D-013).

---

## Part A — Decided

Entries D-001 through D-011 are seeded from decisions the [PRD](../PRD.md) already made; the PRD section cited is the full rationale. D-012 onward originate in this plan tree.

### D-001 — Rust + Smithay for the trusted core
**Status:** accepted (PRD Doc 2 §9, §17)
**Decision:** the trusted core (`vitrind`: compositor, capability kernel, grant store, input router, journal, motion synthesis) is Rust on Smithay.
**Context/consequences:** the core is the entire TCB; memory safety eliminates vulnerability classes in the most privileged component. Smithay is production-proven (niri, COSMIC) at frame deadlines. Go rejected (GC pauses vs. frame deadlines); C/C++ rejected for the core (TCB memory-safety argument).

### D-002 — C + wlroots shims, outside the TCB
**Status:** accepted (PRD Doc 2 §4.2, §17)
**Decision:** the Wayland shim is C on wlroots; the later X11 shim is C/C++ (Xwayland-derived) with an embedded minimal WM. Shims are unprivileged and disposable.
**Context/consequences:** the legacy semantics we want live in wlroots, mature; reusing them *outside* the TCB is the point. See Phase-1 risk R2 for the held-in-reserve Rust-shim pivot option.

### D-003 — Wayland-style Unix-socket wire protocol with SCM_RIGHTS; Cap'n Proto rejected for the local hot path
**Status:** accepted (PRD Doc 2 §3.2)
**Decision:** local principals speak a Wayland-style binary protocol over Unix domain sockets with fd passing; handles are per-connection, sender-constrained. Cap'n Proto RPC's conceptual model (handles-as-capabilities, attenuation, pipelining) is adopted; its transport is not (no shared-memory transport in practice; buffers move as dmabuf fds outside the payload). Protobuf/gRPC and FlatBuffers rejected for the local path.

### D-004 — QUIC (quinn) for network sessions
**Status:** accepted (PRD Doc 2 §10)
**Decision:** remote sessions run over QUIC: multiplexed streams, TLS 1.3, connection migration; workload identity bound to the channel. Cap'n Proto remains optional for the network control plane (final call at E3.1 — see Q6 for the codec question).

### D-005 — Split licensing
**Status:** accepted (PRD §11)
**Decision:** protocol spec + wire definitions under Apache-2.0 (explicit patent grant), spec prose CC-BY-4.0; reference implementation under weak copyleft (MPL-2.0 preferred, LGPL-3.0 the fallback); client SDKs Apache-2.0.
**Consequences:** setup work (LICENSE files, SPDX headers) executes at first public push — see [12-workstream-community.md](12-workstream-community.md) §2.

### D-006 — Naming: Vitrin OS
**Status:** accepted (PRD Naming section)
**Decision:** project **Vitrin OS**, daemon `vitrind`, org `vitrin-os`, npm scope `@vitrin-os`, crates `vitrin-os`/`vitrind` (namespaces claimed 12 July 2026). Kavşak dropped (pronounceability), Torii recorded but not adopted.

### D-007 — Scope tiering: invariants / v1 / horizon / renounced
**Status:** accepted (PRD §5)
**Decision:** scope statements are kept in four distinct classes: permanent invariants (§5.1), v1 sequencing (§5.2), claimed-but-deferred horizon (§5.3), renounced non-goals (§5.4). Every plan document inherits this discipline; horizon items never silently migrate into a phase without an M4 gate review ([04-phase-4-horizon.md](04-phase-4-horizon.md)).

### D-008 — Pluggable identity verifier; no hard commitment to in-flight standards
**Status:** accepted (PRD Doc 2 §5.1, Caveats)
**Decision:** identity verification (SPIFFE SVID, OIDC, SSH certificates, MVP static identity) sits behind a pluggable `Verifier` abstraction. IETF AIMS, MCP authorization revisions, and OID4VC profiles are tracked, pinned, and re-checked — never hard-wired (see the liaison table in [10-workstream-spec.md](10-workstream-spec.md)).

### D-009 — Transparency log for provenance; deliberately not a blockchain
**Status:** accepted (PRD P14, Doc 2 §13)
**Decision:** app provenance uses Sigstore-style identity-bound short-lived signing certificates plus a Merkle transparency log (checkpoint + inclusion proof verified locally). No consensus, no tokens, no ledger on the grant-time hot path. DIDs acceptable as an identity *format* only.

### D-010 — Per-realm isolation dial
**Status:** accepted (PRD Doc 2 §4.5)
**Decision:** isolation strength is per-realm policy over one identical GUI protocol: default (namespaces + seccomp + Landlock), hardened (gVisor-class), paranoid (microVM). Every realm gets its own network/PID/IPC namespaces and UID regardless of tier. Security claims are stated per tier (only the microVM tier escapes shared-kernel escape classes).

### D-011 — v1 deployments: headless fleet + local nested; one Wayland shim first
**Status:** accepted (PRD §5.2, §8)
**Decision:** v1 targets the two deployments with no open incumbent (headless agent fleets; nested-in-a-desktop). The X11 shim, network sessions, and fleet mode follow in Phase 3. Session mode on bare DRM/KMS is horizon-tier.

### D-012 — DCO, not CLA
**Status:** proposed
**Decision:** contributions are accepted under the Developer Certificate of Origin (sign-off), not a Contributor License Agreement.
**Rationale:** a CLA is a contributor deterrent, and a single-maintainer project needs contributors more than it needs relicensing optionality; the licensing split (D-005) already secures the protocol/implementation boundary. Revisit only if a fiscal host requires otherwise.

### D-013 — Single-file decision log
**Status:** proposed
**Decision:** decisions and open questions live in this one file until ~25 accepted entries or external decision proposals arrive; then split into `docs/plan/adr/`.

### D-014 — Spec versions track the implementation (module-freeze ladder)
**Status:** proposed
**Decision:** the protocol spec is published early but versioned `0.x` and explicitly tracking the reference implementation; modules freeze on the ladder defined in [10-workstream-spec.md](10-workstream-spec.md) §2 (0.1 at M0, 0.2 at M1, core 1.0-candidate at M2, network profile at M3).
**Rationale:** the epoch/CAS mechanism is "a design claim, not a proven result" (PRD Caveats); freezing it before E2.3 measures it would enshrine guesswork. Running code before prose authority (the anti-Arcan posture, PRD §9).

### D-015 — No patent filings; defensive publication instead
**Status:** accepted (2026-07-26)
**Decision:** Vitrin OS files no patents. Protection rests on three things instead: **defensive publication** (the PRD and the IDL published with a timestamp are themselves the prior art), the **patent grants already carried by the licenses** (Apache-2.0 §3 on the protocol and SDKs, MPL-2.0 §2.1(b) on the reference implementation — see D-016), and **Open Invention Network membership**, to be joined (free below $10M revenue; OIN 2.0 launched January 2026; 4,000+ members cross-licensing 3M+ patents royalty-free within the Linux System definition, which covers the graphics stack).
**Rationale:** the economics do not work and the posture is wrong. A patent family costs roughly EUR 10–30k per jurisdiction and takes 2–5 years to grant, and Europe's absolute-novelty rule would force filing *before* publication — delaying the one act that actually protects the project. Publishing the design is the protection: it blocks anyone else from patenting these claims, immediately and for free. It is also the only posture consistent with the project's own argument: a capability-security system asking to be trusted is stronger defensive-permissive than behind a patent wall, and D-005's whole point is that the protocol is a commons.
**Consequences:** a public-source patent-landscape scan was performed on **2026-07-26** and is recorded here so a later reader can tell what was and was not checked.

- *Nearest neighbour.* Anthropic's portfolio, acquired via Adept AI Labs. **US20250299023A1** (filed 2024-03-20, pending): claim 1 covers generating **training data** through an intermediary that intercepts user actions and translates them into actuation commands — no mention of permission, authorization, consent, capability, revocation, or a display server/compositor. The sibling **US 12,430,150** covers a client-side interface-automation language at runtime. Neither reads on a capability-scoped display protocol; the overlap is the *setting* (an intermediary between an agent and a GUI), not the claimed mechanism.
- *Prior-art anchors that protect Vitrin's own mechanisms.* Trusted path and the attention key: **US 4,918,653**, "Trusted path mechanism for an operating system" (expired), and the TCSEC / Secure Attention Key lineage behind it. The unforgeable trust band: **Qubes OS**'s dom0-drawn coloured window borders (2010, published). The nested per-app compositor and per-app security context: **Sommelier** and Wayland **`security-context-v1`**, both published. Capability security itself: **Dennis & Van Horn (1966)**, KeyKOS, EROS, seL4, Capsicum.
- *Limits, stated plainly.* This was a **public-source landscape scan, not a freedom-to-operate opinion**. No FTO has been obtained and none is budgeted. Pending claims get amended and continuations get filed, so the Anthropic applications above are an explicit **re-check item before 1.0**, not a settled result.
- *Residual risk.* The realistic exposure is a non-practising entity in the RPA space (UiPath's portfolio; Microsoft via the Softomotive acquisition), and that risk materialises with **revenue**, not with publication — which is another reason publishing early costs nothing here.

### D-016 — D-005's weak-copyleft half executed as MPL-2.0
**Status:** accepted (2026-07-26) — executes D-005, closes the open question in issue #133
**Decision:** the reference implementation ships under **MPL-2.0**, not the LGPL-3.0 fallback D-005 recorded. The boundary between the copyleft and permissive halves is drawn by **derivation, not by directory**: content transliterated from the Apache-2.0 protocol artifacts stays Apache-2.0, original implementation expression goes MPL-2.0. Concretely — the trusted core and the IPC layer (`crates/vitrin-core`, `crates/vitrin-ipc`) and the shim's own C sources, hand-written headers and fixtures go MPL-2.0; `crates/vitrin-protocol` **including its checked-in generated code**, the generated C header under `shim/include/`, the IDL scanner and its `xtask` driver, the conformance instruments (`crates/vitrin-golden`, `crates/vitrin-mock-shim`, `fuzz/`), the SDKs, `tests/integration/` and `examples/` all stay Apache-2.0. `shim/wlcs/` remains the GPL-3.0-only carve-out it already was. Mechanism: per-file `SPDX-License-Identifier` headers plus a per-crate `license` field, with the root [`NOTICE`](../../NOTICE) as the normative path→license map — **not** per-directory LICENSE files.
**Rationale:** MPL-2.0 over LGPL-3.0 on four grounds, one of which is the real one.

- **Security is the core argument.** Vitrin's central claim is a *small, auditable* trusted core. Copyleft on the TCB makes that a property of the license rather than a promise in a README: a modified capability kernel, grant store or consent path cannot be shipped as a black box, and security-relevant fixes come back.
- **File-level scope is the right shape here.** MPL's copyleft attaches to files, not to the process image, so an app running inside a shim is never derivative and the Larger Work allowance (§3.3) makes linking MIT wlroots and MIT Smithay clean rather than an argument.
- **No patent regression.** MPL-2.0 §2.1(b) carries an explicit patent grant and §5.2 a termination-on-litigation clause, so moving a file from Apache-2.0 to the copyleft half does not lose the patent protection D-005 chose Apache-2.0 for (and D-015 leans on).
- **GPL compatibility is load-bearing, not theoretical.** MPL names GPL-3.0 a Secondary License (§1.12) and permits distributing the Larger Work under GPL terms (§3.3) — which is what keeps the advisory `shim/wlcs/` module lawful now that it compiles MPL-2.0 shim sources. **Hard constraint: Exhibit B ("Incompatible With Secondary Licenses") must never be added to any file in this repo.**
- **LGPL-3.0 rejected on deployment reality.** Its anti-tivoization / Installation Information terms (GPLv3 §6) are a known deterrent to embedded and kiosk vendors — and kiosk/embedded panels are a genuine deployment target for a display server, not a hypothetical one.

**Consequences:**

- **Adoption is unaffected by design:** nobody has to touch an MPL-2.0 file to write a client, build an alternate compositor, or ship an integration, because the protocol, the generated bindings, the codegen and the SDKs are Apache-2.0. Copyleft binds the people who modify the trusted core, and only them.
- The workspace-wide `license` default is **removed** rather than changed, so a crate added later cannot silently inherit the wrong half; every crate states its own.
- Root license texts + `NOTICE` + per-file headers, because per-directory LICENSE files would be *false*: `shim/` carries three licenses and `shim/include/` two.
- The repo has shipped a GPL-3.0-only file since P1.9.4 with no GPLv3 text anywhere in the tree, which GPL-3.0 §4 requires. Pre-existing gap; closed by this pass.
- `LICENSE-CC-BY-4.0` had been a 28-line human-readable *summary* that said of itself it was "not a substitute for the license" — so one of the four licenses the map names had no legal text in the tree. Replaced with the verbatim CC BY 4.0 legal code, matching what this pass did for MPL-2.0 and GPL-3.0-only. Another pre-existing gap, closed here rather than noted and left.
- **Inline SPDX headers cover sources only** — every first-party `.rs`, `.c`, `.h`, `.py`, `.sh` and `.js` file. Build manifests, the IDL and its schema, Markdown and fixture data deliberately carry none: `Cargo.toml` states the license in its own field, and the rest is covered by `NOTICE`'s path map, which now includes a catch-all clause so no tracked path is left unassigned. A file without an inline header is not an unlicensed file, and `NOTICE` says so explicitly rather than leaving a reader to infer it.
- The `license: 'MIT'` assertion in the shim's build file — and the MIT prose claims that grew around it — are retired. No MIT license text has ever existed in this repository, so that assertion was never backed by anything. `shim/wlcs/integration.c`'s `SPDX-License-Identifier: GPL-3.0-only` tag is preserved exactly; only the surrounding prose about "the rest of the repository" changes.
- Generated files take their SPDX line from the scanner's templates, never by hand, or `cargo xtask codegen --check` goes red in CI.
- **Known cost, accepted knowingly:** GitHub's license detector reads the root `LICENSE` and will keep labelling the repository "Apache-2.0", which now understates the copyleft half. The clean fix is the REUSE Specification layout plus a `reuse lint` CI check — which would also stop header coverage rotting — and is deliberately deferred to a follow-up rather than folded in here.
- Third-party carve-outs are untouched: the OFL-1.1 font vendored under `crates/vitrin-core/assets/` and the wlroots/wayland trees under `shim/subprojects/` keep their own licenses.
- Two placements are the arguable ones and are recorded as such so a future reversal is cheap: `crates/vitrin-ipc` (MPL-2.0, though its `client` feature is SDK-facing) and `crates/xtask` (Apache-2.0, though it also drives core dev tasks). Each is a one-field change that disturbs nothing else in the map.

### D-017 — Per-principal cursors: the model is decided and on the wire; delivery is deferred to M2
**Status:** accepted (2026-07-26) — closes Q15 / PRD §20.15, issue #147
**Decision:** five answers, one wire change.

1. **Cursor identity needs no new object.** Each principal has exactly one virtual pointer per realm it holds pointer authority over, and `vitrin_actuator_pointer` **is** that pointer's name on the wire. `move` already meant "this principal's virtual pointer"; the model was implicit and is now normative. No new interface, no cursor object, no cursor id.
2. **Cursorless is by construction, not by declaration.** A principal that never petitions for `actuate_pointer` has no cursor. The headless-fleet case therefore costs zero wire vocabulary. There is deliberately **no request** to declare, disown, or hide a cursor — and the missing *hide* is itself the decision: a visually distinct agent cursor is a human override (PRD P10), so visibility is never the actuating principal's own choice.
3. **Visibility is a relation, it is settled on the observation side, and it is asymmetric.** A captured frame contains no cursor except the human principal's, and that one only for a grant holding `observe_cursor` (4) — otherwise the same rule the consent overlay already obeys. The asymmetry is the decision, not an oversight: **agent→agent is closed outright** and purchasable at no verb set, ever (a side channel revealing what another principal is doing), while **agent→human is closed by default** and opens only through a verb. What is refused throughout is a *per-pair toggle matrix*: the only "toggle" that exists is the one grant verb, visible on a consent prompt and revocable with the grant. Human→agent visibility, including the per-agent toggles a human supervising thirty agents needs, is a shell and core concern: the human has no wire presence in v0.
4. **Agent→human cursor visibility is a grant verb**, not a display preference: new bit `observe_cursor` (0x8) on `vitrin_grant.verb`. It attaches to the grant, not to the view facet, because it is authority over what a capture *contains*, and it has no facet interface of its own — it widens `frame_ready`, it does not add a request. It is **meaningful only alongside `observe`**: a petition naming it without `observe` names no capture to widen and resolves `unsupported`, rather than granting a bit that changes nothing (the same rule that forbids granting a verb the deployment does not enforce). Seeing *another agent's* cursor is not purchasable by this or any verb.
5. **Cursors are core-composited.** A realm may never supply the pointer bitmap; `vitrin_shim_surface` has no cursor-surface role and will not gain one. A realm drawing its own could paint a **decoy cursor** and mislead the human about where input is going — the spoofing class the consent surface exists to exclude (issue #85). An app-painted pointer image is ordinary realm content, never the composited pointer.

**Why this simplifies the core rather than growing it:** `ConsentGrab` carries a defensive rule — never let emulated motion relocate the position the human's hit test reads — that exists *only* because one cursor is shared between origins. With structurally distinct pointers the human's hit test follows the human's pointer and the special case is deleted. It also clarifies preemption: with one pointer, "physical input preempts agent input" is a contention rule; with N+1 pointers there is nothing to contend for on the pointer axis, and preemption is purely about focus and actuation ordering.

**DEFERRED, explicitly:** **per-principal cursor *delivery*** — to **M2** (spec 1.0-candidate). Version 1 delivers **one shared pointer position** per realm view to the shim and composites **no cursor at all** (in nested operation the host desktop draws the human's cursor, outside the realm view entirely). Serving `observe_cursor` is likewise deferred: v1 refuses it `unsupported`. The correction is purely additive because the agent-facing half is already principal-relative — only `vitrin_shim_seat` delivery is shared, and it grows `since`-gated sibling events that name the principal, each still ending with `origin` so the schema's B2 rule holds.

**Costs, stated:**
- One verb bit (0x8) is burned on authority nothing implements. Enum values are immutable and `deprecated-since` marks but never removes, so if the model changes the bit is dead weight forever.
- A verb defined but unserved is a claim the core must keep honest at exactly one place; the guard is `grants::UNSERVED_VERB_BITS` (derived from `Verb::VALID_MASK`, so a newly appended verb is unserved by default — forgetting to classify one fails closed at *runtime*) plus the admission refusal and its unit test. Because that constant is derived, "served ∪ unserved = the wire bitfield" is an identity and cannot fail; the *tripwires* that actually go red when a verb is appended to the IDL are two explicit pins — `vitrin-protocol/tests/decode_errors.rs` on `Verb::VALID_MASK == 575` (63 until `realm_launch` = 512 landed at wire version 2; the pin is re-stated at its literal value on every verb addition, which is what makes it a tripwire), and `consent/render.rs`'s catalogue test on the unserved set's exact bits, which forces a human to classify the new verb as served (with prompt copy) or unserved. Stated because the first draft of that doc comment claimed a tripwire the derivation had removed.
- **The Python SDK's hand-transcribed `Verb` mirror is out of sync as of this landing.** `sdk/python/src/vitrin_os/protocol.py` still carries only `observe`/`actuate.pointer`/`actuate.text` (mask 7 against the IDL's 63), and nothing fails: `IntFlag` accepts the undefined bits and no golden vector covers a verb bit. That file's own docstring says the IDL wins and this file must be fixed, so the divergence is a debt, not a design. It is `track:sdk`-owned and out of `track:protocol`'s file set; it is recorded here so it cannot be lost, and the dotted names to add are `observe.cursor`, `layout.arrange`, `layout.focus` (the existing convention maps `actuate_pointer` → `actuate.pointer`). Whoever closes it should add a parity check against `protocol/vitrin-v0.xml` rather than a second hand-transcription. **Closed by WS-E.1.5/#211** on those terms: `sdk/python/tests/test_verb_parity.py` re-derives the members, the dotted names, `VERB_MASK` *and the served/unserved split* from the IDL and asserts the SDK agrees — and, because that last one is a string match against the IDL's own "refused unsupported in version 1" phrasing, it also pins that the phrase is still load-bearing, so a rephrase cannot silently turn the derivation into a tautology that a matching hand-edit of `VERBS_SERVED_IN_VERSION_1` would keep green.
- The shared-cursor defect and its `ConsentGrab` workaround **survive through M1**. The security argument for per-principal cursors is therefore recorded, not yet realised, and the prose says so rather than implying otherwise.
- The human→agent toggle surface is unanswered here because the human is not on the wire; it lands with the mission-control shell (E3) and D-018's arrangement model.

### D-018 — Layout is a capability: grant-governed arrangement, core-enforced ordering
**Status:** accepted (2026-07-26) — closes Q16 / PRD §20.16, issue #149
**Decision:** five answers, two wire bits.

1. **Layout is grant-governed; the shell holds no ambient layout authority.** Layout verbs are attenuable, revocable, journaled verbs on a grant, exactly like `observe`/`actuate_pointer`/`actuate_text`. *"The shell is trusted"* was not available: PRD §5.1 makes it an invariant that window-management policy lives outside the core, so trusting the shell would move exactly the code that invariant exiles back into the TCB, defeating the Nitpicker/Scenic argument the design rests on.
2. **Core-enforced, unpurchasable ordering invariants** (no grant buys these at any verb set, ever): (a) the consent surface and the trust indicator composite above every principal's content; (b) the core's own hit test — never a client's claimed stacking — decides which surface an input event reaches; (c) no arrangement may occlude, fullscreen over, or resize away the consent surface; (d) no **agent** principal's cursor is composited into another principal's captured frame — the one cursor a capture may ever contain is the human's, and only for a grant holding `observe_cursor` (shared with D-017(3)/(4), and the single carve-out). The shell gets *arrangement*; the core keeps *ordering*.
3. **`focus` is a separate verb from placement.** New bits: `layout_arrange` (0x10) covering place/resize/raise/fullscreen, and `layout_focus` (0x20). Focus theft is at once the sharpest attack and the most legitimate need, so it must be attenuable alone. `raise`/`move`/`resize`/`fullscreen` are deliberately **not** split further: with ordering held by the core (2), each stops being an attack primitive, and splitting them would be attenuation theatre — more bits, no more safety.
4. **One layout-holder per output; no arbitration in the core.** Arbitration between two principals holding layout grants is window-management *policy*, which §5.1 forbids inside the TCB. At most one live grant carries `layout_arrange` per output. The refusal code a second holder receives is settled with the shell's design (E3); the additive mechanism is an appended `outcome` entry, since outcome is a plain enum and entries append. Version 1 refuses **every** layout petition `unsupported`, so the contention cannot arise yet.
5. **Epoch interaction (E2.3) is a binding constraint, not a sequencing note.** A layout change invalidates an agent's cached coordinates exactly as a repaint does, so **E2.3's epoch MUST be defined over (frame content + view geometry + stacking), not content alone**, and a layout mutation MUST bump it. Third-party arrangement is also the reason the epoch must be a compare-and-swap *on actuation*, not merely a token returned by observation: between an agent's capture and its click, a shell holding `layout_arrange` may have moved the target. The two are designed together, per Q16's own instruction.

**DEFERRED, explicitly:** **layout enforcement in its entirety** — to **E3** (mission-control shell), gated on M2's epoch work per (5). Version 1 has no window manager; both verbs resolve `unsupported` at petition admission. The layout **facet** (a `since`-gated `get_layout` structural mint on `vitrin_grant`, since `request_grant`'s five `new_id` arguments are frozen) is not added now — an unserved verb needs no facet.

**Costs, stated:**
- Two more immutable bits burned on unimplemented authority, with the same dead-weight risk as D-017's.
- The single-holder-per-output escape is a real restriction, not a neutral simplification: two shells, or a shell plus a tiling agent, cannot both arrange the same output. That is the price of keeping arbitration policy out of the core, and it is revisitable only by an additive design that puts arbitration *outside* the TCB.
- Choosing the refusal code for a second layout holder is left open. Naming one now would either widen an existing `outcome` entry's meaning (a wire-semantics change the growth rules forbid) or append an entry for a mechanism that does not exist.
- The consent surface is unspoofable today partly because nothing outside the core does layout at all. This decision does not make it *more* spoofable — v1 still serves no layout — but it does commit the project to invariants (2) as *invariants*, and their current standing is uneven: (a) holds because the core composites the consent prompt above the realm view; (b) and (d) hold vacuously, since no client can state a stacking order and no cursor is composited at all; (c) has nothing to be true of, because there is no arrangement mechanism. None of the four is tested *as an invariant* against a client trying to violate it, and none can be until something outside the core can arrange realms. That test is E3's, and D-018 is the reason it must exist.

### D-019 — The agent cursor is drawn: display-only, human-visible output only; D-017's delivery deferral stands
**Status:** accepted (2026-07-26) — amends D-017's cursor-*drawing* half only; residual on Q15 unchanged
**Decision:** the core composites a cursor sprite at each actuating agent's own pointer position, into human-visible output and nowhere else. Four parts.

1. **The position is agent-owned, not the shared one.** `input/mod.rs`'s `RealmSeat::agent_pointer` is a second field beside `RealmSeat::pointer`, written **only** when `origin == Emulated` and dropped with the rest of that realm's seat state when its shim generation ends (both were fields of `InputRouter` itself until WS-E.1.6 made the seat state per realm). The shared field is written by both origins — that is exactly the delivery D-017 deferred — so a sprite drawn on it would follow the human's physical mouse and tell the human an agent is pointing wherever the human is. This is the mirror image of `consent/grab.rs`'s `ConsentGrab::pointer`, which is deliberately *physical*-only so an agent cannot slide a hit target under the human's finger: same idiom, one origin over.
2. **Drawing is not delivery, and only drawing changed.** Seat delivery to the shim remains **one shared pointer position per realm view**, `vitrin_shim_seat` events carrying `origin` and not principal identity. `agent_pointer` feeds no hit test, no routing decision, and no wire event; it reaches the compositor through one presentation seam (`session::Presenter::set_agent_cursor`, driven once per dispatch round from `post_dispatch`) and nothing else.
3. **Human-visible output only, at the existing fork.** The sprite is composited at the output stage — downstream of the `Scene::compose` every capture is taken from — exactly like the consent overlay (P1.7.1) and the dead-man hold indicator (P1.7.3). The exclusion from captures is therefore structural, not a checked flag. Both human-visible paths draw it, from one geometry function (`cursor::agent_cursor_rects`): the CPU composite and the nested zero-copy dmabuf draw list. Painting only the first is issue #85's exact bug one property milder, so the sprite rides *inside* `dmabuf::human_visible_frame`'s fixed-length draw list rather than being applied by whoever calls the presenter. The geometry clips every rectangle to `y >= TRUST_BAND_HEIGHT`, because an agent chooses its own position and an unclipped sprite at row 0 would be a new forgery surface against the trusted band, not a cosmetic overlap.
4. **Nested always; headless on `--agent-cursor`.** Nested mode is where the human is, and drawing nothing there is the defect this closes. Headless is off by default because its human-visible framebuffer is *measured* byte-for-byte against the realm view by `backend/band_witness.rs` (issue #139) and by `tests/integration/test_real_trust_band.py`, whose `tracks_view == 1` assertion is taken after a real `grant.pointer.click()` — a sprite on by default there would turn a mock-free gate red for a cosmetic reason. The flag exists rather than the feature being simply absent because headless is the only backend CI can run, so it is the only place the capture-exclusion property can be proved on real composited pixels. `--agent-cursor` with `--nested` is refused at parse time rather than accepted as a no-op.

**What this supersedes, sentence by sentence.** Only the "composites no cursor" claims: `protocol/vitrin-v0.xml`'s §SCENE AUTHORITY "Version 1 serves neither layout verb and composites no cursor of its own", `vitrin_view`'s "version 1 also composites no cursor at all … so the rule is currently satisfied by construction", and `vitrin_actuator_pointer`'s "and composites no cursor of its own"; plus their prose restatements and the "invariant 4 holds vacuously" readings in `docs/protocol/00-conventions.md` §1.4, `docs/protocol/04-vitrin_grant.md`, and PRD §20.15/§20.16.

**What still stands, unchanged.** D-017 (1)–(5) in full, including that cursors are core-composited and that a realm may never supply the bitmap. `observe_cursor` is still refused `unsupported`, so **no capture contains any cursor today**. Agent→agent cursor visibility is still unpurchasable at any verb set, ever. The `ConsentGrab` defensive rule still exists and is still needed, because the *delivered* position is still shared.

**DEFERRED, explicitly:** **per-principal cursor *delivery*** — still **M2**, exactly as D-017 left it, arriving as `since`-gated sibling `vitrin_shim_seat` events that name the principal. Serving `observe_cursor` is likewise still deferred. Per-agent *drawing* over a shared *delivered* position is what v1 now ships; the two are independent, so this closes none of that deferral. Also deferred: a per-agent visual identity (colour or label per principal) — v1 draws one crosshair in one colour, so two agents pointing at once are indistinguishable on screen. That is a real limitation and it lands with the human→agent toggle surface (E3), which needs the human on the wire.

**Costs, stated:**
- **One more thing the compositor draws in the TCB.** `crates/vitrin-core/src/cursor.rs` is integer math over a borrowed buffer with const colours and no allocation — the `deadman::composite_hold_indicator` posture — but it is still new code in the trusted core for a display feature, and it is reachable from a position an agent controls. The band clip and the degenerate-geometry guards are the answer, and both are tested; there is no path here that trusts an agent's coordinate.
- **The two presentation paths can still drift, and only a test stops them.** Nothing structural forces the CPU composite and the dmabuf draw list to agree; what forces it is one shared geometry function plus `no_presentation_path_can_drop_the_agent_cursor`. That is exactly the arrangement the trusted band has, and the band's first cut shipped drift anyway.
- **Nested's sprite is not proved by a mock-free gate.** The capture-exclusion property is proved on headless (`the_agent_cursor_reaches_human_visible_output_but_never_a_capture`, a component test on real composited pixels) and the nested halves are pinned display-free (`window_pixels`, the texture key, the draw list). GL presentation itself needs a display, so "a human really sees the crosshair move in the host window" remains unproven by CI and rests on the operator recipe in `docs/demo/RECORDING.md`. Stated because the whole reason this change exists is a runbook that told an operator to watch something that was not there.
- **Two agents are visually identical**, per the deferral above.
- **Headless's default makes the two backends differ in what a human would see**, which the backend module docs otherwise argue against. The difference is a flag, not a code path — one `if` over the same shared function — and the reason is a named gate rather than convenience, but it is a real asymmetry and this is where it is recorded.
- **A hovering agent now costs composites it did not before.** An emulated motion that changes the integer hotspot dirties the frame and requests a present, where before only a client commit or a consent transition did. It is bounded at one composite per dispatch round by the existing `dirty` gate, and quantizing to whole view pixels drops sub-pixel churn, but an agent sweeping the pointer does make the nested backend draw.

**Amended by WS-E.1.3 (issue #209), 2026-08-07 — the sprite is drawn only for the realm on the output; sharpened by WS-E.1.6 (issue #212).** This decision was taken while a session held one realm, so "human-visible output" and "the realm the agent is acting in" were the same thing and part (3)'s output-stage fork said everything. With the output bound to one of up to `MAX_REALMS` realms, they are not: the sprite is painted in the *output's* coordinates over the *output's* realm, so `post_dispatch` looks the position up **by the realm the output shows** (`InputRouter::agent_pointer(realm)`) and an agent actuating inside a hidden realm draws **nothing**. Under #209 this was a *filter* on one session-wide position, which meant a hidden realm's agent motion could overwrite the position the visible realm would have drawn; the router now keeps one agent pointer per realm, so it cannot. The drawn-versus-delivered gap D-017 defers therefore exists N times over rather than once — per-principal *delivery* is still M2, and there are now N shared delivered positions to be wrong about instead of one. Parts (1)–(4) are otherwise unchanged — one seam, one geometry function, the same band clip and the same capture exclusion. The cost is that the human loses the only visual signal that an agent is acting, for everything off-screen, which is precisely the defect this decision exists to close, reintroduced for hidden realms. It is published in `docs/book/src/limits.md` and in `docs/plan/14-workstream-session-mode.md`; the fix is a per-realm indicator in the trusted band and nobody has scheduled it. Recorded here rather than left in the code because a reader of D-019 would otherwise conclude the sprite always draws.

### D-020 — The realm boundary is a namespace boundary: intra-user by default, in-namespace uid/gid, and a residue that lives outside every realm
**Status:** accepted (2026-08-06) — closes Q11 / PRD §20.11, issue #160; refines [D-010](#d-010--per-realm-isolation-dial)
**Decision:** six answers, one refusal floor.

1. **A realm is intra-user by default.** One host uid for the whole session — the uid `vitrind` already runs as — with the per-realm uid/gid PRD Doc 2 §4.5 promises delivered *inside* an unprivileged user namespace: `CLONE_NEWUSER` with a single-id `uid_map`/`gid_map` written by the parent while the child blocks on a sync pipe, and `setgroups` set to `deny` before `gid_map` (the kernel requires that order for an unprivileged writer). Alongside it, per-realm `CLONE_NEWNS | NEWPID | NEWIPC | NEWUTS | NEWNET`. The alternative — a distinct host uid per realm — was not available as a *default*, because it cannot be reached without privilege: it needs a provisioned subordinate-id range plus a setuid `newuidmap`-class helper, and requiring either would mean `vitrind` cannot start a realm on a machine nobody provisioned. A display server that refuses to run on an unprovisioned host is not a display server.
2. **PRD Doc 2 §4.5's "own UID" is delivered in-namespace, and the property it was bought for survives anyway.** §4.5 asks for own-UID for a stated reason — "so `/proc` snooping, SysV IPC, and same-UID `ptrace` do not cross realms." Each of the three is still closed, by a different mechanism than the one the sentence implies: `/proc` snooping by the PID namespace plus a private `/proc` mount, SysV IPC by the IPC namespace, and cross-realm `ptrace` by the user namespace — `ptrace_may_access` grants a same-uid tracer only when the tracer's user namespace is the target's *ancestor*, and two sibling realms' namespaces are ancestors of neither. So the guarantee holds while the mechanism differs, which is exactly the kind of gap that becomes a false claim if it is left implicit. **This refines D-010's "and UID regardless of tier":** read as a *host* uid, that sentence is false for the default tier as shipped, and the honest reading is per-realm uid/gid *within the realm's own user namespace*.
3. **The per-UID tier is a provisioned upgrade, never a silent default.** Where `/etc/subuid` carries a range for the invoking user and a `newuidmap`-class helper exists, a realm may be mapped to a distinct host uid; the preflight reports whether that tier is reachable, and it is selected explicitly, never inferred. **No packaging for this exists in this repo or anywhere else**, which is why it is stated as an exported limitation on C4 rather than as an available tier: E3.3 must own that packaging or the fleet ships on the weaker intra-user tier.
4. **The realm's private accessibility bus socket is a first-class member of the realm's private resource set** — at the same rank as the realm runtime dir and the realm's private storage, not a later addition. The realm mount table therefore reserves a **fixed in-realm path** for it now, in P2.6.2, before P2.1.3 exists to need it. This is decided here rather than in E2.1 because the ordering is forced: P2.6.2 owns the mount table, so a bus built first would have to be bind-mounted in afterwards and the confinement claim re-made (R2.6). A realm's private resource set is thus: its runtime dir, its private storage, its accessibility bus socket, and nothing else it did not receive by designation.
5. **Host-level sidecars are outside every realm, and therefore outside every realm's confinement.** The VLM parser (P2.4.3) and the egress proxy (P2.7.3) are ordinary host processes with principal identities. They are deliberately not realm members — the parser's memory-unsafety must be irrelevant to the TCB (PRD §17), and the proxy must be able to hold a listener inside a realm's netns without being confined by it. **The consequence is named rather than left to be discovered: the VLM sidecar has unmediated host network access.** E2.7's headline claim is therefore *"a realm with no egress grant emits zero outbound packets"* — a statement about the realm — and is **not** a statement that realm content cannot leave the machine. It can, through a sidecar the realm's netns says nothing about. That sentence belongs in `docs/book/src/limits.md` verbatim, and P2.9.4's sweep is its enumerator. Constraining the sidecars themselves is a decide-by-M3 item; it is not solved by attribution metadata and must not be described as if it were.
6. **The core measures its isolation tier at startup and refuses to start below a floor.** `--isolation=default` requires the full namespace set plus a Landlock ruleset plus seccomp; where the kernel cannot supply them, `vitrind` refuses rather than degrading silently, and `--isolation=none` is the explicit, named opt-out that exists so the confinement gates can run their positive controls. The tier is reported by `vitrind --print-isolation` and journaled per realm at spawn, so the flight recorder answers "what confined this realm" per run rather than per build.

**Why the question could not be deferred.** Q11 is the earliest hard gate in this log because it is not a policy preference — it is the shape of a syscall sequence three epics are written against. P2.6.2's clone flags, P2.6.3's Landlock ruleset, P2.6.6's picker resolution, P2.7.1's netns and P2.1.3's bus socket all encode the answer. Deciding it after any of them means rebuilding that one.

**DEFERRED, explicitly:** the **hardened (gVisor-class)** and **paranoid (microVM)** tiers of D-010's dial — neither ships in Phase 2, and the dial's *existence* must not be read as their availability. Also deferred: **per-UID provisioning packaging** — to E3.3; and **any confinement of the host-level sidecars** — decide-by M3, per (5).

**Costs, stated:**
- **D-010's plainest sentence is now qualified.** "Every realm gets its own network/PID/IPC namespaces and UID regardless of tier" reads, to anyone who has not found this entry, as a distinct host uid. It is not, at the default tier. The PRD sentence stays and this entry qualifies it, per the append-only rule — but a qualification a reader has to go looking for is a weaker instrument than a sentence that was right the first time.
- **A shared host uid means the host-side blast radius of a kernel userns escape is the whole session.** An escape from any realm lands as the user, with the user's files. Only the microVM tier escapes that class (D-010), and it is deferred. This is the cost of being startable on an unprovisioned machine and it is not mitigated, only stated.
- **R2.9 is not retired by this decision, only measured by it.** Distros that restrict unprivileged user namespaces turn the default tier into a refusal to start. The preflight makes that a clear message instead of a mysterious spawn failure; it does not make those machines work.
- **The sidecar residue is real, unmitigated, and ours.** (5) states it; nothing in Phase 2 closes it. Every honest statement of E2.7's guarantee has to carry it, which means four surfaces (`limits.md`, the epic, the gate's docstring, the entry here) must agree, and they will drift unless P2.9.4 checks them.
- **One more startup path that can refuse.** A floor that refuses is the right posture and it is also a new way for `vitrind` to fail on a machine where it previously started. `--isolation=none` keeps that escapable, and that flag is itself a way to run with no confinement while believing otherwise — which is why the tier is journaled per realm rather than only printed at startup.

### D-021 — Session mode is scheduled as a maintainer-dogfooding workstream (WS-E), and that is not the horizon item
**Status:** accepted (2026-08-06) — opens [14-workstream-session-mode.md](14-workstream-session-mode.md); supersedes the "keep at Phase 4" verdict recorded on issue #184
**Decision:** four answers, one boundary that must not blur.

1. **Session mode on bare DRM/KMS becomes scheduled work, as workstream WS-E.** [D-007](#d-007--scope-tiering-invariants--v1--horizon--renounced) says horizon items never migrate class without a decision-log entry, and [04-phase-4-horizon.md](04-phase-4-horizon.md) names session mode the **last** horizon item behind the M4 gate. This entry is that instrument. The maintainer has asked three times for vitrin to replace his existing compositor; the goal is now recorded rather than re-litigated, and WS-E is where its cost lands visibly instead of leaking into Phase 2 as unplanned drift.
2. **WS-E is not Phase 4's session mode, and the M4 gate is untouched.** This is the boundary the entry exists to hold. The horizon item is *a display server other people can run*: a hardware matrix, HDR, color management, fractional scaling, human accessibility, and IME for every user — the support treadmill [PRD](../PRD.md) §5.3 calls "90% of the effort for 0% of the differentiator". WS-E is *one maintainer's one laptop*: a single Intel-driven eDP output at scale 1, Wayland-only, spartan, with the maintainer fixing it when it breaks. Those targets differ by an order of magnitude, and conflating them would let a dogfooding success be read as clearing a gate it never approached. **No WS-E deliverable may be cited as evidence toward M4.**
3. **It is sequenced nested-first, bare-metal-last.** Stages 1–2 (multi-realm, layout verbs, a shell client, cross-realm clipboard — decided by [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing), which is the entry a reader looking for the clipboard's trust argument wants — a core-drawn lock screen) are backend-independent and build inside a window on the existing desktop; only Stage 3 takes DRM master. This ordering is chosen because it front-loads every deliverable that is *also* roadmap work — [D-018](#d-018--layout-is-a-capability-grant-governed-arrangement-core-enforced-ordering)'s layout verbs are allocated and unserved, and raising `MAX_REALMS` is Phase-3 fleet work — and because a backend that takes the seat cannot be iterated on safely from inside the session it would kill.
4. **The shell stays a client.** [PRD](../PRD.md) §5.1 makes "window-management policy lives outside the core" a *permanent invariant*, so WS-E's switcher and launcher are an SDK client holding `layout_focus`/`layout_arrange`, never core code. The cheap path — a switcher inside the compositor — was available, costs about the same, and was refused: an invariant that bends the first time it is inconvenient was never an invariant.

**Why this is defensible rather than merely wanted.** Dogfooding has already paid for itself once, measurably. Within an hour of `vitrind` being runnable by hand, a real terminal aborted the shim on a wlroots assertion (#203): `on_new_deco` answered an xdg-decoration request before the surface's initial commit, killing **every** decoration-aware client. The entire milestone suite could not have found it, because Firefox — the acceptance app — never binds `zxdg_decoration_manager_v1` at all. A project whose acceptance set is two clients has a blind spot exactly the width of what those two clients do not do, and a maintainer living in the thing is the only instrument that finds the rest.

**DEFERRED, explicitly:** everything in (2). No hardware matrix, no HDR, no color management, no fractional scaling (the target panel runs at scale 1, which is why this is affordable), **no accessibility of any kind**, and no IME beyond E2.8's single reference combination. XWayland stays E3.2's, not WS-E's.

**Costs, stated:**
- **Roughly a Phase-2's worth of maintainer time.** WS-E is estimated at 4–6 focused months against a Phase 2 whose remaining budget is about the same. Stage 1 is genuinely dual-use and Stages 3–4 are not; the schedule risk is that the differentiator stalls while the treadmill starts, which is the precise failure PRD §5.3 warns consumed prior alternative display servers. Nothing in this entry mitigates that. It is a priority choice and it is the maintainer's to make.
- **The DRM backend arrives with structurally weaker evidence than anything else in the tree.** GitHub runners have no DRM device and no seat, so the repo's mock-free definition-of-done cannot reach it. That is a real asymmetry against D12 and it must be published in `docs/book/src/limits.md` up front rather than discovered.
- **A shell-as-client means a shell crash loses window management.** The invariant in (4) is right and it has a price: with no core-side fallback, a dead shell leaves a running compositor the human cannot drive. WS-E must state what happens then.
- **`known-limit` grows before it shrinks.** No X11, no bars or launchers (no `zwlr_layer_shell_v1`, measured: waybar connects, binds six globals and never maps), no touch or gestures or lid switch, no accessibility. Each is a published gap this workstream *creates* by making a desktop people might otherwise assume is complete.
- **One machine, one GPU, one output.** Every WS-E number is measured on hardware chosen for being easy: Intel drives the panel, the discrete GPU is not in the display path, and the panel needs no scaling. None of it generalizes, and stating a WS-E result as a portability claim would be false.

### D-022 — Layout enforcement lands early for the nested single-output case; D-018's deferral is discharged, and its unpurchasable set gains a fifth member
**Status:** accepted (2026-08-07) — supersedes [D-018](#d-018--layout-is-a-capability-grant-governed-arrangement-core-enforced-ordering)'s "DEFERRED, explicitly" clause and closes the open name in D-018(4); issue #210, workstream [WS-E](14-workstream-session-mode.md)
**Decision:** six answers, no new verb bits.

1. **`layout_arrange` and `layout_focus` are served now, not at E3.** D-018 deferred *layout enforcement in its entirety* to E3, gated on M2's epoch work. That deferral is discharged **for the nested, single-output case only**: WS-E's shell (#211) is the first client that needs them, and it cannot be written against an unserved verb. What is *not* discharged is D-018(5) — E2.3's epoch does not exist, so an agent's cached coordinates can be invalidated by a shell with no compare-and-swap available to notice. That is a correctness gap for agents, created here and closed later, and it is stated in the costs below rather than implied.
2. **Two facet interfaces, not one, and the dialect forces it.** `vitrin_layout_focus` (`verb="layout_focus"`, request `focus`) and `vitrin_layout_arrange` (`verb="layout_arrange"`, request `set_fullscreen`), each minted by its own `since="2"` structural mint on `vitrin_grant`. `interface/@verb` is one value per interface — it is the codegen chokepoint that generates the single-site authority check — so a combined `get_layout` facet could declare only one of the two verbs and the other's requests would reach the chokepoint with no verb to check them against. D-018(3) requires the two independently attenuable; two interfaces is how the dialect makes that structural rather than conventional. `docs/protocol/00-conventions.md`'s Appendix A row said "layout facet", singular, and **understated the seam**; it is corrected in place, with the correction stated, because that row was the record.
3. **`layout_focus` is one act: bind the output and move the human's physical input with it.** Splitting "which realm is shown" from "which realm receives the human's keys", in a scene that shows one realm at a time, would let a holder make a human type into a realm they cannot see — the sharpest possible form of the focus theft D-018(3) names as "at once the sharpest attack and the most legitimate need". So **D-018(2)'s unpurchasable set gains a fifth member**: *the human's own physical input reaches only the realm the output is bound to.* An agent's injected input is not governed by it — that is addressed to the realm its own grant names and carries the `emulated` origin tag. Mechanically, `session::seat_target` now consults the output binding first and falls back to its old rule only when nothing is bound. **WS-E.1.6 (issue #212) made that its whole job**: it answers for the human's input alone, an agent's actuation is addressed by its own grant's realm through `InputRouter::route_emulated`, and the chokepoint's cross-realm refusal — which had made "an agent's injected input is not governed by it" true only by refusing the input outright — is deleted.
4. **`layout_arrange` serves exactly `set_fullscreen`, and every other arrangement request is ABSENT rather than refusing.** No `place`, no `resize`, no `raise`, no stacking — not a request that refuses, but no request at all. The scene fixed by #209 (one bound realm, no stacking, no overlap, no resize; `scene/layout.rs` says it "must never grow") cannot honour them, and a granted verb whose requests the server cannot carry out is the IDL's own "a deployment MUST NOT grant a verb it does not enforce" turned inside out. The two modes are the only arrangement this scene can express and neither invents a size: **fullscreen** means the realm's view size tracks the output's (`configure` re-sent with the output size, on entry and on every later output resize), **windowed** means the core imposes no size at all and the compositor letterboxes whatever the app keeps committing. A core that chose a third size would be choosing where a window goes, which is the window-management policy PRD §5.1 exiles.
5. **The single-holder answer is `layout_held`, an appended `outcome` entry checked at admission.** D-018(4) fixed the mechanism — "an appended `outcome` entry, since outcome is a plain enum and entries append" — and left the name open; this closes it at value 6. Admission-time rather than use-time, because contention is about who *holds* the authority rather than about one use of it, and because the refusal then never reaches a prompt and costs the human nothing. `busy` could not be reused: its meaning is the consent-fatigue valve, and widening it is a wire-semantics change the growth rules forbid. The check is against **any** holder, not against another *principal*'s — scoping it per principal would let one agent fragment itself into N arrangement grants and leave the core arbitrating between the fragments, which is exactly the arbitration D-018(4) refuses to do. **Holder counts a pending petition as well as a live grant**, and that is a decision rather than an implementation detail: were only live grants counted, two petitions could both be admitted while both waited, a human could approve both, and the session would end up with the two arrangers this rule exists to make unreachable — with no answer left to give the second, because it has already been granted. The slot is therefore taken from admission and released when the pending petition resolves non-`granted`. The cost, stated: a principal whose petition is in front of a human locks out a second principal for as long as that human takes to answer.
6. **Both layout requests are attention-shaped, so they meet `consent_held` and `preempted`.** The chokepoint's step 5b/5c were "actuation only"; they are now "actuation and layout". A principal that could fullscreen a realm over its own pending prompt's card, or move the output away from it, would be arranging the very decision it is waiting on; and moving the output out from under a hand already on the keyboard is the same hazard a synthetic click poses. Both verbs also meet `no_surface`, and the asymmetry with `realm_launch` is deliberate: a vacant realm is the state *launch* exists to leave, while focusing or arranging one would be a successful-looking answer to a request that did nothing.

**Why the four invariants could finally be tested.** D-018's cost note said of its own set that "none of the four is tested *as an invariant* against a client trying to violate it, and none can be until something outside the core can arrange realms". This is that moment, and the tests are the reason this entry exists rather than a note in a PR. Each drives a real client over a real socket, holding **every verb the reference core serves**, through the whole production path, and sweeps the *entire* arrangement space the two verbs can express — finite and small precisely because (4) defines one request. A property proved at the maximum verb set is a property of *no grant*, which is what "unpurchasable" has to mean.

**Costs, stated:**
- **D-018(2) gains a fifth invariant D-018 did not state.** Extending an accepted decision's enumerated set from a later issue is the drift the append-only log exists to prevent, which is why this is an appended entry rather than an edit to D-018 — and an appended entry a reader has to go looking for is still a weaker artifact than having got it right once.
- **The consent surface's unspoofability rested partly on nothing outside the core doing layout at all.** D-018's cost note says so in as many words, and this entry removes that circumstance. What replaces it is five invariants and five tests, and tests are a weaker instrument than "there is no mechanism".
- **The partial-verb hazard is avoided by omission, which is fragile.** Nothing structurally stops a later issue adding a `place` request to `vitrin_layout_arrange` while the scene still cannot honour it. What guards it is prose plus one test that pins the IDL's message count with a comment naming the stake — a tripwire, not a barrier.
- ~~**A `layout_focus` holder can deny service to every other agent.** `enforcement.rs` step 5d refuses an actuation whose grant's realm is not the seat's target; that target now follows the binding, so a holder chooses which *other* principals' actuations are refused. The refusal is recoverable, journaled, spends no token and burns no `once` rung, and it closes when #212 routes per realm — but until then it is a real cross-principal denial-of-service surface created by serving this verb. Published in `docs/book/src/limits.md`.~~ **Closed by WS-E.1.6 (issue #212), 2026-08-07.** Step 5d is deleted rather than relaxed: the grant's realm travels with the event (`UseEnv::grant_realm` → `session::route_seat`), an actuation over a realm the output is not showing is *delivered* to that realm, and there is no comparison left for a holder to influence. The `limits.md` paragraph that published it is gone with it.
- **`set_fullscreen` is a no-op whenever the output and the realm are the same size**, which is the ordinary case for a realm spawned into an output that has not resized. Honest, documented in the IDL, and surprising.
- **Serving layout early breaks D-018's stated sequencing**, per (1). E2.3's epoch is a *binding constraint* on layout in D-018(5), and it does not exist.
- **Two more facet interfaces and two more served verbs inside the TCB's enforcement path.** `single_enforcement_path` keeps the chokepoint singular, but the number of arms it dispatches grows and each is a place a future edit can route around.
- **`Verb::VALID_MASK` is unchanged, so the tripwires here were softer than WS-E.1.1's.** No new bit means `crates/vitrin-protocol/tests/decode_errors.rs` did not fire. **Six** did, and the count is stated exactly because this bullet is the artifact recording the guard's record: the consent catalogue's unserved-set pin (`consent/render.rs`), the grant table's served/unserved pins (`grants.rs`, both halves), `vitrin_grant`'s defined-opcode test, the roundtrip table's message-count exhaustiveness gate (`crates/vitrin-protocol/tests/roundtrip.rs`), the C header's parallel gate (`shim/tests/test_header_compiles.c`, 32 → 36), and `protocol/test-mutations.sh`'s `verb-without-facet` case — which fired by going *stale*: its mutation (`realm_launch` → `layout_arrange`) became a legal document once `layout_arrange` gained a facet, so it reported the schema as broken when the schema was right, and was re-pinned on `observe_cursor`, which is facetless by construction. Each was re-pinned with a stated reason rather than a mechanical bump. Had any been weakened, a verb could have become served with no prompt copy, which is the exact failure D-017's guard was built against. A seventh, in the Python SDK (`test_typed_exception_mappings_are_exhaustive`), did **not** fire when it should have: it counts `Outcome` members against the mapping table, and appending `layout_held` to the IDL alone left both untouched — the SDK's copy of the enum is a hand transcription, so the gate could only fire once a human edited it. That gap is what let `layout_held` decode to `ServerContractViolation` and close the connection until it was found in review.
- **The nested half is not proved by a mock-free gate.** That a human sees the focused realm change in the host window is a manual runbook step: runners have no display and headless is the only backend CI runs (D-019(4)).

### D-023 — The core owns a second physical chord: a tapped, consumed attention key that lifts `preempted` for the two layout verbs only, and delegates nothing
**Status:** accepted (2026-08-08) — falsifies `crates/vitrin-core/src/deadman.rs`'s "the core owns exactly one physical chord" and makes [D-022](#d-022--layout-enforcement-lands-early-for-the-nested-single-output-case-d-018s-deferral-is-discharged-and-its-unpurchasable-set-gains-a-fifth-member)(6)'s `preempted` conditional; issue #232, workstream [WS-E](14-workstream-session-mode.md)
**Decision:** three answers, no new verb bit.

1. **The attention key is a statement about the human's own input state, not a delegation — and the whole design rests on that reading.** A human at an in-realm shell cannot ask it to change the layout: they type `focus editor`, press Enter, and that Enter marks `PhysicalPresence` in the realm they are in, so D-022(6)'s step 5c refuses the request `preempted`. **The input that tells the client to act is the input that forbids it**, and pressing Enter again re-arms the window, so it is a deterministic loop rather than a race; `fullscreen on<Enter>` hits the identical loop. The mechanism is the smallest thing that expresses the missing distinction: a second core-owned chord — **Super, tapped, consumed** — opening a one-second, single-use, session-wide window in which a `layout_focus`/`layout_arrange` use by a principal the signal reached is not refused `preempted`, plus one argument-free `vitrin_principal.attention` event to every principal holding layout authority. What makes a bare bit defensible is that **step 5c is not a focus-theft defence**: it is a 500 ms courtesy, and a `layout_focus` holder can already take the output at any moment the human pauses for half a second, which is most moments. The grant, its revocability and the dead-man switch are what bound focus theft. So the press *withdraws a courtesy the core extends to the human's typing*; every authority exercised afterwards came from a grant approved on a consent card naming the principal and the realm, and a client that provokes the press gains **timing, never authority**. Consequences that follow from that reading and were taken rather than argued around: **no verb bit is allocated** (a grantable "receive the human's attention key" verb would put the delegation framing on the wire — `Verb::VALID_MASK` stays 575 and [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5's registry is untouched); the event carries **no arguments, forever** (a `window_ms` would make the core's own security parameter a client's timer); the chord is **consumed**, so no confined app learns the human pressed it and the authority-gated wire event is the only observation path, closing a free keystroke-timing oracle; and the chord still **marks physical presence**, because the core must not manufacture a false fact about where the human is.
2. **This should not have been a consent prompt, and the reason is that the consent surface's value is its scarcity.** The honest alternative was *no chord at all*: when 5c would refuse a layout use, raise a prompt naming the principal and the realm. That is strictly stronger on every property this decision is weakest at — it cannot be hoarded, it names its subject in core-drawn pixels, and confused-deputy provocation dies against it. It loses on one thing and it is decisive: in an in-realm shell 5c fires on *every* switch, so the prompt would appear on the session's single most-used action, answered by a mouse click through `GUARD_INTERVAL` several times a minute. That trains reflexive clicking on the one surface in this system whose entire worth is that a human reads it, and it degrades every *other* prompt in the session — Q9 already tracks consent fatigue as a live problem and this would be its largest single contributor. A modal card is the right instrument for a first-contact delegation of authority and the wrong one for a courtesy the human is withdrawing from themselves. What replaces the card is: the exemption is **single-use** and claimed only at step-6 admission and only when 5c actually suppressed a refusal (`Exemption` is `#[must_use]`, not `Copy`, and consumed by value, so a second claim from one press is a compile error); delivery is **filtered** to live layout holders and the claim is restricted to that same set resolved at press time; every press and every claim is **journaled**; and the human sees a **marker beside the trusted band** while the window is open — beside, never inside, because the band's whole value is having exactly one correct appearance (#215's rule for the clock and battery, applied here for the same reason).
3. **A second core-owned chord must justify itself and must not borrow the dead-man's warrant.** `deadman.rs`'s module docs were emphatic that the core owns exactly one physical chord *because the human's off-switch must not depend on a client*. That sentence is now false and is rewritten rather than quietly left — but the warrant stays **narrow**: it was never "the core may own chords in general", and a third chord makes its own case from scratch. The general rule this fixes for any future one: **a hold is for the irreversible and severe; a tap is for the cheap and reversible.** An accidental attention press costs at most one focus change, undone by pressing again; an off-switch may not fire by accident at all. The two are kept structurally apart at every level: disjoint vocabularies (`Chord::VOCABULARY` excludes every modifier for its own reason, the attention vocabulary is nothing *but* the two Supers, so they cannot collide even before the startup equality check that is kept anyway); the dead-man detects in `observe` — unconditional, unstoppable, owning all its own state — while attention only ever gates, suppressible by a consent prompt, by the dead-man, and by anything above it; `DeadManHook` is stacked **outside** `AttentionHook` so a chord press wins; `apply` clears any open window belt-and-braces beside `seal_dead_man`; and the hold indicator stays the last thing composited so the marker can never hide it. Attention's failure mode is a focus change that does not happen; the dead-man's is a revocation that does not happen. They are not in the same class and nothing may make them look like it.

**Costs, stated:**
- **The core now eats Super, everywhere, unconditionally.** A confined app that legitimately wants it — a nested compositor, a VM viewer, a remote-desktop client in a realm — loses the key with no pass-through and no way to ask for one. That is the cost `deadman.rs` refused to pay for Escape, paid here for a different key on the argument that every desktop already reserves it for the compositor. If that argument is wrong for someone's workload the only remedy is `--attention-chord rsuper`, which is not a remedy. Published in `docs/book/src/limits.md`.
- **The session-wide window is a real hole and the delivered-to set only narrows it.** Any principal the event reached may claim it; the core cannot tell which of two layout holders the human meant, and it cannot be fixed here — choosing a recipient means choosing a shell, which is the window-management policy PRD §5.1 exiles, and the mapping that would make it structural ("the principal that draws in the bound realm") does not exist because a realm and a principal connection have no binding. A second holder can consume a press the human aimed at the shell; the human's own switch then silently fails and the thief's lands. Journaled, revocable, and still a hole.
- **Confused-deputy provocation is not closed and cannot be.** A shell printing "press Super to apply" is doing the right thing; a malicious one printing the same string and banking the timing is indistinguishable. What bounds it is that the press confers no authority the client did not already hold — an argument only as good as the reader's willingness to follow it, and a human who learns "press Super when the screen tells me to" has learned a habit an attacker can invoke.
- **`preempted` on the layout verbs becomes conditional on invisible core state.** An agent reading its own journal can no longer reconstruct why one `focus()` landed and an identical one did not without correlating attention entries it cannot see. The refusal used to mean one thing. This is the protocol's **first conditional refusal code**, and the precedent is the cost as much as the confusion is.
- **Other principals lose a guarantee nobody tells them they lost.** "A human typing means nobody moves the output" was true for 500 ms at a time and is now suspendable by a gesture no wire event announces to anyone but layout holders — the same shape as the narrowing WS-E.1.6 published, and it needed the same `limits.md` paragraph.
- **`vitrin_principal` grows past "the root of the connection's authority chain".** It becomes the place session-level facts about the human arrive. That is defensible once; it is also the seam through which a future issue puts a second, less defensible fact there because there is now a precedent. Recorded on `docs/protocol/02-vitrin_principal.md` so the precedent is at least visible to whoever cites it.
- **The dead-man's docs were written as if it would stay alone, and rewriting them risks weakening the argument by generalising it.** The sweep kept the warrant narrow — admitting a neighbour rather than opening a category — and that is a harder edit than it looks. What guards it is prose plus `an_attention_press_in_the_same_round_changes_nothing_here`, which compares every observable of a full hold with and without the neighbour stacked.
- **A new way for a session not to start.** Startup now refuses on chord collision. Correct, fail-closed, unreachable today (the vocabularies are disjoint), and one more configuration an operator can get wrong at the moment they least want to.
- **Two indicators now compete for the top strip and a third is scheduled** (#215's clock/battery/focused realm). Nobody has designed that strip as a whole, and each issue that adds to it is deciding the layout of a surface whose whole purpose is being unambiguous.
- **The nested half is not proved by a mock-free gate, and cannot be.** `SeatInput::physical` is private by design, headless has no input device, and headless is the only backend CI runs (D-019(4)). `tests/integration/test_attention.py` proves the *consequence* half through the `physical-input-injector` channel — the same split #212 wrote out and the same one `deadman.rs` accepts for its detection half. That a real Super press on real hardware reaches the gate is a nested manual runbook step (`shim/docs/nested-multi-realm.md`), not a criterion.
- **What this does not fix, and must not be read as fixing:** the in-realm shell's confinement problem (#211 decision 2 — the shell still has to reach the core socket from inside a realm); the absence of a read of which realm is focused (page 17 refuses it on purpose); D-018(5)'s missing epoch, so an agent's cached coordinates are still invalidated by a layout change with no compare-and-swap to notice; a shell crash losing window management; or anything about `actuate_pointer`/`actuate_text`, which stay preempted by a human's hand exactly as they are today.

### D-024 — The cross-realm clipboard is a core-held single slot, PULLED by the core on two human gestures that delegate nothing
**Status:** accepted (2026-08-08) — implements [PRD](../PRD.md) §11's clipboard broker for the nested single-output case, narrows PRD §15's first threat row, and falsifies `shim/src/globals.c`'s *"cross-realm clipboard remains exactly where it belongs, unbuilt"*; issue #213, workstream [WS-E](14-workstream-session-mode.md) §4.1
**Decision:** five answers, one refusal, and **no verb bit**.

1. **The bytes live in one core-held slot, and the maintainer chose that knowing what it costs.** This is the only answer in this log recorded as an owner's call rather than as an argument's conclusion, and it is recorded that way on purpose. Taha was asked, in plain terms, on **2026-08-08**, and given four options: (a) a core-held single slot, (b) no buffer and a direct A→B pipe brokered at paste time, (c) a per-realm broker, and (d) do not build it. He was told the cost of (a) in exactly these words — *for the first time the trusted core retains bytes an application authored, so a compromised core exposes whatever was last copied* — and chose (a). (b) was rejected for its **timing leak**: it needs both realms alive at paste time, and it tells A exactly when B pasted, which is a covert channel running from the sink back to the source, the one direction a mediator exists to close. (c) multiplies state by `MAX_REALMS` and changes no trust question. (d) was offered and declined. Nothing in this decision is a default somebody picked.
2. **The core PULLS, and the wire shape makes that structural rather than conventional.** `vitrin_shim_session` gains three `since="2"` messages: `request_selection` (event, core → shim), `selection` (request, shim → core), `offer_selection` (event, core → shim). There is deliberately **no `selection_changed` event**: a shim that forwarded every app-side copy upstream would make every ordinary Ctrl-C a cross-realm event, which is an ambient channel wearing a broker's clothes and would make the Qubes phrase this design quotes — *"fully controlled by the user, it cannot be triggered/forced by any"* realm — false in the first sentence. The hybrid (push a MIME-and-length notification, pull the bytes) was rejected too: a per-copy cross-realm signal is a free keystroke-timing oracle over the human's own editing, and it buys nothing. What makes "the core pulls" more than a rule the code follows: `ClipboardSlot::fill` takes a `PendingPromotion` **by value**, that type has no public constructor, is neither `Copy` nor `Clone`, and is minted only when a human's promote gesture actually fires — so an unsolicited `selection` from a compromised shim has no ticket to consume and fills nothing. A shim that pushes is a type error, in the mould of D-023's `Exemption` and #207's `SpawnRecord`.
3. **The human path is not grant-governed, and that is a considered answer.** Grants key on a `PrincipalIdentity` bound at `hello`; **the human at the keyboard is not a wire principal in v0**, so a `clipboard` verb bit would name a principal that is not the actor, burn an immutable bitfield entry on authority nobody can hold, and touch `identity.rs`, `principals.toml`, the grant table and the consent surface in one change. The dead-man switch sets the precedent this follows: the human's gesture is **a fact the core acts on, journaled** — never authority the core issued. A consent prompt per transfer was the honest alternative and is refused for [D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing)(2)'s reason, which binds harder here: copy-paste is a several-times-a-minute act, and a modal card on it would train reflexive clicking on the one surface in this system whose entire worth is that a human reads it. `Verb::VALID_MASK` therefore stays **575** and [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5's allocation registry is untouched.
4. **The gesture is Ctrl-Shift-Insert (promote) / Shift-Insert (offer), and it could not have been Ctrl-Shift-C.** `invariant_keysym` is a fixed scancode table with **no letters and no digits** — asserted, not assumed (`input/mod.rs:1772-1774`). Letters reach the core today only in nested mode, because winit resolved `logical_key` and the *host* compositor did the interpreting (#118); on bare DRM in WS-E Stage 3 there is no host, so the Qubes chord would work on the maintainer's laptop and stop working the day the workstream arrived at its point. Growing an xkbcommon keymap in the core is refused here rather than merely deferred: `input/mod.rs:106-109` records that a real keymap moves key pairing from the keysym to the scancode — a **router invariant**, on the path the dead-man switch depends on — and it is Stage 3's decision, which a clipboard issue must not pre-empt. `KEY_INSERT` is in the table and already in the dead-man vocabulary, and Shift-Insert is the historical X11 clipboard chord, so the pair is familiar rather than invented. A chord this build cannot deliver is refused at **startup**, through the same `input::keysym_is_intakeable` check `deadman::Chord::parse` uses, for the same fail-closed reason.
5. **`text/plain;charset=utf-8` only, 61 440 bytes, cleared on timeout, on source-realm death, and on a dead-man trigger.** Every other MIME type is a decoder question and *"no image codec in the core, in any dependency class"* is a rule `crates/vitrin-core/Cargo.toml` states twice; `text/uri-list` is refused separately, because a path is a **designation** and designation belongs to the powerbox (E2.6) — a clipboard that moves paths is a file-transfer channel wearing a clipboard's clothes. The cap is **measured, not asserted** (WS-E §4.1 carries the table). Two bounds meet and only one is a choice: the wire's `u16` frame size caps a whole frame at 65 535 bytes, so the largest string a `selection` can carry is **65 476** and the issue's proposed 1 MiB is *inexpressible* without an fd — which would put a shim-controlled mapping inside the TCB, re-opening the size-lie and SIGBUS class the buffer path already spends `invalid_buffer` on, to carry a clipboard. Within that ceiling, over this repository's text files a 60 KiB cap copies **92.26%** of them whole against the frame maximum's **92.90%** — so the last 4 036 bytes buy **0.64 points** and spend every byte of framing headroom. (Those figures are the corrected ones. The first measurement globbed the working tree, which then held ~40 scratch worktrees, a vendored wlroots checkout and build output, so ~96% of the 6 550 files counted were not this repository and none of its five statistics reproduced; re-measured over `git ls-files`, 310 tracked text files, median **11 410 B**, p95 **106 707 B**, p99 **240 239 B**. WS-E §4.1 was corrected when the error was found and **this entry was not**, which is the drift a decision log exists to prevent — recorded rather than silently patched.) 61 440 leaves 4 039 bytes spare, which is room for `selection` to gain an argument later without the cap moving; the cap lives in the IDL's immutable `(max N bytes)` token and therefore *cannot* move. "Cleared on paste" was rejected because humans paste twice.

**This discharges NONE of E3.5's exit criteria, and the reason is not modesty.** [03-phase-3-network-x11-fleet.md](03-phase-3-network-x11-fleet.md) §E3.5 owns the *hardened* broker, drag-and-drop as designation, window activation and the portal-compat layer, and its criteria are `copy in realm A → paste in realm B requires two explicit user actions and is journaled`, `the portal-compat matrix is published with pass/fail per app`, and `no shared clipboard exists anywhere (verified, not asserted)`. The first *looks* discharged and is not: E3.5's is a **fleet-scale** claim over network sessions and the headless deployment PRD §81 promises *"no shared seat, no shared clipboard"* for, and this is one nested single-output session on one laptop with no network path, no agent-facing verb, no drag-and-drop and no portal. The third is a verification obligation over every deployment, and this issue **adds a clipboard** to one of them. What #213 delivers is the *subset* E3.5 hardens; citing it against any E3.5 criterion would be the exact class of honesty gap the milestone rule in `CLAUDE.md` exists to forbid.

**Also decided here, because two later issues consume it:** the modifier-aware chord matcher (`crates/vitrin-core/src/chord.rs`) is **general**, not clipboard-private. `deadman::Chord` deliberately excludes every modifier (a human holds Shift for seconds at a time, so a modifier off-switch fires during ordinary use) and `attention::AttentionChord` is nothing *but* the two Supers; neither can express `ctrl+shift+insert`. WS-E.2.2's lock chord (#214) and WS-E.2.4's screenshot key (#216) both want one, and whichever lands second must consume this rather than adding a parallel matcher in the same hook stack — which `deadman.rs`'s module docs spend hundreds of lines explaining the hazard of.

**Costs, stated:**
- **The TCB stores application-authored bytes.** (1)'s accepted cost, restated here because it is the entry's whole weight: a password copied from a manager transits `vitrin-core` and rests in a slot with a lifetime. The cap, the allow-list, digest-only journaling and three clearing rules bound it; **none removes it**, and no future entry should describe them as if one did.
- **A published claim becomes narrower, in the PRD itself.** PRD §15 row 1 said a malicious app cannot *"reach the session's real seat/clipboard/a11y bus"*. It can now reach a clipboard — through a human gesture, one direction at a time, one MIME type, 60 KiB at a time. The row is **edited**, not left standing, and `docs/book/src/limits.md` carries the channel. PRD §81's headless-fleet promise is untouched and must stay untouched: nothing here is reachable without a physical keyboard.
- **It is a covert channel with a stated bandwidth, not an absent one.** Two colluding realms move ~60 KiB per human gesture pair. Qubes accepts the same bound. The honest statement is always the bound.
- **New wire surface freezes into v0.** Three `since="2"` messages and one enum, immutable thereafter. A shape chosen against one maintainer's laptop is a shape E3.5 inherits, and the one place that is load-bearing is the byte cap: it is a `(max N bytes)` token, so raising it later is a *new message*, not an edit.
- **The core owns two more physical chords, in the hook stack the dead-man switch lives in.** D-023 said a second chord *"must justify itself and must not borrow the dead-man's warrant"*, and that warrant does not stretch to a third and fourth. What justifies these: they are **taps, for the cheap and reversible** (D-023(3)'s general rule — an accidental promote costs one slot overwrite, an accidental offer costs one seat selection), they live in `gate` only and never in `observe`, they are stacked **inside** both the consent grab and the dead-man hook so neither can be delayed by them, and their vocabulary is disjoint from both existing chords by a startup check rather than by assertion. What it costs anyway: `deadman.rs`'s sentence about how many chords the core owns is now wrong for the second time in two issues, and a stack of four chord matchers is four places to get the gate wrong.
- **Shift-Insert is taken from every app in every realm.** The historical X11 primary-paste chord, consumed with no pass-through and no way to ask for one — the cost `deadman.rs` refused to pay for Escape and D-023 paid for Super, paid a third time. The argument that makes it affordable is narrower than D-023's: not *"every desktop reserves it"* (they do not), but *"the gesture the human loses inside a realm is the gesture they gain across realms"*.
- **The detection half cannot be proved in CI, and that is structural.** GitHub runners have no physical input device; `SeatInput::physical` is private by design and headless is the only backend CI runs (D-019(4)). The gesture's *effect* is proved through the `physical-input-injector` channel, reaching the same entry point a real chord reaches; that a human really holding Ctrl-Shift-Insert produces the gesture is a manual runbook step in `shim/docs/`, and the acceptance criterion is written as a runbook rather than a green check on purpose.
- **The slot has no wire event when it is cleared.** A human who copies, waits out the timeout and then presses Shift-Insert gets nothing and no message. The core has no surface on which to say so — the trusted band is a colour and the consent stack is for authority decisions — and inventing one for this was refused as scope. It is a real usability hole.
- **Dependency budget.** Issue #201 records that there is still no `deny.toml` and no `cargo-deny` job, so plan risk R7's stated mitigation is unbuilt while this adds wire code, C code and core state. Unchanged by this entry; restated because it is still true.

### D-025 — A locked screen does not suspend agent observation; the gap is published, not papered over

**Status:** accepted (2026-08-08) — implements WS-E.2.2's lock screen (issue #214) under [PRD](../PRD.md) §5.1's trusted-path reading of the window-management invariant; workstream [WS-E](14-workstream-session-mode.md) §6

**Decision:** **the maintainer's call, asked and answered in plain terms on 2026-08-08, and recorded as his rather than as an argument's conclusion.** Taha was told, in exactly these words, that a lock screen on this stack takes the *human's* input away and leaves an agent's authority untouched — so a principal holding `observe` keeps capturing the realm across a lock, frame for frame, and one holding `actuate_pointer`/`actuate_text` keeps acting. He was offered the alternatives below and chose to **leave observation concurrent and publish the gap loudly**. Nothing in this entry is a default somebody picked, and it is not to be re-litigated by a later issue that finds it surprising: being surprising is the reason it is published.

**Rejected *with* him, each for a reason that is not "it was hard":**

1. **A new refusal code** (`locked`, or `preempted` widened to cover a lock). This is a **v0 wire-semantic change**: `protocol/vitrin-v0.xml`'s `vitrin_view` states that observation is concurrent by design, so `preempted` and `consent_held` deliberately never refuse a capture. Redefining that is the protocol track's and E3's, not a `track:rust-core` issue's, and `Verb::VALID_MASK` stays **575** with [02-phase-2-semantic-epochs.md](02-phase-2-semantic-epochs.md) §5's allocation registry untouched.
2. **Blanking the realm view for agents while locked.** An agent silently receives black frames and is never told why — a lie by omission, and the exact class of dishonesty `refusal.no_surface` exists to avoid. It would also make "the capture is byte-for-byte `Scene::compose`" false, which is the sentence three modules' structural arguments rest on.
3. **Routing the lock through the enforcement chokepoint as a synthetic human principal.** This invents a wire principal the identity layer does not have. The dead-man switch already sets the precedent for the honest shape: the human's gesture is **a fact the core acts on, journaled** — never authority the core issued.

**What makes it defensible rather than merely decided:** the human's instrument for "stop everything" is unchanged and, by design, **still works while locked**. Holding the dead-man chord revokes every grant, denies every pending petition, seals the table and clears the clipboard slot. Issue #214 called that stacking requirement "not optional — a lock that disables the human's off-switch inverts the safety argument", and it is enforced structurally rather than by review: the lock's policy implements `crate::input::ConsumingGate`, a trait with **no observation method**, and the `PreemptionHook` impl that forwards the observe tap lives in `crate::input`, which has no `use crate::lock` at all. An edit inside `crate::lock` cannot make the off-switch's detection conditional, because the code that observes is not reachable from there. That is the [#210](https://github.com/vitrin-os/vitrin-os/issues/210)/[#232](https://github.com/vitrin-os/vitrin-os/issues/232) shape — make the mistake unconstructible — applied one level up, and `the_dead_man_chord_arms_and_fires_through_a_locked_gate` holds the consequence against the **real** `InputRouter<LockGate<ConsentGate<DeadManHook<ClipboardHook<AttentionHook<NoopHook>>>>>>` rather than a stub.

**Also decided here, because they are the same judgement applied to smaller questions:**

- **The lock screen is core code, and PRD §5.1 does not say otherwise.** The invariant exiles window-management *policy* — decorations, layout, arrangement. It does not exile the trusted path: the consent surface, the trust band, the attention marker and the dead-man indicator are all core-drawn under it. The discriminator is whether the pixels make an authority claim a human must be able to believe, and a lock screen makes the sharpest one in the system. [D-021](#d-021--session-mode-is-scheduled-as-a-maintainer-dogfooding-workstream-ws-e-and-that-is-not-the-horizon-item)(4) closes the alternative: the WS-E shell is deliberately a client and D-021 already prices "a shell crash loses window management" — as a lock screen that would read "a shell crash leaves the session unlocked".
- **The card says the surprising part, not only this log.** `crate::lock::render`'s honesty block tells the human, on the trusted surface itself, that agents keep working and that the dead-man chord is what stops them. A warning a human cannot act on is one `crate::consent::render` already refuses to print; this one names the instrument in the same sentence.
- **A passphrase is nested-only, and refusing it elsewhere is fail-closed.** `crate::input::invariant_keysym` has no letters and no digits — asserted, not assumed. Letters reach the core in nested mode only because winit resolved `logical_key` and the *host* compositor did the interpreting (issue #118). `--lock-passphrase-file` is therefore **refused at startup** with `--headless`, naming the keymap as the reason and exiting non-zero, exactly as `--headless --consent=interactive` is. Growing an xkbcommon keymap is refused here rather than deferred quietly, on [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing)(4)'s grounds: `input/mod.rs:106-109` records that a real keymap moves key pairing from the keysym to the scancode — a **router** invariant, on the path the dead-man switch depends on — and that is Stage 3's decision to take explicitly.
- **The shared rasterizer moved out of `consent`.** `crate::paint` (canvas, embedded-font text engine, one `centered`) is now its own module, because `deadman`, `cursor` and `attention` were already importing `consent::canvas` — a path that said the off-switch draws with the consent surface's private tools. Moved, never copied: two rasterizers in one TCB is two places for a golden to drift.

**Costs, stated:**

- **A locked screen an agent can still watch.** The whole weight of this entry, restated because it is the thing a reader will most want to believe was fixed. It was not fixed; it was decided, and it is published on the card, in `docs/book/src/limits.md` and in [WS-E](14-workstream-session-mode.md) §6.
- **In nested mode this is a demo, not a lock.** `vitrind` is a client of the host compositor, which owns the real session; anyone can alt-tab away. Stages 1–2 ship a lock screen that locks a *window*.
- **On bare DRM, VT switching is an escape** unless the core inhibits it — and inhibiting it means a session a human cannot leave when the compositor wedges. Not decided here, and this entry must not be read as deciding it.
- **A KDF entered the TCB, and it processes operator-supplied input.** Four crates (`argon2`, `base64ct`, `blake2`, `subtle`), measured against `Cargo.lock` rather than estimated. Unlike fontdue — justified on "the only bytes it parses are a compile-time constant" — this one really does parse bytes an operator wrote, though never bytes that arrived over the wire. Issue #201 records that `deny.toml` and the `cargo-deny` job still do not exist; `crates/vitrin-core/Cargo.toml` is the only place the budget is checked.
- **A fourth gate in the input stack, and a fourth chord taken from every app.** D-023 said a second chord *"must justify itself and must not borrow the dead-man's warrant"*, and D-024 already spent that argument twice. What justifies this one: it is the one gesture in the set that **cannot** be a client's, for exactly the reason the dead-man switch cannot; and it is cheap and reversible in D-023(3)'s sense only when no passphrase is configured, which is why the card names which of the two it is. What it costs anyway: `Ctrl-Alt-Delete` is consumed in every realm, and `--dead-man-chord delete` is now refused on an otherwise default command line — because the switch detects in the unconditional observe tap, so a lock chord sharing its key would arm the off-switch every time a human locked their screen.
- **CI cannot prove the security property, and the criterion is written to say so.** "A human at a real keyboard cannot get past it" needs a real keyboard and, on bare metal, a real seat; no GitHub runner has either. What CI proves is the composite, the golden, the gate's pairing behaviour, the recorder entries and the off-switch's survival through the real stack. The end-to-end claim is a dated manual runbook (`shim/docs/nested-lock-screen.md`), which is the same split [D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing) and [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) already accept for their detection halves.
- **New always-resident core state on the frame path.** A second `ConsentSurface`-shaped cost per backend, and a raised lock forces the CPU compositing path for as long as it is up — so the zero-copy dmabuf branch is off while the screen is locked. That last part is not a cost so much as a requirement: without it the branch would present the client's own texture, full-window, with the lock nowhere on it.

### D-026 — The top strip is designed as one surface: the band alone, then the status strip beside it, and the app's rows are still overdrawn

**Status:** accepted (2026-08-08) — implements WS-E.2.3's status strip (issue [#215](https://github.com/vitrin-os/vitrin-os/issues/215)); workstream [WS-E](14-workstream-session-mode.md) §6

**Why an entry at all:** three issues drew into the rows around the trusted band and each was designed without the others — the dead-man hold bar ([D-023](#d-023--the-core-owns-a-second-physical-chord-a-tapped-consumed-attention-key-that-lifts-preempted-for-the-two-layout-verbs-only-and-delegates-nothing)'s neighbour), WS-E.1.7's attention marker (#232), and this strip. WS-E §6 recorded that as an unowned collision and named the third to land as its owner. This is that decision, made once and written where the next person will find it.

**Decision, in draw order:**

```text
realm view -> consent overlay -> lock cover -> STATUS STRIP -> trusted band
           -> attention marker  ...  -> dead-man hold indicator (last of all)
```

1. **Nothing is ever composited into the band.** Rows `[0, TRUST_BAND_HEIGHT)` stay exactly one colour. This is not a review rule: the strip's raster is the *strip's* own height and is blitted at `y = TRUST_BAND_HEIGHT`, so no coordinate expressible in `status::render` lands in the band. It is also measured — `band_witness`'s `band_changes` stays `0` over composites its new sibling `strip_changes` proves were really repainting.
2. **The strip is composited over the lock cover, not under it.** #215 left this open for whoever landed second; #214 landed first, so #215 decided it. A clock is the one thing a human wants on a lock screen, and "the strip is always there" must have no exception — a rule with an exception is a rule a human cannot apply. It leaks nothing the lock exists to hide: the lock's job is that *client* content stops being legible, and every field on the strip is core-owned, including a `realm.toml` id the lock card itself already prints.
3. **The attention marker keeps a lane rather than relying on z-order.** The strip's content starts past `attention::MARKER_W`, read from that constant and never restated, under a `const` assertion that turns an overgrown marker into a compile error. Ordering alone would keep the marker *visible*; it would still leave a glyph half-covered whenever the window is open.
4. **The dead-man hold indicator stays composited last of all.** Unchanged, and restated because every addition to this surface is a chance for it to stop being true.
5. **The strip is opt-in (`--status`, off by default).** The `--agent-cursor` precedent, for the same measured reason: the headless human-visible framebuffer is compared byte-for-byte against the realm view by `band_witness` and by `tests/integration/test_real_trust_band.py`, and a clock on by default would make a mock-free gate a function of the time of day.
6. **The clock is a fixed offset, not a timezone.** The core takes no tzdata parser and no recurring `/usr/share/zoneinfo` read into the TCB for a cosmetic field. `--status-utc-offset` states an offset; the strip always labels the zone it draws, so a wrong hour is a wrong flag rather than a wrong clock. No DST.

**Costs, stated:**

- **The realm view is NOT inset, and #215 asked for it.** The strip overdraws 20 rows of client content the way the band already overdraws 8; the app is not configured smaller and does not lay out for it. A correct inset needs one usable-view value reaching `scene::layout::place` from three paths that share no carrier for a second number (`Scene::compose`, the router's `surface_local`, `dmabuf::human_visible_frame`) plus the `configure` size the shim is told — a `ViewGeometry` refactor of its own — and a half-done version, one path reserving rows the others do not, is strictly worse than none. Deferred deliberately, published in `docs/book/src/limits.md`, and the reason `--status` is opt-in.
- **The indicator story is three rules where it was one.** "Everything above the coloured line is trusted, the line itself is the proof, and the strip below it is trusted-but-not-self-proving." An app can paint a convincing fake strip one row lower; the band is the only anchor. `limits.md` already concedes the indicator is "unforgeable, not necessarily noticed", and this widens what a human has to notice.
- **A recurring filesystem read inside the TCB.** The first one: `/sys/class/power_supply`, every 30 s, bounded to one fixed root, 16 entries and 16–32 bytes per attribute through `Read::take`, every failure an empty slot rather than a guess. When E2.6/E2.7 confine the core with Landlock this becomes a rule the core must grant itself — a real widening of that future sandbox, recorded here and in WS-E §6 rather than left to be rediscovered.
- **The zero-copy draw list gained its first stateful member.** `dmabuf::human_visible_frame` was a pure function returning solid-colour draws, which is what made "no arm omits the band" structurally true. `Draw::StatusStrip` carries a rectangle only — the texture is the executor's — so the function stays pure, but the frame now depends on an upload that can fail. A failed upload drops the strip for that frame and logs; it never drops the band and never refuses to present, because the strip asserts nothing about authenticity and the band asserts everything.
- **It is not a panel.** Three facts, no tray, no notifications, no workspace switcher, no click targets, and no interaction at all — a principal cannot receive physical input and the core is not taking a fifth gesture for a status bar.

### D-027 — The human's screenshot key reads the REALM VIEW, and it is a chord rather than a bare Print

**Status:** accepted (2026-08-08) — implements issue #216, extends [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) to a fifth core-owned chord, and answers a question #216's text raises and does not close; workstream [WS-E](14-workstream-session-mode.md) §6

**Decision:** four answers.

1. **The file contains the realm view, never human-visible output, and that is a security decision rather than a shortcut.** `crates/vitrin-core/src/consent/indicator.rs` is explicit that the session's trusted-indicator secret *"is never written to any descriptor or file"*, because the confined realm runs as the core's own uid: anything the core writes, the app can read. Human-visible output carries that secret twice — the always-present band and the ring around a genuine consent card — so a screenshot of it would destroy the trusted indicator on the first press of the key, permanently, for the rest of the session. Reading the realm view keeps "the indicator never reaches a file" **structural**: it is the same fork `capture.rs` already sits on, and there is no check anyone can forget.

   **Two softer designs were examined and both are worse, which is why this is a decision and not a preference.** *Cropping the band's rows out* does not close it: the ring is painted around a card in the middle of the output, so a crop protects the secret only while no prompt is up — precisely when a screenshot is least wanted. *Redacting by colour* — replacing every pixel equal to the secret — is actively dangerous and it is worth writing down because it looks thorough: it hands the app an **oracle**. An app paints its own surface with a field of candidate colours, the human takes a screenshot, and the app reads back which of *its own* pixels were recoloured; each screenshot tests as many candidates as the output has pixels, so the ~22-bit secret (`TrustedIndicator::generate` scales each channel into `[64, 255]`) falls in a handful of screenshots at 1080p. A structural exclusion has no oracle because there is nothing to compare against.

   The cost is real and is published rather than softened: **a vitrin screenshot cannot show a suspicious dialog.** "Send me a picture of that weird prompt" is the single most useful thing a screenshot does, and this one cannot do it; the answer is a phone camera, which is worse than every other desktop offers.

2. **It touches no grant, and that is a type rather than a rule.** There is no human principal in the identity model and inventing one to satisfy a picture would grow the identity layer for the wrong reason, so the chord's effect is not a *use* at all — no facet, no verb, no bucket, no refusal event, and `Verb::VALID_MASK` stays 575. What holds that up is not review: `capture::render_screenshot` takes a `HumanGesture` whose field is private to `crate::screenshot`, which is `!Copy`/`!Clone` and is minted only from a gesture the physical-origin chord matcher produced — so a principal holding every verb this core serves cannot construct the argument, and "an agent took a screenshot" is a compile error. `enforcement.rs`'s source scan counts the identifiers in **both** directions (zero occurrences of the encoder in the chokepoint; zero occurrences of the chokepoint's entry point in the screenshot module), and `render_frame`'s own single-caller clause stays literally true because the screenshot entry is a *sibling* of it rather than a caller. Same shape as #207's `SpawnRecord` and #213's `PendingPromotion`.

3. **A chord, not the bare `Print` issue #216 proposed — and this is the first core-owned gesture that pays a cost back.** [D-024](#d-024--the-cross-realm-clipboard-is-a-core-held-single-slot-pulled-by-the-core-on-two-human-gestures-that-delegate-nothing) makes `crate::chord` the one matcher later chords consume, and `ModChord` refuses a modifier-less chord by construction, because a bare-key gesture belongs to `deadman::Chord` or `attention::AttentionChord` and a third spelling of one is how two mechanisms end up disagreeing about which keys the core owns. So the choice was a modifier or a parallel matcher in the stack the human's off-switch lives in, and the parallel matcher is what D-024 exists to forbid. The default is `ctrl+print`, and the side effect is the payback: **bare PrintScreen is still delivered**, so an app that binds it keeps it — the first time this workstream has taken a gesture without taking the key. `KEY_SYSRQ` (99 → `XK_Print`) joined `input::invariant_keysym` first, on that table's own terms; the startup collision check is now over five chords.

   **Stack position, deliberately:** inside `LockGate` — so a person standing at a locked machine cannot write the session behind it to a file, which is the single most important line of this decision; inside `ConsentGate` and `DeadManHook` — a convenience whose worst failure is a picture that did not happen must be suppressible by a security question and by the off-switch; inside `ClipboardHook`, its peer, because the clipboard moves an app's bytes across a realm boundary and this only reads; and **outside** `AttentionHook`, which consumes both Supers and would leave a modifier matcher's `super` bit permanently wrong.

4. **PNG, through code already in this tree, and the crate boundary is the point.** *"No image codec in the core, in any dependency class"* is stated twice in `crates/vitrin-core/Cargo.toml`. A raw dump is dependency-free and user-hostile on a daily driver; an external `png`/`image` crate brings a **decoder** into the TCB. So `vitrin-golden`'s hand-rolled artifact encoder was **promoted** to `crates/vitrin-png` — zero dependencies, ~130 lines of arithmetic, consumed by both the harness and the core, so there is one reviewed copy rather than two. The mitigating fact is that it only ever *encodes*: it consumes a buffer the core composited and returns bytes the core writes, so it never parses attacker input — the same argument `Cargo.toml` already makes for fontdue's unreachable `unsafe`. What it costs is that code written for test artifacts is now TCB code and must be reviewed as such, and that argument holds only for as long as nothing else feeds it bytes it did not itself produce.

**Costs, stated:**

- **The first file the core writes whose contents are a picture of the screen.** The recorder's log and `--capture-dump` came first, so this is not the first descriptor; it is the first one worth stealing. Every screenshot is readable by every app in every realm because everything runs as one uid ([D-010](#d-010--per-realm-isolation-dial)'s dial is still at its lowest setting, and E2.6/E2.7 own the fix). Mode `600` is about *other users* and does nothing about the confined app.
- **A wrong `--screenshot-dir` puts pictures of the screen somewhere unintended, and nothing below the core enforces the choice.** The directory is audited at startup (absolute, existing, a directory, not a symlink, not group- or world-writable) and then **held open** for the process's life, so the path is resolved exactly once — before any client exists — and no later rename or planted symlink can redirect a write. Until the core is confined, that audit is the whole of the enforcement.
- **The enforcement module's one-path claim has one more clause to keep true.** Its value comes from being short and grep-checkable, and every carve-out, even a correctly-argued one, makes it slightly less so. The compensating move is that the new clause is *itself* a grep, in both directions, rather than a sentence.
- **A fifth key is taken from every app,** and the collision check five chords must pass is one more thing an operator can trip over on an otherwise reasonable command line.
- **Issue #216's own "CI cannot press a key" criterion is now stale**, and this decision records that rather than repeating it: WS-E.1.6's `physical-input-injector` channel presses this run's configured chord on its own scancodes through the production intake, so `tests/integration/test_screenshot.py` covers detection as well as effect. What remains manual is a real finger on real hardware — `shim/docs/nested-multi-realm.md` step 11.

### D-028 — A bare-metal session interprets the keyboard inside the core, from a pre-compiled keymap file; and key pairing moves to the scancode

**Status:** accepted (2026-08-08) — corrects a claim [`protocol/vitrin-v0.xml`](../../protocol/vitrin-v0.xml) and [page 11](../protocol/11-vitrin_shim_seat.md) stated as fact, discharges the warning `crates/vitrin-core/src/input/mod.rs` has carried since P1.3.7, and gates **WS-E.3.2** (#218); issue #217, workstream [WS-E](14-workstream-session-mode.md) §4 Stage 3

**The problem, in one line.** Under `--nested` the core never interprets a keyboard: winit hands it a resolved `logical_key`, `input::host_keysym` turns that into an X keysym, and `resolve_key_seat` prefers it over everything else (issue #118). libinput hands a DRM backend evdev scancodes and nothing else, and `input::invariant_keysym` maps no letter, no digit and no punctuation — its own test asserts `invariant_keysym(30) == None` for `KEY_A`. **A session-mode core cannot type.** The four sub-questions below are the whole of the answer; a decision that answered only the first would be re-litigated by whoever hit the other three.

**Decision: four answers.**

1. **Interpretation happens in the core, the wire is untouched, and the keysym is normalised to one convention on the way out.** The core owns an `xkb_state`, feeds it `(keycode, direction)` from libinput, and emits `xkb_state_key_get_one_sym` on the existing `keysym` argument of `vitrin_shim_seat.key`. This satisfies the IDL's *normative* modifier-suppression rule exactly as written — keysyms arrive already modifier-resolved, and the shim binds each non-modifier keysym at a plain level — so **the C shim needs no edit at all** and `shim/src/seat.c`'s generated single-key-type keymap keeps working unchanged. No new message, no new interface version, no `since` bump.

   **The part nobody had named, and it is not an implementation detail.** libxkbcommon returns what the keymap says, and a Turkish keymap says `gbreve` — `0x000002bb`, a Latin-3 *legacy* keysym — for `ğ`. That number is not its codepoint (U+011F). The core reads keysyms as codepoints in exactly one place a human touches: `lock::gate::printable`, which types the lock-screen passphrase, and whose rule is the `keysymdef.h` convention (below `0x100` a keysym is its own codepoint, otherwise it must be `0x0100_0000 | codepoint`). Fed raw, `ö` `ç` `ü` type — they are Latin-1, so their keysym *is* their codepoint — and **`ğ` `ş` `ı` `İ` are silently dropped**, which is a maintainer locked out of his own session in a way that looks like a typo. It also forks the two backends: nested already emits Unicode keysyms above Latin-1, so without normalisation the same letter would be a different number depending on which backend produced it. So `input::keymap::unicode_keysym` re-encodes through `xkb_keysym_to_utf32` into that one convention, leaving keysyms that type no character (`Return`, whose UTF-32 is `0x0d`) exactly as the keymap gave them.

   *Rejected: a keymap relay plus a `keycode` event.* The IDL already names this as the growth path and it is architecturally purer — the TCB stays keymap-free. It is a new interface version, a new message carrying an fd, and, decisively, it moves modifier resolution to the shim, inverting the normative rule the shim's replay machinery is built around and making agent `text` actuation and human keys travel through two different mechanisms. Deferring it costs nothing: the wire is untouched, so the relay stays purely additive and this decision closes none of it.

   *Rejected: extending `invariant_keysym` with a hardcoded US-QWERTY table.* It is a lie for every other layout, and unlike today's table it fails by **mistyping** rather than by dropping — worse than the bug it fixes.

2. **The keymap is a pre-compiled keymap FILE the operator names, compiled with `Keymap::new_from_string`; layout-name resolution is never called. Refuse to start if it does not compile.** This is the owner's call, taken 2026-08-08 against three costed options, and the rejected one is the one every other compositor uses — so the reason has to survive here rather than in a PR.

   *Rejected: RMLVO name resolution (`new_from_names`, `XKB_DEFAULT_LAYOUT=tr`).* It is what every other compositor reads and it would need no config schema. It also searches **`~/.config/xkb` before `/usr/share/X11/xkb`** and honours the `XKB_*` environment. Realms run as the core's own uid and confinement is Phase 2 ([D-010](#d-010--per-realm-isolation-dial)'s dial is at its lowest setting), so **an app inside a realm can plant a keymap the trusted core then parses** — and this is not hypothetical: `~/.config/xkb/symbols/vncsuper`, mode 0644, already exists on the machine this workstream is dogfooded on. The same objection applies to the environment: a variable is not a capability, and reading five of them turns "which keymap does the TCB parse" into a question about process environment rather than about operator intent.

   *Rejected: a hand-built in-core scancode→keysym table (~400 rows plus level arithmetic).* Zero dependency delta — the only option that meets this repo's house standard outright, and it types the maintainer's name. It permanently forecloses dead keys, Compose (5 145 sequences in `en_US.UTF-8/Compose`; the file is 5 192 lines, and the difference is comments — the line count is what an earlier draft of this entry quoted) and `xkb_options`, and that same `vncsuper` file is proof the maintainer uses custom options. A table also has to be *right*, and the failure mode of a wrong row is the mistyping (1) rejects.

   **What makes the accepted option more than a preference is that it is structural.** `input::keymap::CoreKeymap` builds its context `NO_DEFAULT_INCLUDES | NO_ENVIRONMENT_NAMES`, so libxkbcommon holds no include path and reads no `XKB_*` variable; the core reads the operator's file *itself* and hands the bytes to `new_from_string`; and a unit test that runs in the **default** build — the configuration where this module is not even compiled — greps the crate for a call to the name constructor and for the environment prefix. A keymap text that tries to `include` anything fails to compile rather than reaching a directory, which is asserted rather than assumed. Fail-closed on a compile failure follows `deadman::Chord::parse`'s precedent and this repo's rule that a session must never come up with a silently-broken human input path; there is deliberately no fallback layout to fall back *to*.

3. **Key pairing moves from the keysym to the scancode, and the release carries the keysym its own press delivered.** `input/mod.rs` has said since P1.3.7 that keysym pairing is sound *only* because `invariant_keysym` is a fixed table with no modifier resolution — the same key yields the same sym on press and on release, by construction. With a keymap it does not: press `a` with Shift held, release it after Shift is up, and the release carries `a` where the press carried `A`. `pressed_keys` would find no pair, drop the release, and leave the app believing a key is held; a latched `Ctrl`/`Alt`/`Super` *"silently rewrites the meaning of every keystroke the app receives afterwards"*. So a key event carries a `KeySource` — the evdev scancode where a device is behind it, the keysym where none is — and the router pairs on that.

   **The second half is the one it is easy to stop one step short of, and it is a wire-visible change in what the app receives.** Pairing correctly inside the core is worth nothing if the wire then carries `a` for a release whose press carried `A`: the shim binds a dynamic keycode *per keysym*, so the app would be told to release a keycode it never held while the one it is holding stays down — the same latched key, one layer out, where the core can no longer see it. The pairing entry therefore remembers the delivered keysym and both the ordinary release path and the two drains send that one back. The drains already did; the ordinary path had no reason to until now. This is a **router invariant** on the path the dead-man switch depends on, and it has been got wrong twice in this codebase already (P1.7.2, and again for the lock gate), which is why it has its own tests rather than a comment.

4. **Resolve the sym *before* `update_key`.** libxkbcommon documents the order — *"you should prefer to get the keysyms before updating the key, such that the keysyms reported for the key event are not affected by the event itself"*. Backwards, a modifier applies to its own event and a released key resolves at the level its own release just left. It is a two-line ordering bug with a silent symptom, so `CoreKeymap::resolve` is the only place either call appears and the ordering has a test that fails under the reverse order.

5. **Key repeat: the core synthesizes it, for `Origin::Physical` presses only, and WS-E.3.2 implements it.** `shim/src/seat.c` disables client-side repeat with the reason that *"the core forwards each host key event individually (the host's own auto-repeat included)"*. Off a host there is no such thing: libinput synthesizes no repeats, so held keys would not repeat at all — no held backspace, no held arrow. The alternative was for the shim to re-enable `wlr_keyboard_set_repeat_info`, which is the architecturally correct Wayland answer and is refused because it is **seat-wide**: an agent's held key would repeat too, inventing keystrokes nobody sent, which is exactly what that comment forbids and what the `origin` tag exists to keep distinguishable. The core can filter on the tag because it has it; the shim's repeat machinery cannot, because `wl_keyboard`'s repeat is a property of the keyboard and not of an event. **The cost is a timer in the TCB**, and a weakening of the "no duplicates" property `seat.c` is defending — the core will now emit key events no device produced. The mitigations are that a repeat can only ever duplicate a press already in `pressed_keys` (so it cannot invent a key the app is not holding), that it is cancelled by the same release, drain, focus change and gate-consume that clears the pairing entry, and that the delay/rate pair comes from the same operator config the keymap path does. Nothing of it is built here.

**What this decision costs, stated in the units that matter rather than in crates.**

- **"Zero new crates" is true of `Cargo.lock` and misleading about the TCB, and the issue's own text said the misleading half.** `xkbcommon 0.8.0` is already in the lock file via smithay → winit → smithay-client-toolkit, so enabling it resolves no new package. But **the shipped binary does not link libxkbcommon today**, measured on this tree: `readelf -d target/release/vitrind` has no `NEEDED` entry matching `xkb` and `nm -D --undefined-only` finds **zero** `xkb_*` symbols — it is in the crate graph and dropped by `--as-needed`, because nothing calls it. Adopting it adds **`libxkbcommon.so.0`, 383 144 bytes** of C (1.13.2) to the runtime image of the entire TCB, reached through **87** `extern "C"` declarations and **91** lines mentioning `unsafe` in the binding crate, plus a **parser** running inside `vitrind` over a ~73 KB keymap file (`xkbcli compile-keymap --layout tr` emits 73 028 bytes). That is strictly larger than the constant table it replaces, and one class weaker than the argument `Cargo.toml` makes for fontdue: fontdue's bytes are a compile-time constant vendored in this repo, and these are a file an operator names. **At the commit that lands this decision that cost is not yet paid, and saying so is part of the measurement**: nothing calls `CoreKeymap` outside tests, so even `--features session-keymap` still links nothing. Wiring a throwaway caller into `main` (built, measured, reverted) is what produced the numbers: `NEEDED libxkbcommon.so.0`, six undefined `xkb_*` symbols, and 9 245 480 → 9 267 160 bytes of binary. #218 is what makes it real.
- **So it is feature-gated, and the gate is checkable rather than claimed.** `session-keymap` is off by default; nested gets its keysyms from winit and headless has no keyboard, so neither may pay. A default build must still show zero `xkb` in `readelf` and zero `xkb_*` in `nm`, and CI's existing `rust` job is what holds that. Unlike `gpu-tests`, `dead-man-injector`, `consent-injector` and `physical-input-injector`, this is **not** a test instrument: it is a deployment feature a shipped bare-metal `vitrind` will have ON, and the only reason it is off today is that no backend needs it yet.
- **A stated invariant becomes conditional.** "No keymap lives in the core" appeared in the IDL, in page 11, and in three module doc comments. It is now a `--nested`/headless property rather than a core property, and the IDL's `<description>` — which by this repo's own rule *wins* over prose — was the worst place for it to be stale. Corrected in the same commit.
- **The two backends resolve keys by different mechanisms**, so a nested integration test that types successfully proves less about DRM than it used to. There are now three paths (the synthetic table, winit's `logical_key`, the core's xkb) and the suite covers two of them end-to-end.
- **Key tests grow a layout dependency.** Anything asserting a keysym must pin its keymap, so three compiled keymaps are checked in under `crates/vitrin-core/tests/fixtures/` rather than resolved at run time — which is also the only shape that tests the production constructor, since the context cannot reach an XKB search path.
- **`Verb::VALID_MASK` stays 575.** This decision allocates nothing and touches no authority: which keysym a scancode produces is not a capability question.
- **Not claimable from CI, and this is not a formality.** That a real keyboard, on the maintainer's real layout, types correctly through a real shim into a real app cannot be shown by any test in this repository: runners have no seat and no input device, and headless is the only backend CI runs ([D-019](#d-019--the-agent-cursor-is-drawn-display-only-human-visible-output-only-d-017s-delivery-deferral-stands)(4)). The unit tests prove the resolution and the pairing; they prove nothing about hardware. That check is a numbered step in **WS-E.3.4**'s manual runbook, and #217 must not be closed citing a unit test as evidence for it.
