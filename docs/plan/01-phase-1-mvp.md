# Phase 1 — MVP slice (deep plan)

**Scope anchor:** [PRD](../PRD.md) §8 Phase 1 and §19 — trusted core in Rust+Smithay (nested + headless) · one Wayland shim (C+wlroots, one instance per app) · Firefox in a realm · agent client with a static identity · one grant (`observe + actuate.pointer + actuate.text`) · core-rendered consent · pixel capture + scoped input injection.

**Explicitly out of Phase 1:** semantic trees, epochs/CAS, network sessions, X11, multi-realm fleet, filesystem powerbox, credential wallet, provenance, signed-journal replay tooling, IME, motion synthesis beyond trivial interpolation.

**MVP object-model subset** (of PRD Doc 2 §3.1): `principal`, `realm` (exactly one, `realm-0`), `surface`, `view` (implicit: one view = the realm's composited framebuffer), `actuator`, `grant`. Not in MVP: `scene`, `epoch`, and the signed `journal` of P6 — a plain structured event log ("flight recorder") is kept as a debugging aid and future journal seed (see the backward requirements below).

**Phase exit = milestone M1** in [00-roadmap.md](00-roadmap.md).

---

## 1. Exported-artifact contract (what later phases may depend on)

Phases 2–3 cite these as their Phase-1 dependencies; anything not listed here is an internal detail free to change.

- **A1 — Principal-facing protocol core:** connect/handshake, grant request/consent, surface observe, actuator inject. Consumed by every Phase-2 epic and by spec extraction (WS-A).
- **A2 — Realm spawn model:** shim fork, realm identity assigned at fork, spawn/sandbox skeleton. Consumed by E2.6/E2.7 (which extend the namespace setup) and E3.2/E3.3.
- **A3 — Grant table + consent surface.** Consumed by E2.6, E2.7, E3.7.
- **A4 — Flight-recorder log** (journal seed). Consumed by E3.4 — see backward requirement B1.
- **A5 — Wayland shim** with buffer/input/damage paths. Consumed by E2.1 (the bridge lives inside it), E2.8, and as the template for E3.2.
- **A6 — Nested + headless output modes.** Consumed by E3.3 (fleet generalizes headless).

### Backward requirements (placed on Phase 1 by Phase-2/3 planning)

- **B1 — Replay-ready log entries.** Flight-recorder entries carry observation digests (hash of each captured frame) and epoch-ready reference fields from day one, even though epochs don't exist yet. E3.4 (journal replay) is unbuildable retroactively if the MVP's records don't identify *what was observed*. Fields may be null-versioned; the schema slot must exist.
- **B2 — Physical-vs-emulated input distinction end-to-end.** The Phase-1 input pipeline tags every event's origin (physical device vs. agent actuator) and preserves the tag through core → shim → app delivery (the libei/EIS model, PRD Doc 2 §4.4). E3.7's physically-originated consent depends on this being structural, not bolted on.

## 2. Planned repository layout (documented now, created when Phase 1 begins)

```
vitrin-os/
├── Cargo.toml                      # [workspace] members = crates/*
├── rust-toolchain.toml             # pinned stable toolchain
├── docs/
│   ├── PRD.md
│   ├── plan/                       # this tree
│   └── protocol/                   # prose spec, one page per interface (spec-first; PRD §9 bus-factor mitigation)
├── protocol/
│   └── vitrin-v0.xml               # single IDL source of truth (Wayland-XML dialect — D1)
├── crates/
│   ├── vitrin-scanner/             # codegen: vitrin-v0.xml → Rust (core/SDK) + C header (shim)
│   ├── vitrin-protocol/            # generated message types + codec; no I/O
│   ├── vitrin-ipc/                 # Unix-socket transport: framing, SCM_RIGHTS, SO_PEERCRED, calloop glue
│   ├── vitrin-core/                # the TCB. binary: `vitrind`
│   │   └── src/{main.rs, comp/, capkernel/, grants/, identity/, input/, consent/, spawn/, capture/, log/}
│   ├── vitrin-sdk/                 # Rust client library (reference client; keeps the protocol honest)
│   └── xtask/                      # `cargo xtask codegen|bless|demo`
├── shim/                           # NOT in the Cargo workspace. C + wlroots, Meson build
│   ├── meson.build
│   ├── include/vitrin-protocol.h   # generated by vitrin-scanner (checked in, regenerated by xtask)
│   └── src/{main.c, compositor.c, upstream.c, seat.c, buffer.c}
├── sdk/
│   └── python/                     # `vitrin_os` package — pure-Python wire client (D8)
├── examples/
│   └── agent-demo/run_demo.py      # the Phase-1 demo agent
├── tests/
│   ├── integration/                # spawn vitrind headless, run scripted clients
│   ├── clients/input-echo/         # tiny Wayland test app logging every event it receives
│   └── golden/                     # reference frames for pixel assertions
└── .github/workflows/ci.yml
```

Layout rationale: the shim is deliberately outside the Cargo workspace (C+wlroots per PRD §17, Meson-built, glued via `xtask`/CI); `vitrin-protocol`/`vitrin-ipc` are separate crates so the codec is testable with zero I/O and the SDK doesn't link Smithay; one IDL file serves both the principal-facing and shim-facing protocols as distinct interfaces (same wire format, different authentication: handshake credential vs. inherited socketpair).

**Two parallel tracks after the IDL freezes** — Track A (Rust: ipc → core → capkernel → consent) and Track B (C: shim skeleton → upstream → seat → Firefox). The IDL freeze (P1.1.1/P1.1.2) is the only hard serialization point. The plan is also valid fully serialized (M1.1 → M1.5) for a single maintainer (R8).

**Walking skeleton (first end-to-end target):** core (headless, pixman) renders a test pattern → Python agent connects with a static identity → grant auto-approved via `--consent=auto-approve` → agent captures the frame to PNG. No shim, no Firefox, no consent UI, no dmabuf. This exercises every seam that is *new invention* (IDL, codegen, framing, fd delivery, handshake/identity, grant table, enforcement, capture, SDK) while deferring everything that is *known-hard integration* (wlroots, Firefox, GPU).

### D12 — Definition of done: a milestone closes only on a named mock-free integration gate

**Adopted following the #111 re-audit.** Through most of Phase 1, every
component was verified against a **mock on the far side of its seam** —
`vitrind` against `vitrin-mock-shim` (a synthetic Rust peer that animates a
hand-drawn buffer and forks no app), and the real C shim against
`shim/tests/mock_core.c` (a hand-written core stand-in). Both mocks are
useful and stay, but neither half had, at the time, ever met the *other real
half*, and the closure record for E1–E8 read "done" without either half
having run once end to end. That gap is now closed by rule:

> **A milestone M1.2–M1.5 is done only when its named integration-gate issue
> passes green, and that gate must have no mock on any seam the milestone
> claims.** `vitrin-mock-shim` and `shim/tests/mock_core.c` are
> **component/unit-test scaffolds only** — they may never be the source of a
> milestone's definition-of-done evidence. Existing green tests that use them
> stay (they still catch real regressions in the half they exercise) but are
> labelled **component tests**, never milestone acceptance, in
> [tests/integration/README.md](../../tests/integration/README.md).

The named gates (table above): **M1.2 = #105**, **M1.3 = #107**,
**M1.4 = #108 + #109 + #138**, **M1.5 = #110**. M1.1 predates this rule (walking
skeleton, no real second app existed yet to be mock-free about) and is not
retroactively gated.

The milestone-closing checklist (used when marking M1.2–M1.5 done in an issue
or PR) requires: (1) the named gate issue is closed; (2) its test file boots
its `Core`/shim with an explicit real binary path, never the mock defaults
(check (2) above); (3) no prose anywhere claims the milestone is met on a
component-test result; and (4) — added by the P1.9.8 gate-integrity pass —
**the gate has been watched failing.** Mock-freeness proves what a test is
*wired to*, never what it *discriminates*: both a gate that waited only for
the view to stop being the empty test pattern and one that asked for 24
changed pixels were mock-free and could not fail on the property they named.
Before citing a gate, break the behaviour it claims to prove and confirm it
goes red. Watching it go red on the *actuation* is still not enough on its
own: the replacement M1.5 predicate failed correctly when the click and the
typed text were removed, and simultaneously accepted a frame pair carrying no
typed text at all, because the quantity it measured was not the quantity its
prose named. Where a gate's criterion is a computed metric, pin the metric
itself against constructed inputs — one it must accept, and one from the
class it claims to reject.

**Closed since, against this checklist (#138):** M1.4's consent half now has
gate-level evidence — `tests/integration/test_real_consent.py` raises a real
prompt from the shipped binary over a real `click-target`, answers it from
outside the process over an inherited socketpair, and asserts the occlusion
split, the `consent_held` hold, and `issuer: human_consent` in the journal. It
was checked the way item (4) asks rather than merely written: **eleven**
separate breakages each turned it red, on a different assertion each time —
never raising the prompt; skipping `composite_over`; folding the two retained
images (pointing `view_rgba` at `latest_output_rgba`); exporting the whole

guard, once accepted and caught by the geometry cross-check); **replacing the
occlusion window's `readback_region` with a synthetic zero buffer**; disabling
the chokepoint's `consent_held` step; suppressing its `use_decision` refusal
record; making `consent_held` refuse *captures* too (the over-broadening a
naive `assertRaises(ConsentHeld)` would have accepted); mis-issuing the

Removing the post-denial control click turns the gate red with a message
saying in as many words that the earlier `ConsentHeld` now proves nothing.

The synthetic-buffer breakage in that list is the one this checklist exists
for, and it was found by an adversarial reviewer *after* the gate was first
written, not before: the occlusion half was a pure ABSENCE (`green == 0`) over
bytes whose provenance nothing tested, so an export that never read the
framebuffer at all passed and printed the success line verbatim. **This is the
P1.9.8 lesson in a second dress: a metric's name is not evidence about the
metric, and neither is an absence.** The fix is a positive control — the
exported rectangle must first be shown to *be* a raster of vitrind's card
(accent ring on all four edges, exact perimeter count, opaque body, buttons,
antialiased text) at exactly the rectangle the core named — and only then is
the app's green looked for and not found. Generalisable: **where a gate's
criterion is the absence of something in a delivered artifact, the artifact's
provenance needs its own assertion, or the gate is equally satisfied by no
artifact at all.**

#### Unspoofability (issue #85): what is gate-proven, and what never will be

**Read this before citing "M1.4 done" for anything about the trusted
indicator.** #139 split the property in two and closed the half that can be
closed. The split is permanent, not a staging post — the second half is not
waiting on a better idea.

| Half | Claim | Status | Where the evidence is |
|---|---|---|---|
| **Negative** | A confined app's own rendering can never reach the trusted band's rows on the human-visible output, and never reaches the capture path at all. | **Gate-proven, mock-free** (property gate, **not** a milestone gate) | `tests/integration/test_real_trust_band.py` — shipped `vitrind` → real `vitrin-shim` → real `click-target`, over a real socket |
| **Positive** | A human who learned the colour off the band can tell a genuine prompt's frame from a forgery. | **Component + human evidence, permanently. Not CI-able, and closed as a CI question.** The human-in-the-loop procedure #139 also asked for is unwritten and unscheduled — see "the fourth direction" below; do not read this row as "nothing left to do". | `consent/mod.rs`'s band and frame tests; `backend/headless.rs`'s `a_prompt_reaches_human_visible_output_but_never_a_capture` and the real-app `c_shim_consent_prompt_occludes_…`; `backend/winit.rs`'s `no_presentation_path_can_drop_the_trusted_band`; `shim/docs/firefox.md` §9, run by a person |
| **The colour itself** | The indicator is a fresh per-session secret, minted from the CSPRNG before any client could connect. | **Component evidence.** No gate reaches it and none can. | `consent/indicator.rs`'s own tests; `run_session`'s startup ordering |

**Why the positive half is closed rather than open.** Any automated check that
the band is *the right colour* has to know the colour, and anything that knows
it is a channel the confined app — same uid, `/proc/<core>/fd` — can use too.
The three escapes were considered and each fails on its own terms, recorded
here so the question is not reopened by someone who has not been through it:

1. **Mirror the human-visible frame to a file.** Writes the session secret
   where a same-uid app reads it. This is what `consent/indicator.rs` forbids
   outright, and it was already rejected once, during #138.
2. **A commitment scheme** (#139's own sketch: the core publishes a hash or
   derived witness). `TrustedIndicator::generate` scales each channel into
   `[64, 255]`, so the secret has at most `192³ ≈ 7.1 M` values — 22.8 bits.
   `H(S)` over that space inverts by exhaustive search in well under a second,
   on the same machine, by the same app. Salting it makes it uncheckable by a
   harness that holds no band pixel, and publishing the salt collapses it back.
   And even a scheme immune to both is *replayable*: the human's check is
   supposed to require seeing the screen, and a witness the app can read is a
   witness the app can quote.
3. **An equality oracle** — export one boolean, "the band's rows equal the
   client's rows beneath them". No pixels, no digest, and it is the worst of
   the three: a confined app paints candidate colour `C` over its whole
   surface, reads the bit, and has `S == C`; 7.1 M commits recover the secret.
   This is the trap worth remembering, because it passes the "export no
   pixels" rule that looks like the right rule.

So the rule the #139 instrumentation holds to is stricter: **every field the
core exports must be a constant function of the run, independent of the
*value* of the indicator** — checked mechanically by `band_witness.rs`'s
`a_report_does_not_depend_on_the_bands_colour` (and again, over composites
that also carry the scrim, the card and the trusted ring, by
`…_with_a_card_up`), which requires two runs identical but for the secret to
produce byte-identical reports.

**The fourth direction, which those three do not touch: a human in the loop.**
#139 proposed it first — "a nested-mode gate with a human in the loop,
extending `shim/docs/firefox.md` §9 into something recorded and repeatable
(accepts that it is not CI-automatable)" — and the reasoning above is no
argument against it, because it is the one direction where nothing a program
can read ever learns the colour: the channel is an eye. It is **not done**, and
saying "closed" without saying that would be the understatement this checklist
exists to catch. What is there today is one clause of §9 ("visible in the
trusted indicator band, issue #85") in a recipe about the dead-man chord;
there is no written procedure in which a person notes the band's colour at
startup, is shown a confined app's rasterized counterfeit of a consent card,
and records that it is unframed or wrong-framed. Writing that — and a fixture
app that renders the counterfeit, which does not exist either — is real,
unscheduled work, tracked nowhere as of this edit. It would not make the
positive half CI-able and would not change the "Not CI-able" verdict in the
table above; it would move that row's evidence from an incidental mention to a
signed-off procedure, which is a different and smaller claim than a gate.
Recorded here so that "closed" reads as *adjudicated* rather than *unmentioned*.

**What the negative gate proves, precisely** — restated on 2026-08-25, because
[#304](https://github.com/vitrin-os/vitrin-os/issues/304) made the old
statement describe a world the tree no longer has. A real `click-target`,
clicked by the agent through the real chokepoint, repaints its **whole
surface** from black to red; that is the strongest counterfeit available to
something that cannot observe the colour it would have to match. **Until #304
"its whole surface" included the band's rows** — the app was configured at the
output's size and the band overdrew it — and the gate's capture claim was that
those rows carried exactly the app's own colour. Since #304 the app is
configured at `ViewGeometry::usable()` and — so long as it commits the size it
was told — cannot address those rows at all, so the claim is the stronger one
that replaced it: the rows the core reserves
are ONE colour in **both** capture artifacts (the agent's `observe()` frame and
`--capture-dump`), the same colour in both, **byte-identical before and after
the repaint**, none of the colours the app paints, and carrying a channel below
the indicator's `[64, 255]` floor — so "the band is not in this capture" is
certainty rather than a 1-in-7-million coincidence, by the same floor argument
as before over a different constant.

Meanwhile the core-side witness reports `band_changes == 0` across every
composite **it evaluated**. Per this checklist's own generalisation — an
absence needs the artifact's provenance asserted, or it is equally satisfied by
no artifact at all — that zero is held up by counterweights in the same reply:
`probe_changes` increases across the repaint, so the witness does see change
when there is change; `composites` rises by **at least two** across a span
containing exactly one `band` request, which is the load-bearing form of that
assertion because `answer_band` recomposites before it reports, so each read
bumps the counter by one on its own and a bare "it went up" would be satisfied
by a witness wired only into the reply path; `tracks_view` refuses a frozen or
erased human-visible framebuffer (which would hold its band rows constant for
free); `band_uniform` refuses a partly-overdrawn or blended band; `refusals ==
0`; and `probe_fnv`, a digest of *realm-view* rows just below the band, must
equal the digest the harness computes over its own dump of the same instant.

**One counterweight stopped weighing, and #304 added the two that replace it.**
`band_changes == 0` used to mean *"the app's repaint did not reach these
rows"*. The app cannot reach them now, so nothing it does can raise that
counter and the zero is the inset's doing rather than the band's;
`band_uniform` goes the same way, because an unpainted matte is one opaque
colour. Measured rather than argued: with `composite_trust_band` made an
unconditional `return` in the shipped binary, the gate's first reading came
back `band_changes=3, band_uniform=1, tracks_view=1, view_reserved=1,
refusals=0, band_over_matte=0` — every older band criterion passing, and the
`3` traceable to the core's own background and consent scrim showing through an
absent band rather than to the client. So the reply carries two more fields and
the gate asserts both: `view_reserved` (the realm view's reserved rows are the
core's own matte, so an app committing the size it was told has no way to
address them) and `band_over_matte` (a band was drawn over that matte).
**`band_over_matte` is now the only criterion in this gate that a session with
no trusted band on the screen fails.**

**One bound on `view_reserved`, stated here because a plan document that
overclaims is how the next reader inherits it.** `Scene::compose` clips a
surface against the *whole* view rather than the usable rectangle, so an app
that ignores its `configure` and commits a buffer more than
`2 * reserved_top()` rows taller is centre-cropped back into the reserved rows
and the band overdraws it there as it always did. `view_reserved` reads the
composite it is handed and goes false in that case, which is honest and is not
a core regression; `band_witness.rs`'s
`a_client_that_ignores_its_configure_can_still_reach_the_reserved_rows` drives
it against the real compositor and asserts `band_over_matte` still holds. So
the property is structural for a cooperating client and the overdraw it always
was for an overflowing one — and issue #85's claim is unchanged either way,
because the band is composited last over whatever reached those rows.

The gap between "every composite it evaluated" and "every composite of the
session" is closed by code, not by the gate: `BandWitness::observe` is called
from `HeadlessOutput::present`, the headless backend's single composition path.
Say it that way round when citing this — the gate rules out a witness that only
looks when asked, which is the mistake worth guarding mechanically; it does not
count the session's composites independently and cannot.

**What it does not prove, stated so a later reader cannot over-read it.** It
proves a negative. It says nothing about whether the band is the right colour,
nothing about the per-prompt trusted ring, nothing about the nested backend
(it is the headless CPU composite; `backend/winit.rs` holds the two nested
presentation paths against each other at component level), and nothing a human
would call "unforgeable". **A green run here is not evidence that the trusted
indicator cannot be forged.**

Watched failing, as item (4) requires: four breakages of the real binary each
turned it red on a different assertion — `composite_trust_band` made a no-op
(`band_changes` 1 ≠ 0); the human-visible frame composited into the capture's
retained image as well (5120 of 5120 band-row pixels off-colour, in one
colour); `BandWitness::observe` stubbed out (the witness reports nothing and
the run refuses to believe its zero); and `probe_fnv` computed over a synthetic
buffer (the digest cross-check fails). The metric itself is additionally pinned
in-process and binary-free in `band_witness.rs`, against one frame pair it must
accept and one — the no-op band's — it must reject.

The instrumentation is as narrowly gated as #138's injector, and rides the same
channel rather than opening a second: the `vitrin-core/consent-injector` cargo
feature (never a deployment build), `--headless`, and
`--consent-injector-fd N` naming an inherited socketpair. The witness type is
compiled under `cfg(any(test, feature = "consent-injector"))` so its arithmetic
stays unit-tested in a plain `cargo test`; its wiring — the field on
`HeadlessOutput`, the call in that backend's composite, the `band` reply — is
under the feature alone. A shipping `vitrind` computes nothing and answers
nothing, and the request is a *read* that confers nothing, so it adds no
authority to the channel it rides.

A third scope belongs in that list and is now recorded in both places: the
gate says nothing about the human-visible frame **outside** the card
footprint. With `click-target` that is structural rather than an omission an
extra assertion could close — the export is clamped to the card, the card is
blitted opaque last, and the realm view outside the card is (measured) 93 840
px of a single black, so a regression erasing the realm view from the
human-visible output entirely leaves the exported window byte-identical.
`backend/headless.rs`'s `a_prompt_reaches_human_visible_output_but_never_a_capture`
and `backend/winit.rs`'s `the_nested_window_uploads_the_consent_overlay` are
what catch that, at component level; both were confirmed red against it.

That review found a gap one level up, now closed too: `unittest discover`
collects whatever `test_*.py` files happen to exist, so a **missing** named
gate was indistinguishable from a green suite — not a gate that cannot fail,
but a gate that cannot be noticed. `tests/integration/run.sh` and CI's "Guard
against milestone-gate drift" step now assert every named gate module is
present, and that the two build-feature lists agree, before anything else runs.
`run.sh` keeps **two** lists for this, `MILESTONE_GATES` and `PROPERTY_GATES`,
and the split is not bookkeeping: a milestone gate's absence is a claim about
that milestone's definition of done, and `test_real_trust_band.py` (#139) is
deliberately not one — it is guarded exactly as hard and cited for its own
property only.

## 7. Phase-1 risks

- **R1 — Smithay nested-mode maturity.** The winit backend is primarily a dev harness (niri/COSMIC run on DRM). Risks: input-model gaps, HiDPI oddities, host-compositor quirks. *Mitigation:* keep nested rendering trivial (one window, one texture blit + overlay); test on GNOME and Hyprland from M1.1; headless is the fallback demo venue and CI never depends on nested.
- **R2 — wlroots as a library.** API churns per release, docs thin, and "tiny compositor serving exactly one app, forwarding upstream" is an unusual shape (closest prior art: gamescope, cage). *Mitigation:* pin + vendor (D11); crib structure from cage; keep the global list a contract, not a floor. *Reserve option:* a Smithay-based Rust shim is viable but weakens the PRD §17 reuse rationale — a deliberate documented pivot, not drift.
- **R3 — dmabuf across the shim boundary.** Format/modifier mismatches, multi-GPU, implicit-sync stalls. *Mitigation:* D3 (shm first; dmabuf is an M1.5 optimization with automatic fallback); linear-only allowlist; per-GPU compatibility notes. MVP success does not depend on zero-copy (PRD caveat: performance numbers are design targets).
- **R4 — Firefox quirks.** Binds many globals, behaves differently without them, Wayland path evolves per release. *Mitigation:* bring-up ladder weston-terminal → GTK app → Firefox (M1.2 gates on the terminal); pin an ESR; drive the stub list from the shim's "globals touched" log; software WebRender fallback.
- **R5 — Text/keymap fidelity.** Synthesized keymaps are known-fiddly (keymap size, xkb state, apps that read the keymap once). *Mitigation:* `input-echo` fidelity tests before Firefox; restrict demo text to what the technique handles; the clean fix is E2.8.
- **R6 — Consent-in-headless contradiction.** A careless `auto-approve` default would quietly rot the security story. *Mitigation:* auto-approve only behind an explicit flag that prints a persistent warning and refuses to run if the identity registry contains more than the demo principal.
- **R7 — TCB dependency creep.** Consent text rendering, capture encoding, config parsing all tempt heavyweight deps into `vitrin-core`. *Mitigation, as built (issue #201):* [`deny.toml`](../../deny.toml) at the repo root, enforced on every PR by the `deny` job in `.github/workflows/ci.yml` in the same blocking posture as `codegen-diff`. It carries the dependency count as a number so "reviewed each milestone" has something to compare against, an itemised `[bans] multiple-versions` decision rather than a blanket allow, an advisory ignore-list where every entry names its reachability argument and its exit condition, and `[bans] deny` tripwires for the crate classes this project has refused in prose (image decoders; text-shaping and vector-rasterization stacks). *Mitigation as originally stated, and what became of it:* the same sentence promised "a checked-in cargo-deny budget for `vitrin-core`, reviewed each milestone" from Phase 1 onward, and no such file existed until issue #201 — so no milestone review can have applied it, and this row said otherwise for the whole of Phase 1. The second clause, "PNG encoding lives in the SDK, never the core", is also no longer true as written: WS-E.2.4 (issue #216) put an encoder in the core as `crates/vitrin-png`. The rule that survived is narrower and is stated where it is enforced — encode-only, in-tree, dependency-free, **no decoder** — with the image-codec crates that would break it now denied by name in `deny.toml`.
- **R8 — Single-maintainer schedule.** The two-track plan assumes parallelism that may not exist. *Mitigation:* milestone order valid fully serialized; IDL + docs-first posture keeps the project enterable by a second contributor at any point (Q8).
